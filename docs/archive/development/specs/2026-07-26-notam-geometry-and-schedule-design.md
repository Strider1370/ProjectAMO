# NOTAM 위치 결정과 발효 시간 판정

- 상태: 승인 대기
- 작성일: 2026-07-26
- 원천: KOCA xNotam KML (`aim.koca.go.kr/xNotam`)

## 1. 배경과 목적

비행 전 브리핑의 "경로 저촉" 판정이 두 방향으로 모두 틀린다. 없는 경고를 만들고, 있어야 할 경고를 지운다.

계기는 김포 출발 브리핑에 뜬 `사격 Z0535/26`이다. 화면에는 분류 이름과 번호만 나와 무엇인지 알 수 없었다. 원문을 열어보니 공항 북쪽 4.2km에서 저녁 두 시간 동안 하는 **불꽃놀이**였고, 순항 중인 항공기와는 무관한 지표~200ft 행사였다.

목적은 **NOTAM이 어디에서 언제 실제로 발효되는지를 확정하고, 확정하지 못하면 그 사실을 드러내는 것**이다. 최종 go/no-go 판단은 조종사가 한다.

## 2. 확인된 사실 (2026-07-26 04:31Z 원본 KML 실측)

원본 KML을 새로 받아 415개 Placemark 전수 분석했다. 이하 수치는 그 한 스냅샷 기준이다.

### 2.1 KML 도형은 두 모양뿐이다

| 도형 | 건수 | 정체 |
| --- | --- | --- |
| Polygon 25각형 | 254 | 원 근사 |
| Polygon 5각형 | 60 | 공항·활주로 윤곽 |
| LineString | 101 | 구역 경계선 |

임의의 실제 다각형이 Polygon으로 오는 경우는 **없다**.

### 2.2 25각형 원은 Q줄을 그린 그림이다 — 정보 추가 없음

25각형 218건(본문·Q줄 좌표가 모두 있는 것)의 중심을 비교했다.

| 비교 | 중앙값 | 최대 |
| --- | --- | --- |
| KML 원 중심 ↔ Q줄 좌표 | **0m** | 56m |
| KML 원 중심 ↔ 본문 좌표 | **650m** | 44,636m |

Q줄 좌표는 분 단위로 반올림되어 있다(최대 약 900m 오차). KML 원은 그 반올림된 점을 그대로 그린다. **정밀 위치는 본문에만 있다.**

### 2.3 LineString 101건은 경로 판정에서 전량 누락된다

`backend/src/briefing/geo-time-match.js:19`의 `polygonsOf()`가 `Polygon`과 `MultiPolygon`만 처리하고 나머지는 빈 배열을 반환한다. 선에는 내부가 없어 `routeIntervalInGeometry()`가 항상 `entered:false`를 낸다.

- LineString 101건은 **전부** 저촉 판정 대상 분류(prohibited/restricted/danger/firing)다.
- 101건 각각에 대해 구역 정중앙을 관통하는 경로를 만들어 시험한 결과: **걸림 0건 / 안 걸림 101건.**

이 101건의 좌표 자체는 정확하다. 본문 좌표가 있는 **94건 전부**가 KML 꼭짓점과 **1m 이내로 일치**한다. 89건은 첫 점과 마지막 점이 같아 이미 닫힌 고리다.

즉 LineString은 본문 다각형을 그대로 담고 있다. KML에서 실제 구역 형상을 가진 유일한 부분이며, 현재 이것만 판정에서 빠진다.

### 2.4 공항 윤곽이 잘못 붙는 경우가 있다

김포 NOTAM 6건(`A0740/26`, `A0908/26`, `A0909/26`, `Z0507/26`, `Z0535/26`, `G3995/26`)이 45m × 3600m 활주로 사각형을 공유한다. 활주로 폐쇄 NOTAM에는 맞는 도형이지만, 4.2km 밖 불꽃놀이에는 틀린 도형이다.

경로 축은 활주로에서 시작하므로 출발 직후 0.13NM에서 이 도형에 진입하고, 그 지점의 계획 고도는 약 78ft다. SFC–200ft 밴드와 겹쳐 **저촉이 성립한다**. 재현 확인:

```
onRoute true | 구간 0.13–1.89NM | 저촉 true
```

같은 원인의 오배치는 현재 스냅샷에서 3건이다(`Z0507/26`, `Z0535/26` 김포, `Z0533/26` 대구 — 모두 불꽃놀이).

5각형 도형을 가진 레코드 56건의 분류는 시설 47, 장애물 5, 기타 1, 사격 3이다. 사격 3건만 오배치이고 나머지 53건은 공항 윤곽이 옳다. (2.1의 Placemark 기준 60건과의 차이 4건은 2.7의 `C)PERM` 탈락분이다.)

### 2.5 본문 서식은 네 문형으로 덮인다 — 정답표 대조로 확인

415건 전수 정답표(10.1)를 파서 코드를 보지 않은 상태에서 원문만 읽어 작성했다. 그 분포다.

| 서술 형태 | 건수 |
| --- | --- |
| `CIRCLE RADIUS n CENTERED ON <좌표>` | 222 |
| `AREA BOUNDED BY <좌표>-<좌표>-…` | 85 |
| `n NM EITHER SIDE OF LINE <좌표>-…` | 15 |
| `PSN : <좌표>` + `RADIUS : n` (CIRCLE 단어 없음) | 3 |
| 이름만 있는 상설 구역 (`RESTRICTED AREA RK R97E ACT` 등) | 38 |
| 위치 서술 없음 (활주로 폐쇄, ILS 고장, GPS RAIM 등) | 51 |
| 단일 지점 (장애물) | 1 |

좌표 표기는 `373547N1264720E` 및 `364254.07N 1273014.94E`처럼 고정폭이다.

**좌표가 줄바꿈으로 잘려 있다.** 원문이 일정 폭에서 개행되며 좌표 한가운데가 끊긴다(`36242` + 개행 + `4N1262847E`). 공백을 제거하지 않고 정규식을 적용하면 **80건에서 좌표 84개를 놓친다**. 해석 전에 E) 본문의 공백을 모두 제거해야 한다.

좌표가 없는 89건(상설 구역 38 + 위치 서술 없음 51)은 문제가 아니다. 상설 구역은 AIP에 경계가 이미 있고, 나머지는 공항 시설 NOTAM이다. 둘 다 KML 도형이 옳다.

### 2.5.1 정확히 그릴 수 없는 서술 9건

호(`ARC`), 반원(`SEMICIRCLE`), 제외구역(`EXC`)을 포함하는 NOTAM이 9건 있다(`E3260/26`, `D1768/26`, `D1842/26`, `E3357/26`, `E3358/26`, `E3512/26`, `E3513/26`, `E3514/26`, `E3515/26`).

예: `E3260/26`은 반원에 시계방향 3NM 호를 붙이고 안쪽 1.5NM 원을 제외한다.

이 서술을 정확히 재현하지 않는다. 넓게 덮는 쪽으로 처리한다(4.5).

### 2.6 D) 시간표가 저촉 판정에 반영되지 않는다

저촉 대상 353건 중 **319건에 D) 시간표가 있고, 그 319건 전부 유효기간이 24시간을 넘는다**(35일, 71일, 75일, 91일 등).

`matchRouteNotams()`는 `valid_from`/`valid_to`만 본다. `Z0535/26`은 실제로 8일간 하루 두 시간만 발효되지만 35일 내내 발효 중으로 판정된다.

파서는 이미 `scheduleText`를 실어 나르고 있고, 해석기 `shared/notam-schedule.js`도 이미 존재한다(2026-07-21 스펙, 라이브 전수조사로 문법 확정, 테스트 17개). 프론트 목록은 `deriveNotamTime()`으로 이를 쓰지만 백엔드 브리핑은 쓰지 않는다. 당시 스펙이 `No new route matching logic`을 Non-Goal로 명시했기 때문이다.

결과적으로 같은 화면에서 같은 NOTAM이 목록에서는 "D) 시간대 외", 배너에서는 "경로 저촉"으로 표시된다.

### 2.7 `C)PERM` NOTAM이 조용히 탈락한다

`backend/src/parsers/notam-parser.js:82`가 종료시각을 `/C\)\s*(\d{10})/`로만 받는다. `C)PERM`(영구)은 매칭되지 않아 `parseOnePlacemark()`가 `null`을 반환하고, 로그 없이 사라진다.

현재 스냅샷에서 4건(`A0876/26`, `A0686/26`, `A0800/26`, `C1040/26`). C) 서식 분포는 10자리 날짜 408, `PERM` 4, `EST` 3이며 `EST`는 앞 10자리가 매칭되어 정상 통과한다.

파서는 415개 Placemark 중 411개만 레코드로 만든다. **탈락 건수를 알리는 경로가 없다.**

### 2.8 분류 이름이 내용과 어긋날 수 있다

`Z0535/26`의 Q코드는 `QWMLW`다. ICAO 규정에서 `WM`은 미사일·총포·로켓 사격이고 `SUBJECT_CATEGORY`의 `WM: 'firing'` 매핑은 규정에 맞다. 발행처가 불꽃놀이를 이 코드로 발행했다.

**분류 매핑은 고치지 않는다.** 화면이 분류 이름만 보여주고 본문을 감추는 것이 문제다.

## 3. 결정

- **위치 신뢰 순서: 본문 좌표 → (Q줄 검산 통과 시 채택) → KML 도형 → 위치 확인 불가.**
- **위치를 확정하지 못하면 조용히 빼지 않는다.** 별도 상태로 표시한다. `route-briefing-source-contract.md`의 *"해결되지 않은 입력을 `clear`나 `matched`로 바꾸지 말고 해당 상태와 이유를 반환하라"*를 따른다.
- **위치 불명을 저촉으로 간주하지 않는다.** 빨간 저촉 목록과 분리된 회색 줄로 낸다.
- **D) 해석 실패(`null`)는 발효 중으로 남긴다.** 모른다고 꺼진 것으로 치면 경고가 사라진다.
- **Q코드 → 분류 매핑은 건드리지 않는다.**

## 4. 모듈 설계 — `backend/src/notam/notam-geometry.js` (신규)

출처별 해석을 전용 어댑터 뒤에 두라는 정책에 따라 파서·판정 코드와 분리한다.

```
resolveNotamGeometry({ summary, rawText, kmlGeometry })
  → { geometry, bufferNm, source, reason }
```

`source`는 `'text' | 'q' | 'kml' | 'none'`. `'q'`는 4.5의 근사 경로다.

### 4.1 1단계 — 본문 좌표 해석

**먼저 E) 본문의 공백을 모두 제거한다.** 원문 개행이 좌표 한가운데를 끊기 때문이다(2.5). 이 정규화를 빼면 80건에서 좌표를 놓친다.

네 문형만 안다. 좌표는 `DDMMSS[.s]N/S DDDMMSS[.s]E/W` 고정폭.

| 본문 | 결과 |
| --- | --- |
| `CIRCLE RADIUS n (M\|KM\|NM) CENTERED ON <좌표>` | 중심·반경으로 25각형 링 생성 (KML 해상도와 동일) |
| `AREA BOUNDED BY <좌표>-…` | Polygon. 첫 점으로 닫는다 |
| `n NM EITHER SIDE OF LINE <좌표>-…` | LineString + `bufferNm = n` |
| `PSN : <좌표>` + `RADIUS : n` | 원. `CIRCLE` 단어 없이 장애물이 쓰는 표기 (3건) |

문형 판정 순서는 `EITHER SIDE` → `BOUNDED BY` → `CIRCLE`/`RAD OF` → `PSN`+`RADIUS`다. 앞선 문형이 걸리면 뒤는 보지 않는다.

**본문에 좌표가 있다는 것만으로 위치로 삼지 않는다.** 위 네 문형 중 하나에 해당해야 한다. `Z0479/26`이 반례다 — VORTAC 사용불가 공지이고, 본문의 유일한 좌표 `3705N12701E`는 대체 웨이포인트지 이 NOTAM이 적용되는 위치가 아니다. 문형 없이 좌표만 보고 찍으면 엉뚱한 곳에 그린다.

해석 실패는 예외가 아니라 다음 단계로의 하강이다.

**꼭짓점이 중복된 다각형은 원본 결함으로 본다.** 닫는 점(첫 점과 같은 마지막 점)을 뺀 목록에 같은 좌표가 두 번 나오면, 발행 과정에서 꼭짓점이 하나 소실된 것이다. `E3296/26`이 그렇다 — 사각형이어야 할 구역이 3개 점으로 온다(거의 동일한 `E3284/26`에는 네 번째 점 `355433N1293008E`가 있다).

이 경우 `{ kind: null, defective: true }`를 반환한다. 3단계(KML)로 내려가지 않는다 — **KML도 같은 3개 점을 가지고 있어 결함이 동일하다**(실측 확인). 4.5의 근사 경로로 보낸다.

"서로 다른 점이 3개 미만"이 아니라 "중복이 있다"를 신호로 쓰는 이유: 정당한 삼각형 구역과 꼭짓점을 잃은 사각형을 개수로는 구별할 수 없다. 중복은 소실의 흔적이다. 415건 실측에서 이 신호에 걸리는 것은 `E3296/26` 한 건이며 오탐은 없다.

**한 NOTAM에 중심이 여러 개면 전부 담는다.** `PSN`이 두 번 나오는 장애물 NOTAM이 있다(`A0798/26` 크레인 2기, `A0907/26`). 각 중심에 원을 만들어 `MultiPolygon`으로 낸다. `geo-time-match.js`의 `polygonsOf()`가 이미 `MultiPolygon`을 처리하므로 하류는 손대지 않는다.

현재 자료에서 `A0798/26`의 두 크레인은 6.0m 떨어져 있고 반경이 각 40m라 하나만 써도 실질적 차이는 없다. 그러나 "첫 번째만 쓴다"는 규칙은 멀리 떨어진 두 구역이 왔을 때 한쪽을 통째로 놓친다.

### 4.2 2단계 — Q줄 원 검산

Q줄 좌표는 ICAO 규칙상 해당 구역을 감싸는 원이다. 1단계 결과의 모든 꼭짓점이 그 원 밖으로 벗어나면 **해석을 신뢰하지 않고 폐기**한다.

허용 여유는 **1NM**. Q줄 좌표가 분 단위 반올림이라 최대 약 900m 오차가 있기 때문이다.

이 검산의 목적은 좌표 오독이 지도에 그대로 반영되는 사고를 막는 것이다. 검산 실패는 3단계로 내려간다.

참고: 현재 스냅샷에서 KML 도형 기준으로 이 검산에 걸리는 것은 303건 중 4건이며(`C1149/26`, `Z0507/26`, `Z0535/26`, `D2108/26`), 4건 모두 실제로 도형이 어긋난 건이다. 다만 `Z0533/26`(대구 불꽃놀이)은 Q반경이 넓어 검산을 통과한다 — **이 검산은 오배치 탐지기가 아니라 본문 해석의 안전장치다.**

### 4.3 3단계 — KML 도형 사용

1·2단계가 결과를 내지 못하면 KML 도형을 쓴다. 이때 **LineString의 첫 점과 마지막 점이 같으면 Polygon으로 닫는다**(현재 스냅샷 89건).

닫히지 않은 LineString은 폭을 알 수 없으므로 그대로 두고, 본문에 `EITHER SIDE` 폭이 있으면 1단계에서 이미 잡혔을 것이다. 남는 것은 4단계로 간다.

### 4.4 4단계 — 위치 확인 불가

`{ geometry: null, source: 'none', reason }`을 반환한다. 호출부는 이 건을 목록에서 제외하지 않는다.

### 4.5 정확히 못 그리는 것은 Q줄 원으로 넓게 덮는다

다음 두 경우는 형상을 정확히 재현하지 않는다.

**하나 — 호·반원·제외구역**(2.5.1의 9건). 본문에 `ARC`, `SEMICIRCLE`, 또는 좌표를 동반한 `EXC`가 있는 경우.

- **제외구역(`EXC`)은 빼지 않는다.** 바깥 형상만 쓴다. 실제보다 넓게 덮으므로 위험을 감추지 않는다.
- **바깥 형상 자체가 호·반원이면** 본문 해석을 버리고 Q줄 원을 쓴다.

**둘 — 원본 결함으로 꼭짓점을 잃은 다각형**(4.1의 `E3296/26`). KML도 같은 결함이라 내려갈 곳이 없다.

두 경우 모두 **Q줄 원**을 쓴다. Q줄 원은 ICAO 규칙상 구역 전체를 감싸는 원이므로 안전한 상한이다. 남은 삼각형은 원래 구역의 일부만 덮어 그 바깥을 지나는 비행에 경고를 내지 못하지만, Q줄 원은 전체를 덮는다.

**Q줄 좌표가 없으면 Q줄 원을 쓸 수 없다.** 이때는 KML 도형으로 내려가고, 그것도 없으면 4.4(위치 확인 불가)다. 정확히 못 그리는 형상을 억지로 그려 내보내지 않는다.

Q줄 원을 쓴 건은 `source: 'q'`, `approximated: true`로 낸다. 화면에 "구역 형태 근사"를 표시한다. 출처를 `'text'`로 적지 않는다 — 정책이 원천 식별을 보존하라고 요구한다.

넓게 덮는 선택은 헛경보를 늘린다. 그러나 형상을 잘못 그려 경고를 놓치는 것보다 낫다.

## 5. 경로 판정 연결

- `geo-time-match.js`의 `polygonsOf()`는 그대로 둔다. 도형 정규화는 4장 모듈이 끝낸 뒤 넘긴다.
- `bufferNm`이 있는 LineString은 같은 파일의 기존 `routeCorridorInGeometry()`로 판정한다. 이미 버퍼 폭을 받는다.
- `matchRouteNotams()`는 도형이 없는 건을 `continue`로 건너뛰지 않고 `positionStatus: 'unresolved'`를 달아 내보낸다. `conflict`는 `false`로 두되 목록에서는 사라지지 않는다.

## 6. 시간 판정 연결

`shared/notam-schedule.js`의 `isScheduleActiveAt()`을 그대로 쓴다. 새 문법 작업은 없다.

기존 함수는 한 시점을 묻는다. 브리핑은 구간(ETD~ETA)을 물어야 하므로 **구간을 훑는 얇은 껍데기 하나만** 얹는다. 5분 간격으로 표본하고 양 끝점을 포함한다.

`ponytail:` 주석으로 한계를 명시한다 — 5분보다 짧은 발효 창은 놓칠 수 있다. 현재 자료의 D) 시간대는 모두 시간 단위 덩어리다. 더 정밀해져야 하면 `notam-schedule.js`에 구간 질의 함수를 추가한다.

프론트 `deriveNotamTime()`의 세 갈래를 그대로 따른다. 목록과 브리핑이 다른 말을 하지 않도록 한다.

| `isScheduleActiveAt` | 목록 (기존) | 브리핑 판정 (신규) |
| --- | --- | --- |
| `true` | 발효 중 | 저촉 판정 진행 |
| `false` | "D) 시간대 외" | 저촉 아님 |
| `null` | "D) 시간 조건 확인" | 저촉 유지 + "시간 조건 확인" 표시 |

## 7. 파서 구제 — `C)PERM`

`C)PERM`이면 `validTo`를 먼 미래로 두고 통과시킨다. `EST` 표기는 현재도 통과하므로 손대지 않는다.

`parseNotamKml()`이 Placemark 수와 생성 레코드 수의 차이를 반환하고, 프로세서가 이를 로그에 남긴다. 조용한 유실을 없앤다.

## 8. 화면 표시

`BriefingBanner.jsx`의 저촉 항목이 분류 이름과 번호만 보여준다. 필요한 값은 이미 `routeConflicts`에 실려 있다.

```
⚠ 발효 중 공역 제한이 경로에 걸립니다 — 2건

  사격  Z0533/26
  불꽃놀이 실시 — 해당 공역 진입 금지
  출발 후 12–18NM · SFC–200FT AGL · 오늘 19:00–21:00

  위험  D1181/26
  임시 위험구역 발효
  출발 후 44–51NM · SFC–FL200

⊖ 위치를 확인하지 못한 제한 — 1건
  제한  R97E   구역 좌표 없음 — 직접 확인 필요
```

- 항목마다 본문 요약, 경로상 구간(NM), 고도 밴드, 발효 시간대를 낸다.
- 항목을 누르면 ⑤ 경로·공항 NOTAM 섹션으로 이동한다(기존 `jumpTo`).
- `positionStatus: 'unresolved'` 건은 빨간 저촉과 **분리된 회색 줄**로 낸다.
- 분류 이름은 그대로 두고 본문 요약을 그 아래에 붙인다.

## 9. 범위 밖

- Q코드 → 분류 매핑 변경. 발행처가 불꽃놀이를 `WM`으로 내는 것은 우리가 고칠 대상이 아니다.
- `H24`, `MON-FRI`, `SR-SS` 등 미지원 D) 표기 지원. 표본에 없다. 모르는 표기는 계속 `null`로 두고 "조건 확인"으로 남긴다.
- 안전 등급, 항로 선택, go/no-go 권고 생성.
- AI/LLM을 이용한 본문 해석. 세 문형이 99.7%를 덮으므로 불필요하다(2.5).
- 지도 레이어 코드 변경. 다만 **도형 자체가 바뀌므로 지도에 그려지는 모양도 함께 바뀐다** — 실측 411건 중 317건의 도형이 KML과 달라진다(92건은 종류까지). 이는 의도된 결과이며, 상설 구역 38건·공항 시설 50건·단일 지점 1건은 KML 도형을 그대로 유지한다(실측 확인). 지도 레이어 코드는 손대지 않되 10.4에 지도 확인을 넣는다.

## 10. 검증

### 10.1 정답표 전수 대조 (1차 관문)

파서를 보지 않고 원문만 읽어 만든 415건 정답표를 고정 자료로 둔다.

```
backend/test/fixtures/notam-2026-07-26.kml                  원본 스냅샷 (415 Placemark)
backend/test/fixtures/notam-geometry-truth-2026-07-26.json  정답표 415건
```

정답표 작성 방식과 신뢰도는 파일 머리말에 함께 저장했다.

- 입력은 KML `CDATA`의 NOTAM 원문뿐이다. 파싱 결과(`latest.json`)를 쓰지 않았다.
- 좌표는 글자 그대로 복사했다. 도분초→소수 변환은 코드가 한다.
- 60건을 독립적으로 재작성해 교차 검증했다. **59건 완전 일치(98.3%).**
- 갈린 1건은 `A0831/26`(장애물 `PSN`+`RADIUS`)이며, `point`인지 `circle`인지 판단이 나뉘었다. `knownHard`에 기록했다.

**테스트는 415건 전수를 대조한다.** 표본이 아니다.

| 대조 항목 | 통과 기준 |
| --- | --- |
| 서술 형태 판정 | 415건 전부 정답표와 일치 |
| 좌표 개수 | 형태가 원·다각형·회랑·점인 320건 전부 일치 |
| 반경·폭과 단위 | 정답표와 일치 |

설계한 문법을 이 정답표로 미리 채점한 결과는 **형태 412/415(99.3%), 좌표 개수 319/320**이다. 어긋난 3건은 전부 `PSN`+`RADIUS` 표기이며 4.1의 네 번째 문형으로 흡수된다. 좌표 개수 1건은 `E3260/26`(반원+호)이며 4.5로 처리한다.

**개별 NOTAM을 위한 예외 분기를 넣어 점수를 올리지 않는다.** 문법 규칙으로 설명되지 않는 건은 정답표에 남겨 두고 4.4·4.5의 안전한 경로로 보낸다.
