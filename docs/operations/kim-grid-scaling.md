# KIM 격자 영역 확대: 저장·계산·지도 제공 검토

## 범위와 현황

2026-10-07 조사. 현재 영역은 119–136°E · 30–44°N, 205×169 격자다.
확대 후보는 100–145°E · 6–50°N, 541×529 격자로 격자점 수가 약 8.26배다.
수집 한도와 별개로 저장 용량, 계산 시 최대 메모리, 사용자 지도 제공 비용을 검증한다.

작업 순서:

1. 같은 실제 KIM 자료로 Zarr와 NetCDF-4의 저장 용량·쓰기·읽기·메모리를 비교한다.
2. 운영 서버 여유 자원을 남기는 계산 작업 크기를 측정하고, 그 결과로 큐의 작업 단위와 동시 실행 수를 정한다.
3. 지도 표시 자료와 수치 조회를 분리한다. 아래는 3번의 코드 조사 결과이며 구현 변경 전 상태다.

## 프론트엔드의 전체 격자 수신

`frontend/src/api/weatherApi.js`의 KIM field 요청은 발표회차·예보시간·고도·revision으로
자료를 고른다. 화면 영역(BBOX)이나 지도 확대 수준을 지정하지 않으므로 선택한 필드의
전체 수집 영역을 JSON 숫자 배열로 받는다. 전체 회차의 모든 시각·고도를 한꺼번에 받는
구조는 아니지만, 고도·시간을 바꾸면 각 필드가 추가로 수신·캐시된다.

기상 계산이 끝난 수치 격자와 지도에 바로 표시할 자료는 다르다.
GKTG와 권계면도 계산 결과를 숫자 격자로 수신한 뒤 브라우저에서 표시 자료를 만든다.
구름·착빙은 백엔드의 `kim-nwp-model.js`가 필드 요청에 맞춰 지표를 산출한다.
프론트엔드가 착빙 산출에 필요한 원래 8개 변수 전체를 받는 것은 아니다.

| 기능 | 현재 수신·처리 | 전체 영역 숫자 배열의 대체 방안 |
|---|---|---|
| 기온·풍속 색상 | T 또는 u/v → Canvas 색상 이미지 | 서버에서 생성·캐시한 이미지 타일 |
| 등온선 | T → 등온선·라벨 | 서버에서 생성한 벡터 자료/타일 |
| 구름 | 이슬점 편차·구름 잠재도 → 색상 | 이미지 타일 |
| 착빙 | 잠재도·등급 → 색상·영역 경계·빗금 | 이미지와 벡터 자료/타일 |
| GKTG 난류 | 산출 강도 → 색상 | 이미지 타일 |
| 권계면·제트 | 권계면·최대풍 격자 및 제트 축 → 평활·래스터·등치선·깃 배치 | 서버에서 색상·선·깃 위치와 필요한 속성을 함께 생성 |
| 바람 애니메이션 | u/v → 입자 이동 계산 | 화면 주변, 확대 수준별 바이너리 u/v 격자/타일 |
| 지상 일기도 | 등압선·기압 중심·강수는 가공 자료, 바람은 숫자 격자 | 가공 자료 유지; 바람깃은 벡터, 입자는 범위별 바이너리 |
| 항로 단면·브리핑 | 서버가 추출·계산한 항로 표본 | 필요한 표본 수치를 계속 제공 |

### 수치가 필요한 기능

- 지도 클릭 조회는 현재 내려받은 격자에서 풍향·풍속·기온·구름·착빙·난류·지위고도를
  직접 찾는다. `weatherPointInspector.js`와 `useWeatherPointInspector.js`가 이를 소유한다.
  클릭한 좌표·정확한 발표회차·예보시간·고도·revision을 서버로 보내는 지점 조회 API로
  전환하면 기능을 유지하면서 전체 격자 수신을 생략할 수 있다. 여러 필드에 중복 포함되는
  전체 지위고도 배열도 이 방식으로 대체할 수 있다.
- 바람 입자는 연속적인 이동 계산에 u/v가 필요하다. 기능을 유지하려면 수치가 필요하지만
  전체 영역·원 해상도·JSON 배열일 필요는 없다. 화면 주변의 여유 영역을 포함한 격자,
  확대 수준별 해상도, 바이너리 인코딩과 제한된 캐시를 사용한다.
- `describeTropopauseJetPoint`는 지점 설명 함수가 있으나 조사 시점의 제품 코드에는 호출자가
  없다. 제트 축의 최대풍 표본은 실제 렌더러가 사용하므로 서버로 옮길 때 해당 속성도 제공한다.
- 에코탑과 CTPS는 이미 클릭한 지점의 값을 별도 API로 요청한다. KIM 지점 조회도 이 패턴을
  참고할 수 있다. 항로 단면 API도 전체 수집 영역이 아니라 항로 표본을 반환한다.

### 제공 방식 결정 (2026-10-08)

**브라우저가 숫자 격자로 그리는 구조를 유지하고, 전송 형태만 바꾼다.** 서버 이미지·벡터 타일은 택하지 않는다.
(이 절의 이전 권장인 "이미지·벡터 타일"을 대체한다.)

현재 한반도 영역 필드 한 장(한 시각·한 고도) 실측과 확대 영역 환산(×8.26):

| 필드 | 전송(gzip) | 풀린 JSON | 확대 영역 환산 |
|---|---:|---:|---|
| 바람 850 hPa | 119 KB | 486 KB | 약 1.0 MB / 4.0 MB |
| 기온 850 hPa | 61 KB | 382 KB | 약 0.5 MB / 3.2 MB |
| 구름 850 hPa | 81 KB | 408 KB | 약 0.7 MB / 3.4 MB |
| 착빙 700 hPa | 12 KB | 313 KB | 약 0.1 MB / 2.6 MB |
| GKTG 300 hPa | 248 KB | 745 KB | 약 2.0 MB / 6.2 MB |
| 권계면·제트 | 127 KB | 849 KB | 약 1.1 MB / 7.0 MB |

확대 영역 실제 자료로 비교한 JSON과 int16 바이너리(바람 850 hPa u·v): JSON 3.07 MB(gzip 0.96 MB),
int16 1.14 MB(gzip 0.78 MB). 기온 850 hPa: JSON 2.00 MB(gzip 0.43 MB), int16 0.57 MB(gzip 0.34 MB).

변경 4가지:

1. **바이너리 전송.** 필드 값을 int16(scale·offset·결측값은 작은 JSON 메타데이터) 배열로 보내고 브라우저는
   TypedArray로 바로 쓴다. 전송 약 20% 감소, 브라우저 해석·메모리 약 1/3.
2. **지점 조회 API.** 지도 클릭 값(풍향·풍속·기온·구름·착빙·난류·지위고도)은 좌표·회차·예보시각·고도·revision을
   보내 서버에서 받는다. 필드 응답에 붙은 전체 지위고도 배열을 뺀다(GKTG 응답 약 절반). 기존 보간·결측·단위 규칙을
   유지하고 늦게 온 응답이 다른 선택을 덮지 않게 한다.
3. **화면 범위 요청.** 화면 범위에 여유를 더한 BBOX만 받는다. 한반도 확대 시 받는 양 약 1/10.
4. **캐시 상한·그림 해상도.** 필드 캐시는 바이트 기준 상한(예: 64 MB)으로 오래된 것부터 지운다.
   래스터는 영역 전체를 볼 때 해상도를 낮춘다(확대 영역 4배 래스터 17.5 MB → 2배 4.4 MB).

등온선·착빙 경계·빗금·제트 깃·바람 입자는 지금처럼 브라우저가 만든다.

타일을 택하지 않은 이유:

- 서버 CPU: 확대 영역 계산이 하루 약 4시간이다. 미리 그리면 레이어·고도·예보시각 조합이 하루 약 6,700장이고,
  요청 때마다 그리면 사이트 응답과 CPU를 다툰다.
- 바람 애니메이션에는 숫자가 필요해 숫자 전송 경로가 어차피 남는다.
- 평활·빗금·제트 깃 렌더링을 서버에서 다시 구현해야 한다.

예상: 필드 한 장 전송은 확대 영역 전체 약 0.3~0.8 MB, 한반도 확대 시 0.1 MB 이하. 브라우저 메모리는 캐시 상한 안에서 유지.
구현 후 모바일에서 레이어 켜기·시각 변경 반응을 측정하고, 부족하면 가장 무거운 권계면·제트부터 서버 이미지로 옮긴다.
구현 순서: 지점 조회 API → 바이너리 전송 → 캐시 상한·해상도 → 화면 범위 요청.

## 결정 사항

- **격자 저장 형식: NetCDF-4, zlib 4, 128×128 블록** (2026-10-07).
  Zarr보다 디스크 21% 작고(117 MB 대 148 MB) 여러 층 읽기 2.6배 빠르며, 한 회차가 한 파일이다.
  Zarr의 메모리 이점은 실제 계산에서 10~25 MiB로 줄어 큐·블록 크기로 관리한다.
  적용 조건: 회차 전체 변환 시 최대 608 MiB였으므로 예보시각별 파일·변수별 cache 축소로
  계산 worker 예산(600 MiB) 아래임을 실측한 뒤 도입한다.
- **확대 영역 GKTG: 블록 분할 필수, 큐 동시 실행 1개.** 근거는 아래 2절.
- **수집 운영안**(회차별 키·예보시각·시간·용량): 문서 끝 [운영안](#운영안-2026-10-08-결정).

### Zarr/NetCDF-4 실험 방법

- 입력: 앞선 대용량 API 실험으로 수집한 2026100700 회차, F000–F012, 205×169.
- 숫자 격자 585개 JSON 파일(기본 286, GKTG 273, 권계면 13, 상층 13), 총 665,055,103 bytes.
  원시 TEXT 캐시와 다른 스냅샷은 이 형식 비교에서 제외한다.
- 약 1억 3,962만 숫자 격자값, 그중 JSON null 약 211만 개를 포함한다.
- 두 형식 모두 product/level/variable별 `(예보시간, y, x)` 배열로 구성하고, 예보시간 축의
  chunk 길이는 1로 둔다. 변수마다 모든 시각의 값을 검사한 뒤 기존 정밀도를 그대로 표현할
  수 있는 int16/int32/int64 또는 float32/float64를 선택한다. 현 입력은 int16 279개,
  float32 21개, float64 10개 배열이다. 기존 scale/offset와 정수 결측값은 메타데이터에 유지한다.
- JSON null은 float 배열의 NaN으로 저장하고 null 위치까지 대조한다. 추가 반올림, float16,
  유효 자릿수 제한은 사용하지 않는다. NetCDF의 자동 mask/scale은 끈 상태로 비교한다.
  본 실험은 전용 raw 배열 reader를 사용하는 저장 구조 원형이다. 일반적인 CF 자동 해석이나
  xarray의 기본 mask/scale로 바로 연결하는 호환성 시험은 아니다. 실제 도입에서는 유효한 0과
  결측값이 혼동되지 않도록 `_FillValue`, 좌표·차원·단위 등의 스키마를 별도로 확정한다.
- 압축 조건 일치 비교: NetCDF-4 zlib level 1 + byte shuffle와 Zarr v2 zlib level 1 + byte shuffle,
  공간 chunk 128×128. 추가 후보는 NetCDF zlib level 4, Zarr Blosc/Zstd level 1 + byte shuffle,
  공간 chunk 64×64다. NetCDF 변수당 chunk cache 상한은 512 KiB, Zarr I/O 동시성은 2,
  Blosc 압축 스레드는 1로 제한한다. 압축 알고리즘 효과와 포맷 효과를 구분한다.
- 실제 EC2의 별도 `artifacts/kim-storage-benchmark` 폴더와 임시 venv에서 실행한다.
  운영 의존성·수집 경로·API 게시 경로를 바꾸지 않는다. 새 기상청 API 호출은 없다.
- 쓰기는 JSON 읽기/파싱부터 메타데이터·배열 저장·close/metadata consolidation까지 측정한다.
  전역 디스크 cache flush는 수행하지 않으므로 전원 장애 내구성이나 물리 매체 flush 시간 측정은 아니다.
- 읽기 시험마다 새 Python 프로세스를 사용하고, 같은 요청을 5회 실행한 중앙값을 기록한다.
  운영 서버의 OS page cache를 비우지 않으므로 warm cache가 가능한 읽기 결과다.
  읽기 시간에는 store open/close를 포함하고 Python 시작/import 시간은 제외한다.
  프로세스 RSS는 Python과 라이브러리 기본 비용, 내부 cache를 포함한다.
- 읽기 시나리오: F006의 850 hPa 지도용 6개 배열, 지점용 5개 값, 21층×6변수 계산 입력 전체,
  그 입력의 128×128 지역 블록, 한 예보시각의 모든 배열. 계산 알고리즘 자체는 실행하지 않는다.
- 전체값 검증은 모든 파일의 모든 숫자·결측 위치·메타데이터를 원본과 비교한다.
  포맷별 동일 순서의 SHA-256과 조회 결과의 크기·합계도 대조한다.
- 보호 기준: host available RAM 192 MiB 미만, 디스크 여유 2 GiB 미만, 한 단계 15분 초과,

서버 30 GB 중 사용 가능 11 GB(시험 파일 삭제 후). 현재 한반도 회차 하나는 0.71 GB
(normalized JSON 605 MB, derived 32 MB, raw 75 MB)이며 운영 중 2회차 1.42 GB를 보관한다.
확대 영역은 면적비 8.26배, 06 UTC는 예보시각 27개(13개의 2.08배)로 계산했다.

| 저장 방식 | 00 UTC(13개) | 06 UTC(27개) | 동시 보관 최대* |
|---|---:|---:|---:|
| 현재 JSON | 5.9 GB | 12.2 GB | 약 19.5 GB — **불가** |
| NC, raw 텍스트 유지 | 1.6 GB | 3.3 GB | 약 6.3 GB |
| NC, raw도 NC로 변환 | 1.0 GB | 2.1 GB | 약 3.5 GB |

\* 게시 중인 확대 회차 + 수집 중인 다른 확대 회차 + 한반도 2회차(JSON 1.42 GB)의 합.
NC 크기는 2026-10-07 저장 형식 실측(숫자 JSON 666 MB → 117 MB)을 면적·예보시각 비율로 늘린 값이며,
표시용 이미지·벡터 타일과 계산 임시파일(확대 시 수백 MB)은 포함하지 않았다.
회차당 다운로드 13~27 GB는 응답마다 바로 변환해 디스크에 원문으로 쌓지 않는 현재 방식을 전제로 한다.

서버 정리(2026-10-08): Android 빌드 도구(`.gradle`·`android-sdk`), 2026-07-28 스냅샷 백업, npm·pip 캐시를 삭제하고
journald 상한을 200 MB로 설정했다(`/etc/systemd/journald.conf.d/projectamo-size.conf`). 사용 가능 11 GB → 16 GB.
`~/.cache/ms-playwright`는 NOTAM 수집기(`backend/src/notam/notam-crawler.js`)가 쓰므로 유지한다.

정리 후 재계산(2026-10-08): KIM에 쓸 수 있는 공간 = 사용 가능 16 GB + 현재 KIM 1.42 GB = 약 17.4 GB.
최대는 다운로드 중(게시 중 확대 + 수집 중 확대 + 한반도 2회차), 평소는 정리 시점 수정 후(확대 1 + 한반도 1).

| 저장 방식 | 최대 | 최대일 때 남는 공간 | 평소 |
|---|---:|---:|---:|
| 현재 JSON | 19.5 GB | **−2.1 GB (불가)** | 12.9 GB |
| NC, raw 텍스트 유지 | 5.3 GB | 12.2 GB | 3.5 GB |
| NC, raw도 NC | 3.2 GB | 14.2 GB | 2.1 GB |

### 확대 영역 예보시각 구성 비교 (2026-10-08)

KIM 전구는 +135h까지 1시간 간격 제공. 예보시각당 다운로드 1 GB·4.5분, 계산 3.5분, NC(raw 포함) 약 0.08 GB 기준.

| 구성 | 예보시각 | 일 수신 | 00 UTC 게시(KST) | 06 UTC 게시(KST) | 공백(정상 / 한 회차 실패) | 3시간 간격으로 보이는 시간(48시간 중) |
|---|---|---:|---|---|---|---:|
| A: 00 UTC +0~12, 06 UTC +0~26 (1시간) | 13 + 27 | 40 GB | 약 16:45 | 약 23:55 | **매일 21:00~23:55** / 06 실패 약 20시간, 00 실패 약 7시간 | 0 |
| B: +0~12 1시간 + +15~36 3시간 | 21 + 21 | 42 GB | 약 17:50 | 약 23:05 | 없음 / 없음 | 약 34시간 |
| C: +0~24 1시간 + +27~36 3시간 | 29 + 29 | 58 GB | 약 18:50 | 약 00:05 | 없음 / 없음 | 약 8시간 |

회차는 발표 후 8~9시간 뒤 게시되므로, 게시 시점에 앞쪽 +8~9h는 이미 지난 시각이다.
그래서 B는 +12h까지만 1시간 간격이라 게시 후 1시간 간격 구간이 회차당 3~4시간밖에 남지 않는다.
C는 3시간 간격이 하루 약 4시간(00 UTC 게시 전 오후)으로 줄고 한 회차가 실패해도 공백이 없다.
최대 디스크(NC, raw 포함)는 A 3.2 GB, B 3.5 GB, C 약 4.7 GB.
타임라인: https://claude.ai/artifact/KUmzk38cFuwcrvqdEKdG1f
게시 시각은 다운로드 후 계산을 순차로 한 값이며, 받은 예보시각부터 계산하면 앞당겨진다.

## 운영안 (2026-10-08 결정)

### 회차별 수집

시각은 KST. 대용량 키 사용 가능 시간은 2026-11-06까지 15:00~24:00.

| 회차 | 한반도 영역(205×169) | 확대 영역(541×529) |
|---|---|---|
| 00 UTC (14:12 수집 가능) | 일반 키(KIM 키), 지금과 같음 | 대용량 키, 15:00 시작 |
| 06 UTC (20:12 수집 가능) | **일반 키로 받지 않음.** 확대 영역에서 잘라 게시 | 대용량 키, 20:15 시작 |
| 12 UTC (02:12 수집 가능) | 일반 키(레이더·위성 키), 지금과 같음 | 받지 않음 |
| 18 UTC (08:12 수집 가능) | 일반 키(항공 키), 지금과 같음 | 받지 않음 |

- 한반도 영역 예보시각은 지금과 같이 +0~12h 1시간.
- 확대 영역 예보시각
  - 00 UTC: +0~24h 1시간 + +27~36h 3시간 = 29개.
  - 06 UTC: +0~24h 1시간 + +27~48h 3시간 = 33개.
- 확대 영역은 앞쪽 예보시각부터 받고, 받은 예보시각부터 바로 처리한다(NC 변환 → GKTG 16블록 → 권계면, 순번 동시 1개).
- 06 UTC 한반도 영역은 확대 영역의 +0~12h 13개 처리가 끝나면 한반도 범위를 잘라 먼저 게시한다(약 21:20,
  현재 약 20:35보다 약 40분 늦음). 확대 영역 전체는 33개가 끝난 뒤 게시한다.
- 2026-11-06 승인 종료 후에는 확대 영역 수집을 멈추고 06 UTC 한반도 영역을 다시 일반 키로 받는다.
  따라서 한반도 영역 단독 수집 경로는 계속 유지한다.

### 호출·시간·용량

| 항목 | 확대 00 UTC | 확대 06 UTC | 하루 |
|---|---:|---:|---:|
| 호출 | 약 7,700건 | 약 8,750건 | 약 16,400건 |
| 수신 | 약 29 GB | 약 33 GB | 약 62 GB (2 TB의 3%) |
| 다운로드 | 2시간 11분 (~17:11) | 2시간 29분 (~22:44, 마감까지 1시간 16분) | |
| 처리(예보시각당 약 4.1분) | 약 1시간 58분 | 약 2시간 14분 | 약 4시간 12분 |
| 게시(받으면서 처리) | 약 17:15 | 한반도 약 21:20, 확대 약 22:50 | |
| 디스크(NC) | 약 2.2 GB | 약 2.5 GB | |

- 일반 키 사용량: KIM 키는 06 UTC 한반도 회차(약 1.6 GB)가 빠져 하루 약 1.7 GB. 나머지 두 키는 지금과 같음.
- 20:12 한반도 06 UTC 수집이 없어져 확대 06 UTC 처리와 겹치지 않는다.
- 산정 근거: 확대 영역 예보시각당 호출 약 265건·약 1 GB(기존 영역 한 회차 3,446건·1.57 GB, 건당 크기 면적비 8.24배),
  전송 3.67 MB/s(동시 2건 실측), NC 변환 약 0.5분 + GKTG 2분 20초 + 권계면 1분 10초.

### 사용자에게 보이는 범위

- 앞 보기(볼 수 있는 마지막 예보시각까지) 최소 약 21시간 45분(17:15 직전), 최대 약 40시간(22:50 직후).
- 현재시각 기준 3시간 간격 구간은 하루 약 2시간 15분(15:00~17:15).
- 한 회차 실패 시 공백 없음. 06 UTC 실패 시 다음 날 17:15 직전 앞 보기가 약 3시간 45분까지 줄어든다.

### 서버 여유

- 디스크: KIM에 쓸 수 있는 공간 약 17.4 GB(사용 가능 16 GB + 현재 KIM 1.42 GB) 중 최대 약 7.9 GB
  (이전 06 + 게시 00 + 수집 중 06 + 한반도 NC 2회차 + 임시). 이전 회차 정리 시점 수정 후 약 5.3 GB.
  남는 공간 9.5~12 GB, 디스크 사용률 최대 약 72%. 표시용 타일은 미포함.
- 메모리: 처리 worker 최대 약 510 MiB(권계면) + 다운로드 약 140 MiB가 겹친다. 운영 backend 포함 시 사용 가능 RAM이
  약 0.4 GiB까지 줄 수 있어 실측 필요. 부족하면 권계면만 다운로드 뒤로 미루며 확대 06 UTC 게시는 약 23:30.
- CPU: 계산은 1코어·낮은 우선순위.

### 관리 방법 (2026-10-08 결정)

기존 장치(키별 사용량 장부 `backend/src/api-hub-usage.js`, 텔레그램 운영 알림 `backend/src/alerts/ops-rules.js`,
관리자 수집 시간표 `collector_runs`, 지도 업로드 최소 여유 `MIN_FREE_BYTES` 3 GiB)를 재사용한다.

| 항목 | 규칙 |
|---|---|
| 회차 보관 | 한반도·확대 영역을 따로 센다. 각 영역은 게시 중 회차 1개 + 수집 중 회차 1개. 정리는 기본 격자 게시 때와 GKTG·권계면 게시 직후 모두 실행. 게시 못 한 부분 회차는 24시간 뒤 삭제(기존 규칙) |
| 디스크 보호선 | 확대 회차 시작 전 여유 공간 ≥ 예상 회차 크기(약 2.5 GB) + 3 GiB가 아니면 그 회차를 건너뛰고 이전 회차 유지. 다운로드 중 예보시각마다 확인해 3 GiB 아래면 중단. 수집 기록에 `skipped`/`disk_reserve` |
| 메모리 보호 | 계산 블록 시작 전 서버 사용 가능 RAM ≥ 512 MiB를 확인하고 부족하면 기다린다. 다운로드 중에는 권계면을 다운로드 뒤로 미룰 수 있다 |
| 24시 마감 | 앞쪽 예보시각부터 받고 23:50에 새 요청을 멈춘다. 사용시간 안에서 실패한 예보시각은 이어받기(이미 받은 것 재사용). 06 UTC 수집이 시작되면 00 UTC 이어받기는 멈춘다 |
| 부분 회차 게시 | 받은 예보가 다음 회차 게시 예정 시각 + 1시간까지 이어지면 게시: 00 UTC는 +15h(KST 24시, 다음 게시 22:50), 06 UTC는 +27h(다음 날 18시, 다음 게시 17:15). 중간에 빠진 예보시각은 시간 막대에서 비활성. 조건 미달이면 게시하지 않고 이전 회차 유지(짧은 새 회차로 바꾸면 이전 회차가 덮던 시간에 공백이 생기므로) |
| 한반도 06 UTC 대체 | 21:30까지 확대 06 UTC의 +0~12h 13개가 끝나지 않으면 한반도 06 UTC를 일반 키(KIM 키)로 받는다 |
| 만료·키 오류 | `.env`에 키·만료일(2026-11-06)·사용시간(15~24 KST)을 둔다. 만료, 키 없음, 401/403이면 확대 수집을 자동으로 끄고(관리자 화면 `disabled`) 한반도 06 UTC는 일반 키로 돌아간다. 만료 7일·1일 전 텔레그램 알림 |
| 사용량 기록 | API 장부에 `bulk` 키 분류 추가(한도 2 TB, 호출 건수도 기록). 기존 90% 한도 알림 그대로 적용 |
| 감시 | 관리자 수집 시간표에 확대 00·06 UTC를 별도 행으로 표시. 사용시간 밖은 `quiet`로 처리해 오경보를 막고, 확대 회차가 연속 2회(약 30시간) 게시되지 않으면 텔레그램 알림 |

### 미확인

- 15시·20시대 실제 전송 속도. 확대 영역 한 회차 전체 수집 실측.
