## 2. 실측 (운영 서버 t3.small, 2 vCPU·1.9 GiB)

### 2026-10-09 06 UTC 회차 (ACI 포함 첫 회차, 33시각)
- 20:45 시작(일시정지 후 재개) → 다운로드 끝 22:51 → 게시 23:45. 실패 0. ACI 33/33, 강수 33장.
- 시각당 계산 평균: GKTG 169초(최대 305), ACI 60초(최대 87), 권계면 36초, 지도 파일 33초, 강수 5.5초. 합계 약 5분.
  계산이 병목이다(다운로드는 시각당 약 3.5~4분, 동시 4건).
- 게시 단계(마지막 계산 뒤 게시까지) 10분 15초 → 10-10 수정으로 거의 0(아래 3-3).
- 메모리: 남은 메모리 최저 218 MiB(멈춤 기준 250 MiB 아래 2번, 3번 연속은 아님), 스왑 최대 460 MiB, 계산 자식 최대 798 MiB.
- 회차 크기 5.83 GB. 디스크 여유 약 10 GB.
- CPU: 회차 동안 100%(받은 텍스트 파싱·NC 저장 Node 약 88% + 계산 Python). 사이트는 우선순위가 높아 응답 정상.
  같은 GKTG가 이 PC에서는 시각당 42초 — 서버는 CPU 경합으로 4~5배 느리다.

### 대용량 키 사용량
- 요청 한 건 = 5.83 MB(확대 영역 텍스트, 변수와 관계없이 같음). 시각당 약 270건.
- 2026-10-09 서버 약 16,800건·**약 98 GB**(00 UTC 45 GB, 06 UTC 49 GB 등) + 이 PC 시험 약 11 GB. 하루 한도 2 TB의 약 6%.
- 정상 운영 하루 약 95 GB(처음 추정 62 GB보다 1.5배 — 요청 크기를 3.8 MB로 잡았었다).
- 동시 요청 수: 8·16·24건 모두 초당 약 4건에서 막힘(기상청 쪽 상한). 8건이면 충분, 늘리면 메모리만 는다.
  서버는 CPU 때문에 4건으로 두었다.

### AWS
- t3 unlimited로 전환(10-09). CPU 초과 요금은 하루 약 0.2달러 추정, 크레딧(약 82달러)에서 빠진다. 최악(24시간 100%)이어도 하루 약 1.9달러.

## 3. 최적화 (한 것)

### 3-1. 지도 응답: JSON → 미리 만든 이진 파일 (6fd8f1d2)
- 원인: 요청마다 NC 읽기(0.2~0.3초) + 착빙·구름 계산(0.6~0.8초) + 지면 가림(0.3초) + JSON·압축을 백엔드가 하나씩 처리 → 레이어 다섯 개 4~7초.
- 형식 `KMB1`(shared/kim-map-binary.js): 머리말 JSON + 정수 배열, 행 차분·바이트 섞기 후 gzip. 브라우저는 JSON과 같은 객체로 푼다.
  압축 크기 JSON 대비 39~56% 감소(기온 737→317 KB). 화면은 JSON과 픽셀 단위로 같음(로컬 Playwright 비교).
- 저장 `runs/<회차>/derived/map-bin/<응답 이름>/<고도>/hfNNN.bin.gz`, 주소 `/data/...`로 nginx가 정적 제공. 없으면 백엔드가 만들어 저장.
- 확대 회차가 착빙·구름 전 고도와 기온·바람 700 hPa를 미리 만든다. 운영 실측: 이미 있는 장 0.04~0.08초, 처음 만드는 장 1~3초.
- 참고: 기상청 날씨누리(wnuri-map)도 KIM을 0.25° Zarr(zstd+shuffle)로 미리 만들어 정적 제공, GPU로 칠한다. 같은 원리.

### 3-2. 착빙 계산 6배 (6fd8f1d2)
- 칸마다 객체를 만들던 반복을 판정 조건(-35~0°C, RH≥60%) 밖은 바로 0으로. 장당 207→33 ms, 54장 결과 동일.

### 3-3. 게시 단계 재확인 없애기 (10f97c70)
- 원인: 게시 때 GKTG·권계면 처리기를 다시 불러 33시각 입력을 다시 준비하고 결과 693개를 다시 열었다(10~20분).
- 시각별 계산이 돌려주는 결과 목록·입력 지문·계산 판으로 바로 게시(`publishComputedGktg`·`publishComputedTropopause`).
  입력 파일 지문과 결과 파일 존재만 확인, 실패하면 예전 방식(`derived_publish_fallback`). 로컬 실제 자료로 manifest 동일 확인.
- GKTG 계산 판에 requirements.txt 전체 대신 numpy·numba 줄만 넣는다(MetPy 추가로 판이 바뀌어 다시 계산하던 문제).

### 3-4. 그 밖
- 지도 응답 공용 메모리 캐시 64 MB, GKTG 값 소수 셋째 자리 버림(등급 경계 유지) (44449478).
- 이웃 시각·고도 미리 받기: 장이 뜨면 앞뒤 시각·위아래 고도 이진 파일을 HTTP 캐시에만 받아 둔다 (7b8697a7).
- 강수 레이어를 확대 회차에서 매시간 만들기(시각당 2건 추가, 바람은 확대 10 m 재사용) (2fd78489).
- ACI(CAPE·강수·OLR 실험 점수): Numba 커널 20 hPa, 시각당 운영 약 60초 (65821701, 70260c94).

## 5. 운영 명령

```bash
# 회차 보고(읽기 전용): 게시 상태, 시각별 시간, 메모리, 디스크
cd /opt/projectamo/current && node scripts/kim-expanded-report.mjs --data /opt/projectamo/shared/data [--tmfc 2026100906] [--memory]
# 지금 한 회차 돌리기(정기 실행과 같은 함수·환경). 사용량 장부에는 남지 않는다(아래 6-3)
nohup node scripts/kim-expanded-run.mjs --cycle 00|06 [--stop-kst 20:10] > ~/kim-expanded-run.log 2>&1 &
# 회차 일시정지: run-<회차>.lock에 살아 있는 프로세스(pid)를 적어 두면 정기 실행이 건너뛴다
```

관리자 화면: 자료 수집 → "KIM 확대 영역" 행 → 받기·계산 진행률, 예상 끝, 지도·강수, 메모리. API 사용량 → 대용량(KIM).

## 6. 겪은 문제와 교훈

1. **한 층 일시 오류로 회차 전체 미게시**(10-09 00 UTC): +10h 22층 중 1층 `fetch failed` → 앞에서 이어진 시각만 게시하던 규칙에 걸림. 시각 안 재시도와 빈 시각 허용으로 고침.
2. **게시 단계가 10~20분**: 처리기 재호출 구조 때문. 3-3으로 고침.
3. **수동 실행 사용량이 장부에서 사라짐**: 프로세스마다 장부 전체를 덮어써서 백엔드가 수동 실행 기록을 지웠다. 정기 실행(백엔드 안)은 정상. 수동 실행이 드물어 아직 고치지 않음.
4. **배포가 수집을 끊음**: 1절의 배포 피할 시간 참고.
5. **CPU 2개 한계**: 다운로드 파싱과 계산이 CPU를 나눠 계산이 서버에서 4~5배 느림. 회차 게시가 늦은 근본 원인.
6. **회차 크기·사용량 추정 과소**: 실측으로 갱신(5.83 GB, 하루 95 GB).

## 7. 남은 일 (우선순위 순)

1. **같은 격자 네 번 읽기 없애기**: GKTG·권계면·ACI·지도 파일이 같은 NC를 각자 푼다(시각당 약 20초, 회차당 약 10분). 다운로드 때 계산용 f32 배열을 한 번 써 두고 공유.
2. **GKTG 시간 쪼개 재기**: 계산의 약 57%. Node 입력 준비와 Python 계산 중 어디가 무거운지 측정 후 결정.
3. **다운로드 쪽 CPU**: 텍스트 파싱(서버 장당 약 150 ms)·NC 저장이 백엔드 본 프로세스에서 돈다. 작업 스레드로 옮기거나 파서 최적화.
4. **nginx `immutable` 머리글**: map-bin 재방문 시 304 왕복 제거(서버 nginx 설정).
5. 지도 공간 조각(화면 범위만 받기), GPU 색칠, 멀리서 볼 때 0.25° 파일(휴대폰 위주).
6. 수동 실행 사용량 장부 합치기(3번 문제).
7. **서버 결정**: 11/21 무료 크레딧 종료 전. 확대 영역을 계속 쓰면 CPU 많은 기계(노트북 이전 검토: Lenovo 15ABR8 Ryzen 6코어)나 유료 전환.
   11/6 대용량 키 연장 여부에 따라 달라진다.
8. ACI: 실제 CB 탐지 성능(위성·낙뢰 대조) 미검증. 한반도 회차·기관 고정 브리핑 연동은 범위 밖.
