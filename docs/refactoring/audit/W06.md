### W06-07 — 개인 bundle의 source 회차와 NWP 부분 갱신 provenance 수명

**사실:** personal `briefingProvider.js:15` 이후는 먼저 briefing API를 기다린 뒤 profile/crossSection을 allSettled로 받는다. `backend/server:1160`의 composeBriefing도 NWP를 로드하고(`briefing-composer:164` 이후), 별도 cross-section endpoint는 다시 그 시점 active root를 읽는다. 개인 응답에는 세 요청을 묶는 source revision 검증이 없다. **가설/영향:** 중간 source 게시/시연 문맥 전환 시 briefing 요약의 run과 차트 run이 달라질 수 있다. 시간 offset 갱신 후에도 기존 ribbon/model 요약과 provenance가 남는 동작이 의도된 ‘NAVLOG만 갱신’인지, 화면의 현재 NWP 상태를 뜻하는지 계약을 정해야 한다. 현재 화면 `BriefingView:426`~454는 enroute.model ribbon을 계속 소비한다. 발생률/성능/실황 일치 여부 미측정.

**검증/선행:** 두 API 사이 sourceRevision 변화 fixture, 선택 hf/offset 변경 전후 chart.run/NAVLOG/ribbon/provenance 대조가 필요하다. 주 담당의 cross-section 일반 cache vs timeRules 측정과 별도인 **정합성 질문**만 반환한다. 실제 요청 수·CPU·I/O 측정은 실행하지 않았다.
