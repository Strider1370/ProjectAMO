## 발견별 근거·유지 구조·후속 검증

### W02-01 · nginx 직접 서빙과 backend 공개 경계/캐시 차이 — 개선 후보, 우선 추가 재현

**사실:** `deploy/nginx/projectamo.conf.example:35`는 backups/organization-files/DB 확장자를 막지만 CTPS/Echo Top `.bin` 규칙은 없다. :39~41은 `.active-data`를 alias로 읽고 파일이 있을 때 직접 응답하는 형태다. 반면 `backend/server.js:204`~210은 두 정확한 binary URL을 404로 막은 뒤 express.static을 사용한다. Architecture.md:196/:201도 server-only binary 차단을 명시한다.

**실제 자료 흐름:** `echo-top-processor.js:118`의 publish → `echo-top-store.js:45`가 실황 root에 같은 tm의 `.bin`(:48)과 공개 `.webp`(:49)를 쓰고 메타에는 이미지 경로만 공개(:57); CTPS도 `convective-satellite-store.js:34`~46이 `.bin`과 12개 이미지를 게시한다. `backend/src/dev/data-view.js:17`/45는 live/demo `.active-data` 링크를 유지한다. 서버 지점 API(`backend/server.js:1064`, :1086)는 binary를 읽어 한 지점 JSON으로 변환하며, 브라우저는 `frontend/src/api/weatherApi.js:260`/:265의 point API를 호출한다.

**가설/영향:** 이 nginx 예제가 실제 적용되고 해당 파일이 있으면 외부 direct binary 요청이 Express 차단을 우회할 수 있다. 예제의 정적 불일치는 확인했지만 운영 공개 여부·응답·데이터 민감도는 미확인이다. 또한 일반 `/data/` alias는 backend의 `setGeneratedDataCacheHeaders`를 거치지 않아 Echo Top·WISSDOM/QPF WebP 등의 정책도 backend와 달라질 수 있다. 현재 예제의 명시적 immutable frame regex(:44/:57)가 모든 backend 분기를 담지는 않는다.

**유지/제안·효과:** 공유 `.active-data`와 허용된 이미지 직접 서빙은 유지한다. 공개/비공개 URL 계약을 nginx와 backend 양쪽에서 검증하고, proxy 경유 또는 명시 차단/allowlist 중 작은 범위로 일치시키는 후보다. 불필요한 원시 파일 공개 및 캐시 정책 차이를 줄이는 효과이며 성능 수치는 없다.

**위험·선행·검증:** blanket `.bin` 차단은 다른 허용 자료를 끊을 수 있어 공개 목록부터 확정한다. W03/A09와 파일 범위만 대조; 격리 nginx에 임시 CTPS/Echo Top binary·정상 이미지·메타를 두고 direct `/data/...bin` 404, 이미지 200/immutable, 메타 no-cache, 기관/DB 경계, live/demo link 전환을 재현한다. 관련 기존 검사는 `backend/test/echo-top-api.test.js:87`의 backend 404, `backend/test/convective-satellite-api.test.js:45`의 point/binary 경계, `deploy/test-nginx-rate-limit.mjs:7`(현재 API burst 문자열만 검사)이다. **이번에는 nginx/테스트 실행 없음.** 배포 스크립트는 예제를 복사/대조하지 않고 nginx -t/reload만 하므로 예제 수정만으로 운영 반영 완료가 되지 않는다.

### W02-02 · 배포 시각의 생성 위치/성공 의미 불일치 — 확인된 개선 후보

**사실·소비 흐름:** fast `deploy-vm.sh:28`은 빌드 전에 `.deployed-at`를 쓴다. full에는 해당 기록이 없다. `backend/src/admin/deployment.js:30`의 `deployedAt`는 파일 내용 대신 `.deployed-at` mtime을 최우선(:32/:41)으로 읽고, `deploymentInfo:50` → `backend/src/admin/router.js:52` → `frontend/src/features/admin/screens/ServerResourceScreen.jsx:130`의 “전 배포” 표시로 전달한다.

**영향:** 기존 marker가 있으면 full 성공 후에도 이전 fast 시각이 남는다. fast에서 build/PM2/nginx/health 실패 시 이미 바뀐 시각이 남는다. 이는 코드 분기로 확인된 상태 의미의 차이이며 실제 운영 화면 오표시 횟수는 미측정이다. git commit도 `git rev-parse HEAD`(:20)라 pull 이후 아직 재시작하지 않은 프로세스와 배포 산출물의 revision을 식별하지는 않는다.

**유지/제안·효과:** 무정보 환경에서 null/fallback을 허용하는 admin 계약은 유지. 공통 성공 지점에서 성공 시각/배포 revision을 기록하는 작은 후보; 시도 시각이 필요하면 별도 의미를 붙인다. 운영 진단 신뢰도를 높이며 성능 목적은 아니다.

### W02-05 · 개발 런처의 readiness가 자신이 시작한 프로세스와 연결되지 않음 — 가설/후속 재현

**사실:** `projectamo-dev.mjs:startProcess`는 자식 exit를 로그만 남긴다(:25). `waitForUrl`(:50)는 HTTP 성공만 검사하고 자식 exit 여부/PID를 받지 않는다. `withServers`(:108)는 backend/frontend start 후 URL 성공이면 task를 실행한다. managed contract에는 별도 port guard가 있으나 일반 serve/verify/smoke/screenshot 경로에는 없다. root `npm run dev` 및 `.claude/launch.json`의 `autoPort:true`도 표준 런처와 다른 포트 계약이다.

### W02-07 · staging build의 보호 범위와 이전 자산 수명 — 유지 + 후속 가설

**유지/선행/위험/검증:** staging과 index 확인, 메모리 제한은 유지. 이전 버전 자산 보존 기간·revision 디렉터리 전환·클라이언트 재로딩 중 어떤 계약을 택할지 사용자 경험 및 VM 디스크 조건을 먼저 확인. 격리한 A/B production build에서 A 첫 진입 → B 교체 → A 미방문 lazy 화면 열기, build 실패 및 swap 실패 주입, 정상 캐시 재검증으로 확인한다. 현재 미실행; 바로 원격/CI 빌드로 이동하거나 전환 구조를 바꿀 근거는 아직 없다.
