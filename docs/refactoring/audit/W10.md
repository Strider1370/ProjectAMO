## 판단 요약

우선 검토 대상은 **푸시의 브라우저 구독과 사용자별 서버 등록을 같은 성공으로 취급하는 경로(W10-02)**, **감시용 복제본의 ETD/ETA와 재개 브리핑의 ETD/ETA가 다른 경로(W10-03)**, **저장 속도 필드 차이로 ETA가 빠져 목적지·교체공항 판정이 생략되는 경로(W10-05)**다. 세션의 현재 계정 상태 재검증(W10-01), 감시 복제본이 저장 목록·상한에 섞이는 현상(W10-04), 전달 실패 재시도(W10-08)도 구체 소비자가 있다. 아래의 사실은 소스에 존재하는 분기·자료 흐름이고, 재현·발생 빈도·실제 전달 결과는 모두 미검증이다.

유지할 핵심 구조는 SQLite 세션과 세션 사용자 ID 기반 소유권 필터, 공개 날씨 API와 개인 API 분리, 입력 스냅샷 저장과 기상 재계산 분리, 순수 알림 조건/diff와 전달 seam 분리, 공항+역할별 변화 감지, 만료 push 구독 정리, 운영 알림과 개인 비행 알림의 서로 다른 규칙이다. DB/HTTP 실패를 React 상태나 발송 성공으로 바꾸는 접점부터 좁게 정리하는 편이 현재 구조를 보존한다. 새 라이브러리 필요성을 입증할 근거는 없으며 권고하지 않는다.

## 개선 후보 — 사실·가설·미검증 분리

### W10-01 — 현재 계정 상태와 세션에 복사된 권한의 수명이 다르다

- **사실/근거:** `auth/router.js:48`은 로그인 시 status를 확인하지만 `:51`에서 기존 세션에 userId/role을 대입하고 regenerate 호출은 없다. `auth/middleware.js:8,17`은 userId·absoluteExpiry·세션 role만 확인한다. `db/users.js:53`의 me projection에는 status가 없다. 실제 상태 변경 진입은 `admin/router.js:76,85` reject→`users.js:65` UPDATE이고 세션 파기 작업은 없다. 기관 멤버 gate는 `organizations/middleware.js:22`에서 현재 userStatus까지 확인하여 개인 me/admin/forecaster와 차이가 있다. `scheduler.js:130`도 active 사용자 여부와 무관하게 감시행을 선택한다.
- **실제 효과/가설:** active 계정을 거절해도 이미 발급된 세션의 개인/역할 API는 다음 인증 만료까지 같은 권한을 사용할 수 있는 코드 경로다. 권한 회수 시점이 로그인 제한만인지 즉시 차단인지 정책은 미확인이다. 로그인 SID 회전 부재의 실제 악용 가능성은 조사/재현하지 않았다.
- **유지/후보·효과:** SQLite 세션과 세션 ID 소유권은 유지하고, 현재 계정 상태 확인 및 로그인 세션 갱신을 인증 경계에 둘지 결정한다. 효과는 계정 상태·HTTP 권한·백그라운드 알림의 수명 일치다.
- **위험/선행:** 기관 권한은 별도이므로 전역 role로 대체하지 않는다. 상태 회수·기존 세션 보존·작업중 데이터·로그아웃 후 push 정책을 먼저 정해야 한다. 제안 문서의 logout-all 후속 범위와 구분 필요.
