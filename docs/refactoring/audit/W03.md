## 발견별 근거·판정·검증 요구

### W03-01 — 수집의 이전값 원본이 일부 active cache다 (A10/A09/A11)

**사실:** `store.js:227` 공통 merge는 liveCache를 사용하지만 `taf-processor.js:43` previous TAF, `airport-info-processor.js:42`, `takeoff-forecast-processor.js:35`, `ground-forecast-processor.js:512`, `overseas-forecast-processor.js:112`, `terminal-flight-processor.js:306`은 `getCached`를 읽는다. `flight-category-processor.js:280` KIM/CTPS는 live root인데 `:299,302` ASOS/AMOS는 active cache다. `demo-session.js:49,50`은 active를 demo로 바꾸고 수집은 멈추지 않으며 `store.js:288,328`은 실황에 게시한다.

**가설/영향:** demo 활성 중 수집의 일부 실패·이전 발행 부착·부가 입력 조립 조건에서 시연 자료가 새 실황 snapshot의 일부로 섞일 수 있다. live 게시가 demo 화면을 덮는 문제와 반대 방향이다. 단순 `getCached` 전부 치환은 브리핑/조회까지 live로 바꾸므로 금지해야 한다.

**유지/후보:** active/live 분리와 즉시 pointer 전환 유지; 수집용 previous/read-input 원본을 명시하는 작은 accessor 또는 입력 주입 경계 검토. 기대효과는 snapshot 출처 일치; 위험은 TAF previous 의미·terminal arrival fallback·미수집 초기값 차이. 선행은 각 수집자의 입력 원본 계약 합의, W11 demo 정책 검수.

**미실행 검증:** 임시 root에 live/demo에서 식별자가 다른 자료를 두고 demo 활성+부분 upstream stub 실행 후 live 파일에 demo 식별자가 없는지 확인. `backend/test/store-data-view.test.js:7`은 반대 방향만 검증; processor까지 연결한 케이스가 필요하다.

### W03-02 — 취소를 게시 금지로 해석하지 않는 경로가 있다 (A10/A09)

**사실:** `overseas-forecast-processor.js:122` abort면 loop break, :140은 무조건 save다. 아직 순회하지 않은 공항은 failed에도 들어가지 않고 빈/부분 결과가 저장될 수 있으며 전송 `:97`에 signal도 전달되지 않는다. `index.js:75` 이후 정상 resolve면 :78~79 성공으로 기록하여 signal.aborted 자체는 거부하지 않는다. KIM `:630` signal은 공항비교에는 전달하지만 `:670~701` 지도 격자 작업과 :729~750 게시에는 전달/체크가 없다. KTG, NOTAM, AMOS, airport_info 등 기존 process()도 controller를 소비하지 않는다.

**가설/영향:** snapshot capture의 `quiesceCollections` 시 오래 대기하거나, 해외 예보가 취소된 회차의 일부만 게시될 수 있다. 취소 후 추가 게시가 실제 얼마나 발생하는지 미측정이다. `runWithLock` 하나에 마지막 abort check를 더해도 이미 끝난 processor save는 되돌릴 수 없다.

**유지/후보:** 타입별 lock/finally 및 satellite child 종료대기 유지. 네트워크→루프→게시의 signal 책임을 한정된 processor부터 정리하는 후보; 항공 자료 삭제 회귀/이미 완료한 부분 게시 허용 여부를 먼저 정해야 한다. 효과는 capture 일관성과 취소 지연 상한이다.

**미실행 검증:** `collector-cancellation.test.js:9`의 기존 세 타입 전송 abort 외에 overseas를 첫 호출 전/중간/저장 직전에 abort하여 이전 latest 유지와 rejected 결과 확인; KIM 지도 격자 전송·게시 중 fault/abort를 별도 검증. 전체 수집 전종 signal 지원을 이번에 확인했다고 처리하지 않는다.

### W03-03 — 파서 null·소스 전부 실패·정상 빈 자료의 게시 의미가 다르다 (A10/A11)

**사실:** METAR/TAF는 `metar-processor.js:21~31`, `taf-processor.js:22~32`에서 parser가 null이면 공항 추가도 failed 기록도 하지 않고 전체 snapshot을 저장한다. parser는 `metar-parser.js:247,358`, `taf-parser.js:319,408`에서 null 반환 경로가 있다. 반면 NOAA 공항 수집은 `overseas-weather-processor.js:31` 누락까지 failed로 보존한다. environment는 `:169~203` 주/대체 소스가 모두 rejected이면 pm/uv null을 게시하며 이전 usable 값을 읽지 않는다. API wrapper는 정상 빈 warning/resultCode 03을 의도적으로 허용한다(`api-client.js:53~55`).

**가설/영향:** 200이지만 기대 payload가 없는 응답 또는 provider 전부 장애가 정상 빈값처럼 기존 값을 제거할 수 있다. source의 실제 정상 무자료 조건·만료 삭제 계약은 미확인이다.

**후보/효과·위험·선행:** `성공 빈 자료 / 해석 불가 / 전송 실패 / stale 유지`의 타입별 결과 계약부터 정하고 adapter별 보존 정책을 적용할 후보다. 이전 자료 무기한 유지도 부적절하므로 시각/신선도 A11 검수와 frontend null/undefined 계약이 선행한다. 효과는 장애시 last-good 보존, 위험은 종료된 경보/낡은 환경값 계속 표시다.

**미실행 검증:** 외부 호출 없이 invalid IWXXM/정상 empty/공항 하나 누락/전 provider rejected fixture 각각의 save payload·failed 목록·응답 상태 확인. 기존 parser 테스트 존재만으로 processor 게시 정책이 보호된다고 보지 않는다.

### W03-04 — 일반 latest와 일부 meta의 게시가 직접 덮어쓰기다 (A10/A01)

**사실:** `store.js:111,140` 이력·latest를 writeFileSync로 순서대로 쓰고 :144 rotation 뒤 cache 갱신한다. 내용 불변 경로 :299도 latest 직접 쓰기다. `adsb-processor.js:75,175`, `rainviewer-processor.js:55`도 직접 쓰기. 반면 `kim-nwp-store.js:12`, `ktg-store.js:10`, `C/store.js:18`과 영상 store들은 임시 이웃 파일 rename을 쓴다. `server.js:293` readLatest는 손상 읽기에 기존 메모리 fallback이 있지만 재시작/정적 `/data` 소비까지 보장하지 않는다.

**가설/영향:** 프로세스 강제 종료·디스크 쓰기 실패 또는 다른 프로세스 읽기와 겹칠 때 partial JSON/이력과 최신 불일치가 가능하다. 같은 Node 이벤트루프 안의 동기 쓰기 도중 다른 JS handler가 개입한다고 주장하는 것은 아니다. 전용 store 또한 파일별 원자성과 다중 파일 transaction은 구분해야 한다.

**후보:** 일반 store와 ADS-B/RainViewer의 게시 seam만 먼저 원자화 검토; 파일명·이력 rotation·last-good 정책 유지. 효과는 재시작 복원/파일 소비 일관성; 위험은 임시 파일 cleanup·권한·디스크 오류 후 성공 판정 차이. 쓰기 실패 주입과 기존 `api-cache-policy`, `store-data-view`, `notam-store` 회귀가 선행/필요 검증. 속도 개선은 미측정이다.

### W03-05 — stale 변경이 content hash와 디스크에 반영되지 않을 수 있다 (A10/A11/A02)

**사실:** `store.js:209` canonical hash에서 `_stale`, fetched_at, type, content_hash를 재귀 제외한다. failed 공항 merge :234는 `_stale:true`를 덧붙인다. 해시가 같으면 :296 기존 disk JSON을 읽고 fetched_at/content_hash만 바꿔 쓰지만 :302 새 data를 메모리에 넣는다. `server.js:339,401` ETag/snapshot은 같은 hash, frontend `snapshotMeta.js:1,24`도 hash 비교다.
