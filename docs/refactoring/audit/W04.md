추가로 늦은 initial 전체 교체는 이미 합친 지연 필드를 초기 null placeholder로 되돌릴 수 있다 (`weatherApi.js:228`, `:234`). loadedDeferredKeys는 initial 시작/자료뷰 변경에 reset되지 않아 상태의 null과 Set의 등록 여부가 어긋난다. 지연 완료마다 `buildSnapshotMetaFromData`를 쓰면 **기존 snapshot의 viewRevision이 소실**된다. 이후 main poll의 revision mismatch가 모든 비교 키를 true로 만들어 일부 상태는 다시 회복하지만, 이는 순서 보장이나 원자적 자료뷰 commit이 아니다.

**판정/기대효과.** 우선 개선 후보. 문서상의 mounted/in-flight를 실제 요청 generation, 활성 자료뷰 identity, dataset writer 최신성으로 나누면 late commit과 불필요 재수신을 막을 수 있다. 단순 전역 latest-request-wins는 서로 다른 키의 유효한 동시 요청까지 버릴 수 있으므로 **전역 자료뷰 epoch와 키별 요청 소유권** 또는 동등한 명시 계약을 먼저 정해야 한다. transport abort만으로 이미 도착한 응답·abort 미지원 API를 보호할 수 없으므로 commit gate도 필요하다.

**위험/선행.** 초기 교체의 null 의미, 증분 undefined 보존, SIGWX 묶음, deferred 등록/재시도, main/monitoring의 다른 profile을 유지해야 한다. snapshot metadata를 받은 시점과 뒤따른 payload들의 자료뷰가 같다는 보증도 현재 client에서 검사하지 않으므로 backend response identity 계약(W03/A11)과 맞춰야 한다. 오래된 데이터의 서버 변환 여부와 network 지연 분포는 조사하지 않았다.

**필요검증.** 주 담당이 실제 hook으로 R1/R2/R3/R4를 각각 제어된 Promise로 실행하여 각 단계 data/hash/viewRevision/Set 및 최종 consumer props를 기록. 성공 순서·실패/abort·진짜 unmount·StrictMode·서로 다른 deferred 키 동시 완료도 포함. 읽은 영구 테스트에서 hook 렌더 수명/순서 검사는 찾지 못했고 pure merge/diff 테스트만으로 R1~R5는 보호되지 않는다.

### 4. W04-03 — 실패·빈 자료·초기 재시도

**사실 A: optional body 실패 경계.** `weatherApi.js:24`의 try 안에서 `return res.json()` (`:33`)을 await하지 않는다. native Response.json의 비동기 rejection은 이 catch를 지나지 않으므로 HTTP 200 malformed/truncated body는 optional=true/preserve라도 상위 Promise.all을 reject시킨다. monitoring의 별도 helper `monitoringApi.js:3`·`:7`도 같다. HTTP/network 오류→null/undefined와 body parse 오류의 동작이 달라, 정상 형제 응답까지 해당 initial/changed batch에서 commit되지 않을 수 있다. XHR fallback `weatherApi.js:52`는 JSON.parse가 동기 호출되어 native 경로와도 실패 처리 모양이 다르다.

**사실 B: null 계약의 차이.** `pollingData.js:1`은 undefined만 건너뛰고 null은 실제 빈 자료로 반영한다. `hasIncompletePollingData:10`에서 하나라도 undefined이면 전체 snapshot 전진을 보류하여 다음 poll 재시도를 가능하게 한다. 그런데 monitoring `loadChangedMonitoringData:66`은 `value ?? undefined`로 HTTP 200 JSON null까지 실패로 바꾼다. 따라서 같은 shared hook이라도 monitoring에서는 정상 empty 응답으로 이전 표시를 비울 수 없다. 이것이 monitoring만의 명시 정책인지 확인이 필요하며 Architecture `:62`의 전역 설명과는 차이가 있다.

**사실 C: monitoring 초기 실패 이후.** `loadMonitoringInitialData:69`는 날씨+필수 `/api/alert-defaults`를 Promise.all로 묶는다. 최초 defaults 실패 또는 optional 자료의 body parse reject로 초기 hook이 실패하면 onInitialData가 실행되지 않아 alertDefaults=null→intervalMs=null (`MonitoringPage.jsx:247`). error overlay `:741`에는 retry UI가 없다. 초기 실패 후 자동 poll로 다시 시작하는 main과 다르다. shared hook은 재초기화 성공 때 initialError를 지우지 않고 시작 때 loading을 true로 바꾸지도 않는다. 실제 일시 장애 빈도·운영 복구 행동은 미확인이다.

**개선 후보/효과.** transport/body decoding 실패를 optional 정책 안에서 일관되게 변환하고, HTTP 200 null 의미를 profile별로 명시. monitoring 초기 retry/loading/error 전이를 명시하면 일시 오류 뒤 정상 카드와 타이머가 복구되는지 판단 가능하다. 대규모 API-client 통합보다 좁은 실패 경계 수정과 profile 계약 검증이 먼저다.

**위험/선행/검증.** null을 실패로 보는 기존 화면의 경고 보존 목적을 W08와 확인해야 한다. stale 자료를 무조건 비우는 방향도 위험하다. 각 helper에 native async json rejection/HTTP503/network reject/200null을 같은 input matrix로 넣고 healthy sibling 보존, snapshot retry, 다음 성공 후 error 해제까지 검증한다. `monitoringApi.test.js:68`은 503→undefined만 보호하며 200null/body reject/재시작 경로는 다루지 않는다. `pollingData.test.js`의 기존 null/undefined 계약을 유지한다.

### 8. 유지할 구조와 우선순위

1. **W04-01 우선:** 같은 state에 쓰는 요청 수명과 자료뷰/키 identity를 명확히 한다. 실제 소비자까지 이어지는 production R1/R2 입력을 먼저 검증한다.
2. **W04-02 다음:** profile key를 대조하고 convective 불변 재조회, deferred 후 revision 소실부터 좁힌다. NOTAM 정책 결정과 main의 미소비 특보를 묶어 자동 수정하지 않는다.
3. **W04-03:** optional body 오류/200null/profile 초기 retry 계약을 확인한다. 특히 monitoring은 W08의 카드/alert 보존 의도와 함께 결정한다.
4. **W04-04:** demo clock 단일 구독과 자료뷰 시각 일관성은 A11/W11/W09와 설계한다. 실제 요청 감소/CPU/렌더 개선율은 기준선 측정 후 산출한다.
5. **W04-05/06:** 부트 preference 예외 방어는 좁은 개선 후보, 언어 설정·개인 딥링크 late intent는 제품/소비자 확인 후 결정한다.

유지 근거: route별 lazy 경계; main/monitoring의 제한된 data profile; 국내/해외 원본 분리; undefined와 null 구분 및 실패 때 snapshot 전진 보류; SIGWX 관련 payload의 의도적 묶음; no-store graphics metadata 정책; modelComparison 응답 공항 검증; 기관 진입 abort/auth/version 문맥; KIM subscriber/inFlight 공유; 지도 상태를 끌어올리지 않는 ref action/registry; 글꼴의 기존 lazy dedup; 모바일 뒤로가기 단일 stack과 cleanup; 테스트 가능한 순수 diff/merge/view-model 모듈. 파일의 크기·이름을 이유로 분할/삭제하는 후보는 없다.
