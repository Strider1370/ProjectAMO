### W09-04 — 권한 종료·문맥 전환과 발표 요청 수명

**사실.** 활성 회원 검사는 모든 새 기관 요청을 차단한다. 그러나 발표 동안 일반 목록 polling은 중지(`OrganizationLoungePage:117`)되고 발표 session polling `useOrganizationPresentation:169`는 401/403/404와 네트워크 오류를 구분하지 않고 삼킨다. 후보 준비의 403은 error만 설정하고 표시 bundle을 유지한다(`:94`). 상위 AuthProvider는 mount 때 refresh 한 번이며 이 오류들이 user를 null로 만들지 않는다(`AuthContext:18,24`). 발표 분기는 일반 EMPTY_DATA 경계 밖(`OrganizationLoungePage:163`)이고 이미 그린 지도/PDF/메모를 그대로 유지한다. 직접 logout은 user=null로 상위 분기를 바꿔 발표를 unmount하므로 그 정상 경로까지 누락으로 보지 않는다.

**판정/가설.** 현재 사용자의 기관 회원 자격이 서버에서 사라지고 다음 요청이 403으로 확정된 경우에도 기존 private 발표 화면이 남을 수 있다. 이는 새 API 권한 우회가 아니라 이미 전달된 자료의 표시 수명 문제다. 단순 일시 단절에는 마지막 자료 유지가 적절하므로 인증/기관 접근 종료와 일반 부분 실패를 구분할 필요가 있다. 이미 내려받은 PDF 바이트의 회수 가능성을 주장하지 않는다.

**문맥/취소 세부 사실.** sessionStorage key는 orgId+sessionId이고 userId가 없다(`hook:14`); 초기 restore는 active만 검사(`:115`), run 소유자는 UI 버튼 disabling에서 비교(`OrganizationPresentation:181`). API GET run은 회원에게 허용되므로 타 사용자의 active run을 같은 브라우저 저장 key로 복원하면 mutation은 403이고 새 자기 run 시작 UI가 없다. hook 인수/effect는 user identity를 포함하지 않으며 presentation 자체는 user별 key가 없다. candidate success는 epoch/token/runID/version으로 상당 부분 보호되지만, prepare/apply/end는 signal을 전달하지 않고 session polling success/error와 end commit에는 org/session 세대 조건이 없다(`:80,162,181`). end 완료 뒤 caller의 onExit도 이전 navigation closure를 실행할 수 있다. 이러한 역순 완료의 실제 브라우저 영향은 미재현이다.

**후보/효과.** 인증 주체+기관+회차+run을 요청 수명 문맥으로 명시하고 초기화/poll/prepare/apply/end 모두 결과·오류·finally를 해당 세대에 한정한다. 401/403/존재하지 않는 기관의 종료 상태에서는 권한 있는 화면에서 벗어나고, 네트워크 실패에는 last usable bundle을 유지한다. 읽기 취소와 이미 시작된 서버 mutation의 commit은 구분한다. **위험/선행:** AbortController만 추가해 서버 적용이 취소되었다고 간주하면 이미 적용한 run을 잃는다; command 결과 재조회/중복 방지와 owner restore 정책을 W10 세션 계약과 함께 정해야 한다. **검증(미실행):** active 회원→inactive 후 403, 같은 browser에서 사용자 변경, 기관/회차 전환 전의 session 응답과 end 응답을 각각 지연해 이전 자료/error/navigation이 새 문맥에 적용되지 않는지; PDF URL/문서 task cleanup도 함께 확인한다.

### W09-05 — 파일 게시·실패 정리의 공유 소유권과 교체 충돌

**사실.** `materials.js:162`의 `persistFile`은 내용 hash의 공용 경로가 없으면 즉시 원본을 쓰고 createdPaths에 기록한다(`:169`). 이미지이면 그 뒤 thumbnail 생성에서 await한다(`:172`). 두 번째 요청은 같은 원본이 이미 있으면 사용하되 자신의 createdPaths에는 넣지 않는다. 저장된 파일을 참조하는 material version DB transaction은 그 이후이며, 제목 검증도 create transaction 내부(`:284`)다. 실패 시 `cleanupCreatedFiles(:185)`는 해당 요청이 만들었던 경로를 DB 참조/진행 중 사용자 확인 없이 unlink한다(`:290,:333`). 파일 시스템과 DB transaction은 하나의 원자적 게시가 아니다.

**구체적 조건부 순서.** 같은 이미지의 A 업로드가 원본을 생성하고 thumbnail await → B 업로드는 원본을 발견해 재사용하고 thumbnail await → A가 제목 검증 또는 DB 실패로 rollback하며 원본 삭제 → B가 성공한 DB version을 저장하면 존재하지 않는 storage_key를 참조할 수 있다. B가 먼저 commit한 뒤 A가 실패해도 동일 위험이다. 실제 경합은 실행하지 않았고 sharp scheduling/프로세스 수에 대한 발생률 판단은 하지 않는다. 정상 단일 업로드·교체와 과거 버전 원본 보존이 잘못되었다는 뜻도 아니다.

**별도 충돌 상태.** 같은 material version을 교체하는 두 요청은 `:301`의 초기 version 검사 뒤 await를 통과할 수 있다. 둘 다 next=current+1을 정하고 `:318`에서 version 행 INSERT를 먼저 한다. `(material_id,version)` PK(`schema.sql:257`) 때문에 후행 요청은 `:328`의 CAS까지 도달하기 전에 UNIQUE 오류가 날 수 있다. `common.js:84`의 오류 매핑은 OrganizationError/FK만 구분하므로 이 경로가 의도한 409 대신 일반 500이 될 조건이 있다. 실제 SQLite 응답 확인은 미실행이다.

**후보/효과.** 내용 주소 파일의 게시·채택·참조 여부와 실패 정리 소유권을 하나의 명시적 저장 절차로 묶는다. 원본을 공유할 경우 staging 후 최종 채택/참조 기반 청소 같은 방식의 설계를 먼저 비교하고, 변경 전 단일 쓰기·불변 과거 원본 계약을 유지한다. async 파일 작업 이후 transaction 내부에서 현재 version을 다시 검증하면 stale writer를 의미 있는 conflict로 돌려줄 수 있다. **위험/선행:** 즉시 unlink를 모두 없애면 고아 파일 보존량이 증가하고, process-local lock만 두면 다중 프로세스/재시작에는 충분하지 않다; 백업·restore는 저장 파일과 DB 버전의 일관성에 의존한다(W10/W11). 파일 식별자에 조직 ID를 추가하는 변경은 기존 key/backup migration 검토 없이 제안하지 않는다. **필요 검증(미실행):** isolated 임시 저장소에서 동일 이미지 두 요청을 thumbnail 앞뒤 barrier로 제어하고 한 요청만 invalid title/DB 실패시키며 성공 자료의 original/thumbnail byte 보존 확인; 같은 expectedVersion 교체는 성공 하나·409 하나와 과거 v1/v2 원본 확인; rollback 이후 DB 참조 파일 누락이 없어야 한다. 이 worker는 임시 실행 코드도 만들거나 실행하지 않았다.

## 유지할 구조와 성급히 합치지 않을 경계

1. **기관 권한·별도 API:** request마다 활성 회원 조회, role/owner/assignee별 제한, 조직 ID로 SQL scope, trusted Origin, versioned original/Range의 동일 권한 체인. 개인 route API로 우회시키지 않는다.
2. **불변 버전·CAS·이력:** flight/material/briefing 내용 버전과 run application history, 현재 배정·상태 메타의 의도적 분리. 자료 soft delete와 pinned 과거 원본 접근도 보존한다.
3. **후보/표시 분리:** source revision이 바뀌어도 후보만 준비하고 명시 적용 때 표시 bundle 변경. per-flight applied history와 해당 bundle.organizationSnapshot 우선 hydration.

## 성능·취소·미확인 범위

- **성능은 미측정:** NWP/cacheRevision을 포함한 자료 snapshot fingerprint의 파일 I/O, 매 후보 hash와 JSON 저장량, 60초 후보 누적/보존량, reload 시 application events 전체 hydration, PDF worker/canvas memory, 지도 레이어 렌더 비용. 큰 파일/함수/테이블이라는 이유로 비효율을 확정하지 않는다. 주 담당이 수행한 RF-003 API/production browser 측정과 중복 실행하지 않았다.
- **취소는 부분 확인:** frontend 후보 token은 stale success를 막지만 서버 async 분석의 비용을 중단하지 않는다. Express handler에 browser abort를 지형/NWP 작업으로 전달하는 조직용 signal 연결은 찾지 못했다. 개인 API/cross-section 취소 내부는 W03/W06 입력이며 서버 성능/작업량은 주 담당의 별도 측정 대상이다.
- **권한 시간 경계:** 요청 시작 시 회원 검사와 장시간 업로드/분석 중 권한 변경의 commit 정책, signed-out 다른 탭 auth 갱신, 복원 run의 owner가 달라질 때 UX는 미검증이다. 새 요청의 권한 검사와 이전 화면 정리는 분리하여 W10과 좁혀야 한다.
- **자료 전체성:** KML/KMZ parser 내부 전체 입력 공격면, PDF 모든 MIME/Range/네트워크/stream close 오류, 실제 삭제·복원·retention의 권한/이력 보존은 이 묶음에서 전수 검증하지 않았다. 내용 주소 파일 실패 정리는 W09-05로 좁혔다.
- **동일 회차:** 자료함에서 과거 material을 열 때 root metadata의 updatedAt/owner와 버전 content가 함께 내려오는 의미, per-flight 이전 applied bundle과 새 run header의 표시 의미는 아직 제품 계약 확인이 필요하다. 값이 다르다는 이유만으로 불변성 파괴로 판정하지 않는다.
- **소스 상태:** presentationWeatherState는 알려진 일부 status만 제한 상태로 분류(`lib/presentationModel.js:89`)하므로 미래에 `unknown/expired/conflicting`이 componentStatus에 실제 도달하면 정상 label로 통과할 가능성은 있다. 현재 backend generator의 도달 가능한 enum을 넘어선 가설이며 신규 확정 결함으로 올리지 않는다. advisory 누락의 종단 표시는 W06-06/A11과 통합한다.
- **상황 동시성:** timer끼리 lock은 있지만 GET/timer evaluation의 역순 완료·sourceRevision 비교, 알림 read와 situation write를 한 fan-out에서 호출하는 시차는 미검증. 대표 정상/부분 실패 흐름만 확인했으므로 상황 영역 전체 완료를 주장하지 않는다.
- **UI/자산:** 4개 CSS의 모든 selector·폭/접근성·실제 PDF 캔버스·preview JSON의 모든 flight 좌표/예시문구를 검사하지 않았다. backend preview JSON/PDF는 자산의 생산/소비 관계를 기록하고 손코드 복잡도/결함 근거에서 제외했다.
