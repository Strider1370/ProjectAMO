# 프로젝트 전체 리팩토링 계획

작성일: 2026-09-11. 최초 조사 기준: `075eb89a8a2ffe5fde8ccf9bf1cbec954284fa41` (`main`).

목표는 프로젝트 전체의 변경 비용과 실행 비용을 조사하고, 근거가 있는 개선을 작은 작업으로 완료하는 것이다. 프론트엔드, 백엔드, 공통 데이터, 자산, 테스트, 개발·배포 도구, 문서를 모두 조사한다. `server.js`, `useRouteBriefing.js`, `MapView.jsx`는 초기 후보이며 작업 범위나 실행 순서를 확정한 목록이 아니다.

S004에서는 RF-001~003의 기준선·15영역 진단·대표 성능을 조사하고 [선택용 진단 보고서](report.md)를 작성했다. S007~S009에서 사용자가 고른 범위의 구현·통합 기록을 남겼고, **전체 1단계는 S009에서 문서 마감**했다. 이 말은 선정 카드의 완료·부분 완료·보류를 [작업 목록](tasks.md)에 기록했다는 뜻이며, 실행하지 않은 전체 브라우저 묶음이나 Stage 2 후보를 통과로 계산하지 않는다. 현재 상태와 다음 작업은 [진행 기록](progress.md)을 먼저 읽는다.

S009의 “전체 1단계”는 이 계획의 단계 1(RF-001~003)을 다시 실행했다는 뜻이 아니라, 사용자가 S009에서 선정한 구현 묶음의 첫 종료 단위다. RF-004~007 및 S007/S008의 완료 기록은 유지한다. 다음 구현은 완료되지 않은 S009 카드와 새 사용자 선택을 대상으로 하는 Stage 2이며, 기존 기준선의 미검증 범위를 소급해 통과로 만들지 않는다.

단계 1에서는 전체 디렉터리 목록과 소비 경로를 확인한 다음 위험과 변경 빈도에 따라 깊이를 조절한다. 조사하지 않은 영역을 빈칸으로 남기거나 세 파일의 정리만으로 전체 진단을 완료하지 않는다. 새 영역이나 교차 문제가 발견되면 진단표를 추가한다.

RF-001의 실행 환경 문제가 RF-002의 읽기 전용 조사를 막지는 않는다. 미확인 성능이나 브라우저 동작이 있으면 해당 결과에 의존하는 작업만 대기시키고, 근거가 확보된 독립 작업은 계속할 수 있다. 다만 전체 범위의 분류와 우선순위 검토를 거친 뒤 구현 묶음을 선정한다.

## 탐색과 구현의 경계

2026-09-12 사용자 요청에 따라 `정교한 탐색 → 진단 보고서 → 사용자의 실제 작업 대상 선정 → 리팩토링 구현`을 구분한다. RF-001~003과 RF-004의 보고서 준비까지는 진단 범위다. 주 담당과 서브에이전트는 후보를 발견했다는 이유로 앱 코드·설정·저장 형식·영구 테스트를 수정하지 않는다. 진단에 필요한 임시 재현·측정 도구는 ignored artifacts 아래에 두고 결과를 기록한다.

진단 보고서는 문제의 원인·소비 경로·재현 또는 측정 근거, 제안 변경, 효과·위험·의존성·검증 방법을 갖춘 후보를 포함한다. 확인된 문제, 개선 가치 판단, 미검증 가설을 구분하고, 파일 크기만으로 수정 필요를 확정하지 않는다. 유지할 부분과 추가 확인이 필요한 부분도 제시한다.

주 담당은 보고서와 추천 작업 묶음을 먼저 완성해 제시한다. 사용자가 이를 보고 `이번에 작업 / 보류 / 제외 / 추가 조사`를 선택한 뒤에만 RF-005~006과 선정된 구현 카드에 착수한다. 이 선택 단계는 사용자가 요청한 진행 방식이며, 후보의 우선순위를 정하거나 서브에이전트 보고서를 받았다는 이유로 생략하지 않는다.

선택한 ID·범위와 사용자 지시의 날짜를 작업 목록에 기록한다. 이미 선택한 범위의 일상적인 구현·검증마다 다시 확인을 요구하지 않는다. 새 문제나 범위 확대는 별도 후보로 남겨 사용자 선택과 구분한다. 다음 세션도 이 기록을 확인하며 진단 완료를 구현 착수 지시로 해석하지 않는다.

## 개선 후보를 고르는 기준

각 발견 사항을 `구조`, `성능`, `검증`, `정리`, `버그`로 구분한다. 버그로 인한 동작 변경은 명시하고 구조 변경의 전후 비교에 섞지 않는다.

- 효과: 같은 규칙을 여러 곳에서 수정하는 비용, 변경 빈도, 반복 장애, 사용자의 대기, 요청량과 자원 사용으로 설명한다.
- 근거: 코드 위치·소비자·재현 사례 또는 같은 조건에서 측정한 수치를 제시한다. 줄 수는 탐색 단서다.
- 위험: 상태 전이, 외부 응답, 저장 형식, 인증·기관 경계, 지도 생명주기처럼 동작이 바뀔 수 있는 범위를 적는다.
- 의존성: 다른 개선을 가능하게 하는 공통 경계와 필요한 테스트를 먼저 식별한다.
- 검증 가능성: 변경 전후를 비교할 관찰값과 필요한 환경을 정한다.

우선순위는 `P1`(영향이 크거나 후속 작업의 선행 조건), `P2`(효과가 확인된 독립 개선), `P3`(효과가 작거나 사용 빈도가 낮은 정리)로 기록한다. 근거가 부족한 항목은 `미정`으로 둔다. 변경하지 않기로 한 영역도 이유와 재검토 조건을 남긴다.

시범 작업은 검증이 가능하고 책임 경계가 명확한 한 묶음을 고른다. 현재 백엔드 기상 조회 API 분리는 후보 중 하나다. 전체 진단에서 공통 데이터·요청·테스트 문제가 확인되면 그 작업이 먼저 올 수 있다.

## 구현과 검증 원칙

- 한 작업에서 하나의 개선 목적을 다룬다. 상태와 상태를 바꾸는 로직을 함께 검토하고 공개 인터페이스와 소비자를 확인한다.
- 기존의 기능별 어댑터, 폴링, 레지스트리, 요청 취소, 저장소 경계를 먼저 평가한다. 새 추상화나 라이브러리는 실제 중복·비용의 근거가 있는 작업 카드에서 결정한다.
- API·화면 동작·저장 형식의 유지 조건을 카드에 적는다. 구조 정리와 기능 추가·디자인 변경·의존성 대규모 갱신은 별도 작업으로 구분한다.
- 시간과 부분 실패는 [데이터·시간 정책](../policies/engineering/data-and-time.md), 브리핑은 [자료 계약](../policies/engineering/route-briefing-source-contract.md)을 따른다. 누락·미확정 자료의 상태와 출처를 보존한다.
- 지도는 [지도 정책](../policies/engineering/map-and-layers.md)에 따라 현재 상태 복원, 이벤트 정리, 토글·팝업·배경지도 두 차례 전환을 확인한다.
- UI/CSS는 [디자인 정책](../policies/design/design-language.md)에 따라 토큰·판독성·반응형·접근성을 보존한다. 생성 CSS와 외부 자산은 생성기·원본·라이선스를 기준으로 다룬다.
- 테스트는 실제 동작을 보호하는 필요한 범위에 보완한다. 소스 문자열 검사에만 의존하는 중요한 흐름은 입력·출력 또는 브라우저 동작으로 검증한다.
- 작업별 관련 테스트를 실행하고, 통합 시 `npm run check` 및 변경 범위의 브라우저 계약을 실행한다. 이미 통과한 검사는 새로운 변경이나 미해결 우려가 있을 때 반복한다.
- 의존성·배포는 [운영 문서](../operations/operations.md)를 따른다. 이 계획 자체는 운영 배포나 운영 데이터 변경 지시가 아니다.

## 서브에이전트 활용

### 배정과 결과 통합

1. 주 담당이 기준 HEAD·기존 변경, 조사 질문, 대상 파일과 소비자, 읽을 규칙, 허용 작업, 반환 형식을 지정한다. 한 배정의 질문은 1~3개로 좁힌다.
2. 조사자는 경계의 전체 목록을 확인하고 변경 빈도·위험에 따라 실행 경로를 깊게 읽는다. 범위가 너무 크면 확인한 범위와 남은 구간을 반환하고 주 담당이 후속 묶음으로 나눈다.
3. 조사 중에는 소스·공통 문서·설정·데이터를 수정하지 않는다. 추가 서브에이전트 생성도 주 담당이 조율한다. 전체 테스트·서버·수집을 임의로 시작하지 않는다.
4. 결과에는 사실과 가설, 유지할 구조, 소비자까지 이어지는 코드 근거, 미검증 사항을 담는다. 문제 개수 목표를 두지 않는다.
5. 주 담당은 작업 후보로 채택할 근거와 시간·권한·저장·지도 생명주기 관련 판단을 직접 대조한다. 해석이 충돌하면 해당 경로를 재확인하거나 좁은 검증을 추가하고, 해소 전에는 미확인으로 둔다.
6. 확인한 보고서는 즉시 진단표에 반영한다. 같은 문제에 대한 중복 보고는 하나의 OBS ID로 합치고, 에이전트가 종료됐다는 사실과 영역의 조사 완료를 구분한다.

주 담당은 조사자가 일하는 동안 RF-001, 범위 분류, 공통 계약 추적, 앞선 결과 검수 등 독립 작업을 진행한다. 완료한 결과부터 받아 필요한 후속 작업을 배정하며 모든 슬롯이 끝날 때까지 일괄 대기하지 않는다.

### 동시 실행과 파일 소유권

- 읽기 전용 소스 조사는 서로 같은 파일을 참조해도 된다. 실행 코드가 바뀌면 영향받은 보고서의 기준을 확인하고 해당 근거만 재검증한다.
- 전체 테스트·빌드·관리형 브라우저 검사는 주 담당이 한 번에 한 실행자에게 배정한다. Playwright 기본/기관 설정은 3001·5173과 보고서 디렉터리를 공유하므로 동시에 실행하지 않는다. 작은 단위 테스트도 다른 작업과 파일·DB·출력이 분리됐는지 먼저 확인한다.
- 성능 측정 동안에는 같은 호스트의 테스트·빌드·대량 검색·수집 등 측정에 영향을 주는 작업을 겹치지 않는다. 서브에이전트는 별도 측정을 시작하지 않고 확보한 결과를 분석한다.
- 병렬 구현은 파일 소유권, 의존 인터페이스, 검증 방법이 정해진 카드만 대상으로 한다. 같은 파일의 서로 다른 줄을 수정하는 것도 별도 소유권으로 취급하지 않는다.
- `backend/server.js`, `MapView.jsx`, `useRouteBriefing.js`, 공통 API·모델, package/lock, 공통 CSS·계획 문서는 한 시점에 한 담당만 수정한다. 여러 카드가 같은 파일을 필요로 하면 먼저 공통 경계를 정리하거나 실행을 순차화한다.
- 작업자가 범위 밖 수정이 필요하다고 발견하면 근거를 주 담당에게 전달한다. 주 담당이 소유권과 순서를 재조정하고 이미 허용된 범위의 작업을 이어간다.
- 통합 문서의 OBS ID 발급, 작업 상태 변경, 세션 인계 갱신은 주 담당이 맡는다. 서브에이전트의 보고는 독립 작업 ID로 식별한다.

### 효율과 세션 지속성

처음에는 RF-002의 준비 조사 세 묶음으로 분담을 평가한다. 배정·반환 시각과 추가 확인을 요청한 이유를 기록해 조사 시간과 통합 비용을 판단한다. 보고서에 근거가 부족하거나 중복 조사·재작업·검수 비용이 크면 질문을 좁히고 동시 수를 줄인다. 작은 수정·이미 원인이 확정된 짧은 작업은 주 담당이 처리한다. 사용할 수 있는 슬롯을 항상 채우는 것을 목표로 하지 않는다.

배정 시 [작업 목록](tasks.md)에 상태를 기록하고 [진행 기록](progress.md)에 현재 작업 ID, 에이전트 식별자, 코드 기준, 허용 파일/실행, 아직 반영하지 않은 결과를 남긴다. 장시간 작업은 조사자가 중간 체크포인트를 반환하고 주 담당이 세션 종료 전에 저장한다. 다음 세션은 작업 ID와 보존된 근거를 기준으로 재개하며 이전 에이전트가 계속 존재한다고 가정하지 않는다.

## 세션 시작과 재개

1. 최신 사용자 지시와 `AGENTS.md`를 읽고 [진행 기록](progress.md)의 재개 지점을 확인한다.
2. `git status --short`, `git branch --show-current`, `git rev-parse HEAD`로 작업 트리와 기준을 확인한다. 이전 기록 이후 변경이 있으면 해당 작업의 근거·검증 유효성을 확인한다. 기존 변경은 보존한다.
3. [작업 목록](tasks.md)에서 진행 중 항목을 먼저 확인한다. 없으면 의존성이 충족된 다음 항목을 선택하고 `in_progress`로 갱신한다.
4. 선택한 작업의 진단 근거, 완료 조건, 관련 정책·테스트를 읽는다. 완료한 조사를 처음부터 반복하지 않고 달라진 부분을 재확인한다.
5. 기록된 범위 안에서 진행한다. 실행 불가 항목은 정확한 원인과 재개 조건을 남기고 독립적으로 진행 가능한 항목을 선택한다.

## 작업 종료와 세션 인계

1. 작업 카드에 실제 변경·조사 범위와 결과를 반영한다. 구현됐지만 검증이 남은 항목은 완료로 표시하지 않는다.
2. 진단표에 새 근거, 조사 완료·보류 판단, 성능 수치를 갱신한다.
3. 진행 기록 상단의 현재 위치와 다음 작업을 갱신하고, 세션 기록에 명령·결과·차이·결정을 추가한다.
4. 커밋이 있으면 해시를 기록한다. 미커밋이면 수정 파일과 남은 검증을 기록한다. 커밋·푸시 여부와 로컬 문서 저장을 구분한다.
5. 코드 소유권이 바뀌면 `Architecture.md`, 검증 계약이 바뀌면 해당 등록 문서를 갱신한다. 공통 안내를 바꿀 때 `AGENTS.md`와 `CLAUDE.md`를 동일하게 유지한다.

한 세션에서 여러 작업을 완료할 수 있다. 세션 경계 때문에 별도 승인 단계를 추가하지 않고 최신 사용자 지시와 기존에 허용된 범위를 따른다.

## 전체 종료 기준

- 진단표의 모든 영역에 범위·근거·판정이 있고, 확인하지 못한 부분에는 이유와 재개 조건이 있다.
- 이번 회차에 선정한 개별 작업이 모두 검증을 마쳤다. 보류는 사유와 재검토 조건이 명시돼 있다.
- 주요 사용자 흐름, 시간·부분 실패·인증 경계, 데이터 계약에서 회귀가 없다. 실행하지 못한 검증은 통과로 합산하지 않는다.
- 성능 개선을 주장하는 항목은 같은 조건의 전후 수치가 있다. 미측정 항목은 구조 개선 효과만 보고한다.
- 새 기능을 추가할 위치, 데이터·상태의 소유자, 테스트 방법이 코드와 문서에서 일치한다.
- 최종 미검증 사항이 남으면 해당 부분의 검증을 포함해 전체 완료했다고 표현하지 않는다.
