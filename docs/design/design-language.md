# ProjectAMO 디자인 헌법 (Design Language)

> **이 문서는 ProjectAMO 디자인 규칙의 유일한 출처(single source of truth)다.**
> 모든 UI·CSS·레이아웃·반응형·디자인 작업 전에 이 문서를 먼저 읽고 그대로 따른다.

## 1. 정체성
> 조종사·관제사·기상 담당자가 **비행 전 위험 기상을 즉시 판독**하도록 돕는 지도 기반 관제 대시보드. 깊이(브리핑 전문성) 우선, 넓이(EFB 기능) 비추구.

## 2. 핵심 원칙
1. **판독성 > 미관.** 보기 좋아도 인식이 느리면 실패.
2. **색 = 의미.** 한 의미 = 한 색. 장식 색·그라데이션 금지, 색은 아껴 쓴다(정상=무채색, 위험만 색).
3. **데이터가 주인공.** 베이스맵은 차분히 뒤로, 데이터 레이어가 떠 보이게.
4. **빽빽하되 위계 있게.** 밀도는 높이되 크기·굵기·간격으로 정리.
5. **상태 먼저, 컨트롤 나중.** 화면은 "무엇을/얼마나 안전한가"부터 답한다.
6. **하나의 시스템, 반응형 표현.** 데스크톱·모바일이 색·글씨·의미는 동일, 배치·터치만 다름.

## 3. 하지 말 것
- 보라/파랑 그라데이션, 장식용 그라데이션
- 의미 없는 강조색, 한 색에 두 의미
- rainbow/jet 컬러맵 (→ viridis/cividis/cmocean)
- 색만으로 등급 구분 (→ 색 + 명도 + 범례 + 해칭 병기)
- 데스크톱 레이아웃을 모바일에 그대로 축소
- 눈에 보일 만큼 진한 그림자, CDN 폰트 의존

## 4. 색 사용 3버킷
| 버킷 | 규칙 | 예 |
|---|---|---|

## 5. 토큰 (단일 소스)

- **레벨:** green `#166534`/bg `#dcefe2` · amber `#92400e`/`#fdecc8` · red `#c0291f`/`#f7dcd9` · gray `#475569`/`#eef2f7`

## 6. 반응형·레이아웃 (구 ui-responsive-guidelines 흡수)

### 6-0. 플랫폼·기기 타깃 (2026-07-05 명시)

**주 사용자 = 조종사, 주 기기 = iPad (iOS Safari).** 항공 EFB(전자비행가방)는 iPad가 지배적이다(ForeFlight iOS 전용, 항공사 EFB 대부분 iPad 표준화). 안드로이드는 부차.

- **개발·테스트 우선순위: iPad Safari(가로) ≥ 데스크톱 > 폰 > 안드로이드.** 반응형·QA는 iPad 가로(대략 1024×768 / 1180×820)를 1급 표면으로 본다.
- **배포 형태 = 네이티브 앱 아님 → 웹앱 + PWA.** 홈화면 설치(앱 아이콘·전체화면) + iOS 웹푸시(iOS는 홈화면 추가 시에만 동작 — #13 알림 온보딩에 반영). 앱스토어 배포가 정말 필요해지면 Capacitor로 현 React 앱을 래핑(먼 미래 옵션), Swift 재작성은 지양.
- ⚠️ **현재 갭: 태블릿(iPad) 반응형이 아직 미대응.** 지금 반응형은 데스크톱·폰(≤719) 위주이고 태블릿 가로 표면은 별도 검토 필요. 구조 변경은 헌법 §6-D(제안·승인 후 구현) 원칙을 따른다.

---

ProjectAMO는 마케팅 사이트가 아니라 운영 도구다. UI는 조종사·관제사·기상 담당자가 **시간 압박 속에서 중요한 상태를 빠르게 인식하고 자신 있게 행동**하도록 도와야 한다.

**제품 렌즈 — 사용자는 이런 질문을 한다:** 지금 어떤 공항·항로·기상 상황인가? · 현재 상태가 안전/제한/곧 변화인가? · 다음에 중요한 경보·예보 변화는? · 다음에 열 컨트롤·상세는?

**정보 경합 시 우선순위:**
1. 정체성·범위 (공항, 항로, 모드, 활성 컨텍스트)
2. 현재 운영 상태 (flight category, 경보, 제한, 안전 영향 조건)
3. 다음 중요한 변화 (TAF 전환, 경보 발생, 예보 변화)
4. 의사결정 보조 상세 (지도 맥락, 보조 카드, 설정)
→ 저우선 컨트롤·장식이 현재 상태·다음 변화 정보를 가리면 안 된다.

**문제로 간주(CSS 오버플로 없어도):** 중요 상태가 덜 중요한 컨트롤 아래 묻힘 · 핵심 기상/경보 찾기 전 카드 너무 많이 스캔 · 지도와 데이터가 주 작업 없이 경합 · 모바일이 데스크톱 구조 유지로 읽기 어려움 · 표/카드가 들어가긴 해도 너무 빽빽 · 핵심 정보 도달에 인터랙션 과다. (전통적 실패: 클리핑·오버랩·잘림·숨은 컨트롤·깨진 클릭·페이지 가로스크롤도 포함.)

**반응형 철학:** 모든 데스크톱 표면을 태블릿/모바일에 한꺼번에 유지할 필요 없다. 좁은 화면에선 — 작업 분리 > 빽빽한 공존 · 모드 전환 > 읽기 힘든 혼합 · 전용 읽기 뷰 > 데스크톱 나란히 구성 유지. 좁아져서 읽기 어려우면 폰트 축소·간격 압축보다 **구조 단순화**.

### 6-A. 모바일 대원칙 (AI 검증용)

> 각 원칙은 `{스크린샷 + 소스}`로 위반/준수를 판정할 수 있게 임계값을 명시한다. 임계값은 §5 토큰에 바인딩한다.
> 근거: Nielsen 10 휴리스틱 + iOS HIG / Material + 터치·WCAG 실무 표준.

**P1. 플랫폼 관습을 따른다.** OS 네이티브 패턴(하단 탭·바텀시트·스와이프·풀스크린 상세)을 우선. 커스텀 인터랙션은 네이티브로 표현 불가할 때만, 정당화와 함께.
- 내비게이션이 하단 탭바 또는 표준 시트/드로어 패턴인가? 커스텀 슬라이드 레일·비표준 제스처면 **위반**
- 라이브 지도 위에 데이터 폼/모달을 고정했는가? 바텀시트/풀스크린으로 분리 안 됐으면 **위반**
- 닫기/뒤로가기가 표준 위치(좌상단 또는 시트 핸들)인가? 아니면 **주의**
- *검증법:* 소스 내비 컴포넌트 구조 + 스크린샷의 지도 위 오버레이 고정 여부.

**P2. 상태 가시성 우선.** 화면은 컨트롤·장식보다 현재 운영 상태(flight category·경보)부터 답한다.
- 첫 뷰포트(스크롤 0, 390×844)에 flight category 또는 경보 상태가 보이는가? 안 보이면 **위반**
- 상태 요소가 상단 1/3 + 크기 ≥ `--fs-400`(16px)인가? 컨트롤/장식이 더 큰 비중이면 **위반**
- 빈 지도/빈 리스트만 뜨고 상태 요약 한 줄이 없는가? 있으면 **위반**
- *검증법:* 스크린샷 상단 1/3 스캔 + 소스 JSX 렌더 순서.

**P3. 점진적 노출 & 미니멀.** 한 화면 한 작업. 핵심만 먼저, 상세는 펼친다. 데스크톱 밀도를 줄여 끼우지 않고 재구성한다.
- 한 화면에 독립 작업이 2개 이상 동시 노출(예: 지도+폼+리스트)? **위반**
- 읽기 표면(TAF·AMOS·해설)이 한 줄 요약/심각도부터 시작하는가? 원문 덤프 먼저면 **위반**
- 데스크톱 표를 그대로 축소해 폰트 < `--fs-200`(12px)로 넣었는가? **위반**(재구성 필요)
- 페이지 가로 스크롤 존재? **위반**(패널 내부 표 폴백만 허용)
- *검증법:* 스크린샷 스캔 + 소스 폰트 크기·`overflow-x`.

**P4. 일관성 & 표준.** 같은 의미 요소는 화면 간·데스크톱과 같은 토큰·모양·위치·동작.
- 색·간격·radius·타이포가 전부 §5 토큰에서 오는가? 하드코딩 px/hex 있으면 **위반**
- 3표면의 헤더·시트·칩·1차버튼이 동일 컴포넌트/패턴인가? 표면마다 다르면 **위반**
- 같은 의미(경보=red, VFR=green)에 §5 시맨틱색만 쓰는가? 임의색이면 **위반**
- 데스크톱 대응 요소와 색·타이포·라벨이 일치하는가(패리티)? 어긋나면 **위반**
- *검증법:* 소스 grep으로 하드코딩 hex/px + 3표면 CSS 클래스·컴포넌트 대조.

**P5. 터치 인체공학.** 주요 액션은 엄지 도달 범위, 오작동 없는 크기·간격.
- 모든 탭 가능 요소의 히트 영역 ≥ `--touch-min`(44×44px, Apple HIG 최소)? 미만 **위반**
- 인접 터치타깃 간격 ≥ `--space-s`(8px)? 미만 **위반**
- 주 액션(탭바·1차 CTA)이 화면 하단 60% 엄지존인가? 상단 코너 단독이면 **주의**
- *검증법:* 소스 `min-height/width·padding` 계산 + 스크린샷 간격 측정 + axe(target-size 룰) 자동 스캔.

**P6. 접근성은 기본값.** 대비·동적 타입·스크린리더·색 이외 단서가 기본값.
- 텍스트/배경 대비 ≥ WCAG AA(본문 4.5:1, 큰 텍스트 3:1)? 미만 **위반**
- 등급/상태가 색만으로 구분되는가? 색+아이콘/라벨/명도 병기 아니면 **위반**(§3 일치)
- 아이콘 단독 버튼에 접근성 이름(aria-label/텍스트)이 있는가? 없으면 **위반**
- 폰트/간격이 고정 px라 확대에 안 따르는가? 상대단위 권장, 고정이면 **주의**
- *검증법:* axe(color-contrast·aria·label 룰) 자동 스캔 + 스크린샷 대비 확인 + 소스 `aria-*`·단위.

### 6-B. 적용 예 (참고, 규칙 아님)
대원칙의 구체 적용 예시 — 위반 판정 시 참고만 한다:
공항 상세=풀스크린+전 섹션 1탭(P1·P3) · 하단 작업 탭바(P1) · TAF/AMOS 세로 스택 읽기 블록(P3) · 읽기 표면 한 줄 요약 먼저(P3) · 마스코트/장식은 상태보다 낮은 비중(P2) · monitoring 화면이 밀도·재구성 참조 모델(P3).

### CSS·레이아웃 규칙
- 폭·간격·breakpoint 추가/변경 전 **공유 토큰(`layoutTokens.css` + 본 헌법 §5)부터 확인.** 새 고정 픽셀 폭은 정당화 없이 추가 금지.
- CSS로 구조 문제를 가리지 말 것. **나쁜 수정:** 빽빽한 데이터가 들어맞을 때까지 폰트 축소 / 충돌 안 나게 간격만 축소 / 데스크톱 표를 좁은 모바일에 그대로 / 읽기 어려운 지도+패널 나란히 유지. **좋은 수정:** 정보 위계 변경 / 작업별 모드 분리 / 보조 컨트롤 뒤로 / 데스크톱 읽기 표면을 모바일 읽기 흐름으로 전환.

### 스크롤 규칙
- 페이지 가로 스크롤 = 실패.
- 패널 내부 가로 스크롤은 본질적으로 2차원인 콘텐츠(빽빽한 표, 다일 예보 그리드)의 폴백으로만 허용. 더 명확한 구조가 있으면 그쪽 제안.

## 7. 워크플로우 (구 ui-responsive-guidelines 흡수)

**보이는 UI 작업 절차:** (1) 관련 상태·뷰포트 캡처 → (2) 편집 전 이슈 기록 → (3) 기계적 깨짐 vs 운영 명료성 문제 분리 → (4) read-only 리뷰어로 점검 → (5) 이슈 수집 후에만 집중 수정 → (6) 재캡처·상태 갱신.
반응형 작업은 영향받는 패널/탭 상태마다 **스크린샷 증거** 필수. `artifacts/responsive-screenshots/<phase>/<YYYY-MM-DD_HHMM_label>/`에 저장 + 짧은 manifest + `review/issues.md`.

**리뷰어 질문:**
- *UI QA:* 핵심 상태를 몇 초 안에 찾나? · 압박 속 읽기 어려운 값/라벨/경보? · 컨트롤이 보이고 닿고 명확한가? · 클릭 가로채기·숨은 상태·오버플로? · 지도가 주 읽기를 압도하지 않나?
- *디자인:* 밀도가 운영 도구다운가? · 타이포가 스캔을 돕나? · 색·강조·그룹핑이 기능적인가? · 간격 폴리시 문제인가 정보구조 문제인가? · 더 강한 구조 변경이 속도·이해를 높이나?
- *스펙:* 승인 범위 안인가? · 미승인 구조 행동을 넣었나? · 제안이 승인 전 구현됐나?

### Proposal-First 규칙 (구조 변경)
새 모바일 작업탭 모델, map/data 모드 분리, drawer→sheet 전환, 풀스크린 스텝 흐름 등 **인터랙션 아키텍처 변경은 기본 미실행.** 캡처·분석·결함 식별·운영자 중심 제안서·기대 효과 정리까지만 하고, **사용자 명시 승인 후** 구현한다.
