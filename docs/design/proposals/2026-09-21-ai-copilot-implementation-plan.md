# ProjectAMO LLM 챗봇·MCP 구현 계획

- 작성일: 2026-09-21
- 기준: [실제 설계안](2026-09-21-ai-copilot-chatbot-v2.md). 이 문서는 구현 순서·작업 경계·완료 증거를 관리한다.
- 상태: 계획 작성 완료, 기능 구현 미착수. 첫 작업은 **0 → 1A**다.
- 목표: 사용자가 앱에서 공항기상과 경로를 질문하고, 근거를 확인하며, 기존 화면과 개인 기능으로 이어갈 수 있게 한다.
- 로컬 MCP와 고정 입력은 개발 검증 수단이다. 고정 경로만 동작한다고 실사용 기능을 완료 처리하지 않는다.

## 1. 순서와 제품 완성 지점

```text
0 기준 자료·회귀 확인
  → 1A 공항 도구
  → 1B 브리핑·상세 서비스
  → 2 로컬 MCP 연결·검증
  → 3A 대화 API·실행기 → 3B 앱 채팅 패널
  → 4A 현재 경로 연결 → 4B 고도 비교 → 4C 같은 결과의 화면 연결
  → 5A 경로 계산 공용화 → 5B 자연어로 새 경로 생성
  → 6A 저장 경로 → 6B 예정 비행 알람
```

| 단계 | 사용자가 얻는 기능 / 개발 결과 | 선행 조건 | 기존 설계 PR 대응 |
| --- | --- | --- | --- |
| 0 | 기존 기능과 자료 상태의 기준 기록 | 없음 | 각 PR의 준비 |
| 1A | 기상 조회·시간창·자료 상태를 반환하는 실제 도구 | 0 | PR 1A |
| 1B | 입력된 경로를 계산하고 요약·상세를 제공하는 실제 서비스 | 1A의 공통 계약 | PR 1B |
| 2 | Codex에서 같은 도구를 자연어로 호출 | 1A, 1B | PR 2 |
| 3A/3B | 앱 안에서 공항기상 질문·후속 질문 해결 | 2, 실제 모델 평가 시 공급자 연결 | PR 3 |
| 4A/4B/4C | 현재 경로 설명·고도 비교·근거·관련 화면 연결 | 1B, 3 | PR 4 |
| 5A/5B | 공항·비행 조건만 말해 새 경로와 브리핑 생성 | 4의 입력/결과 계약 | PR 5 |
| 6A/6B | 내 저장 경로 활용·특정 예정 비행 알람 설정 | 로그인, 4; 서버 복원 경로는 5 재사용 | PR 6 |

**첫 실사용 기능은 3B, 경로까지 포함한 읽기 기능 묶음은 4C, 국내 IFR 신규 경로 자동화는 5B, 초기 개인 기능은 6B에서 완성**한다. MCP 연결만 완료한 상태와 제품 기능 완료를 구분한다. 공개 MCP·외부 개인 데이터용 OAuth·공식 등재는 후속이며 MCP 자체는 2단계에서 구현한다.

공급자·계정 공개 범위·예산·외부 전달 자료 정책은 필요한 시점에 정한다. 0~2단계는 그 결정을 기다리지 않는다. 공급자 미정이면 3A/3B의 가짜 공급자 테스트는 진행할 수 있지만 실제 응답·비용 검증은 미완료로 남긴다. 해당 대기 동안 서비스·경로 계산 작업은 진행할 수 있으며, 가짜 공급자 통과를 제품 완료로 표시하지 않는다.

## 2. 변경 위치와 공통 계약

### 2.1 모듈 경계

아래 신규 파일명은 구현 위치 제안이다. 역할을 유지하는 범위에서 기존 패턴에 맞춰 합칠 수 있다. 현재 존재하는 파일과 구분한다.

| 위치 | 역할 | 상태 |
| --- | --- | --- |
| `backend/src/ai/contracts.js`, `registry.js` | 입력/결과 검증, 도구 목록·실행 허용 목록 | 신규 |
| `backend/src/ai/tools/`, `digests/` | 질문 단위 도구와 코드 기반 요약 | 신규 |
| `backend/src/ai/reference-store.js`, `conversation-store.js` | 크기·TTL·호출자 범위가 있는 메모리 상태 | 신규 |
| `backend/src/ai/data-context.js` | 자료·기상 기준 시각·자료 버전을 명시적으로 주입 | 신규 |
| `backend/src/briefing/briefing-service.js` | REST와 도구가 공유할 자료 취합·입력 검증·기존 계산 호출 | 신규, `server.js`의 해당 부분 추출 |
| `backend/src/ai/mcp.js`, `backend/ai-mcp-dev.js` | 재사용 가능한 MCP 어댑터, loopback 전용 개발 entry | 신규 |
| `backend/src/ai/chat-runner.js`, `router.js`, `providers/`, `usage.js` | 대화 실행·공급자 1개 어댑터·실제 사용량 집계 | 신규 |

| `frontend/src/app/App.jsx`, `features/map/MapView.jsx` | 앱에 패널과 명시적 화면 동작 연결 | 기존, 연결 지점만 수정 |

| `shared/route-planning/` | 환경 독립 경로 계산 | 단계 5에서 신규 추출 |

초기부터 별도 에이전트 프레임워크나 범용 워크플로 엔진은 도입하지 않는다. 도구 실행기는 허용 함수 호출과 제한된 반복만 담당한다. MCP transport는 공식 SDK의 구현 시점 지원 버전을 확인해 고정하며 직접 프로토콜을 재작성하지 않는다. 의존성은 실제 도입 단계에서 해당 package/lockfile에 추가한다.

### 2.2 입출력 경계

- 모델 도구 입력에는 공항/시간창, `context_ref`/`briefing_ref`, section, 고도 등 작업 값만 둔다. 사용자·기관·권한·파일 경로는 서버가 결정한다.
- 자료 상태 결과는 설계안 §7의 `schemaVersion`, `status`, `reference`, `data`, `sources`, `coverage`, `issues`, `truncation`, `error`를 따른다. 없는 source 필드를 만들어 채우지 않는다.
- `context_ref`는 검증한 입력, `briefing_ref`는 그 입력과 자료 버전으로 얻은 결과다. 공항 상세에는 같은 규칙의 공항 결과 참조를 사용한다.
- 모델용 digest와 브라우저용 카드/전체 결과 payload를 분리한다. 좌표·격자·표 전체를 설명 프롬프트에 넣지 않는다.
- 도구는 `execute(input, executionContext)` 형태의 일반 함수로 구현한다. MCP와 채팅 API가 이 함수를 공유하며 내부에서 자기 REST API를 호출하지 않는다.

초기 API 표면은 다음처럼 제한한다. 모두 **신규 구현 예정**이다.

| API | 목적 | 도입 단계 |
| --- | --- | --- |
| `/mcp` | 로컬 MCP transport | 2 |
| `POST /api/ai/chat` | 메시지·대화 ID·선택 맥락을 받아 설명/카드/부족 입력/동작 반환 | 3A |
| `POST /api/ai/contexts` | 브라우저의 적용된 경로를 검증·등록 | 4A |
| `GET /api/ai/results/:ref` | 소유권/만료를 확인한 보관 결과 조회 | 4C |
| `POST /api/ai/confirm` | 준비된 저장/알람 변경 확인 실행 | 6B |

처음에는 유한한 JSON 응답으로 구현한다. 진행 상태는 실제 요청 상태를 표시하고 검증 전 설명을 스트리밍하지 않는다. 취소는 브라우저 AbortController와 서버/공급자 취소 신호를 연결한다. SSE는 필요가 확인되면 추가한다.

## 3. 단계별 구현

### 0. 현재 기능과 데이터의 기준 확인

작업:

- `git status`와 변경 파일을 기록한다. 현재 `backend/server.js`, `App` 주변, 지도 기능 등에 다른 작업이 있을 수 있으므로 기존 변경 위에 필요한 부분만 적용한다.
- 기존 공항·TAF·브리핑·고도 테스트와 출력 구조를 확인한다. 계획 작성 시점의 주요 근거는 `backend/test/airport-summary.test.js`, `taf-window.test.js`, `briefing-composer.test.js`, `route-briefing-integration.test.js`, `altitude-weather-comparison.test.js`다.
- live 자료와 검증 snapshot의 위치·reference time·publication/run·누락 항목을 조사한다. 활성 data view나 운영자료를 변경하지 않는다.
- 김포–제주 경로 입력은 현재 기능으로 성립한 geometry/routeModel/절차/ETD/ETA/고도와 함께 준비한다. 기존 integration fixture의 직선 예제를 실제 생성 경로와 동일하다고 취급하지 않는다.
- 오프라인 회귀에 쓸 최소 자료와 실제 모델 평가용 자료를 구분한다. 필수 자료가 없으면 누락을 기록하며 새 수집 체계 개발로 범위를 넓히지 않는다.

완료 증거: 기준 테스트 결과, fixture manifest와 확보/미확보 자료 목록, 현재 API 결과 샘플. 개인 정보 없는 작은 fixture만 저장소에 두고 큰 로컬 자료·임시 보고서는 `artifacts/ai-copilot/`에 둔다.

### 1A. 공항 도구와 공통 결과 계약

작업:

- `contracts.js`에 공항·시간창과 공통 결과를 정의한다. 기존 `zod`를 사용한다.
- 공항 별칭을 기존 공항 카탈로그에 연결하고 불명확한 이름은 후보를 반환한다. 정의되지 않은 지역 묶음을 모델이 임의 생성하게 하지 않는다.
- `data-context.js`에 자료 reader와 기상 시계/실제 시계를 주입한다. 도구 import만으로 서버·스케줄러·수집을 시작하지 않는다.
- `get_airport_weather`와 공항 digest를 구현한다. `airport-summary.js`, `taf-window.js`, `flight-category.js`의 맞는 함수만 재사용한다.
- TAF 요청 시간창과 유효범위를 명시적으로 교차 판정한다. 최근 시각 선택 함수만 호출해 기간 밖 예보를 유효하게 반환하지 않는다.
- 원문은 요청 때만 제공하고 재구성 TAC, RVR 미보고, MVFR 원래 범주를 보존한다.

검증: 정상 관측·예보, 일부 자료 실패, 시간창 부분/전체 미포함, 경보 없음/조회 실패, UTC/KST·날짜 경계, 잘못된 ICAO, 재구성 원문, RVR 미보고. 원본→digest의 중요한 값과 상태를 대조하고 바이트 수/필드 수를 기록한다. 모델 미선정이면 토큰 수는 미측정으로 둔다.

완료: LLM·MCP 없이 실제 자료 또는 재현 가능한 fixture로 올바른 공항 결과가 나온다. 프론트 기상 표시와 기존 API는 계속 동작한다.

### 1B. 브리핑 서비스를 공유하고 상세 조회를 추가

작업:

- `server.js`의 `/api/route-briefing` 검증·자료 취합을 `briefing-service.js`로 추출한다. 기존 REST가 같은 서비스를 호출하게 하고 응답 형식·오류 의미를 보존한다.
- `composeBriefing` 자체의 기상 계산을 다시 작성하지 않는다. `warnings`와 `provenance`를 포함해 digest에 필요한 상태를 보존한다.
- `reference-store.js`에 입력·원본·자료 식별자·기상 기준 시각을 보관한다. TTL은 실제 시계로 계산하며 최대 항목/바이트·소유 범위·만료 오류를 구현한다.
- `get_route_briefing`, `get_briefing_detail`과 section별 페이지/크기 상한을 추가한다. 상세 요청이 새 기상자료를 조용히 다시 읽지 않게 한다.
- 고정 경로/자료는 reader 주입으로 동일 서비스를 실행한다. 테스트용 `fixture_id`는 개발 설정에서만 등록하고 일반 도구 인자에서 임의 경로 읽기를 허용하지 않는다.
- 계산 중 사용하는 모델 파일이 바뀔 수 있으면 source/run을 고정한다. 최소한 이미 계산한 결과와 근거는 결과 참조에 보관하며, 동일 자료를 재확보하지 못하면 새 자료로 대체하지 않고 상태를 반환한다.

검증: 같은 입력·주입 자료에서 추출 전후 결과 일치, ETD/ETA 역전, hazard 수평/고도/시간 분리, 부분 자료, 상세 ID/시각 보존, TTL·다른 호출자의 참조 접근·크기 제한. 원본/digest 크기와 계산시간 기록.

완료: 공항·경로·상세의 세 도구가 일반 함수로 동작하고 기존 경로 브리핑 회귀가 통과한다.

### 2. 로컬 MCP 연결

작업:

- 공식 SDK로 도구 목록·입력/출력 schema·오류를 연결하는 `mcp.js`를 만든다. 일반 도구 함수는 MCP 타입을 import하지 않는다.
- `ai-mcp-dev.js`를 독립 entry로 만들어 loopback에 바인딩한다. `backend/server.js`를 import해 전체 앱·수집·자동 로그인을 띄우지 않는다.
- 개발 reader는 지정한 자료를 읽기 전용으로 사용한다. 필요 시 live 저장 파일을 다시 읽어 최신 자료를 조회할 수 있게 하고, 재현 fixture 실행은 별도 데이터 컨텍스트로 유지한다.
- 입력 크기·Origin/Host 정책·실행시간·동시성·호출 제한과 참조 범위를 적용한다. 도구별 외부 입력을 다시 검증한다.
- 빈 포트를 확인한 뒤 같은 WSL의 Codex에 등록하고 실제 MCP로 공항·브리핑·상세·실패 질문을 검증한다. 연결 명령은 설계안 §11.1을 따른다.

검증: MCP 초기화·목록·정상/잘못된 인자·미지원 도구·부분 오류·실제 호출 기록. 셸로 자료를 직접 읽는 답변은 MCP 검증으로 세지 않는다. 서버는 이번 작업이 시작한 프로세스만 종료한다.

완료: 세 도구가 실제 클라이언트에서 호출되고 설명이 도구 결과와 맞는지 기록된다. 공개 주소·nginx·OAuth는 이 단계에 포함하지 않는다. SDK 추가에 따른 backend lockfile을 갱신하며 배포 시 full deploy가 필요함을 기록한다.

### 3A. 자체 챗봇의 대화 실행기와 API

작업:

- `conversation-store.js`에 부분 슬롯, 값의 출처, 맥락 revision, 최근 관련 대화·결과 참조를 저장한다. 한 대화에서 한 요청만 실행한다.
- 질문의 명시적 값 → 확정된 대화 → 현재 화면 순서로 슬롯을 정리한다. “이 경로”와 “아까 브리핑”의 맥락을 구분하고 충돌하면 필요한 항목만 확인한다.
- 모델 호출/도구 호출/설명 종료를 처리하는 작은 실행기를 만든다. 입력은 서버에서 검증하고 권한·실행 컨텍스트는 모델이 변경할 수 없게 한다.
- 공급자 어댑터의 요청/응답·도구 호출·오류·usage 인터페이스를 고정한다. 먼저 가짜 공급자로 테스트하고, 실제 공급자 한 곳을 연결해 완료한다.
- 지시문·도구 정의를 짧게 유지한다. 원본 도구 결과를 대화에 계속 누적하지 않고 관련 digest만 모델에 제공한다.
- 호출 3회·도구 4회·45초를 초기 설정값으로 적용하고 부분/미완료 결과를 처리한다. 네트워크/공급자 취소와 중복 전송도 처리한다.
- 기존 로그인 middleware와 mutation-origin 검사 패턴을 재사용한다. 기능 플래그와 미설정 시 비활성화를 둔다.

검증: 입력 부족의 여러 턴, 서버 시간 해석, 존재하지 않는 도구/허용되지 않은 인자, 자료 텍스트 속 지시문, 중복 전송·취소, 공급자 실패·상한 도달, 다른 사용자의 대화 접근. 실제 공급자 평가에서 usage·비용·처리시간과 정상/실패를 함께 기록한다.

완료: 공항 질문과 후속 질문이 실제 API에서 끝까지 처리된다. 가짜 공급자 테스트만 끝났으면 “통합 준비 완료, 실제 모델 검증 대기”로 표시한다.

### 3B. 앱 내부 채팅 패널

작업:

- `CopilotPanel`, 대화 hook, 메시지/공항 사실 카드, 입력부를 `features/copilot/`에 만든다. `App.jsx`에는 패널 연결만 둔다.
- 기존 Fluent 토큰·모바일 `MobileSheet`를 재사용한다. 공항/시간대 맥락, 전송/중지/재시도, 추가 입력 요청과 자료 상태를 표시한다.
- 대화 기록과 스크롤을 패널 전환 동안 유지한다. 모바일에서 공항/브리핑 시트와 중첩하지 않는다.
- 표·자료 시각·버튼은 서버 결과로 렌더링한다. 모델 문장을 HTML로 직접 실행하지 않고 화면 action도 허용 목록으로 제한한다.
- 초기 화면 action은 공항 패널과 기존 기상 레이어에 연결한다. 실제 적용 결과를 확인한 후 완료 문구를 표시한다.

검증: 데스크톱·태블릿·모바일, 키보드/포커스/live region, 공항 질문·되묻기·오류·취소·키 미설정 상태. 새 브라우저 계약 `copilot-chat`을 구현·등록한다.

완료: 사용자가 앱에서 공항기상을 질문하고 후속 질문과 공항 상세 열기까지 사용할 수 있다. 첫/열 번째 질문의 정확도·누적 사용량을 평가한다.

### 4A. 현재 경로를 대화에 연결

작업:

- `useRouteBriefing`에서 미적용 초안과 구분되는 적용 경로의 입력 export를 만든다. geometry·routeModel·절차·ETD/ETA·고도·NWP 선택·revision을 포함한다.
- `/api/ai/contexts`에서 입력 크기·유한 좌표·시간·모델 버전·구간 일관성을 검증한다. 클라이언트의 기상 계산이나 AIP 제한값을 사실로 신뢰하지 않는다.
- 채팅 전송 시점의 context를 고정하고 `context_ref`로 기존 브리핑 도구를 실행한다. 화면 변경은 진행 중인 결과의 대상을 바꾸지 않는다.
- 상단 맥락 표시·해제와 이전 대화/현재 화면 충돌 확인을 구현한다. 기관 provider로 열린 경로는 처음에는 미지원 상태를 반환하며 개인 경로로 조용히 우회하지 않는다.

완료/검증: 실제 사용자가 만든 서로 다른 경로에서 브리핑과 상세 후속 질문이 작동한다. 계산 중 경로 변경, 적용 실패한 초안, 필수 값 누락, NWP 선택, 타 사용자 참조를 확인한다. 고정 김포–제주만 통과하면 완료가 아니다.

### 4B. 고도 비교 도구

작업:

- `/api/briefing/altitudes`의 처리 흐름을 공유 서비스로 추출해 기존 화면과 도구가 사용하게 한다.
- 요청한 고도 목록을 제한된 개수로 검증하고 기존 후보 생성/제약 판정을 통해 각 요청 고도의 상태를 보존한다. 임의 입력을 `valid`로 강제하지 않는다.
- 원래 브리핑과 같은 경로·ETD/ETA·자료/run을 사용한다. 비교에 필요한 cross-section/제약 입력은 결과 컨텍스트에 보관하거나 같은 버전으로 재확보한다. 불가능하면 갱신 필요를 알리고 새 결과를 만든다.
- 난류·착빙·바람, 적용 프로파일/coverage, `valid`/`input_only`/`input_invalid`를 표로 제공한다. 추천 순위는 만들지 않는다.
- 계산시간과 이벤트 루프 점유를 측정한다. 긴 동기 계산은 AbortController만으로 45초 중단을 보장하지 못하므로 문제 확인 시 해당 계산을 worker 등 취소 가능한 실행 경계로 옮긴다.

완료/검증: 요청한 두 고도의 비교, 자료 없는 고도, AIP 미확정/충돌, 자료 버전 변경, 계산 실패를 검증한다. 비교표와 LLM 설명이 같은 행을 사용하며 실제 토큰/시간을 기록한다. MCP에는 도구를 등록하되 유효한 경로 맥락이 있을 때만 실행한다.

### 4C. 답변과 같은 브리핑·연직단면 화면 열기

작업:

- 결과 조회 API와 `openCopilotResult` 성격의 명시적 UI 동작을 추가한다. 기존 `loadRouteBriefing`은 저장 경로 복원/재조회이므로 그대로 결과 복원으로 사용하지 않는다.
- `briefingProvider.js`와 request gate 패턴을 활용해 결과를 설치한다. 브리핑·고도표는 보관 결과를, 단면은 같은 경로와 고정 자료 버전의 payload를 사용한다.
- 대용량 단면은 버튼을 눌렀을 때 조회할 수 있지만 이 과정은 LLM을 거치지 않는다. 원래 자료가 만료됐다면 동일 결과처럼 표시하지 않고 갱신 동작을 제공한다.
- 지도 로딩 전 action과 오래된 요청은 대기/취소를 명시적으로 처리하고 최근 경로를 덮어쓰지 않는다.

검증: 새 계약 `copilot-route`에 답변↔브리핑↔고도표의 결과 ID·값, 단면 경로/run, 만료·갱신·모바일 전환을 추가한다. 기존 `route-workflow`, `briefing-view`, `airport-panel` 중 영향 범위를 실행한다.

완료: 현재 경로의 설명→근거→전체 브리핑/단면까지 앱에서 일관되게 연결된다. 이 지점이 읽기 중심 첫 제품 묶음의 완료다.

### 5A. 서버에서 쓸 수 있게 경로 계산 추출

작업:

- 현재 브라우저 경로의 절차·geometry·routeModel·거리·ETA 입력을 비교 fixture로 먼저 고정한다.
- `routePlanner.js`, `procedureData.js`의 파일 읽기와 캐시를 주입식 provider로 분리한다. 직접 fetch·합성 그래프·IAP 캐시를 같은 publication 단위로 관리한다.
- `routePreview.js`에서 순수 geometry만 분리하고 `aircraftProfiles.js`의 localStorage와 기본 성능 데이터를 나눈다.
- 추천→편집 모델 정규화→적용→최종 경로/프로파일 요청을 `planRoute`로 추출한다. `buildEditorPreview`와 적용 과정이 빠지지 않게 한다.
- 국내 IFR을 먼저 지원하고 화면의 해당 흐름도 같은 계산을 사용하게 한다. VFR·해외·기관 기존 화면의 미이관 동작은 보존한다.
- `Architecture.md`에 루트 shared의 환경 독립 도메인 계산 역할을 명시한다. backend의 frontend 소스 import는 금지한다.

완료/검증: 동일 자료·입력의 브라우저/서버 결과가 일치한다. 절차 부족·풍향 없음·AIRAC 변경·수동 입력/기존 경로 복원 영향과 기존 UI 회귀를 확인한다. root `test:shared`가 `shared/*.test.js`를 대상으로 하므로 신규 중첩 테스트가 누락되지 않도록 root 테스트 entry 또는 실행 대상을 명시적으로 연결한다.

### 5B. 새 경로 생성과 대화 흐름 연결

작업:

- 출발·도착·ETD·고도·비행 방식과 필요한 성능 입력을 한 번에 모아 확인한다. 기본값을 썼으면 사용자에게 표시한다.
- `planRoute` 결과로 `context_ref`를 만들고 기존 브리핑 도구로 이어간다. 모델이 좌표·ETA·순위를 직접 계산하지 않는다.
- MCP에도 같은 입력 방식의 일반 경로 생성 도구를 제공한다. fixture 분기를 일반 기능으로 확장하는 대신 개발 전용으로 유지한다.
- 실패 원인과 현재 가능한 수정 방법을 반환하고, 생성한 경로를 기존 편집·브리핑 화면에 연결한다.

완료/검증: fixture ID 없이 여러 국내 지원 공항 조합에서 자연어→입력 확인→새 경로→브리핑→화면 열기가 작동한다. 절차/경로 없음·미지원 유형·시간창 밖 자료도 처리한다. 브라우저 계약에 `copilot-route-create`를 추가한다.

### 6A. 내 저장 경로 조회·불러오기

작업:

- `backend/src/me/routes.js`의 소유권 있는 읽기를 재사용 가능한 서비스로 추출하고 검색·후보 선택 도구를 만든다.
- “저장 입력 불러오기”, “저장 당시 결과 보기”, “현재 자료로 다시 브리핑”을 구분한다. 과거 결과가 실제로 보관돼 있지 않으면 없다고 표시한다.
- 같은 이름의 경로가 여러 개면 날짜/출도착 정보로 선택하게 한다. 모델의 사용자 ID 입력을 받지 않는다.

완료/검증: 로그인 사용자의 경로만 검색·복원되고, 여러 후보·삭제된 경로·현재 재브리핑·과거 결과 없음이 구분된다. 초기 지원 범위 밖인 기관 경로는 개인 경로로 처리하지 않는다.

### 6B. 예정 비행 알람 등록·해제

작업:

- `backend/src/me/alerts.js`의 등록/해제 흐름을 서비스로 추출한다. 원본 `route_id`와 감시 행 `alert_id`를 구분하고 ETD·사용자를 함께 확인한다.
- 모델 호출은 실행 준비까지만 한다. 확인 카드의 실제 클릭을 `/api/ai/confirm`에 보내 실행하며 토큰은 대상·작업·ETD·소유자·만료에 묶는다.
- 멱등 실행 기록으로 재전송·응답 유실 뒤 중복 등록을 막는다. 실행 직전에 권한과 실제 미래 시각을 다시 검사한다.
- 기존 삭제/FK 실패 시 비활성화 동작을 보존한다. 저장 경로 원본을 지우지 않는다.

완료/검증: 같은 원본의 여러 예정 비행 선택, 확인 만료, 재클릭/응답 유실, 타 사용자 접근, 과거 ETD, 실제 알람 완료/실패 응답. 새 계약 `copilot-personal`과 기존 알람 테스트를 실행한다. 고정 시연 시각으로 실제 알람을 만들지 않는다.

## 4. 단계마다 실행할 검증

| 변경 | 필수 검증 | 완료 기록 |
| --- | --- | --- |
| 1A/1B 및 서비스 변경 | 새 Node 테스트 + 영향 받은 기존 공항/TAF/브리핑 테스트 | 실제 실행 명령, 통과/실패, 원본·digest 보존 항목 |
| 2 MCP | SDK 클라이언트 protocol 테스트 + 같은 WSL의 Codex 실제 호출 | 도구명·인자·결과·설명 대조, 서버 응답 크기/시간 |
| 3 대화/UI | 가짜 공급자 실행기 테스트 + 실제 공급자 평가 + `copilot-chat` | 첫/열 번째 질문 usage·정확도·상한 결과 |
| 4 경로·고도·화면 | 공유 서비스 테스트 + `copilot-route` + 영향 받은 기존 계약 | 결과/경로/run 일치, 누락·취소·만료, 비용·지연 |
| 5 경로 추출 | 기존 planner/procedure 테스트 + 서버/브라우저 동일 입력 비교 + 경로 UI 계약 | 추출 전후 결과 비교, 지원 범위·실패 상태 |
| 6 개인 데이터 | 실제 DB fixture 기반 소유권/멱등성 테스트 + `copilot-personal` | 원본/감시 행 분리, 중복 없는 실행, 실패 사례 |

새 `copilot-*` 계약은 아직 없다. 해당 구현 단계에서 파일과 [계약 레지스트리](../../policies/verification/contracts.md)를 추가한 뒤 `npm run dev:contract -- --grep <contract-id>`로 실행한다. 통합 묶음에서는 `npm run check`를 실행한다. 오프라인 테스트에 실제 LLM 호출·운영자료 수집을 넣지 않는다. 브라우저 테스트는 managed launcher가 소유한 서버와 고정 자료로 수행하며 기존 사용자 서버를 종료하지 않는다.

실제 모델 평가는 별도 실행 대상으로 만든다. `docs/evaluation/ai-copilot/`에 질문·기대 사실/금지 판단·평가 기준을 관리하고, 임시 출력은 `artifacts/ai-copilot/`에 둔다. 개인정보 없는 대표 결과와 버전/사용량 집계만 지속 기록한다. 토큰 목표와 상한은 설계안 §9를 따르며 미측정 수치를 달성값으로 보고하지 않는다.

각 단계는 다음 네 조건을 충족해야 완료다: 해당 사용자 흐름 동작, 필수 실패 상태 처리, 영향 회귀 통과, 실제 검증 범위/미실행 항목 기록. 후속 질문·시간/자료 조건이 바뀐 사례도 평가한다. 시연 질문 하나의 성공으로 완료 처리하지 않는다.

## 5. 일정·보류 결정·배포

작업량 추정은 설계안 §12를 유지한다. 3A/3B는 기존 PR 3, 4A/4B/4C는 PR 4, 5A/5B는 PR 5, 6A/6B는 PR 6의 내부 분할이며 추정 일수를 중복 가산하지 않는다. 첫 공항·브리핑 구현 후 실제 난도·자료 상태로 재산정한다. 공급자 연결 대기와 자료 확보 대기는 구현 완료로 계산하지 않는다.

- 0~2: 사용자 추가 선택 없이 공통 도구와 MCP까지 구현 가능.
- 3 실제 모델 평가 전: 공급자·모델·자격정보와 평가 자료 전달 범위를 확정. API 키를 저장소에 넣지 않는다.
- 사용자 공개 전: 허용 계정·실측 기반 예산·로그/보관 정책 확정. 기능 플래그로 활성화한다.
- 공개 MCP 전: 주소·TLS·Origin/Host·프록시·방문 집계 제외·호출 제한을 실제 배포 경로에서 검증. 개인 데이터 공개 시 외부 인가 연동 추가.
- 의존성 변경 배포는 `deploy/deploy-vm-full.sh`를 사용한다. 배포 실행은 별도 작업이며 이 구현 계획으로 운영 서버를 변경하지 않는다.

해외·기관 전체 지원, 영속 대화, 다중 탭 동기화, 문장별 자동 근거 검증, 고급 RAG, 모델 자동 분기는 후속 확장이다. 국내 IFR 자동 생성과 저장 경로·알람은 본 계획 5~6단계의 작업으로 남기며 단순 시연 완료를 이유로 제외하지 않는다.

## 6. 구현 담당과 모델 간 작업 분담

핵심 구조와 첫 기능은 주 담당 에이전트가 구현·검증까지 직접 완료하고, 검증된 패턴이 생긴 뒤 낮은 단계의 모델에 제한된 반복 작업을 분담한다. 주요 코드의 골격만 작성한 뒤 나머지 통합을 통째로 넘기는 방식은 사용하지 않는다. 이 절의 모델 분담은 개발 작업에 관한 것이며, 제품 챗봇의 공급자·모델 선택과는 별개다.

### 6.1 주 담당이 직접 완료할 범위

- **0 → 1A → 1B → 2 전체:** 기준 자료·회귀 확인, 공통 도구 계약, 공항 도구, 브리핑 서비스 추출·상세 조회, 로컬 MCP 실제 호출 검증. 코드 초안이 아니라 테스트와 실제 호출 증거가 있는 기준 구현을 만든다.
- **3 이후의 핵심 연결:** 대화 실행기와 권한·호출 제한·취소·사용량 집계, 현재 경로/자료 버전/결과 참조, 서버용 경로 계산 추출을 직접 맡는다.
- **개인 기능의 변경 경계:** 소유권, 사용자 확인, 알람 변경의 멱등성과 실패 처리는 주 담당이 설계·구현·검증한다.
- 각 단계의 최종 코드 검토, 통합, 회귀 검증과 완료 판정은 주 담당이 책임진다.

### 6.2 기준 구현 이후 분담할 수 있는 작업

| 작업 | 분담 전 확보할 기준 |
| --- | --- |
| 공항 카드·비교표·로딩/오류 상태 UI | 확정된 응답 예제, 디자인 패턴, 접근성·화면 동작 계약 |
| 누락·만료·잘못된 입력 등 테스트 추가 | 독립적으로 정한 기대 결과와 기존 테스트 예제 |
| 단순 조회 도구·반복적인 어댑터 연결 | 검증된 도구 구현, 입력/출력 schema, 권한·오류 처리 방식 |
| 문서·테스트 등록 | 실제 구현 결과와 실행 명령·등록 위치 |

분담은 3단계부터 필요할 때 적용하며 필수 절차는 아니다. 경로 계산·권한·자료 시각 등 새 판단이 필요한 작업은 단순 반복 작업으로 취급하지 않는다. 분담 모델이 공통 계약을 바꾸거나 범위를 넓혀야 한다면 주 담당에게 돌려보낸다.

### 6.3 작업 전달과 인수 기준

작업마다 수정 허용 파일, 참조할 기준 구현, 입력/출력 예제, 금지 변경, 실행할 테스트와 완료 조건을 함께 전달한다. 같은 파일을 동시에 수정하지 않도록 작업 경계를 나눈다. 분담 결과의 자체 통과 보고만으로 완료 처리하지 않고, 주 담당이 diff와 기대 동작을 확인하고 관련 테스트·통합 검증을 실행한다.

비용은 모델 단가만으로 판단하지 않는다. 작업 전달·검토·재작업을 포함한 총 사용량과 소요 시간을 기록해 분담 효과를 판단한다. 절감 효과는 아직 측정하지 않았으므로 보장하지 않는다. 이 문서는 향후 분담 원칙을 기록하며, 이번 문서 수정에서 다른 모델 실행이나 기능 구현을 시작하지 않는다.
