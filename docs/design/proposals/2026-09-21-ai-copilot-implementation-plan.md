## 1. 순서와 제품 완성 지점

### 1.1 실제 실행은 7단계로 관리

아래 1~7은 사용자에게 진행 상황을 보고하는 구현 단계다. 기존 `0`, `1A` 등의 번호는 §3의 상세 작업 ID로 유지한다. 0은 1단계의 준비 작업이며 별도의 제품 단계가 아니다. 순서를 바꾸거나 기존 범위를 삭제한 것이 아니라, 작업 완료를 판단할 단위를 명확히 한 것이다.

| 구현 단계 | 내부 작업 순서 | 결과물과 완료 기준 | 이 단계에서 제외 |
| --- | --- | --- | --- |
| **1. 공통 도구 기반** | 0+1A → 1B | 기존 기능·자료 기준 기록, 공항 조회·경로 브리핑·상세 도구와 코드 요약. 동일 입력의 기존 계산 결과 보존 및 누락/시간/참조 테스트 통과 | 모델 SDK, 채팅 UI, 새 경로 생성 |
| **2. 로컬 MCP 연결** | 2 | 같은 도구를 로컬 HTTP MCP로 노출. 실제 클라이언트 호출·오류·부분 자료·근거 설명 검증. 앱 서버 전체나 수집기를 불필요하게 기동하지 않음 | 공개 MCP, OAuth, 자체 챗봇 완료 선언 |
| **3. 첫 실사용 LLM 챗봇** | 3A → 3B | 실제 공급자 1개와 채팅 API, 우측 하단 상시 원형 기상이 버튼·플로팅 창 연결. 앱에서 공항 질문→후속 질문→근거 확인까지 동작. 실제 usage·취소·오류와 UI 계약 검증 | 현재 경로 전체 연동, 저장/알람 변경 |
| **4. 현재 경로·고도·화면 연결** | 4A → 4B → 4C | 전송 시점의 적용 경로를 설명하고 요청 고도를 비교. 답변과 브리핑/단면의 경로·자료 버전 일치. 새 경로 질문은 기존 설정 화면의 입력 채우기·사용자 생성 흐름으로 연결. 경로 변경·만료·갱신·지연 응답 검증 | 서버의 자연어 신규 경로 자동 생성, 고도 안전 순위 |
| **5. 자연어 신규 경로 생성** | 5A → 5B | 국내 IFR 경로 계산을 서버/브라우저가 공유. 출도착·시간·고도 등 입력을 모아 경로 생성→브리핑→화면 연결. 여러 지원 공항 조합에서 동일 계산 및 실패 처리 검증 | 해외/VFR 전체 서버 이관, 모델의 좌표·ETA 계산 |
| **6. 개인 기능 연결** | 6A → 6B | 로그인 사용자의 저장 경로 검색·선택·재조회, 확인 후 예정 비행 알람 등록/해제. 소유권·확인 대상·중복 방지 테스트 통과 | 외부 MCP의 개인 데이터 공개, 기관 전체 지원 |
| **7. 통합 검증·공개 준비** | 7 | 단계별 증거를 종합하고 실제 공급자로 대표 사용자 흐름·장애·비용·지연을 평가. 전체 회귀와 영향 UI 계약, 플래그 비활성화 복귀, 운영 설정/보관 정책·미해결 항목 기록 | 별도 승인 없는 운영 배포, 공개 MCP 확장 |

**첫 사용 가능 지점은 3단계**, 현재 경로까지 설명하는 첫 제품 묶음은 4단계다. 5~6은 그 위의 확장 기능이며 범위에서 제외하지 않는다. 7단계가 첫 테스트 시점은 아니다. 정확도·권한·토큰·회귀 검증은 각 구현 단계에서 수행하고 7에서 합쳐 확인한다. 일부 묶음을 먼저 공개하려면 공개 대상 범위에 대해 7의 검증을 먼저 통과시킨다.

### 1.2 작업을 넘기는 단위와 첫 착수 범위

하나의 큰 PR 대신 다음 **13개 작업 묶음**을 순서대로 구현·검토한다. 각 묶음은 변경 코드와 해당 테스트를 함께 포함하며, 실제 변경량에 따라 더 작게 나눌 수 있다. 13번의 대화나 고정된 일정 약속을 의미하지 않는다.

`0+1A → 1B → 2 → 3A → 3B → 4A → 4B → 4C → 5A → 5B → 6A → 6B → 7`

- **바로 다음 작업은 0+1A만:** 기존 공항/TAF/브리핑 기준 테스트, 자료 목록과 누락 확인 → 입력/결과 계약과 reader 주입 → 공항 도구·코드 요약 → 정상·누락·시간창 회귀 테스트. 이 묶음에 MCP SDK나 UI를 섞지 않는다.
- 0은 Astra high로 기준 조사·공통 계약을 확정하고, 같은 검토 묶음의 1A는 Terra medium으로 구현한다. 1B는 Sol high로 브리핑 서비스 추출·상세 조회를 완성하고 2는 Terra medium으로 MCP를 연결한다. 주 담당이 작업 명세와 인수를 책임지며, 구체적인 구현·검토 배정은 §6을 따른다.
- 3A 착수 시 실제 공급자 연결에 필요한 선택을 확인한다. 미정이면 가짜 공급자 단위 테스트와 UI 작업은 가능하지만, 실제 모델 검증 없이 3단계를 완료 처리하지 않는다.
- 매 묶음의 종료 기록에는 **사용 가능한 결과, 변경 파일, 실제 검증 명령/결과, 미완료 사항, 다음 작업**을 남긴다. 기존 기능 회귀가 생기면 해당 묶음에서 해결하거나 원인을 분리한 뒤 완료 여부를 판단한다.
- 계정 공개·운영 배포·새 외부 연동은 이 순서만으로 자동 승인되지 않는다. 필요한 결정을 해당 시점에 확인한다.

### 1.3 상세 작업 의존성

```text
0 기준 자료·회귀 확인
  → 1A 공항 도구
  → 1B 브리핑·상세 서비스
  → 2 로컬 MCP 연결·검증
  → 3A 대화 API·실행기 → 3B 앱 채팅 패널
  → 4A 현재 경로 연결 → 4B 고도 비교 → 4C 같은 결과의 화면 연결
  → 5A 경로 계산 공용화 → 5B 자연어로 새 경로 생성
  → 6A 저장 경로 → 6B 예정 비행 알람
  → 7 통합 검증·공개 준비
```

| 단계 | 사용자가 얻는 기능 / 개발 결과 | 선행 조건 | 기존 설계 PR 대응 |
| --- | --- | --- | --- |
| 0 | 기존 기능과 자료 상태의 기준 기록 | 없음 | 각 PR의 준비 |
| 1A | 기상 조회·시간창·자료 상태를 반환하는 실제 도구 | 0 | PR 1A |
| 1B | 입력된 경로를 계산하고 요약·상세를 제공하는 실제 서비스 | 1A의 공통 계약 | PR 1B |
| 2 | Codex에서 같은 도구를 자연어로 호출 | 1A, 1B | PR 2 |
| 3A/3B | 앱 안에서 공항기상 질문·후속 질문 해결 | 2, 실제 모델 평가 시 공급자 연결 | PR 3 |
| 4A/4B/4C | 현재 경로 설명·고도 비교·근거·관련 화면 연결 | 1B, 3 | PR 4 |
| 5A/5B | 공항·비행 조건만 말해 새 경로와 브리핑 생성 | 4의 입력/결과 계약 | PR 5 |
| 6A/6B | 내 저장 경로 활용·특정 예정 비행 알람 설정 | 로그인, 4; 서버 복원 경로는 5 재사용 | PR 6 |

**첫 실사용 기능은 3B, 경로까지 포함한 읽기 기능 묶음은 4C, 국내 IFR 신규 경로 자동화는 5B, 초기 개인 기능은 6B에서 완성**한다. MCP 연결만 완료한 상태와 제품 기능 완료를 구분한다. 공개 MCP·외부 개인 데이터용 OAuth·공식 등재는 후속이며 MCP 자체는 2단계에서 구현한다.

공급자·계정 공개 범위·예산·외부 전달 자료 정책은 필요한 시점에 정한다. 0~2단계는 그 결정을 기다리지 않는다. 공급자 미정이면 3A/3B의 가짜 공급자 테스트는 진행할 수 있지만 실제 응답·비용 검증은 미완료로 남긴다. 해당 대기 동안 서비스·경로 계산 작업은 진행할 수 있으며, 가짜 공급자 통과를 제품 완료로 표시하지 않는다.

### 2.2 입출력 경계

- 모델 도구 입력에는 공항/시간창, `context_ref`/`briefing_ref`, section, 고도 등 작업 값만 둔다. 사용자·기관·권한·파일 경로는 서버가 결정한다.
- 자료 상태 결과는 설계안 §7의 `schemaVersion`, `status`, `reference`, `data`, `sources`, `coverage`, `issues`, `truncation`, `error`를 따른다. 없는 source 필드를 만들어 채우지 않는다.
- `context_ref`는 검증한 입력, `briefing_ref`는 그 입력과 자료 버전으로 얻은 결과다. 공항 상세에는 같은 규칙의 공항 결과 참조를 사용한다.
- 모델용 digest와 브라우저용 카드/전체 결과 payload를 분리한다. 좌표·격자·표 전체를 설명 프롬프트에 넣지 않는다.
- 도구는 `execute(input, executionContext)` 형태의 일반 함수로 구현한다. MCP와 채팅 API가 이 함수를 공유하며 내부에서 자기 REST API를 호출하지 않는다.

초기 API 표면은 다음처럼 제한한다. 모두 **신규 구현 예정**이다.

| API | 목적 | 도입 단계 |
| --- | --- | --- |
| `/mcp` | 로컬 MCP transport | 2 |
| `POST /api/ai/chat` | 메시지·대화 ID·선택 맥락을 받아 설명/카드/부족 입력/동작 반환 | 3A |
| `POST /api/ai/contexts` | 브라우저의 적용된 경로를 검증·등록 | 4A |
| `GET /api/ai/results/:ref` | 소유권/만료를 확인한 보관 결과 조회 | 4C |
| `POST /api/ai/confirm` | 준비된 저장/알람 변경 확인 실행 | 6B |

처음에는 유한한 JSON 응답으로 구현한다. 진행 상태는 실제 요청 상태를 표시하고 검증 전 설명을 스트리밍하지 않는다. 취소는 브라우저 AbortController와 서버/공급자 취소 신호를 연결한다. SSE는 필요가 확인되면 추가한다.

### 4A. 현재 경로를 대화에 연결

작업:

- `useRouteBriefing`에서 미적용 초안과 구분되는 적용 경로의 입력 export를 만든다. geometry·routeModel·절차·ETD/ETA·고도·`routeMarkers`·`nwpTimeSelection`·revision을 포함하고 context에 함께 보관한다. `routeMarkers`는 안정적인 경유점 ID·좌표를 가진 별도 입력이며 routeModel로 대체하지 않는다.
- `/api/ai/contexts`에서 입력 크기·유한 좌표·시간·모델 버전·구간 일관성을 검증한다. 클라이언트의 기상 계산이나 AIP 제한값을 사실로 신뢰하지 않는다.
- 마커 ID 중복·좌표/경로 일관성과 NWP 시간 선택의 경유점 ID 연결을 검증하고 거리값은 대조/재계산한다. 경유점별 시간 선택에 필요한 마커가 없거나 2개 미만이거나 ID가 맞지 않으면 입력 오류/재등록 필요를 반환한다. 현재 계산기의 시간 규칙 미적용 fallback으로 조용히 진행하지 않는다.
- 채팅 전송 시점의 context를 고정하고 `context_ref`로 기존 브리핑 도구를 실행한다. 화면 변경은 진행 중인 결과의 대상을 바꾸지 않는다.
- 상단 맥락 표시·해제와 이전 대화/현재 화면 충돌 확인을 구현한다. 기관 provider로 열린 경로는 처음에는 미지원 상태를 반환하며 개인 경로로 조용히 우회하지 않는다.
- 2026-09-23 구현 결정: 충돌 시 전송 전에 현재/이전/연결 없이를 선택한다. 이전은 마지막 요청의 적용 입력 snapshot을 사용한다. 다른 기준 또는 연결 해제는 **새 서버 대화 경계**로 분리해 기존 슬롯·참조·문장을 모델에 넘기지 않으며, 화면의 기존 대화·근거 카드는 보존한다. 현재 선택을 확정할 때 화면을 다시 대조한다. [구현·검증 기록](../../evaluation/ai-copilot/2026-09-23-context-choice.md).

완료/검증: 실제 사용자가 만든 서로 다른 경로에서 브리핑과 상세 후속 질문이 작동한다. 계산 중 경로 변경, 적용 실패한 초안, 필수 값 누락, NWP 선택, 타 사용자 참조를 확인한다. 고정 김포–제주만 통과하면 완료가 아니다.

서로 다른 경유점 시간 오프셋을 설정한 fixture에서 같은 자료 버전의 기존 화면 요청과 도구 요청이 같은 구간 시각·기상 결과를 만드는지 대조한다. 마커 누락·중복·알 수 없는 ID·불일치 좌표도 회귀에 포함하고, 4B 고도 비교와 4C 결과 복원에서도 동일한 마커·시간 선택을 보존한다.

### 4B. 고도 비교 도구

작업:

- `/api/briefing/altitudes`의 처리 흐름을 공유 서비스로 추출해 기존 화면과 도구가 사용하게 한다.
- 요청한 고도 목록을 제한된 개수로 검증하고 기존 후보 생성/제약 판정을 통해 각 요청 고도의 상태를 보존한다. 임의 입력을 `valid`로 강제하지 않는다.
- 원래 브리핑과 같은 경로·ETD/ETA·자료/run을 사용한다. 비교에 필요한 cross-section/제약 입력은 결과 컨텍스트에 보관하거나 같은 버전으로 재확보한다. 불가능하면 갱신 필요를 알리고 새 결과를 만든다.
- 난류·착빙·바람, 적용 프로파일/coverage, `valid`/`input_only`/`input_invalid`를 표로 제공한다. 추천 순위는 만들지 않는다.
- 계산시간과 이벤트 루프 점유를 측정한다. 긴 동기 계산은 AbortController만으로 45초 중단을 보장하지 못하므로 문제 확인 시 해당 계산을 worker 등 취소 가능한 실행 경계로 옮긴다.

완료/검증: 요청한 두 고도의 비교, 자료 없는 고도, AIP 미확정/충돌, 자료 버전 변경, 계산 실패를 검증한다. 비교표와 LLM 설명이 같은 행을 사용하며 실제 토큰/시간을 기록한다. MCP에는 도구를 등록하되 유효한 경로 맥락이 있을 때만 실행한다.

### 4C. 같은 결과 열기와 경로 설정 화면 연결

작업:

- 결과 조회 API와 `openCopilotResult` 성격의 명시적 UI 동작을 추가한다. 기존 `loadRouteBriefing`은 저장 경로 복원/재조회이므로 그대로 결과 복원으로 사용하지 않는다.
- `briefingProvider.js`와 request gate 패턴을 활용해 결과를 설치한다. 브리핑·고도표는 보관 결과를, 단면은 같은 경로와 고정 자료 버전의 payload를 사용한다.
- 대용량 단면은 버튼을 눌렀을 때 조회할 수 있지만 이 과정은 LLM을 거치지 않는다. 원래 자료가 만료됐다면 동일 결과처럼 표시하지 않고 갱신 동작을 제공한다.
- 지도 로딩 전 action과 오래된 요청은 대기/취소를 명시적으로 처리하고 최근 경로를 덮어쓰지 않는다.
- 2026-09-23 구현 선택: 보관 결과는 기존 `BriefingView`/지도 preview에 **읽기 전용 보기 맥락**으로 설치한다. 적용 경로·편집 초안 자체를 교체하지 않아 닫으면 기존 상태가 복원된다. 원본 결과의 weather/profile/geometry를 재계산하지 않는다. 화면/계정 변경 중 도착한 결과는 취소하며 내 지도 편집 중에는 열지 않는다. 입력 채움은 별도 명시적 변경 action으로 남겨 초안 충돌 확인을 적용한다.
- 적용 경로가 없는 새 경로 질문에는 허용된 화면 action으로 검증된 출발·도착과 명시된 비행 조건을 기존 경로 설정 초안에 채운다. 사용자가 연결 버튼을 눌러 실행하고 기존 편집값과 충돌하면 덮어쓰기 전에 확인한다. 모호한 공항은 후보를 먼저 확인하고 입력 부족·미지원 조건을 명시한다.
- 입력 채움은 생성·적용 완료가 아니다. 사용자가 기존 화면의 생성/적용 흐름을 진행한 뒤 4A로 적용 맥락을 등록한다. 모델이 좌표·ETA를 만들어 채우거나 서버 자동 생성/브리핑을 완료했다고 알리지 않는다. 서버 자동화는 5A/5B에 유지한다.
- 2026-09-23 구현: 앱 전용 `prepare_route_settings`와 공용 입력 검증으로 국내 IFR 출도착/명시한 고도·시간을 검증하고, 사용자 클릭으로 기존 토큰 편집기·설정 폼에 채운다. 편집 중이면 기존 초안/적용·대체 경로 초기화 확인 및 상태 revision 재검증을 거친다. 미지원 조건은 제거해 부분 적용하지 않고 `blocked`/버튼 없음으로 표시한다. 실제 Luna high의 차단 의미 설명 오류를 발견·보완했다. [구현·검증 기록](../../evaluation/ai-copilot/2026-09-23-route-settings.md).

검증: 새 계약 `copilot-route`에 답변↔브리핑↔고도표의 결과 ID·값, 단면 경로/run, 만료·갱신·모바일 전환을 추가한다. 기존 `route-workflow`, `briefing-view`, `airport-panel` 중 영향 범위를 실행한다.

추가 인수 사례: 경로 없는 상태에서 “김포에서 제주로” 질문 → 입력 채움 버튼 → 기존 설정 화면의 출도착 확인 → 사용자 생성/적용 → 적용된 경로 질문. 기존 초안 충돌의 취소·확인, 모호한 공항 되묻기, 연결 실패 시 완료 문구 금지도 검사한다.

완료: 현재 경로의 설명→근거→전체 브리핑/단면까지 앱에서 일관되게 연결되고, 경로 없는 질문도 기존 설정 화면의 입력 채움·사용자 생성으로 이어진다. 이 지점이 읽기 중심 첫 제품 묶음의 완료다.

### 5A. 서버에서 쓸 수 있게 경로 계산 추출

작업:

- 현재 브라우저 경로의 절차·geometry·routeModel·거리·ETA 입력을 비교 fixture로 먼저 고정한다.
- `routePlanner.js`, `procedureData.js`의 파일 읽기와 캐시를 주입식 provider로 분리한다. 직접 fetch·합성 그래프·IAP 캐시를 같은 publication 단위로 관리한다.
- `routePreview.js`에서 순수 geometry만 분리하고 `aircraftProfiles.js`의 localStorage와 기본 성능 데이터를 나눈다.
- 추천→편집 모델 정규화→적용→최종 경로/프로파일 요청을 `planRoute`로 추출한다. `buildEditorPreview`와 적용 과정이 빠지지 않게 한다.
- 국내 IFR을 먼저 지원하고 화면의 해당 흐름도 같은 계산을 사용하게 한다. VFR·해외·기관 기존 화면의 미이관 동작은 보존한다.
- `Architecture.md`에 루트 shared의 환경 독립 도메인 계산 역할을 명시한다. backend의 frontend 소스 import는 금지한다.

완료/검증: 동일 자료·입력의 브라우저/서버 결과가 일치한다. 절차 부족·풍향 없음·AIRAC 변경·수동 입력/기존 경로 복원 영향과 기존 UI 회귀를 확인한다. root `test:shared`가 `shared/*.test.js`를 대상으로 하므로 신규 중첩 테스트가 누락되지 않도록 root 테스트 entry 또는 실행 대상을 명시적으로 연결한다.

### 5B. 새 경로 생성과 대화 흐름 연결

작업:

- 출발·도착·ETD·고도·비행 방식과 필요한 성능 입력을 한 번에 모아 확인한다. 기본값을 썼으면 사용자에게 표시한다.
- `planRoute` 결과로 `context_ref`를 만들고 기존 브리핑 도구로 이어간다. 모델이 좌표·ETA·순위를 직접 계산하지 않는다.
- MCP에도 같은 입력 방식의 일반 경로 생성 도구를 제공한다. fixture 분기를 일반 기능으로 확장하는 대신 개발 전용으로 유지한다.
- 실패 원인과 현재 가능한 수정 방법을 반환하고, 생성한 경로를 기존 편집·브리핑 화면에 연결한다.

완료/검증: fixture ID 없이 여러 국내 지원 공항 조합에서 자연어→입력 확인→새 경로→브리핑→화면 열기가 작동한다. 절차/경로 없음·미지원 유형·시간창 밖 자료도 처리한다. 브라우저 계약에 `copilot-route-create`를 추가한다.

### 6A. 내 저장 경로 조회·불러오기

작업:

- `backend/src/me/routes.js`의 소유권 있는 읽기를 재사용 가능한 서비스로 추출하고 검색·후보 선택 도구를 만든다.
- “저장 입력 불러오기”, “저장 당시 결과 보기”, “현재 자료로 다시 브리핑”을 구분한다. 과거 결과가 실제로 보관돼 있지 않으면 없다고 표시한다.
- 같은 이름의 경로가 여러 개면 날짜/출도착 정보로 선택하게 한다. 모델의 사용자 ID 입력을 받지 않는다.

완료/검증: 로그인 사용자의 경로만 검색·복원되고, 여러 후보·삭제된 경로·현재 재브리핑·과거 결과 없음이 구분된다. 초기 지원 범위 밖인 기관 경로는 개인 경로로 처리하지 않는다.

### 6B. 예정 비행 알람 등록·해제

작업:

- `backend/src/me/alerts.js`의 등록/해제 흐름을 서비스로 추출한다. 원본 `route_id`와 감시 행 `alert_id`를 구분하고 ETD·사용자를 함께 확인한다.
- 모델 호출은 실행 준비까지만 한다. 확인 카드의 실제 클릭을 `/api/ai/confirm`에 보내 실행하며 토큰은 대상·작업·ETD·소유자·만료에 묶는다.
- 멱등 실행 기록으로 재전송·응답 유실 뒤 중복 등록을 막는다. 실행 직전에 권한과 실제 미래 시각을 다시 검사한다.
- 기존 삭제/FK 실패 시 비활성화 동작을 보존한다. 저장 경로 원본을 지우지 않는다.

완료/검증: 같은 원본의 여러 예정 비행 선택, 확인 만료, 재클릭/응답 유실, 타 사용자 접근, 과거 ETD, 실제 알람 완료/실패 응답. 새 계약 `copilot-personal`과 기존 알람 테스트를 실행한다. 고정 시연 시각으로 실제 알람을 만들지 않는다.

### 7. 통합 검증과 공개 준비

작업:

- 공항 질문, 여러 턴의 부족 입력 보완, 현재 경로/고도/근거, 자연어 신규 경로, 저장 경로와 확인 후 알람의 대표 흐름을 평가한다. 단계별 평가 세트를 재사용하며 누락 자료·오래된 자료·기간 밖 요청도 포함한다.
- 실제 모델의 질문당 전체 호출 usage·비용·처리시간을 집계한다. 첫 질문과 긴 후속 대화를 비교하고, 상한 도달·공급자 오류·취소·동시 요청 제한 때의 응답과 기존 대시보드 사용 가능 여부를 확인한다. 목표 예산/지연 기준은 실측과 공개 범위에 따라 정하며 미측정 수치를 통과값으로 만들지 않는다.
- 실제 앱의 공항 패널·브리핑·지도 조작부가 열린 상태에서 플로팅 버튼/창의 위치, 가림, 포커스, 크기 변경·접기·상태 보존을 검증한다. HTML 캡처 시안 통과로 실제 UI 계약을 대신하지 않는다. 폰의 시트/키보드 동작도 검증한다.
- `npm run check`와 영향받는 기존 계약 및 새 `copilot-*` 계약을 실행한다. 실제 모델 평가는 별도 명령으로 실행하고 결과를 기록한다.
- 허용 계정·사용량 상한·자료 외부 전달/로그 보관 정책·환경변수·키 미설정 상태를 확정한다. 기능 플래그를 끄면 기존 화면만 정상 사용되는지 검증하고, 의존성 변경 시 full deploy가 필요함을 배포 체크리스트에 남긴다.

완료: 공개 대상 흐름의 기능/실패 상태/회귀/실제 모델 평가 증거와 운영 설정이 준비되고 미해결 항목이 명시된다. 운영 배포 실행은 별도 승인 작업이다. 공개 MCP/OAuth·새 기능 추가를 통합 검증에 끼워 넣지 않는다.

## 4. 단계마다 실행할 검증

**2026-09-22 확인: 공통 도구 자동 테스트 → Codex CLI의 실제 MCP 호출 → 자체 챗봇의 실제 모델 평가 → 실제 브라우저 통합 검증 순서로 진행한다.** 각 기능이 구현되는 단계부터 검증하며 마지막 통합 단계까지 미루지 않는다. Codex는 외부 MCP 클라이언트로 사용하고, Codex의 답변 성공을 자체 챗봇의 품질·비용·UI 검증으로 대신하지 않는다.

입력·초점·키보드 계약은 `ipad-safari`의 명시적 실행 대상에도 추가한다. 일반 계약 명령의 통과만으로 WebKit 검증을 추정하지 않고, §3의 3B처럼 해당 프로젝트의 실행 건수·결과 또는 미실행 사유를 별도로 남긴다.

실제 모델 평가는 별도 실행 대상으로 만든다. `docs/evaluation/ai-copilot/`에 질문·기대 사실/금지 판단·평가 기준을 관리하고, 임시 출력은 `artifacts/ai-copilot/`에 둔다. 개인정보 없는 대표 결과와 버전/사용량 집계만 지속 기록한다. 토큰 목표와 상한은 설계안 §9를 따르며 미측정 수치를 달성값으로 보고하지 않는다.

각 단계는 다음 네 조건을 충족해야 완료다: 해당 사용자 흐름 동작, 필수 실패 상태 처리, 영향 회귀 통과, 실제 검증 범위/미실행 항목 기록. 후속 질문·시간/자료 조건이 바뀐 사례도 평가한다. 시연 질문 하나의 성공으로 완료 처리하지 않는다.

### 4.1 Codex CLI로 실제 MCP 검증

프로젝트와 같은 WSL Ubuntu에서 loopback 전용 개발 MCP 인스턴스와 Codex CLI를 실행한다. 공개 주소·nginx·TLS는 이 검증의 선행 조건이 아니다. 아래는 **MCP 구현·기동 이후 실행할 예시**다. 기존 서버와 충돌하면 별도 포트를 사용하며 사용자 서버를 종료하거나 바인딩을 변경하지 않는다.

```bash
codex mcp add projectamo --url http://127.0.0.1:3001/mcp
codex
```

새 세션에서 `/mcp`로 연결 상태와 도구 노출을 확인한다. HTTP 인증을 설정했다면 그 정책에 맞는 별도 자격정보도 준비한다. Codex 자체의 모델 사용 인증과 MCP 접근 인증은 구분한다. [공식 연결 문서](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [설계안 §11.1](2026-09-21-ai-copilot-chatbot-v2.md#111-pr-2-같은-wsl의-codex-cli)

| 질문/조건 | 통과 기준 |
| --- | --- |
| “ProjectAMO 도구로 제주공항 기상 알려줘” | 올바른 공항 도구·인자를 사용하고 수치·단위·관측/예보·자료 시각이 원자료와 일치 |

질문별로 **실제 MCP 도구명·인자 → 반환 digest/참조 → 최종 설명 → 원자료 대조 판정**을 기록한다. 기준 시각·snapshot ID도 함께 고정한다. 셸·직접 파일 읽기·웹 검색으로 대신 답한 경우는 MCP 검증 성공으로 인정하지 않는다. 도구가 실패했을 때도 우회해서 성공처럼 처리하지 않는다.

초기에는 공항과 준비된 경로를 검증한다. 임의의 출발·도착 공항에서 신규 경로를 만드는 평가는 5A/5B 이후 여러 지원 공항 조합으로 수행한다. 개발 fixture 성공을 일반 경로 생성 완료로 표시하지 않는다.

### 4.2 자체 챗봇의 정확도·권한·비용 평가

- 고정 기상 snapshot과 기준 시각에 대한 기대 사실·필수 근거·금지 동작을 먼저 작성하고, 공통 도구 테스트·MCP 평가·자체 챗봇 평가에서 재사용한다. 실시간 자료 평가는 별도로 기록한다. 자료가 없는 환경에서는 누락 처리만 검증할 수 있으므로 정상 답변 품질까지 통과 처리하지 않는다.
- 실제 채택 공급자·모델·제품 프롬프트·대화 실행기로 동일 질문과 후속 질문을 여러 번 실행한다. 반복 횟수와 실행 조건을 기록하고, 정확히 같은 문장이나 호출 순서 대신 기대 사실·근거·금지 동작으로 판정한다. 가짜 공급자 테스트는 제한·취소·오류 흐름 검증이며 실제 답변 평가를 대체하지 않는다.
- 없는 자료 생성, 타 사용자 결과 접근, 사용자 확인 없는 알람 실행은 필수 실패 항목이다. 모델 설명 평가와 별도로 서버의 소유권·확인·멱등성 테스트를 통과해야 한다. 평균 점수로 이러한 실패를 상쇄하지 않는다.
- 질문마다 전체 모델 호출의 입력·출력 usage, 재시도 포함 비용, 도구 호출 횟수·응답 크기, 전체 처리시간을 기록한다. 공급자가 제공하는 캐시·추론 usage는 중복 합산하지 않도록 정의를 확인한다. 첫 질문과 10번째 후속 질문의 개별·누적 사용량을 비교하며, 누락된 usage는 0이 아닌 미측정으로 표시한다.
- 비용·지연 기준은 제품의 실제 모델에서 측정한다. Codex 사용량을 제품 API 비용으로 환산하지 않는다. Codex의 모델 사용 자격과 자체 챗봇 공급자 자격정보·과금은 별도이며, 로컬 MCP 연결이 로컬 LLM 추론을 뜻하지 않는다. 외부 추론에 전달할 질문·도구 결과의 범위를 평가 전에 확인한다.

### 4.3 실제 UI 통합 및 완료 증거

실제 앱에서 브라우저 자동 테스트와 직접 사용 검토를 병행한다. 기상이 실행 버튼, 창 이동·크기 변경·접기/복원, 메시지·입력·스크롤 보존, 요청 중지·늦은 응답 무시, 근거 및 같은 결과의 화면 연결을 확인한다. 공항/브리핑 패널을 연 상태의 가림·지도 조작·키보드 접근성과 좁은 화면도 포함한다. 정적 HTML 시안이나 가짜 응답만으로 실제 채팅 UI 통합을 완료 처리하지 않는다.

완료 기록에는 코드·모델·프롬프트 버전, 자료/기준 시각, 실행 명령과 반복 횟수, 기대값/실제값, 통과·실패·미실행 사유, 사용량·지연을 남긴다. 민감한 원문과 자격정보는 기록하지 않는다. **최신 실행 상태는 §7 및 연결된 평가 기록을 따른다. MCP 실사용·자체 모델 평가·브라우저 계약 실행과 전체 제품 통합 인수는 구분한다.**

## 5. 일정·보류 결정·배포

작업량 추정은 설계안 §12를 유지한다. 3A/3B는 기존 PR 3, 4A/4B/4C는 PR 4, 5A/5B는 PR 5, 6A/6B는 PR 6의 내부 분할이며 추정 일수를 중복 가산하지 않는다. 첫 공항·브리핑 구현 후 실제 난도·자료 상태로 재산정한다. 공급자 연결 대기와 자료 확보 대기는 구현 완료로 계산하지 않는다.

7단계는 기존 단계별 테스트와 구분되는 통합 인수·공개 준비 묶음으로 명시했다. 기존 PR 추정에 이미 포함된 테스트 시간을 다시 더하지 않으며, 추가 운영 준비/미해결 회귀 작업량은 실제 결과를 보고 산정한다. UI 시안 제작이나 로컬 캡처를 기능 구현 실적으로 계산하지 않는다.

- 0~2: 사용자 추가 선택 없이 공통 도구와 MCP까지 구현 가능.
- 3 실제 모델 평가 전: 공급자·모델·자격정보와 평가 자료 전달 범위를 확정. API 키를 저장소에 넣지 않는다.
- 사용자 공개 전: 허용 계정·실측 기반 예산·로그/보관 정책 확정. 기능 플래그로 활성화한다.
- 공개 MCP 전: 주소·TLS·Origin/Host·프록시·방문 집계 제외·호출 제한을 실제 배포 경로에서 검증. 개인 데이터 공개 시 외부 인가 연동 추가.
- 의존성 변경 배포는 `deploy/deploy-vm-full.sh`를 사용한다. 배포 실행은 별도 작업이며 이 구현 계획으로 운영 서버를 변경하지 않는다.

해외·기관 전체 지원, 영속 대화, 다중 탭 동기화, 문장별 자동 근거 검증, 고급 RAG, 모델 자동 분기는 후속 확장이다. 국내 IFR 자동 생성과 저장 경로·알람은 본 계획 5~6단계의 작업으로 남기며 단순 시연 완료를 이유로 제외하지 않는다.

## 6. 구현 담당과 모델 간 작업 분담

**2026-09-23 사용자 피드백에 따른 실행 우선 규칙:** 서브에이전트의 인계·대기·재작업이 전체 완료를 늦추면 주 담당이 직접 구현·수정한다. 첫 0+1A에서 이 비용이 커져 진행 중인 파일을 안전하게 인수한 뒤 주 담당이 마무리하기로 했다. 이후 기본은 **주 담당의 핵심 구현 + 실제로 분리 가능한 테스트/독립 검토의 선택적 위임**이다. 아래 모델 표는 위임할 경우의 역할별 참고 배정이며, 단계 전체를 반드시 위임하거나 Astra→Terra→Sol을 차례로 호출하라는 규칙이 아니다. 파일 소유권 회수 전에 동시 편집하지 않는 원칙과 독립 인수 기준은 유지한다.

**2026-09-22 최종 검토 반영: Astra는 설계·고난도 경계, Sol은 핵심 구현, Terra는 계약이 명확한 작업을 맡는다.** 앞서 기록한 Terra 중심 배정을 최근 합의한 역할별 배정으로 대체한다. 주 담당은 작업 명세·배정·독립 검증·최종 인수 책임을 유지한다. 이 배정은 프로젝트 운영 계획이지 성공률이나 비용 절감 폭의 보장이 아니며, 실제 제품 챗봇의 추론 모델 선택과 개발용 모델 배정은 별개다.

### 6.1 고정 역할과 모델

| 역할 | 모델/설정 | 책임 |
| --- | --- | --- |
| 조율·통합 책임자 | 현재 대화의 주 담당 모델 유지 | 명세·파일 소유권·배정 관리, 독립 검증과 최종 완료 판정. 확인 없이 주 담당의 모델을 Astra라고 단정하지 않음 |
| 설계·고난도 구현 | Astra (`gpt-6-astra`), reasoning `high` | 0의 기준/공통 계약, 5A의 경로 계산 공용화, 고위험 변경 및 통합 단계의 핵심 검토 |
| 핵심 구현·일반 검토 | Sol (`gpt-5.6-sol`), reasoning `high` 또는 `medium` | 실행기·결과 버전·브리핑·멱등성 등 핵심 구현, Terra 결과 검토. 작업별 설정은 §6.2 |
| 명세가 확정된 구현 | Terra (`gpt-5.6-terra`), reasoning `medium` | 공항 도구, 얇은 MCP 어댑터, 플로팅 UI, 소유권 서비스 기반 저장 경로 조회 |

이 배정의 `medium`/`high`는 추론 설정이지 별도 모델이나 품질 보증이 아니다. 추론 설정을 높이는 것만으로 다른 모델의 역할을 대체한다고 가정하지 않는다. 실행 시 모델·추론 설정의 지원 여부와 실제 적용값을 확인하고, 사용할 수 없으면 임의 모델로 조용히 대체하지 않고 배정 변경을 기록한다.

이 절은 앞선 모델 비교에서 제안한 배정안을 기록한 것이다. 작업 난도·계약의 명확성·검토 비용을 기준으로 배정하며, 실제 절감 효과는 구현·재작업·검토 사용량을 합쳐 판단한다. 모든 작업에 세 모델을 연쇄 호출하지 않는다.

### 6.2 13개 작업 묶음의 위임 시 참고 모델 배정

모든 행에서 주 담당이 최종 인수한다. 구현자가 쓴 코드와 같은 구현자가 쓴 테스트끼리 일치한다는 사실만으로 통과시키지 않는다. 0+1A는 한 검토 묶음이지만 0의 설계/기준 조사와 1A의 구현 모델은 구분한다.

| 구현 단계 / 작업 | 구현 모델 | 주 담당이 먼저 확정할 내용 | 인수 때 직접 확인할 핵심 |
| --- | --- | --- | --- |
| 1 / **0+1A 기준·공항 도구** | **0: Astra high → 1A: Terra medium** | reader/시계 주입, 도구 함수 서명·결과 schema, 정상/누락/기간 밖 fixture 기대값 | 원본 정보 보존, TAF 시간창, 자료 없음/경보 없음 구분, 기존 테스트 |
| 1 / **1B 브리핑·상세** | **Sol high** | REST 추출 범위, 기존 응답 보존, 결과 참조의 소유 범위·TTL·자료 버전 | 추출 전후 동일 결과, 상세 조회가 자료를 바꾸지 않음 |

| 6 / **6B 알람 변경** | **Sol high**, 확인 준비와 실행을 나눠 검토 | 확인 토큰·권한·ETD·멱등 실행 상태 전이 및 공격/재시도 테스트 | 권한 재검사, 응답 유실/재클릭에도 한 번만 실행, 원본 경로 삭제 없음 |

Terra 구현은 Sol 검토를 기본으로 한다. Sol 구현은 독립 테스트와 주 담당 인수를 기본으로 하고, 공통 계약·권한/쓰기·자료 동일성을 바꾸는 핵심 부분만 Astra 검토를 추가한다. Astra가 직접 구현한 5A도 기존 기준 fixture와 독립 회귀를 생략하지 않는다. 주 담당이 해당 검토 역할을 이미 수행하면 같은 역할의 에이전트를 중복 호출하지 않는다.

### 6.3 구현자에게 넘기기 전에 준비할 작업 명세

주 담당은 해당 작업 착수 직전에 현재 코드와 맞는 아래 항목을 완성한다. 전체 작업의 구현 코드를 미리 모두 작성하지는 않는다. 함수 경계나 실패 정책을 말로만 설명하기 어려운 부분에만 실제 schema·인터페이스·기준 함수·실행 가능한 테스트를 먼저 만든다. 테스트 기대값은 새 구현에서 역으로 생성하지 않고 기존 동작과 원자료 계약에 근거한다.

1. **목표/제외 범위:** 이번 작업에서 끝낼 사용자 흐름과 손대지 않을 기능.
2. **파일 소유권:** 읽을 파일, 수정 허용 파일, 동시 수정 금지 파일. 공유 계약 변경은 주 담당에게 요청.
3. **구체적인 계약:** 함수 서명, 입력/출력 schema와 예제, 자료/시계/사용자 컨텍스트 출처, 오류 형식.
4. **실행 로직:** 호출 순서·상태 전이·중단 조건·부분 실패·멱등성. 필요한 부분에는 의사코드가 아니라 테스트 가능한 기준 코드를 제공.
5. **테스트:** 기존 회귀 명령, 정상/경계/실패 fixture와 기대값, 추가해야 할 테스트. 의미 변경 없는 통과 목적의 assertion 완화는 금지.
6. **반환 형식:** 변경 파일, 실제 실행 명령·결과, 미실행 항목, 남은 문제, 계약 변경 필요 여부. 테스트를 실제 실행하지 않았다면 미실행으로 보고.

첫 `1A` 작업에서는 `backend/src/ai/contracts.js`, `data-context.js`, `tools/`, `digests/`의 필요한 파일과 `backend/test/`의 해당 테스트만 수정 범위로 잡는다. 공항/시간창 계약과 정상·부분 누락·TAF 기간 밖·UTC/KST 경계의 기대 결과를 먼저 고정한다. Terra는 기존 공항/TAF 계산을 호출하는 도구와 요약을 구현한다. `server.js` 전체 리팩터링, 모델/MCP SDK 추가, 프론트 수정, 새 수집은 제외한다. 구체적인 schema 필드와 테스트 이름은 0의 코드·자료 확인 후 확정하며, 현재 계획만을 바로 실행 가능한 작업 명세로 간주하지 않는다.

### 6.4 검토·수정·작업 회수 규칙

- 배정된 구현자의 자체 테스트 → §6.2에 따른 diff·불변조건 검토 → 미리 정한 기대값/회귀의 독립 실행 → 실제 앱·MCP·모델 연결 검증 → 주 담당 인수 순서로 진행한다. 공급자 자격정보 등 미확보 항목은 완료로 표시하지 않는다.
- 같은 원인의 검토 실패가 수정 지시 후 **2회 반복**되면 주 담당이 재현·명세·환경을 먼저 점검한다. 요구/fixture 문제는 명세를 고치고, 구현 난도가 원인이면 Terra 작업은 Sol로, Sol 작업의 구조적 문제는 Astra로 인계한다. Astra 작업도 반복 실패 시 주 담당이 범위를 재분할하거나 필요한 결정을 확인한다. 단순 추론 상향이나 모델 연쇄 재호출을 자동 복구로 사용하지 않는다.
- 권한 우회, 자료 시각/버전의 의미 변경, 기존 응답 계약 변경, 테스트 삭제/완화, 허용 범위 밖 파일 수정이 발견되면 횟수와 무관하게 즉시 검토한다. 이는 단순 난도 상승이 아니라 정확성/범위 문제다.
- 첫 1A 인수 결과로 전달량·검토량·재작업을 확인한다. 명세를 보완해도 분담 비용이 더 크면 해당 종류의 작업을 직접 구현하는 쪽으로 조정하고 이유를 기록한다.

### 6.5 실행 단위·비용 관리

- 사용자 확인 이후 기본은 **주 담당 직접 구현**이다. 실제로 독립적인 작업을 위임할 때만 해당 구현자 1개를 사용한다. 필요한 파일/계약/검증만 전달하고, 이 긴 대화 전체를 모든 작업에 복제하지 않는다. 새 작업에는 최소 맥락과 명시적 모델/추론 설정을 사용하고, 같은 작업의 수정은 기존 구현자 문맥을 재사용한다.
- 병렬화는 계약이 확정되고 쓰기 파일이 겹치지 않을 때만 한다. 예를 들어 3A 서버와 3B UI는 API 계약 확정 뒤 분리 가능하다. 먼저 구현한 결과가 다음 작업의 전제인 1A→1B, 4A→4B→4C, 5A→5B는 기본적으로 순차 진행한다. 테스트가 같은 서버/DB/산출물을 사용하면 실행도 분리한다.
- 보고서는 구현 결과·검증·문제 중심으로 짧게 받는다. 개발 모델의 입력/출력·호출 수, 재시도, 주 담당 검토·수정 시간과 전체 완료 시간을 기록한다. 사용량 정보가 없으면 미측정으로 남기고 추정 비용을 실측처럼 보고하지 않는다.
- 개발 에이전트 비용과 제품 챗봇의 사용자 질문당 비용은 별도 집계한다. API 단가를 이 앱의 실제 구독 청구액과 동일하게 간주하지 않는다. 총 비용 절감률은 아직 측정하지 않았다.
- 0+1A에서는 Astra high 계약 설계 → Terra medium 초안 → Sol high 독립 검토·수정을 실행하고 주 담당이 최종 인수했다. 이후 1B/2는 주 담당이 직접 구현했다. 1A 근거는 [기준/검증 기록](../../evaluation/ai-copilot/2026-09-22-1a-baseline.md), 로컬 MCP 완료 근거는 [후속 실행 기록](../../evaluation/ai-copilot/2026-09-23-local-mcp.md)을 따른다. 제품 채팅 UI를 완료했다는 뜻은 아니다.

### 7.2 2026-09-24 잔여 인수 작업

완료 항목을 반복 확장하지 않도록 다음 작업과 끝나는 조건을 구체화한다. 기존 전체 범위를 줄이거나 아래 시험만으로 모든 요구를 증명했다는 뜻은 아니다. 최종 완료 시 §2~4의 각 요구와 §7 증거를 다시 대조한다.
