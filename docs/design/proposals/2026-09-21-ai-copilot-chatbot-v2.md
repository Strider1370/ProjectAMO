## 1. 구현 가능성과 제품 방향

**도입 가능성이 높다.** 공항기상·경로 브리핑·고도 비교의 계산 기능과 로그인·화면 제어가 이미 있다. 새로 필요한 핵심은 도구 실행 계층, 작은 근거 데이터, 대화 상태, 채팅 UI다. 전체 프로젝트를 챗봇 중심으로 다시 작성할 필요는 없다.

이 판단은 **토큰을 통제하는 구조를 구현할 수 있다**는 뜻이다. 목표 토큰 안에서 충분한 답변 품질과 운영비를 달성했다는 뜻은 아니다. 기존 코드 재사용, 신규 개발, 실측이 필요한 가정을 §9에서 구분하며, 결과를 측정하기 전에는 비용 절감률·답변 정확도·처리시간을 보장하지 않는다.

다만 “김포에서 제주로 가는데 알아서 브리핑해줘”를 서버 단독으로 처리하는 것과 “지금 선택한 김포–제주 경로를 설명해줘”는 구현 범위가 다르다. 전자는 브라우저의 경로 생성 흐름을 추출해야 한다. 후자는 현재 경로의 구조화된 입력을 서버에 전달해 기존 계산을 재사용할 수 있다. **첫 배포는 공항 질의 + 현재 경로 설명 + 후속 질문 + 화면 연결로 완성하고, 새 경로 자동 생성은 다음 단계로 확장한다.** 좌표가 브라우저에서 서버로 전송되는 것은 LLM 입력 토큰과 무관하다.

**MCP도 초기 구현 범위다.** “공항 도구 + 준비된 경로의 브리핑 → 로컬 Codex MCP 시연 → 자체 채팅창 → 서버 자동 경로 생성” 순서로 진행한다. 공통 도구를 얇은 MCP 어댑터로 연결해 도구 선택·입력·요약 품질을 먼저 확인한다. 브리핑 계산은 미리 준비한 경로 입력으로 실행할 수 있으므로 경로 자동 생성 전체를 기다리지 않는다. 인터넷 공개, 개인 데이터용 OAuth, 공식 디렉터리 등재는 후속 작업이다.

## 2. 첫 버전에서 사용자가 할 수 있는 일

| 질문 | 기대 동작 | 필요한 조건 |
| --- | --- | --- |
| “제주 내일 오전 날씨 알려줘” | 요청 시간대의 TAF와 현재 관측을 구분해 설명 | 예보 유효기간 밖이면 해당 범위를 표시 |
| “이 경로에서 주의할 점만 알려줘” | 선택 경로의 브리핑을 생성·조회해 핵심 항목과 자료 상태 표시 | 적용된 경로, ETD·ETA, 고도 |
| “그 SIGMET은 우리 고도에 걸려?” | 같은 브리핑의 수평·고도·시간 판정 근거 조회 | 유효한 `briefing_ref` |
| “FL320과 FL340을 비교해줘” | 같은 경로·시간·자료 기준으로 비교표 표시 | 요청 고도 지원·제약 판정 필요 |
| “연직단면 보여줘” | 답변이 참조하는 경로의 기존 단면 화면 열기 | 해당 경로 참조와 화면 기능 준비 |
| “난류 레이어 켜줘” | 허용된 화면 동작 실행 후 실제 실행 결과 표시 | 지도 준비 |

새 경로가 필요한 질문은 첫 버전에서 출발·도착 등 입력을 경로 설정 화면에 채우고 생성 흐름으로 연결한다. 서버 경로 생성이 추가되기 전까지 자동 브리핑 완료로 표현하지 않는다. 범용 지식 검색, 문서 RAG, 자율적인 장시간 작업, 해외·기관 브리핑 전체 지원은 첫 버전의 완료 조건에 포함하지 않는다.

### 2.1 PoC와 후속 기능의 구분

아래는 완료 범위다. 이후 장의 장기 설계를 한 번에 구현할 필요는 없다.

| 항목 | PoC에서 완료 | 후속으로 확장 |
| --- | --- | --- |
| MCP 검증 | 같은 WSL의 Codex CLI에서 localhost 접속·도구 호출·후속 질문 | 공개 HTTPS, 원격 웹 커넥터, OAuth·등재 |
| 경로 | 개발용 김포–제주 입력으로 실제 브리핑 서비스 실행, 자체 챗봇에서는 적용된 화면 경로 사용 | 공항명만으로 임의 경로 자동 생성, 해외·FIR·VFR 확장 |
| 사실·근거 | 자료 ID·시각·누락·기간 미포함 보존, 상세 조회, 정해진 시나리오로 설명 대조 | 문장별 `evidence_id` 자동 연결·의미 검증 |
| 대화 | 대화당 한 요청, 부분 슬롯 보관, 취소/경로 변경 뒤 늦은 응답 무시 | 여러 탭의 같은 대화 동기화, 충돌 병합, 영속 대화 저장 |
| 결과 보관 | 프로세스 내 크기 제한·TTL·호출자 범위가 있는 참조 저장, 재시작 시 만료 | 공유 저장소, 장기 이력·결과 캐시 |
| 사용량 | 도구 입력/응답 크기·실행시간·동시성 제한; 자체 챗봇은 호출 횟수·전체 비용 상한 | 다중 모델 분기, 정교한 사용자별 과금·대시보드 |

개인 정보가 없는 로컬 MCP 단계는 개발용 호출자 범위로 참조를 격리한다. MCP 세션을 사용자 인증으로 간주하지 않는다. 자체 챗봇에서 개인 자료를 다루면 기존 로그인 소유권 검사를 적용한다. PoC에서도 자료 없음과 위험 없음의 구분, 입력 검증, 쓰기 도구 미노출은 유지한다.

## 3. 사용자 경험

채팅은 지도와 브리핑을 보면서 사용할 수 있는 보조 패널로 만든다. 기존 디자인 토큰과 모바일 `MobileSheet` 패턴을 따른다. 모바일에서는 두 장의 시트가 겹치지 않도록 채팅/자료 화면 전환 시 대화와 스크롤 위치를 보존한다.

입력창 위에는 서버가 확인한 현재 맥락을 짧게 표시한다. 예: `RKSS → RKPC · 9/22 09:00 KST · FL340 · 적용 경로`. 맥락이 없으면 선택 공항에 맞는 시작 질문을 제공한다. 사용자가 명시한 값, 현재 화면에서 가져온 값, 기본값의 출처를 구분한다. “현재 화면 사용”은 언제든 해제할 수 있다.

답변은 다음 순서를 기본으로 한다.

1. 질문에 대한 짧은 설명. 자료 부족이나 기간 미포함이 결론을 제한하면 먼저 밝힌다.
2. 서버가 만든 사실 카드 또는 비교표. 관측과 예보를 구분하고 수치·단위를 그대로 표시한다.
3. 자료 관측/발표 시각, 유효기간, 누락·지연 상태 및 원자료 보기.
4. 해당 결과에 연결된 버튼. 후속 질문은 제안하되 자동 실행하지 않는다.

진행 표시는 `자료 확인 중 → 브리핑 계산 중 → 설명 작성 중` 정도로 제한한다. 중지·재시도와 키보드 탐색을 제공하고, 새 메시지는 접근성 live region으로 알린다. 중간 텍스트를 검증 완료된 기상 결론처럼 표시하지 않는다.

## 4. 실행 구조와 경계

```text
ProjectAMO 채팅 패널
  ├─ 화면 맥락 → 입력 검증/경로 등록 → context_ref
  └─ 질문 + conversation_id + context_ref
                    ↓
             서버 대화 실행기
              ↔ LLM 공급자 어댑터
                    ↓ 허용된 도구 호출/입력 검증
             애플리케이션 서비스
                    ↓
       기존 저장 자료 · 브리핑/고도 계산 · 권한 검사
                    ↓
        서버 보관 원본 + LLM용 digest + 근거 목록
                    ↓
          설명 + 사실 카드 + 실행 가능한 UI 버튼

로컬 Codex CLI → localhost MCP 어댑터 → 같은 도구/서비스
                                      ↑ 개발용 경로 입력 fixture
```

권장 모듈 위치는 `backend/src/ai/{tools,digests,providers}`와 별도 대화·참조 저장소, `frontend/src/features/copilot/`이다. `server.js`의 기존 브리핑 데이터 수집·검증·호출을 서비스로 추출해 REST와 도구가 공유한다. 서버 안에서 자기 HTTP API를 다시 호출하거나 Express `req/res`를 흉내 내지 않는다.

도구 정의는 입력·출력 JSON Schema와 실행 함수로 관리한다. MCP 전용 타입을 도메인 서비스로 전파하지 않는다. 초기에는 공급자 한 곳과 작은 어댑터만 구현하고 다중 모델 자동 분기는 평가 후 추가한다. 모델·요금·캐시 할인율은 이 설계에서 확정하지 않는다.

도구 실행 컨텍스트의 사용자·기관·권한·기준 시각은 서버가 넣는다. 모델 인자에 `userId`, 권한, 임의 URL·SQL·파일 경로를 허용하지 않는다. NOTAM·저장 이름 등 외부 텍스트는 자료로만 취급하고 도구 실행 권한을 바꾸지 못하게 한다.

## 5. 현재 경로를 재사용하는 방법

첫 버전은 브라우저의 **적용된 경로**를 사용한다. 미적용 편집 초안이나 화면에 보이는 좌표를 추정하지 않는다. 브라우저는 `routeGeometry`, 버전 있는 `routeModel`, 절차 맥락, ETD·ETA, 고도, NWP 시간 선택, 화면 경로 revision을 등록 API에 보낸다. 개인 저장 경로는 가능하면 ID로 서버에서 조회한다.

이 방식은 자체 챗봇의 경로 연동에 적용한다. 외부 MCP 클라이언트는 현재 ProjectAMO 화면 맥락을 자동으로 공유하지 않는다. 초기 로컬 MCP에는 별도로 준비한 김포–제주 경로 입력을 제공해 브리핑·상세 조회를 검증한다. 출발·도착만 받아 임의 경로를 만드는 기능은 서버 경로 생성 단계에서 추가한다. 브라우저의 참조를 외부 앱으로 전달하는 기능은 초기 연결의 전제로 두지 않는다.

서버는 크기·좌표·시각·모델 버전·기하와 구간의 일관성을 검증한다. 클라이언트가 보낸 기상 결과나 AIP 제한을 사실로 신뢰하지 않고 서버 자료로 계산한다. 등록 성공 시 세션/사용자에 묶인 불투명 `context_ref`를 반환한다. LLM에는 이 참조와 공항·시간·고도만 전달한다. 대용량 원본·격자는 전달하지 않는다.

`context_ref`는 계산 입력, `briefing_ref`는 특정 입력·자료 버전으로 계산한 결과를 가리킨다. 두 참조를 구분한다. 화면이 바뀌어도 기존 답변은 기존 결과를 가리킨다. 새 질문은 최신 맥락을 확인하며, 이전 경로를 대상으로 계속 묻는 경우 이를 명시한다.

“전체 브리핑 보기”는 같은 입력으로 재계산해 우연히 비슷한 결과를 만드는 대신 해당 `briefing_ref`의 보관 결과를 연다. 실제 화면에 이를 주입하는 어댑터는 새로 필요하다. 현재 `loadRouteBriefing`은 저장 경로를 복원하는 동작이므로 그대로 쓰면 결과 동일성을 보장하지 못한다. 새 자료로 갱신할 때는 새 참조를 발급하고 “갱신된 브리핑”으로 표시한다.

예시 수명 정책은 결과 TTL 30분 + 사용자별 개수/바이트 상한이다. TTL·요청 제한·세션 만료는 실제 시계로 계산한다. 소유권 검사를 매 조회에 적용하고, 만료되면 `REFERENCE_EXPIRED`와 재조회 방법을 반환한다. 초기 단일 프로세스에서는 제한된 메모리 저장소가 가능하며 재시작 시 만료를 허용한다. 다중 프로세스 운영이면 공유 저장소가 필요하다.

## 6. 도구 구성

| 도구 | 핵심 입력 | 결과/정책 |
| --- | --- | --- |
| `get_airport_weather` | 공항 목록, 조회 시간창 | 실황·TAF·경보, 범위/누락/자료 시각 |
| `get_route_briefing` | `context_ref`, 또는 로컬 시연 전용 `fixture_id` 중 하나 | 같은 브리핑 서비스의 digest와 `briefing_ref`; fixture 사용 명시 |
| `get_briefing_detail` | `briefing_ref`, section, item/cursor, limit | 같은 결과의 제한된 상세 내용 |
| `compare_altitudes` | `briefing_ref`, 요청 고도 목록 | 동일 경로·비교 조건의 행, 제약 상태와 자료 범위 |
| `request_ui_action` | action enum, 검증 가능한 target/ref | 허용 목록·현재 화면 능력 확인 후 구조화된 동작 |

PR 2의 MCP 검증 대상은 `get_airport_weather`, `get_route_briefing`, `get_briefing_detail`이다. `compare_altitudes`는 PR 4에서 추가하며, `request_ui_action`은 자체 챗봇에서만 제공한다. 개발용 `fixture_id` 분기는 시연 설정에서만 노출하고 서버의 고정 목록으로 검증한다. 모델이 임의 파일 경로나 좌표를 생성하도록 하지 않는다. 일반 앱과 공개 배포에서는 fixture 인자를 노출하지 않는다.

김포–제주 fixture에는 실제로 성립한 경로의 geometry·버전 있는 routeModel·절차 맥락·고도·ETD/ETA·navdata publication을 기록한다. 가능하면 기존 테스트 입력을 재사용하고, 없으면 현 UI에서 정상 적용한 입력을 준비·검증한다. 정답 문장을 반환하는 목업이 아니라 **같은 서비스가 원자료로 브리핑을 계산**하게 한다. 고정 기준 시각과 기상 snapshot을 짝지어 재현 가능한 시연을 구성하고, 자료가 부족하면 그 상태를 그대로 반환한다. fixture와 snapshot의 식별자·기준 시각·시연 표시를 응답에 포함한다. 최초 PoC는 fixture의 고정 비행 조건만 지원하며 다른 날짜·고도·공항 요청은 불일치를 알린다. 활성 운영/공유 개발 데이터나 전체 서버 시계를 시연 때문에 바꾸지 않는다.

공항 이름/별칭/지역 묶음은 서버 카탈로그로 해석한다. “남부권”의 범위가 카탈로그에 정의되지 않았다면 공항 목록을 확인한다. 모든 공항표를 매번 프롬프트에 나열할 필요는 없다. 모델은 한글 이름을 전달할 수 있고, 서버가 ICAO와 후보를 반환한다.

상세 조회에는 `airport_ref`도 받을 수 있게 확장해 공항 단독 질문의 원문 후속 질의를 지원한다. section별 허용 입력·페이지 상한을 둔다. METAR 재구성 문자열은 원본 TAC와 구분해 `rawKind: reconstructed`로 표시한다.

고도 비교는 현재 API가 임의의 `altitudes_ft` 목록을 직접 처리하지 않는다는 점을 반영해 서비스 확장이 필요하다. `valid`, `input_only`, `input_invalid`를 보존한다. `input_only`는 제약 미확정이며 불가 판정이 아니다. 알려진 제약과 충돌, 판정 불가, 기상자료 없음도 각각 구분한다.

고도별 난류·착빙·바람 차이를 설명할 수 있지만, `rank`와 “최적/가장 안전한 고도” 권고는 현재 범위에서 제외한다. 기존 경로 브리핑 자료 규약이 순위·고도 선택을 금지하므로 가중치 결정만으로 활성화할 수 없다. 추후 필요하면 별도 제품 요구사항과 규약 변경으로 다룬다.

저장 경로 도구와 알람 도구는 후속 단계에서 추가한다. 도구를 한꺼번에 모두 노출하지 않고 권한과 현재 맥락에 맞는 집합만 제공한다. 첫 버전에 별도 분류 모델은 필요하지 않다.

## 7. 결과 계약과 근거

아래는 제안 형태이며 기존 API가 이미 반환한다는 의미가 아니다.

```json
{
  "schemaVersion": "1",
  "status": "partial",
  "reference": {
    "effectiveNow": "2026-09-21T06:00:00Z",
    "clockMode": "live",
    "displayTimezone": "Asia/Seoul"
  },
  "data": {},
  "sources": [],
  "coverage": {},
  "issues": [
    { "code": "DATA_UNAVAILABLE", "source": "KTG", "reason": "자료 미확보" }
  ],
  "truncation": { "omittedCount": 0, "nextCursor": null },
  "error": null
}
```

`status`는 `ok | partial | error`. 성공 여부와 자료 완전성을 분리한다. source마다 존재하는 필드만 담는다: 원자료 ID, publication/run ID, 관측/발표/수신 시각, 유효 시작·종료, content hash, 수집 상태, 최신성 판정과 이유. 시각을 알 수 없으면 `null`이며 수신 시각으로 발표 시각을 대체하지 않는다.

`stale` 하나로 수집 실패·오래됨·기간 미포함을 합치지 않는다. 최신성, 수집 상태, 요청 시간 포함 여부를 구분한다. 정상 수집됐어도 요청한 내일의 예보가 없을 수 있고, 마지막 정상 자료를 유지해도 아직 유효할 수 있다. 기존 저장소에 수집 실패 이력이 없으면 알 수 없다고 표시하고 필요한 메타데이터를 추가한다.

digest가 보존해야 할 내용:

- 관측과 예보의 구분, TAF 유효범위와 TEMPO/BECMG/PROB, 요청 시간 중 미포함 구간.
- 위험기상별 원자료 ID와 수평·고도·시간 판정, 미확정 이유. 단순 “겹침”으로 합치지 않는다.
- 비교 범위가 항로 구간인지 전체 비행인지, 적용된 고도 프로파일과 시각 가정.
- KIM/KTG 각각의 실행·유효 시각, 결측 범위와 보간/대체 시각 사용 여부.
- AIP publication ID 및 unavailable/partial/conflicting 상태, NOTAM 식별자·영향·유효기간.
- 생략 항목 수와 상세 조회 경로. 위험 10건/NOTAM 5건 같은 상한만으로 목록을 완전하다고 보이게 하지 않는다.

수치 카드와 비교표는 서버가 검증한 값으로 렌더링하고 LLM은 설명을 작성한다. PoC에서는 원자료 ID·시각·상태와 상세 조회를 보존하고, 고정 시나리오에서 설명이 실제 결과에 맞는지 대조한다. 문장별 `evidence_id` 연결과 자동 의미 검증은 후속 작업이다. 자유 문장 속 숫자를 정규식으로 대조하는 것만으로 의미의 정확성을 증명할 수는 없다. 자체 챗봇의 생성 실패 시 확인된 카드만 표시하는 대체 응답을 제공한다.

`summarizeAirport`나 화면 view model은 그대로 LLM에 넘기지 않는다. 예를 들어 현재 공항 요약의 RVR 미보고 표시 `2000+`는 관측값으로 옮기면 안 되고, 재구성 METAR는 원문이라고 부르면 안 된다. `briefingViewModel.catDisplay`의 MVFR→VFR 표시 축약도 원래 비행 범주를 대체하면 안 된다. digest는 원래 구조화된 사실을 기준으로 만든다.

## 8. 대화 상태와 시간

대화 상태에는 값뿐 아니라 출처와 revision을 보관한다. 우선순위는 이번 발화의 명시적 수정 → 사용자가 채택한 대화 맥락 → 현재 화면 맥락 → 공개된 기본값이다. 서로 다른 경로의 ETD·고도가 조용히 섞이지 않도록 경로 변경 시 종속 슬롯을 재검증한다. 아직 필수 입력이 부족해도 검증된 부분 슬롯은 저장한다.

PoC는 대화당 한 요청만 처리하고 처리 중 중복 전송을 막는다. 취소나 화면 경로 변경 뒤 늦게 도착한 결과는 요청 ID/revision으로 무시한다. 탭마다 별도 대화를 사용하며 여러 탭의 같은 대화 동기화와 충돌 병합은 후속 작업이다. 대화는 메모리에 보관하고 재시작 시 초기화한다. 장기 대화 압축·영속 보관을 추가하더라도 참조와 슬롯을 사실의 기준으로 유지한다.

“내일 9시”는 모델이 임의의 날짜로 완성하는 대신 제한된 표현(`relativeDay: 1`, `time: 09:00`, `timezone: Asia/Seoul`)으로 전달하고 서버가 기준 시각을 사용해 해석한다. 절대 날짜와 상대 표현을 모두 지원하되 월말·연말·자정·UTC/KST 전환을 검증한다. “오전” 같은 시간창은 명시된 제품 기본 범위를 보여주거나 필요한 경우 되묻는다. 기본 시간대는 현재 선택값이다.

기상 질의는 `getEffectiveNow()`와 시연 여부를 표시한다. 실제 알람은 현재 코드처럼 실제 미래 시각이 필요하다. 첫 버전의 시연 모드에서는 실제 알람을 만들지 않고, 후속 구현 때 별도 동작 정책을 정한다. 슬롯에 남은 시연 날짜가 실제 알람 날짜로 흘러가지 않게 한다.

브리핑 ETD뿐 아니라 ETA도 필수다. 현재 화면의 ETA를 우선 사용한다. 자동 추정이 필요한 후속 단계에서는 TAS·성능 기본값과 ETA 산출 근거를 명시하고 기존 계산 흐름을 재사용한다. LLM 또는 기상 자료 계층에 성능 계산을 추가하지 않는다.

시간 변환·권한·중복 방지·화면 상태 검사 등은 서버/프론트 코드가 맡는다. 이 규칙의 구현 전체를 프롬프트에 설명할 필요는 없다. LLM에는 입력 규약과 실행 결과만 전달한다. 기능 수나 백엔드 계산량을 곧바로 LLM 토큰 사용량으로 해석하지 않는다.

### 9.2 질문 한 번의 전체 비용

토큰 측정 단위는 **사용자 질문 한 번을 처리하는 모든 모델 호출의 합계**다. 도구 결과 1,500토큰이 질문당 입력 1,500토큰을 뜻하지 않는다. 아래는 실측이 아닌 계산 예시다.

| 단계 | 입력 토큰 | 출력 토큰 |
| --- | ---: | ---: |
| 도구 선택 | 지시문·도구·맥락·질문 2,500 | 도구 호출 100 |
| 결과 설명 | 이전 2,500 + 도구 호출 100 + 결과 1,500 = 4,100 | 설명 600 |
| 질문 한 번의 합계 | 6,600 | 700 |

이 예시에는 내부 추론 토큰·공급자별 추가 처리량·재시도를 포함하지 않았다. 같은 사용량으로 하루 1,000번 질문하면 입력 660만·출력 70만 토큰이다. 금액은 선택한 공급자·모델의 단가를 적용한 후에 계산한다. 이는 운영 사용량 예측이나 견적이 아니다.

이전 응답 ID로 대화를 이어가더라도 이전 입력이 무료가 되지 않는다. OpenAI의 `previous_response_id`도 체인에 포함된 이전 입력이 과금 대상이다. [대화 상태 공식 문서](https://developers.openai.com/api/docs/guides/conversation-state)

보이는 답변 길이만으로 출력 비용을 판단하지 않는다. 추론 모델은 내부 추론도 비용에 포함될 수 있다. 공급자의 `output_tokens`에 추론 토큰이 포함돼 있으면 다시 더하지 않고 세부 항목으로 기록한다. [추론 모델 공식 문서](https://developers.openai.com/api/docs/guides/reasoning)

### 9.3 토큰을 줄이는 실행 규칙

1. 공항·시간창·항목으로 조회 범위를 제한한다. “그 SIGMET의 고도는?”에는 그 항목과 경로 고도 판정을 제공하며 전체 브리핑을 반복하지 않는다.
2. 좌표·연직 격자·전체 원문은 서버에 보관한다. 모델에는 작은 요약과 참조를 전달한다. 참조 ID 자체에 내용이 담겨 있다고 가정하지 않고 필요한 상세를 도구로 조회한다.
3. 새 질문에는 확정된 슬롯과 관련 대화만 전달한다. 오래된 도구 원본을 계속 누적하지 않는다. 슬롯·미해결 질문·참조를 보존하며, 찾을 수 없는 이전 내용은 다시 조회하거나 사용자에게 확인한다.
4. 대화 정리를 위해 매 메시지마다 별도 모델을 호출하지 않는다. 구조화된 상태는 코드로 갱신하고, 장기 대화 요약이 필요해지면 예산 초과 시점에만 수행하며 그 호출 비용도 집계한다.
5. 브리핑 자료 취합과 정량 계산은 서버 도구 하나에서 수행한다. 자료 종류마다 모델이 중간 판단을 반복하도록 만들지 않는다.
6. 자체 챗봇의 표·시각·버튼은 코드로 렌더링한다. LLM은 핵심 차이를 설명하고 표 전체를 다시 출력하지 않는다. 관련 화면 버튼 클릭에는 모델을 호출하지 않는다.

원본 보관·맥락 관리·자료 검증 기능은 토큰을 줄이는 기반이다. 이를 빼는 대신 무엇을 모델에 전달할지 통제한다. 중요 위험·누락·조건부 예보·기간 미포함은 크기 목표 때문에 삭제하지 않는다. 상세가 길면 페이지와 생략 수를 제공한다.

### 9.4 목표와 상한, 아직 검증하지 않은 가정

| 항목 | 초기 제안 | 의미와 한계 |
| --- | --- | --- |
| 일반 도구 결과 | 보통 1,000~2,000토큰 | 목표값. 원문 상세·여러 공항 비교는 별도 분류 |
| 일반 조회/브리핑의 턴당 누적 입력 | 약 4,000~8,000토큰 | 모든 호출을 합친 **미측정 목표**, 하한/강제 상한이나 품질 보장 아님 |
| 일반 조회/브리핑 모델 호출 | 보통 2회 | 도구 선택 → 결과 설명. 추가 조회·확인이 필요하면 늘어남 |
| 자체 챗봇 실행 상한 | 모델 3회, 도구 4회, 전체 45초 | 초기 운영 설정안. 재시도 포함, 상한 도달 시 부분/미완료 응답 |
| 화면 조작 | 자연어 요청은 모델 1회 목표, 답변 버튼 클릭은 0회 | 해석 후 실행 결과는 코드로 표시. 모호한 요청은 확인 필요 |
| 출력 토큰 제한 | 선택 모델의 추론·출력 특성 평가 후 설정 | 짧은 자연어 답변이 낮은 전체 출력 비용을 보장하지 않음 |

위 수치로 품질과 비용이 충족되는지는 아직 확인하지 않았다. 실측이 필요한 가정은 ① 요약에서 중요 정보가 보존되는가 ② 짧은 대화 상태로 후속 질문을 해석하는가 ③ 보통 두 번의 호출로 끝나는가 ④ 캐시가 실제 적중하는가 ⑤ 상한에 도달해 답변이 미완료되는 비율이 어느 정도인가다.

로컬 Codex가 대화를 관리하는 PR 2에서는 MCP 서버의 요청 크기·호출 빈도·계산 동시성·실행시간을 제한한다. 모델 호출 수·전체 대화 기록·턴 비용을 MCP 서버가 통제한다고 가정하지 않는다. Codex에서 노출되는 사용량은 참고 자료로만 기록하며, 제공되지 않는 전체 사용량을 도구 응답 길이로 추정해 실측값처럼 보고하지 않는다. 최종 비용 평가는 자체 챗봇의 공급자 사용량으로 한다.

### 9.5 캐시·사용량 제한

고정 지시문·도구 정의는 짧고 안정적으로 유지해 프롬프트 캐시를 활용한다. 매번 도구 정의를 바꾸면 입력은 줄어도 캐시 재사용이 줄 수 있으므로 현재처럼 소수 도구일 때는 안정된 정의부터 측정한다. 권한에 따른 실행 허용 여부는 서버에서 별도로 검사한다. 캐시 적중·할인율을 보장하지 않으며 비적중과 적중 결과를 구분한다. [프롬프트 캐시 공식 문서](https://developers.openai.com/api/docs/guides/prompt-caching)

자체 챗봇의 첫 버전은 로그인 또는 제한된 파일럿 계정을 대상으로 전체 비용·호출 횟수·계산 동시성 상한을 적용한다. 세분화된 사용자별 예산 관리는 후속 확장한다. 비로그인 공개는 별도 사용량 정책 후 결정한다. 예산 소진·공급자 오류·타임아웃 때 기존 자료 화면은 계속 사용할 수 있어야 한다. 앱의 LLM 자격정보가 없으면 자체 채팅 기능을 비활성화한다. 로컬 MCP 도구 자체는 앱용 LLM 키 없이 시험할 수 있으며, 추론은 Codex에 구성된 인증·모델을 사용한다.

PoC는 참조로 조회하는 결과 보관만 구현하고, 요청 간 계산 결과 캐시는 후속으로 둔다. 캐시를 도입할 때는 정규화한 입력, 소유/기관 범위, route revision, AIRAC, 자료별 hash/run, 조회 시간, 시연 모드, 계산/digest 버전을 포함한다. content hash가 같아도 시간이 지나면 유효기간·stale 판정이 달라지므로 만료 시각을 제한하거나 해당 판정을 다시 계산한다. 사용자별 답변 전체를 “같은 질문+같은 hash”만으로 공유하지 않는다.

서버 계산 캐시와 프롬프트 캐시는 별개다. 계산 결과를 재사용해도 모델이 결과를 읽고 설명하면 토큰을 사용한다. 캐시가 없어도 질문당 비용을 계산할 수 있어야 하며, 캐시 효과를 기본 견적에 확정 할인처럼 넣지 않는다.

### 9.6 실측 순서와 완료 증거

1. 실제 공항·브리핑 자료로 코드 기반 digest를 만든다. 원본과 요약의 보존 필드·누락/유효기간 상태를 자동 테스트로 대조한다. 추가 LLM 요약 호출은 사용하지 않는다.
2. 원본·digest의 크기를 비교한다. 토큰은 사용한 모델용 계수 방법과 버전을 기록한다. 문자열 길이/바이트 수를 토큰 수로 표기하지 않으며 모델 미선정 시 토큰 수는 미측정으로 둔다.
3. 공항 현재/미래, 경로 브리핑, 고도 비교, 특정 항목 상세, 입력 부족, 부분 실패를 실제 모델로 평가한다. 첫 질문과 같은 대화의 열 번째 질문을 포함해 맥락 손실과 입력 누적을 확인한다.
4. 질문 종류별 모델/도구 호출 수, 누적 입력, 캐시 입력, 공급자가 제공하는 캐시 쓰기 항목, 전체 출력·추론 세부값, 비용, p50/p95 처리시간, 완료/미완료율을 집계한다. 실패·재시도에서 실제로 발생한 사용량도 포함한다.
5. 중요 정보 누락, 잘못된 시간·공항 적용, 자료 없음을 현상 없음으로 해석하는 오류를 결과별로 표시한다. 비용 절감과 답변 정확도를 함께 비교하고 digest·기록 범위·상한을 조정한다. 저렴해졌다는 이유만으로 통과시키지 않는다.

모델·프롬프트·도구 스키마·digest 버전, 데이터/질문 세트 ID, 계수 방법, 실제 사용량, 단가 기준일을 측정 기록에 남긴다. 비용은 공급자가 구분하는 과금 항목별 사용량×단가를 합산하며 캐시/추론 포함 관계를 확인해 중복 계산하지 않는다. API 사용량에 포함되는 스키마·포맷 등 추가량 때문에 사전 계산과 실제 사용량이 다를 수 있으므로 운영비는 실제 사용량을 기준으로 산정한다.

공통 필수 사례에서 확인된 중요 정보 누락·잘못된 대상/시간·근거 없는 수치를 해결하고, 미완료 사례·원인과 비용/지연 분포를 기록해야 해당 기능의 평가가 완료된다. 모델 결정 후 사용자당 비용과 서비스 전체 예산을 설정하고 그 안에서 달성 가능한 기능 범위를 확인한다. 한두 건의 짧은 답변이나 고정 경로 통과만으로 운영비·정확도를 검증했다고 하지 않는다.

프롬프트와 개인 경로 원문을 기본 운영 로그에 남기지 않는다. 요청 ID, 도구·모델 버전, 지연, 사용량, 오류 코드 중심으로 관측한다. 재현 가능한 평가 기록은 비개인 fixture/허용된 데이터로 별도 관리한다. 외부 공급자에 보낼 데이터 범위와 보관 정책은 도입 시 실제 계약·설정에 맞춰 정한다.

## 10. 다음 단계: 서버 경로 생성과 개인 데이터

### 서버 경로 생성

`createRoutePlanner({loadJson, navdataVersion})` 같은 인스턴스를 만들고 파일·합성 그래프·절차·IAP 캐시를 같은 publication 단위로 관리한다. `loadOverseasLinks`의 직접 fetch도 포함한다. 모듈 전역 캐시를 그대로 서버에 옮기면 AIRAC 갱신과 테스트 격리가 깨질 수 있다.

`planRoute` 추출에는 절차 준비 → METAR 기반 활주로 후보 → SID/STAR/IAP 후보 선택 → 경로 검색 → 편집 모델 정규화/적용 → 최종 geometry/routeModel → 프로파일 요청 구성과 ETA 입력 연결이 필요하다. `buildEditorPreview`와 적용 과정이 빠지면 현재 화면과 다른 경로가 생긴다. 활주로 자동 선택은 현재 관측에 근거한 계산 가정으로 표시하며 미래 실제 사용 활주로로 단정하지 않는다.

DOM·지도 렌더링·React 취소 처리는 UI에 남긴다. `routePreview.js` 앞부분의 순수 geometry 함수만 분리하고, `aircraftProfiles.js`는 기본값/정규화와 localStorage 어댑터를 나눈다. 국내 IFR을 먼저 추출하고 FIR 진입·이탈, VFR 수동점/왕복, 해외는 별도 회귀 범위로 확장한다. 지원하지 않는 유형은 명확히 반환한다.

루트 `shared/route-planning/`가 후보 위치다. 현재 `Architecture.md`는 루트 shared를 공통 상수로 설명하지만 실제 `shared/route-model.js`는 함수도 포함한다. 구현 PR에서 문서 경계를 “환경 독립 공통 도메인 모델·순수 계산”으로 명시적으로 정리해야 한다. `backend`가 `frontend/src`를 import하는 방식은 사용하지 않는다.

현재 배포 스크립트는 전체 저장소를 pull하므로 `frontend/public/data/navdata` 읽기는 가능하다. 하지만 경로를 하드코딩하기보다 navdata provider에 캡슐화하고 기동 시 publication/필수 파일을 검사한다. 여러 파일을 읽는 도중 AIRAC가 바뀌면 혼합 publication으로 결과를 만들지 않는다. 빌드 산출물과 서버가 읽는 자료의 버전도 비교한다. `/opt/projectamo/shared/data`의 운영자료와 정적 navdata의 생명주기를 구분한다.

### 개인 데이터

자체 채팅창의 저장 경로·알람은 기존 로그인 세션을 재사용한다. OAuth는 외부 MCP 앱에 사용자 자료를 제공할 때의 별도 과제다.

저장 경로에는 “저장 당시 결과 열기”와 “현재 자료로 재브리핑” 모드를 구분한다. 현재 알람의 마지막 snapshot 포인터가 임의의 과거 브리핑 이력을 제공한다는 뜻은 아니므로 과거 비교에는 보관 범위부터 확인해야 한다.

알람은 원본 경로가 아니라 예정 비행 감시 행에 연결된다. 같은 원본에 여러 ETD가 가능하므로 해제 대상 `alert_id`를 특정한다. 기존 확인 카드 설계를 유지하되 실행 토큰을 사용자·작업·대상·ETD·만료와 묶고 실행 시 권한을 다시 검사한다. 멱등 키로 중복 등록을 막으며 실패 후 모델이 임의로 재시도하지 않는다. API의 삭제/비활성화 fallback은 기존 서비스를 통해 재사용한다.

## 11. 초기 MCP 연결과 확장

### 11.1 PR 2: 같은 WSL의 Codex CLI

검증 환경은 이 프로젝트와 **같은 WSL Ubuntu에서 실행하는 Codex CLI**다. 로컬 MCP는 loopback으로만 접근 가능한 개발 인스턴스에 올린다. 예시 주소는 `http://127.0.0.1:3001/mcp`이며 이미 사용 중인 서버가 있으면 별도 포트를 사용한다. 기존 공유 서버의 바인딩이나 데이터 모드를 임의로 바꾸지 않는다.

공항 조회와 준비된 김포–제주 브리핑·상세 조회를 제공한다. 개인 데이터·알람 쓰기·화면 제어는 노출하지 않는다. 같은 서비스를 자체 챗봇에서도 재사용한다.

다음 명령은 `/mcp` 구현·기동 **이후에 실행할 연결 예시**이며, 이 문서 수정에서 서버를 등록하거나 시연을 실행했다는 의미는 아니다.

```bash
codex mcp add projectamo --url http://127.0.0.1:3001/mcp
codex
```

새 Codex 세션에서 `/mcp`로 서버 상태를 확인한다. Codex는 Streamable HTTP와 로컬 프로세스 STDIO를 지원하며, 공식 문서에도 localhost HTTP 예제가 있다. 이 프로젝트는 Express와의 재사용을 위해 로컬 HTTP로 시작한다. [Codex MCP 공식 문서](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

초기 시연 질문은 다음과 같다.

1. “ProjectAMO 도구로 제주공항 기상을 알려줘.” → 공항 도구 호출, 관측/예보·자료 시각 확인.
2. “준비된 김포–제주 시연 경로를 브리핑해줘.” → fixture ID로 실제 서비스 실행, 기준 시각·고정 조건 표시.
3. “그 브리핑의 SIGMET 근거를 보여줘.” → 직전 `briefing_ref`의 상세 조회, 같은 자료 ID 확인.
4. 자료 누락/예보 기간 밖 fixture와 불일치한 비행 조건으로 질문 → 추정하지 않고 해당 상태 설명.

완료 증거에는 질문, 실제 MCP 도구명·인자, 반환 digest, 최종 설명, 원자료와 대조한 결과를 남긴다. 셸로 저장 파일을 직접 읽은 답변은 MCP 검증으로 세지 않는다. 고정된 기준 시각·snapshot ID도 함께 기록한다. Codex의 모델·프롬프트가 최종 자체 챗봇과 다르므로 제품의 응답 정확도·비용·UI 검증을 대체하지 않는다. 로컬인 것은 MCP 연결이며 LLM 추론까지 로컬이라는 뜻은 아니다.

### 11.2 로컬에서 할 일과 공개 연결에서 할 일

HTTP와 stdio 등 전송 방식이 있으므로 “MCP는 반드시 공개 HTTPS가 필요하다”는 일반화는 피한다. 원격 클라우드 커넥터를 쓸 때는 해당 클라이언트가 접근할 수 있는 주소와 인증이 필요하다. [MCP 전송 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

로컬 PR 2에서도 Origin 검증, 본문 크기, 프로토콜 헤더, 오류 응답, 실행시간·동시성 제한을 구성한다. CLI 요청에는 Origin이 없을 수 있으므로 헤더 부재와 허용하지 않은 Origin을 구분한다. 기존 Express middleware를 공유하면 `/mcp` GET의 방문 집계 제외와 개발 자동 관리자 로그인 분기 분리도 이 단계에 포함한다. 독립 개발 entry를 사용하면 방문 통계/로그인 middleware를 아예 연결하지 않는다.

nginx·도메인·TLS·공개 접속 정책은 후속 공개 연결 단계에 둔다. 현재 nginx 예시에 `/mcp` 프록시가 없으므로 공개할 때 추가한다. compression과 proxy buffering/timeout은 해당 스트리밍 경로를 실제로 도입할 때 검증한다. 공개 준비가 로컬 시연의 선행 조건은 아니다.

OAuth를 도입해도 인가 서버를 반드시 직접 만들 필요는 없다. 기존 로그인과 연결 가능한 인가 서비스와 MCP의 리소스 서버 역할을 나눠 설계한다. MCP 세션 ID는 사용자 인증을 대체하지 않는다. [MCP 인가 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

도구는 작업 단위로 제한하고 결과의 간단/상세 모드를 나누는 방향을 유지한다. 다만 자료 ID는 근거 추적에 필요하므로 의미 있는 이름과 함께 보존한다. [Anthropic 도구 설계 가이드](https://www.anthropic.com/engineering/writing-tools-for-agents)

첫 PR 1A에는 모델 SDK, MCP, UI, 전체 경로 공용화를 넣지 않는다. 기존 `zod`를 활용해 공항/시간창 입력, 도구 결과, 자료 상태부터 확정하고 실제 저장 자료에서 digest 크기를 측정한다. 경보 없음과 조회 실패, TAF 시간창 미포함, UTC/KST, RVR 미보고, 재구성 원문을 fixture로 구분한다. PR 1B에서 준비된 경로로 브리핑 계산·요약을 추가하고 PR 2에서 두 종류를 로컬 MCP로 검증한다.

출시 검증은 정확한 도구 호출 문자열을 고정하기보다 기대 결과·필수 근거·금지 동작으로 평가한다. 동등한 호출 순서 차이를 허용한다. 최소 평가 세트에는 공항 정상/기간 밖, 부분 수집 실패, 누락 입력 멀티턴, 날짜 경계, 화면 경로 변경, 요청 취소, 참조 만료/타 사용자 접근, AIP 미확정/충돌, 자료 없는 고도, 도구 실패/예산 소진, 자유 텍스트 주입을 포함한다.

일반 기능 테스트와 LLM 평가를 분리한다. 구현 PR마다 해당 서비스 테스트와 UI 계약을 실행하고 통합 단계에서 `npm run check`와 관련 브라우저 검증을 완료한다. 경로 공용화를 시작하기 전 비교 fixture를 먼저 고정한다. 모델 변경 시 한국어·멀티턴·도구 정확도 평가를 다시 실행한다.

## 13. 다음 구현에서 정할 사항

검증 클라이언트는 같은 WSL의 Codex CLI, 전송은 로컬 HTTP로 정했다. 다음 구현에서는 김포–제주 fixture와 짝이 되는 기상 snapshot·기준 시각을 확인한다. 자체 챗봇 공급자/API 자격정보, 파일럿 사용자 범위와 비용 상한, 외부 전달·보관 정책은 해당 단계 전에 정한다. 자체 채팅 공급자 선택 없이도 도구·로컬 MCP 검증을 진행할 수 있지만 모델별 토큰·운영비는 미측정으로 남긴다. 질문당 비용·지연과 품질은 §9.6의 결과로 확정한다.

초기 MCP는 공항 기상과 준비된 경로의 브리핑 요약을 검증한다. 자체 챗봇은 현재 화면 경로로 확장하고, 서버 자동 경로 생성 이후에는 MCP도 임의의 지원 경로를 다룬다. 개인 알람, 공개 연결·외부 개인 데이터용 인가, 고급 대화/근거 기능은 후속 단계로 나눈다. 이 문서는 계획 수정이며 MCP 서버 구현·등록·실제 시연은 아직 수행하지 않았다.
