# 내 지도 — 실제 KMZ 두 파일의 목록·가져오기 검토

검토: 2026-09-19. 사용자가 제공한 로컬 원본을 읽기만 했다. 제품 구현은 변경하지 않았다.

[UI/UX 명세](2026-09-19-flight-map-ux-design.md) · [구현 계획](2026-09-19-flight-map-implementation-plan.md)

## 결론

두 파일 모두 현재 parseMyMapFile로 읽힌다. **시안과 같은 보기 패널을 사용하되, 목록의 항목은 원본 Placemark 단위로 유지해야 한다.** 렌더링용 도형 조각을 목록 행으로 그대로 사용하면 맥케이 지도에서 56,980행이 생긴다. 기존 파서의 결과를 그대로 새 목록과 편집 저장소에 연결하는 것으로는 충분하지 않다.

## 입력과 실제 구조

로컬 입력 위치:

~~~text
/mnt/c/Users/Jond Doe/Downloads/맥케이 비행지도 ver.230729.kmz
/mnt/c/Users/Jond Doe/Downloads/공역정보 지도자료 및 사용방법('26년 5차 AIP 기준)/공역정보(AIRAC AIP 5_26 기준).kmz
~~~

| 항목 | 맥케이 비행지도 | 공역정보 AIRAC AIP 5_26 |
|---|---:|---:|
| 압축 파일 크기 | 1,867,169 bytes | 714,871 bytes |
| 내부 파일 | doc.kml 하나 | doc.kml 하나 |
| 원본 지도 이름 | 맥케이 비행지도 ver.230729 | AIP 26년 5차 기준 |
| Folder 수 | 175 | 30 |
| Folder 중첩 깊이 | 최대 3단계 | 최대 4단계 |
| 원본 Placemark 수 | 2,135 | 754 |
| 현재 파서의 렌더링 feature 수 | 56,980 | 756 |
| 점 / 선 / 면 조각 | 1,491 / 39,319 / 16,170 | 0 / 316 / 440 |
| 변환 후 좌표 수 | 222,632 | 66,613 |
| 렌더링 GeoJSON JSON 크기 | 26,254,266 bytes | 4,198,715 bytes |

숫자는 압축 원본 XML과 현재 프로젝트 파서 결과를 각각 계산한 것이다. 원본 항목 수와 도형 조각 수는 서로 다른 수치이며 UI에 구분해 사용한다. 중첩 Document는 Folder 깊이에 포함하지 않았다. 파일명의 AIP 차수는 원본 식별 정보이며 최신성 검증 결과가 아니다.

## 보기 패널 예시

원본의 이름과 폴더를 이용하면 다음처럼 표시할 수 있다. 아래는 실제 항목 중 일부이며 전체 트리가 아니다.

~~~text
맥케이 비행지도 ver.230729
  RKTA TAEAN
    RKTA 출항절차
      마검포 abeam TRK360
      좌측 해안선 abeam
      안흥Range 침범 전 TRK360
    VFR POINT
    CROSS COUNTRY
  RKPD JEONGSEOK LOCAL
  AIRSPACE/AIRPORT/AIRBASE

AIP 26년 5차 기준
  1.Airspace_관제공역
    관제권
      CHEONGJU
      DAEGU
      GIMHAE
    관제구
  3.Airspace_통제공역([AIP차수])
    비행금지구역
    비행제한구역(2605)
~~~

처음에는 상위 폴더를 접어 보여주고, 펼침·검색으로 항목에 접근한다. 한 행 선택/표시 토글은 그 원본 항목에 속한 모든 지도 조각에 적용한다. 파일의 중첩 폴더를 읽는 것은 사용자에게 중첩 그룹 작성 기능을 제공하는 것과 구분한다. 편집본의 한 단계 그룹 규칙은 유지한다.

## 실제로 확인된 보완 사항

### 1. 원본 항목 ID와 렌더링 조각 ID 분리

맥케이의 SEL 항목 하나는 점 1개와 선 1,388개로 구성된다. 지도상 표현을 위해 여러 조각이 필요한 것이므로, 목록에 SEL을 1,389번 표시하면 안 된다. 현재 맥케이 변환 결과에서 id가 남은 feature는 1개뿐이라, 기존 ID만으로 모든 원본 항목을 다시 묶을 수도 없다.

XML/변환 경계에서 파일 내 안정적인 원본 항목 식별자를 부여하고 folderId·이름·설명·복수 기하를 보관한다. 렌더링을 분해할 때 sourceItemId를 모든 조각에 남긴다. 항목 이름이 같다는 이유만으로 합치지 않는다. 새 작성 도구는 여전히 점·선·면·원뿐이며, 복합 항목의 수치/형태 편집은 변환 미리보기에서 지원 범위를 알린다.

### 2. 상세 설명의 HTML 자료

공역정보의 754개 원본 항목 모두 설명을 가진다. 현재 파서는 이 설명을 문자열 대신 { @type: 'html', value: '...' } 형태로 반환한다. 예시 CHEONGJU의 표에는 Name_Txt, DistVertUpper_Val, DistVertUpper_UOM, DistVertUpper_Code, DistVertLower_Code, Class_Code 등이 있다.

description을 바로 input 또는 KML 문자열에 넣으면 객체가 잘못 표시되거나 원문이 손실될 수 있다. 원문을 보관하고, 보기 상세에는 안전하게 정리한 텍스트/속성 표를 사용한다. 원문 HTML을 그대로 실행하지 않는다. 이 파일의 고도 정보는 설명 표에도 있으므로 좌표 Z만 읽어 0ft로 확정하면 안 된다. Height/Surface 등 기준을 일괄 MSL로 바꾸지 않고 원래 값·단위·기준을 표시한다. 표를 자동 해석하지 못한 항목도 설명을 볼 수 있어야 한다.

#### 전체 메타데이터 대조 — 추가 확인

사용자가 메타데이터 조회를 필수로 지정하여 공역정보의 원본 754개 Placemark와 실제 파서 결과를 ID로 대조했다. HTML 표의 중첩 레이아웃을 제외한 필드명/값 쌍 10,497개, 필드명 25종을 추출했다. 렌더링 조각은 756개지만 고유 원본 ID는 754개이며, 원본 ID 누락과 추출 필드명/값 불일치가 모두 0건이었다. 공백을 정리한 표 내용의 비교이며 원문 HTML의 바이트 동일성을 검사한 것은 아니다.

| 내용 | 원본 필드 | 확인 범위 |
|---|---|---|
| 이름·식별·비고 | Name_Txt, Ident_Txt, Remarks_Txt | 전체 754개에 필드 존재, 값이 빈 항목도 있음 |
| 상한·하한 | DistVertUpper/Lower_Val, _UOM, _Code | 전체 754개에 필드 존재, 값·단위·기준을 함께 보관 |
| 공역 유형·등급 | Type_Code, Class_Code | 유형 440개, 등급 73개에 필드 존재 |
| 항로 유형·방위·길이 | RouteType_Code, TrueTrack_Val, MagTrack_Val, ReverseTrueTrack_Val, ReverseMagTrack_Val, Length_Val | 314개 항목에 필드 존재 |
| 원본 관리/공간 속성 | GFID, GlobalID, RuleID, SHAPE, 공역구분, SHAPE_Length, SHAPE_Area, Output_Name | 항목별 상이, 전체 속성에서 접근 가능하게 유지 |

예시 CHEONGJU의 원본은 상한 5000 / Feet / Height, 하한 값 없음 / 단위 없음 / Surface, 유형 Control Zone, 등급 D다. 현재 layersToFeatures 결과는 floorFt=0, ceilFt=0이므로 이 숫자를 상세에 표시하면 원본 메타데이터와 맞지 않는다. 파서에 설명이 남아 있다는 사실과 제품이 의미 있는 고도를 표시한다는 것은 별개다.

단위는 Feet, FT, Flight Level, FL 등이 섞여 있고 기준도 Height, Altitude, Surface, Ground, MSL, SFC, UNLTD, Unlimited 등이 있다. 임의로 모두 ft MSL로 통일하지 않는다. 길이처럼 단위가 해당 필드에 명시되지 않은 값에 NM 등을 추측해 붙이지 않는다. 빈 문자열·<Null>은 화면에서 ‘자료 없음’으로 표시하되 원래 표현을 보존하며 숫자 0과 구분한다.

상세 패널의 구현 계약:

아래 주요 정보 요약은 이 파일에서 확인한 형식에 적용한다. 공통 상세는 가변 속성표이며, 다른 KML에 공역 필드 양식을 강제하지 않는다. 알 수 없는 필드는 원래 이름/값으로 바로 표시하고, 글/표 설명·속성 없음·해석 실패를 구분한다. 상세 계약은 UI/UX 명세 FM-21을 따른다.

1. 항목 선택 시 이름·유형/등급·상한/하한·식별자·비고를 먼저 보여준다. 고도에는 값뿐 아니라 단위와 기준을 함께 표시하고, 확실하지 않은 기준은 원문 코드도 노출한다.
2. 항로 항목에는 항로 유형·정/역방향 진방위/자방위·길이 등 해당 원본에 있는 필드를 추가한다. 공역 양식에 맞추느라 항로 메타데이터를 숨기지 않는다.
3. ‘전체 원본 속성’을 펼치면 인식하지 못한 필드까지 원본 필드명/값으로 확인할 수 있다. 원본 HTML 자체를 실행하지 않고 표 내용만 안전한 UI로 렌더링한다.
4. 개인 메모·사용자가 수정한 도형 고도는 가져온 원본 속성과 구분한다. 스타일/이름/메모 수정으로 원본 속성을 덮거나 삭제하지 않는다.
5. 개인 편집본 생성·저장·기관 공유·KML 재내보내기에도 원본 속성/설명을 보존한다. 이름을 바꿔도 원본 식별자와 출처 연결을 유지한다. 재가져오기 후 이 표의 필드/값을 다시 대조한다.

전체 대조 실행은 artifacts/flight-map-design/audit-airspace-metadata.mjs와 audit-airspace-metadata.py, 결과는 airspace-metadata-audit.json에 있다. 이것은 로컬 추출·비교 검증이며 제품 상세 UI 구현 완료를 뜻하지 않는다.

### 3. 면의 내부 구멍

공역정보의 ‘비행정보구역 내 공해’는 현재 파서에서 링 3개인 Polygon으로 나온다. 바깥 링만 내보내는 /draw 경로로 보내면 내부 경계가 사라질 수 있다. 보기·변환·내보내기에서 전체 링을 보존하는 실제 표본으로 사용한다.

### 4. 용량과 목록 성능

편집용 layersToFeatures 결과의 JSON도 각각 23,992,302 / 4,145,446 bytes다. 현재 서버 1mb JSON 한도와 /draw의 localStorage 저장 방식에 그대로 넣을 수 있다고 가정하지 않는다. 복제된 설명/스타일을 원본 항목으로 모으고, 원본 파일·도메인 자료·렌더링 결과를 분리한다. 서버 한도와 복구 저장소는 정규화 후 크기로 결정한다.

목록은 접힌 폴더의 자식 행을 전부 렌더링하지 않는다. 실제 파일로 펼침·검색·선택·그룹 토글·undo 메모리를 확인하고 필요하면 보이는 행만 렌더링한다. 해석 성공이 지도 프레임 속도나 터치 조작 성능을 증명하지는 않는다.

## 구현에 반영할 완료 기준

- 두 파일을 열면 원본 지도 이름과 폴더 계층, Placemark 단위 목록이 나온다.
- SEL 선택/숨김은 해당 조각 전체에 적용되고 목록에는 한 행만 나온다.
- 공역정보 설명은 [object Object]가 아니라 읽을 수 있는 내용으로 표시된다.
- 복합 항목·내부 링·원문 설명을 원본 보존 없이 단순 도형으로 자동 덮어쓰지 않는다.
- 새 개인 지도로 변환할 때 지원/변환/제외와 예상 항목 수를 확인할 수 있다.
- 읽기 성능과 편집 저장 한도를 두 표본으로 따로 검증한다.

## 실행 기록과 한계

로컬 Node v22.23.1 + xmldom으로 실제 parseMyMapFile 및 layersToFeatures를 실행했다. 두 파일 모두 변환에 성공했다. 이번 실행의 파서 시간은 약 1.9초 / 0.2초였으며 단일 Node 실행 측정치로, 브라우저 렌더링 성능 수치가 아니다.

ignored 경로 artifacts/flight-map-design/ 아래 inspect-real-kmz.py, parse-real-kmz.mjs, real-kmz-structure.json, real-kmz-parser.json에 상세 기록이 있다. 원본 파일이나 전체 내용을 저장소에 복사하지 않았다. 라이브 Mapbox 표시·편집·저장·왕복 내보내기는 이번 확인 범위에 포함하지 않았다.
