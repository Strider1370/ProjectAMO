# 확대영역 실험 ACI 운영서버 실측 결과

2026-10-09. [적용 계획](2026-10-09-expanded-aci-implementation-plan.md)의 추가 검증 기록이다. 운영서버에서 독립 검증 작업을 실행했으며, 운영 수집기·API·지도 레이어에 ACI를 게시하거나 활성화하지 않았다.

## 결론

현재 3변수 실험식을 확대영역에 적용하면 **예보시각당 약2분21초, 하루 62개 시각에 약2시간26분의 추가 단일 worker 작업**으로 추산된다. **API는 하루186회, 응답 본문 약1.09GB 증가**한다. 원문 압축 캐시와 입력/결과 NC를2회차 보관하면 **약0.43~0.46GB**, Python 검증 환경의 추가 의존성은 별도로약0.4GB다.

계산 worker의 최대 RSS는 **350.5MiB**였다. 운영2vCPU 서버에서1코어만 사용했다. 과학 계산 표본 비교·기존 NC reader 호환 검사는 통과했다. 운영 적용은 가능성을 확인한 단계이며, 기존 무거운 작업과의 순차 실행·메모리 보호·게시시간 예산 연결이 필요하다. 배포 빌드와 무거운 계산을 동시에 실행하지 않는 조건이 중요하다.

## 환경·시험 범위

- 실제 AWS 운영VM: x86_64,2vCPU, RAM약1.9GiB, swap2GiB.
- 실제 운영 확대 입력: `KIMG_NE57_2026100900`, 90–160°E/6–50°N, **841×529=444,889개**.
- 시험 예보시각: **+0/+12/+24/+36h**. 총 **1,779,556개 격자를 생략 없이 계산**.
- 새 입력: q2m/pr/ulwrtoa를 각 시각마다 운영서버에서 실제API 호출. 지상기압ps와T/q/t2m은 운영 저장자료 재사용.
- 별도폴더: `/opt/projectamo/current/artifacts/aci-operating-check-20261009`.
- 독립Python3.12 환경. 운영 GKTG 환경의 NumPy2.5.3/Numba0.68.0를읽기 전용으로 재사용하고 MetPy1.7.1/h5py를 검증 환경에만 설치했다. 운영Python 환경은 변경하지 않았다.
- 1 worker,1 thread, CPU affinity1개, nice10. 기존 NC에서64×64 블록을 읽고 계산·합성·압축 저장했다.
- 최초 시험은 기존KIM 파생 작업과 겹쳤다. 중간에 별도 배포 빌드가 시작되어 본 시험만 종료하고, 빌드 완료 후+24/+36h를 다시 실행했다. 다른 배포/서비스를중단하거나변경하지 않았다.

## CPU·메모리·응답

- ACI는1개CPU코어에서실행했다. 계산중1코어를주로사용하여2vCPU 서버전체로는약50%에해당하는CPU부하다.
- 완결4개시험의worker 최대 RSS: **350.50MiB**. 입력수집/캐시파싱을독립Node로재생한최대 RSS는**154.3MiB**였지만HTTP를제외한캐시재생값이므로실제수집통합시의피크RAM이라고단정하지않는다.
- NumPy/Numba등을이미운영에설치한환경에서검증용MetPy/h5py등추가환경의디스크는약406MiB였다. 실제full-deploy시공유·중복설치방식에따라달라진다.
- 중간동시프런트엔드빌드에서전체서버MemAvailable가**47.5MiB**까지낮아지고swap사용이약1,047MiB까지올랐다. ACI시험만종료하고빌드완료뒤다시실행했다. 이수치는ACI단독요구메모리가아니며, 동시빌드에따른혼합부하다.
- 5초간격감시290개중3개에서health3초제한요청이실패했다. 2개는ACI가돌던구간,1개는외부배포의서비스재시작구간이었다. 단일타이밍비교로앞의2개를ACI만의원인으로확정할수는없다.
- 마지막 계산이끝난뒤약175초의36개감시에서는**실패0개**, health최대약**2.78ms**, MemAvailable최소약**1,056MiB**였다. 최종health도200이다.

따라서권장운영조건은GKTG·권계면·ACI를무거운worker동시1개로순차실행하고, 빌드/배포와배타적으로운영하는것이다. 블록시작전최소512MiB여유를확인하는보호조건을시험에넣었다. 메모리보호선은필요조건이며갑작스러운외부빌드를보장해막는장치는아니다.

## 추가저장·표시용량

- 새입력3개의원문gzip캐시는평균**2.686MB/시각**.
- 같은시각의입력3개+CAPE/CIN/점수/상태를압축NC로저장한최종평균은**4.314MB/시각**.
- 합계약**7.00MB/시각**. 29+33개회차보관이면**434MB**, 최대33개두회차면**462MB**추정.
- 점수만int16+gzip으로제공하면약**0.50MB/시각**실측이다. 기존수집/예보결과를저장해사용하므로지도열기·격자클릭때상류API를다시호출하지않는다.
- 위디스크에는의존성환경·JIT캐시·임시f32입력·새지도타일캐시를포함하지않는다. 의존성약0.4GB까지더하면추가지속디스크는대략**0.9GB**수준이다. 기존KIM저장용량과별도로예산을잡는다.

## 정확도·저장검증 및 수정한문제

전체격자는4시각에서모두계산했고, 과학 정확도는모든64×64블록에서고르게고른열과강한CAPE지점을포함해**4,459개 프로파일**을MetPy1.7.1과비교했다. 확대자료전체를MetPy로 전수재계산한시험은아니다.

발견/수정사항:

1. 한반도시제품의‘유효층12개이상’이라는임의제한이고산 지역의계산가능한프로파일을제외했다. MetPy의필수조건이아니므로제거하고, 충분한적분노드와150hPa상한/입력유효성을검증하도록수정했다. 고산지대회귀검사를추가하여테스트8개 통과.
2. 점수를1e-4단위로반올림하면경계직전값이상위색구간으로바뀌었다. 4시각에서총57개격자가영향을받았다. 기본색경계를유지하도록내림양자화로바꾸어저장색구간불일치를0개로만들었다. 양자화최대오차는1e-4미만이다. 계산점수와표시용인코딩을구분해야한다.
3. 부력이0근처인교차점은기존처럼MetPy로재확인했다. 4시각에서6,162개/1,779,556개(약0.35%)이며, 재확인시간을위생성시간에포함했다.

정상격자는각시각443,941/443,071/443,670/442,400개였다. 비정상CAPE는0으로대체하지않고상태2로남겼다. 현재실험은0~1점수이며운정고도/발생확률변환이나관측 기반 예측 성능 검증까지완료한것은아니다.

1. 새입력3종을확대수집의같은회차·예보시각작업에연결하고기존ps캐시를공유한다. 현재동시요청상한을유지한다.
2. compiled worker를기존무거운derived 작업의순차큐에연결하고revision재계산회피·메모리보호·부분실패게시를구현한다.
3. NC의자료형/상태/양자화정책과기존API의시각·영역선택을연결한다. 44만GeoJSON사각형전송을운영형식으로쓰지않는다.
4. 00/06UTC회차전체의게시완료시간과서비스응답을운영스케줄에서확인한후활성화한다. 이번시험은전체62개시각게시까지수행한것은아니다.

측정원본은로컬`artifacts/aci-operating-check/`와운영독립검증폴더에보관한다. 벤치마크및감시프로세스는종료했다. 운영서버에남은독립검증환경/결과는운영데이터에게시되지않은검토용산출물이다.

## 저위도 CB에 대한 목적과 검증 범위

2026-10-09 사용자 논의 기록. CAPE·강수·OLR를 결합하는 목적은 CB(적란운)와 같은 깊은 대류의 신호를 찾아 영역으로 표시하는 것이다. 저위도 CB도 탐지 대상에 포함된다. 현재 3변수 실험식 역시 CAPE와 강수강도가 높고 OLR가 낮을수록 점수가 높아지도록 그 목적에 맞춰 설계했다.

다만 보고서 원본 ACI를 그대로 재현한 식은 아니며, 현 임계값과 가중치는 실험 설정이다. 이번 검증으로 확인한 것은 수치 계산의 기준 알고리즘 일치, 실제 확대영역 입력 처리, 운영서버의 계산 시간·자원·호출·저장 비용이다. **저위도에서 실제 CB를 얼마나 정확히 탐지하는지는 아직 검증하지 않았다.**

후속 예측 성능 검증에서는 저위도의 실제 사례를 위성영상·낙뢰·가능한 레이더 관측과 비교한다. 넓게 높은 CAPE를 보이는 지역에서 CB 위치를 구분하는지, 낮은 OLR의 모루구름을 과대 표시하는지, 발생 위치·시각을 놓치는지를 확인하고 임계값과 가중치 보정 여부를 결정한다. 이는 탐지 목적 자체를 부정하는 것이 아니라, 해당 목적을 얼마나 잘 달성하는지 평가하는 별도 단계다.

현재 상태: 실험식의 목적·수치/운영 검증까지 기록 완료. 운영 수집기·API·지도에 자동 갱신 ACI를 활성화하는 작업과 관측 기반 탐지 성능 검증은 수행하지 않았다.

## 후속 최적화 검토: 적분 간격 (2026-10-09)

운영 실측에서 CAPE 계산과 경계 재확인이 생성 시간 대부분을 차지하므로, 적분 간격을 추가 비교했다. 원본 격자와 예보시각은 유지하고 **습윤 상승 ODE의 내부 기압 간격만** 바꾸는 시험이다. 이번 추가 비교는 로컬 실제 한반도 34,645개 프로파일을 사용했으며, 운영서버의 확대자료에서 재측정한 결과는 아니다. 기본 커널 간격도 아직 변경하지 않았다.

|---|---:|---:|---:|---:|
| 1hPa (현재) | 5.573초 | 0 | 0개 | 0개 |

| 10hPa | 1.855초 | 약1.32e-4J/kg | 0개 | 0개 |

5hPa에서 약2.48배, 10hPa에서 약3.00배 개선됐다. 경계의 MetPy 재확인은 각308개로 유지했다. 우선5hPa를 후보로 삼고 실제 확대영역의 따뜻하고 습한 저위도, 고산지역, 다른 회차에서 수치 비교·속도를 재측정한 후 채택한다. 이전 운영 생성 평균135초에 동일 비율이 적용된다면 약55초 수준이라는 단순 추정이 가능하지만, 실제 입력 읽기·재확인 비율·CPU 경합이 달라질 수 있어 운영 실측값으로 취급하지 않는다.

그다음 순서는 입력 revision/계산 버전 캐시로 반복 계산을 피하고, worker를 재사용해 반복 import/JIT 준비를 줄이며, 계산 단계의 NC 읽기를 블록/배열별로 묶는 것이다. 생성 시간 대부분이 CAPE인 현 상태에서는 I/O 미세 최적화보다 적분 비용 절감이 우선이다. 배포와 무거운 계산의 배타적 실행 및 메모리 보호는 속도 최적화와 별개로 적용해야 한다.

추가 원본 측정은 `artifacts/aci-capacity/step-comparison.json`에 기록했다.

## 20hPa 채택 후 전체 확대영역 재측정

사용자 요청에 따라 실험 커널의 기본 내부 적분 간격을 **20hPa(2000Pa)**로 변경했다. 운영 수집기에는 활성화하지 않았다. 운영서버의 독립 검증 폴더에서 2026-10-09 00UTC +12h, 841×529=444,889개 격자를 1 worker로 전부 계산했다. 입력은 기존 캐시를 사용했다.

| 항목 | 실측 |
|---|---:|
| ACI 생성(입력 읽기·계산·NC 저장·시작 비용 포함) | **41.23초/예보시각** |
| 이 중 CAPE 커널·경계 재확인 | 34.43초 |
| 검증 계산까지 포함한 시험 전체 | 56.81초 |
| 최대 RSS | 340.38MiB |
| MetPy 비교 표본 | 1,118개 |
| 유효 판정·허용 오차 초과·색 구간 불일치 | 각각0개 |
| 최대 CAPE 차이(MetPy 대비) | 0.03339J/kg |
| 0.5hPa 대비 최대 CAPE 차이 | 0.00213J/kg |

기존 실측의 새 입력3종 수집·파싱·캐시 저장 평균6.01초를 더하면 **ACI 추가 처리 약47.25초/예보시각**이다. 같은 비용을 회차 전체에 적용한 추정은 다음과 같다.

| 확대영역 회차 | 예보시각 수 | ACI 추가 시간 추정 | 기존 GKTG·권계면까지 순차 합산한 처리 시간 추정 |
|---|---:|---:|---:|
| 00UTC | 29개 | **약23분** | 약2시간12분 |
| 06UTC | 33개 | **약26분** | 약2시간30분 |

전체 합산은 기존 신규 생성 평균 GKTG186.37초+권계면38.55초와 ACI47.25초를 합한 약272.17초/예보시각 기준이다. 기존 KIM 원본 다운로드 시간은 이 전체 합산에 포함하지 않았다. 수집·계산의 병렬 실행이나 캐시 재사용에 따라 실제 게시 완료 시간은 달라진다. **20hPa에서 실제 수행한 것은 예보시각1개의 전체 확대영역이며, 29/33개 회차를 전부 돌린 실측은 아니다.** 이전 1hPa 생성 평균135.14초 대비 이번 생성41.23초는 약3.28배 빠르지만 비교 예보시각 수가 다르다.
