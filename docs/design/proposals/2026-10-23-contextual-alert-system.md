# 통합 알림 구현 계획 — 공항·경로 패널에서 설정, 종 아이콘에서 확인

> 구현 현황(2026-10-24): 공항·경로 판정의 단일 주기 실행기와 기기별 푸시 대기열, 한 알림 패널의 개인·기관 목록, 공항·경로 설정 진입, 모의 수신 시험이 연결되었다. 기존 예정 비행 감시의 등록·발송과 상황판의 독립 알림 판정·팝업·소리는 중단하고 옛 예정 비행 이력은 읽기 전용으로 보관한다. 기관의 판정·저장소는 별도이며 공항·경로 이벤트 테이블도 아직 물리적으로 분리되어 있어 아래의 단일 저장소 목표는 남아 있다. 운영 배포와 실기기 수신 확인도 아직 수행하지 않았다.

작성일: 2026-10-23. 이 문서는 구현 계획이며, 현재 배포 상태를 뜻하지 않는다.

## 교체 원칙과 범위

서버·자료 수집·공개 사이트의 장애를 관리자에게 알리는 **시스템 운영 알람**(`backend/src/alerts/ops-alerts.js`, `ops-rules.js`, `alerts_sent`)은 그대로 독립 운영한다. 이 문서의 "통합 알림"은 개인·기관·상황판의 **사용자용 기상 알림**을 뜻한다. 시스템 운영 알람의 판정, 발송 대상, 발송 주기는 바꾸지 않는다.

현재 개인 공항 감시(`backend/src/airport-alerts/`), 예정 비행 알림(`backend/src/alerts/scheduler.js`, `diff.js`), 상황판의 브라우저 알람(`frontend/src/features/monitoring/legacy/utils/alerts/`), 기관 관심대상 알림(`backend/src/organizations/situation.js`의 저장·상태 경로)은 최종적으로 새 사용자 알림 시스템으로 교체한다. 기존 `NotificationCenter`, 개인 알림 페이지, 공항 팝업과 기관 알림 화면은 새 시스템의 UI로 바꾸거나 제거한다. 날씨 수집기·파서, 공항경보/낙뢰 데이터, 지도·공항·경로의 **정보 표시 기능**은 알림 엔진이 아니므로 유지한다. Web Push 전송과 구독 관리도 기반 기능으로 재사용할 수 있다.

최종 상태에는 사용자 알림의 **설정 저장소, 이벤트 저장소, 중복 방지, 발송기, 읽음/종료 규칙이 하나씩** 존재해야 한다. METAR·TAF·경보·낙뢰·SIGMET은 그 시스템에 입력되는 종류별 판정기다. 이후 추가되는 사용자 알림도 이 경로로만 구현한다. 기관 알림은 같은 코어를 쓰되 `organization` 소유 범위와 구성원별 확인 권한을 유지한다. 기관 소속 사용자에게만 알림 패널의 `기관` 필터를 노출한다. 상황판이 계속 알림 표를 표시한다면 자체 판정기 대신 새 이벤트의 읽기 전용 화면이 된다.

"다 지운 다음 만들기"는 **완성된 코드의 상태**로 적용한다. 작업 중에는 새 시스템을 발송 없이 검증하고, 한 종류당 발송 주체를 하나로 전환한 뒤 옛 코드를 제거한다. 그래야 알림 공백과 이중 발송을 피할 수 있다. 오래된 발생 이력은 읽기 전용으로 보관하고 운영 알람 기록은 건드리지 않는다.

## 결정한 사용자 경험

알림은 새 독립 페이지가 아닌 앱 안의 패널에서 확인·설정한다. 종 아이콘은 어디서나 알림 진입점이다. 누르는 즉시 감시 상태를 바꾸지는 않는다.

| 진입 위치 | 버튼 | 처음 열리는 화면 | 닫거나 뒤로 갈 때 |
| --- | --- | --- | --- |
| 데스크톱 사이드바·모바일 상단 | 종 `알림` + 안 읽은 건수 | 전체 알림 패널의 `진행 중` | 이전 지도·패널 맥락으로 복귀 |
| 공항 패널 | 종 `이 공항 알림` + 감시 상태 | 해당 ICAO의 설정 편집 | 보던 공항 탭과 스크롤 위치로 복귀 |
| 경로 생성 결과 | 종 `이 경로 알림` + 감시 상태 | 현재 확정 경로의 SIGMET 감시 편집 | 경로 입력값과 결과를 유지하며 복귀 |

알림 패널의 첫 화면은 `진행 중`과 `지난 알림` 전환, `알림 설정` 버튼으로 구성한다. 설정 화면은 `감시 공항`과 `감시 경로` 목록을 보여준다. 목록에서 대상을 선택하거나 공항을 추가하면 위의 맥락별 진입과 **같은 편집 컴포넌트**를 연다. 경로 추가는 경로 생성 패널로 연결한다. 설정 편집 상단에는 `← 알림으로` 또는 `← 공항 정보`처럼 실제 복귀 위치를 표시한다. 로그인하지 않았다면 로그인 후 원래 대상의 설정으로 돌아온다.

데스크톱은 지도 옆 한 자리의 우측 패널, 모바일은 화면을 채우는 패널로 표시한다. 공항·경로 패널과 알림 패널을 나란히 중첩하지 않는다. 알림 패널을 열 때 기존 패널 상태는 유지하고 화면에서만 교체한다. 알림 행을 누르면 알림 패널을 닫고 해당 공항 또는 경로의 **정확한 섹션과 발생 당시 자료**를 연다. 브라우저 새로고침·OS 푸시 탭도 같은 결과가 나와야 한다.

종 아이콘은 `BellRing` 하나로 통일한다. 전체 진입점의 숫자는 안 읽은 건수만 뜻한다. 공항·경로 버튼은 `감시 중` 또는 `미설정`을 글자로 표시하며 숫자 배지를 쓰지 않는다. 아이콘만 있는 화면에도 접근 가능한 버튼 이름과 툴팁을 준다. 모바일 `더보기`의 업데이트 아이콘은 종과 겹치지 않게 바꾼다.

## 화면별 버튼과 상태

### 알림 패널

1. 종 `알림` → `진행 중` 목록. 행은 `대상명 / 발생 종류와 근거 / 발생 시각` 순서. METAR 여러 항목은 한 이벤트에 모두 표시한다. TAF는 `새 발표` 또는 `AMD`, SIGMET은 현상과 유효기간을 표시한다.
2. `지난 알림` → 해소·만료·대체된 이력. `읽음`은 종료와 별개다. `모두 읽음`은 읽음 상태만 바꾼다.
3. `알림 설정` → 감시 공항·경로 목록. 각 대상에 `설정`, `일시정지/재개`, `삭제`를 제공한다. 삭제는 대상 감시만 종료하고 발생 이력은 보존한다.
4. 알림 행 → 해당 정보 패널. METAR는 공항 METAR, TAF는 해당 발표의 TAF 전문, 공항경보·낙뢰는 공항의 해당 정보, SIGMET은 해당 경로 브리핑의 SIGMET 위치를 연다. 대상이 삭제돼도 저장한 이벤트 상세를 읽을 수 있어야 한다.
5. PC 팝업의 `X`는 팝업만 닫는다. 진행 중 이벤트는 목록에 남는다. 팝업을 누르면 알림 행과 동일하게 이동한다.

`진행 중`의 종류별 정의: METAR는 조건이 해소되지 않은 동안, 공항경보·SIGMET은 유효하고 대상에 해당하는 동안, 낙뢰는 설정한 관측 시간창에 해당하는 동안이다. TAF 발표는 최신 유효 발표인 동안 표시하고 대체·만료 시 이력으로 이동한다. 자료 누락·지연은 `해소 확인 불가`로 보여주며 정상 해소로 처리하지 않는다.

### 공항 패널의 알림 편집

공항 패널 상단에 종 `이 공항 알림`을 둔다. 버튼은 그 공항의 편집 화면을 열며 즉시 켜고 끄지 않는다. 모바일에서 헤더가 좁으면 공항명 아래의 짧은 작업 줄에 둔다. 편집 내용은 다음 네 묶음이다.

- `METAR 관측`: 시정·운고·풍속·돌풍·기온은 각각 사용 스위치, 기준값, 단위와 비교 방향을 한 줄에 표시한다. 급변풍 및 FZRA는 발생 여부 선택이다. 기본값은 입력 예시이지 저장 전 감시 활성화가 아니다.
- `TAF 발표`: `새 TAF`, `TAF AMD` 스위치. 예보 악화 해석이나 TAF 임계값은 넣지 않는다.
- `공항경보·낙뢰`: 각각 사용 스위치. 낙뢰를 켰을 때만 반경 km, 최근 분, 최소 건수를 편집한다.
- `받는 방법`: 웹이 열려 있을 때 PC 팝업, 웹 푸시 사용 여부, 이 기기의 권한·구독 상태. 계정 설정과 기기 권한은 별개임을 상태 문장으로 설명한다.

하단 주 버튼은 미등록 시 `저장하고 감시 시작`, 등록 시 `변경사항 저장`이다. `알림 띄워보기`는 현재 편집값으로 모의 내용을 보여주지만 실제 이벤트에는 저장하지 않는다. 저장한 감시는 종류별 `실제 수신 테스트`도 제공한다. 휴대폰의 테스트 푸시는 현재 기기 구독에만 발송한다. 저장하지 않은 변경사항이 있으면 이탈 시 알리고, 저장 성공 후 공항 패널로 돌아가면 `감시 중` 상태가 즉시 반영된다.

### 경로 생성 패널의 알림 편집

경로선이 확정된 결과·저장 작업 근처에 종 `이 경로 알림`을 둔다. 경로선이 없으면 비활성화 이유를 표시한다. 누르면 현재 경로의 이름, 출발·도착 시각, 계획 고도, 감시 시작 시점, SIGMET 감시 여부를 확인하는 편집 화면이 열린다. 주 버튼은 `이 경로 감시 시작`이다. 신규 경로는 로그인한 계정에 경로 스냅샷을 저장한 뒤 감시를 등록한다. 게스트는 로그인 후 동일한 경로 초안으로 돌아온다. 이미 감시 중인 경로를 편집했다면 `감시 경로 업데이트`를 명시적으로 선택하게 하며, 현재 감시가 참조하는 경로와 새 초안을 혼동하지 않게 표시한다.

현재 `routeStore.saveRoute()`는 **로그인 시 서버**, 게스트일 때 로컬에 저장한다. 앞서 로컬에만 저장된다고 설명한 것은 잘못이었다. 새 경로 감시는 로그인 계정의 서버 저장 경로 스냅샷을 참조하되, 기존 `POST /api/me/alerts`와 옛 예정 비행 스케줄러에 의존하지 않는다. 새 시스템에서 한 사용자의 여러 활성 경로를 각각 평가하도록 만든다. 경로별 ETD·ETA·고도·설정 상태를 분리하고, 경로 수정은 사용자가 `감시 경로 업데이트`를 눌렀을 때만 감시에 반영한다.

## 실제 알림의 내용과 이동

| 종류 | PC 팝업·알림 목록에서 우선 보일 내용 | 도착 위치 |
| --- | --- | --- |
| METAR | 해당한 **모든** 항목의 관측값·설정 기준, 관측 시각 | 해당 공항 METAR 섹션 |
| FZRA | `어는 비(FZRA) 관측`, 관측 시각 | 해당 공항 METAR 섹션 |
| TAF/AMD | 발표 종류·발표/유효 시각·TAF 전문 | 해당 공항 TAF 섹션의 그 발표 |
| 공항경보 | 경보명·발효/종료 시각 | 해당 공항 경보 섹션 |
| 낙뢰 | 반경·최근 관측 시간·건수·가장 가까운 거리(있을 때) | 해당 공항 낙뢰 정보 |
| SIGMET | 경로명·현상·유효기간·겹치는 구간 | 해당 경로의 SIGMET 표시 |

TAF 전문은 이벤트 생성 시 문자열과 자료 출처를 보관한다. 국내 IWXXM 자료는 TAC을 서버가 재구성하므로 `재구성 전문`, 실제 TAC 원문이 있는 자료는 `원문`으로 표기한다. PC 팝업은 긴 전문을 내부 스크롤로 끝까지 읽게 한다. 웹 푸시의 본문에도 가능한 범위의 전문을 전송하되 OS 잠금화면의 표시 길이는 앱이 제어할 수 없다. 푸시를 탭하면 저장된 전문 전체가 열리는 것을 필수 계약으로 둔다. SIGMET도 클릭 시 최신 자료가 바뀌었더라도 발생 당시 현상·유효기간·구간을 확인할 수 있게 이벤트 스냅샷을 남긴다.

딥링크는 별도 알림 페이지 경로를 만들지 않고 `/?alert=<event-id>` 형태로 둔다. 앱이 이벤트 상세를 사용자 권한으로 조회해 적절한 기존 패널을 연다. 현재 `?airport=...`가 공항 패널의 기본 경보 섹션만 여는 문제를 해결하고, 탭/섹션과 해당 보고 식별값을 전달한다. 기존 `/alerts`, `/alerts/settings` 링크는 패널을 여는 형태로 연결하거나 호환 리다이렉트를 둔다.

## 새 사용자 알림 시스템의 구조

```text
기상 자료 게시·갱신
    → 종류별 판정기(METAR/FZRA, TAF, 경보, 낙뢰, 경로 SIGMET)
    → 공통 이벤트 서비스(원자료 식별·중복 방지·상태 변경)
    → 공통 이벤트 저장소
    → 수신 서비스(앱 패널·PC 팝업·웹 푸시)
```

`backend/src/user-alerts/`를 새 사용자 알림 도메인의 소유자로 만든다. 자료 수집기와 브리핑의 기존 기상·경로 계산은 읽기 전용 입력으로 재사용하되, 옛 알림 판정기나 이력 테이블에 새 기능을 추가하지 않는다. 종류별 판정기가 하나의 거대한 조건문이 되지 않게 독립 모듈로 나누고, 이벤트 생성·해소·발송은 공통 서비스만 호출한다. 서버가 발행한 **동일 이벤트 ID**를 패널·팝업·푸시가 사용한다. 화면이나 채널이 조건을 재판정하지 않는다.

새 저장 모델은 역할을 분리한다.

| 저장 대상 | 주요 내용 |
| --- | --- |
| `user_alert_watches` | 소유 범위(`user` 또는 `organization`), 대상 종류·ID, 활성/일시정지, 종류별 규칙, 수신 설정, 경로 스냅샷 버전. |
| `user_alert_watch_state` | 자료별 마지막 평가·소스 상태, TAF 마지막 발표, METAR 조건 상태, 활성 SIGMET ID 등 재시작 후에도 필요한 기준. |
| `user_alert_events` | 불변 이벤트 ID, 종류, 대상, 원자료 키, 발생 당시 값/전문, 관측·발표·감지시각, 유효기간, 활성/종료와 종료 이유. `watch + kind + sourceKey`의 유일성으로 중복 생성 방지. |
| `user_alert_recipient_state` | 개인 또는 기관 구성원의 읽음·확인·숨김 상태. 읽음과 현상 종료를 혼동하지 않는다. |
| `user_alert_deliveries` | 이벤트·채널·기기별 발송 시도와 결과. 실패 후 재시도할 때 같은 이벤트를 중복 생성하지 않는다. |
| `user_alert_test_runs` | 실행 사용자·감시·시나리오·모의 입력·판정/발송 결과·만료시각. 시험용 평가 상태와 이벤트 ID를 실제 감시 상태와 분리한다. |

`push_subscriptions`와 Web Push 전송 함수는 기반 설비로 유지한다. 서버·자료 장애 알람은 위 테이블에 저장하지 않는다. 운영 알람이 현재 옛 `alerts/sender.js`의 `sendTelegram()`을 가져오는 의존성은 운영 전용 전송 모듈로 옮긴 뒤 옛 경로 발송기를 삭제한다. 운영 알람의 텔레그램 내용과 발송 동작은 변경하지 않는다.

종류별 판정 계약은 다음과 같다.

- **METAR 수치·FZRA:** 신선한 새 관측에서 설정한 조건에 진입하면 한 번 생성한다. 같은 관측의 여러 수치 초과는 한 이벤트에 모두 보관한다. 관측 누락은 정상 해소가 아니다. 해소 후 다시 진입하면 새 이벤트다. 감시를 막 켰을 때 현재 관측이 이미 기준에 해당하면 `현재 조건 해당`으로 표시한다.
- **TAF:** 최초 평가의 기존 보고는 기준점으로만 기록한다. 이후 새 정시 TAF나 AMD의 `공항 + 발표시각 + 종류 + 전문 식별값`이 바뀌면 생성한다. 전문과 유효기간은 이벤트에 보관한다. 국내 재구성 TAC과 원문 TAC을 구분한다. 예보 악화 판정은 하지 않는다.
- **공항경보:** 공항·경보 원자료 ID·발표시각을 키로 발효 중인 신규 경보만 생성한다. 기한 만료 또는 확인된 해제에 종료한다.
- **낙뢰:** 설정 반경·시간창·최소 건수 진입 시 생성한다. 관측 범위가 완전하게 확인될 때만 해소하고, 불완전하면 `확인 불가`로 둔다.
- **SIGMET:** 저장 경로의 실제 영역 교차와 유효 시간 겹침을 확인한다. 고도 범위가 있으면 계획 고도와 비교하고, 고도 자료가 없으면 이를 명시한다. 브리핑의 30NM 주변 범위를 그대로 `경로와 겹침`이라고 부르지 않는다. 발표 ID·유효기간·해당 경로를 키로 중복 방지한다. 경로 감시 시작 시 이미 유효한 SIGMET은 `현재 유효`로 알린다.

설정 변경·일시정지·삭제는 기상 현상이 `정상 해소`됐다는 뜻이 아니다. 이때 열린 이벤트는 `설정 변경/감시 중단` 사유로 종료하거나 상태 확인을 중단하고, 이력과 원래 발생 근거를 보존한다. 기관 확인(acknowledge) 역시 현상의 종료와 분리한다. 시각은 UTC/epoch로 저장하고 사용자가 선택한 시간대로 표시한다. 소스가 지연됐을 때는 마지막 유효 자료를 유지하며 상태를 패널에 표시한다.

## 구현 위치와 API

**백엔드**

- 새 `backend/src/user-alerts/`: watch 계약·검증, 종류별 평가 어댑터, 이벤트 저장/종료, 수신 대상 결정, 전달, 상태 조회. 기존 `backend/src/briefing/`의 경로 교차·시간/고도 계산과 `backend/src/organizations/situation.js`의 낙뢰·경보 자료 해석은 **판정 라이브러리로만** 필요한 부분을 추출한다. 기관 알림 저장·전달은 새 코어로 옮긴다.
- `backend/src/db/schema.sql` 및 마이그레이션: 새 watch/state/event/recipient/delivery 테이블. 옛 `airport_alert_watches`, `airport_alert_events`, `triggered_alerts`, `organization_alerts`는 전환 완료까지 읽기 전용으로 보존한다.
- `backend/server.js`: 새 스케줄러 시작 지점 하나. 종류별 평가 주기는 자료 갱신 주기에 맞추되 발송 소유자는 새 시스템 하나로 고정한다. 운영 `startOpsAlerts()`는 별도로 그대로 둔다.
- `backend/src/me/`와 기관 API: 아래 새 API에 소유자·구성원 권한을 적용한다. 기존 `/api/me/alerts`와 `/api/me/notifications`는 전환 중 호환용으로만 두고 이후 호출자를 새 API로 옮긴다.

**프런트엔드**

- 새 `frontend/src/features/user-alerts/`: 전체 알림 패널, 공항·경로 공통 설정 편집기, 이벤트 행/상세, 팝업, 테스트 미리보기, 동일 이벤트 포맷터. 기존 `NotificationCenter`, `AirportAlertPopup`, 공항 알림 독립 페이지를 점진적으로 교체한다.
- `frontend/src/app/App.jsx`: 패널 상태 `{view, target, returnContext}`와 `/?alert=<event-id>` 딥링크 처리. 공항·경로·알림 패널은 한 번에 하나만 보이고 이전 편집 맥락은 유지한다.
- `frontend/src/app/layout/Sidebar.jsx`, `MobileMoreMenu.jsx`, 모바일 지도 작업 영역, `AirportPanel.jsx`, `RouteBriefingPanel.jsx`/`MapView.jsx`: 같은 종 아이콘과 대상별 진입 액션. 기존 날씨 표시 탭·지도 화면은 유지한다.
- `frontend/public/sw.js`: 푸시 클릭 시 새 이벤트 ID로 앱을 열어 그 이벤트의 정확한 공항/경로 정보를 보여준다. 잠금화면에서 TAF 전문 전체가 보이지 않아도 앱에서 보관된 전문을 끝까지 읽는다.
- `frontend/src/features/copilot/`의 비행 알림 등록 도구, 관리자 감시 화면, 브리핑 변경 띠, 상황판·기관 화면: 옛 저장소를 직접 읽거나 판정하지 않고 새 API/이벤트를 사용하게 바꾼다.

새 API의 경로는 옛 `/api/me/alerts`와 충돌하지 않게 분리한다.

| 요청 | 역할 |
| --- | --- |
| `GET/POST /api/me/alert-watches`, `PATCH/DELETE /api/me/alert-watches/:id` | 여러 공항·경로 감시 조회·생성·수정·중지. 대상 소유권과 설정값 검증. |
| `GET /api/me/alert-events?state=active|history`, `GET /api/me/alert-events/:id` | 패널 목록·딥링크·발생 당시 TAF/SIGMET 상세. 읽음 수와 소스 상태 포함. |
| `POST /api/me/alert-events/:id/read`, `POST /api/me/alert-events/read-all` | 수신자 읽음 상태만 변경. |
| `POST /api/me/alert-preview` | 저장하지 않은 편집값의 화면 미리보기. 실제 수신·판정 시험은 하지 않는다. |
| `POST /api/me/alert-tests` | 저장된 감시와 허용된 시나리오로 운영서버에서 본인 대상의 실제 수신 시험을 실행한다. |
| 기관 범위의 동등한 `/api/organizations/:id/alert-*` | 같은 코어를 쓰되 기관 권한·구성원별 확인/숨김 상태 적용. |

통합 이벤트 응답에는 `id`, `kind`, `ownerScope`, `targetType`, `targetId`, `title`, `detectedAt`, `sourceObservedAt/issuedAt`, `validFrom/validTo`, `active`, `endedReason`, `readAt`, 종류별 `payload`가 있다. `payload`는 표시·검증에 필요한 발생 당시 정보만 담고, 무제한 원자료 객체를 복사하지 않는다. 클라이언트는 `readAt`으로 진행/종료를 분류하지 않는다.

## 운영서버에서 사용자가 직접 하는 수신 테스트

실제 기상 현상이 없더라도 운영 사이트의 로그인 계정에서 **종류별 `실제 수신 테스트`**를 실행할 수 있게 한다. 공항·경로 설정에서 저장한 감시를 열고 `테스트`를 누르면 감시 중인 종류와 시나리오를 고른다. 예를 들어 METAR는 `설정 기준 초과`, TAF는 `새 발표`와 `AMD`, 공항경보는 `신규 발효`, 낙뢰는 `반경·건수 충족`, SIGMET은 `내 경로와 교차`를 선택한다. FZRA도 별도 시나리오를 둔다. 서버는 사용자의 **현재 저장된 기준**을 읽어 초과값을 만들고, 선택한 경로의 저장 스냅샷을 사용한다. 따라서 어떤 기준을 설정했든 실제 현상을 기다리지 않고 그 설정의 발동 결과를 볼 수 있다. 발동하지 않아야 하는 경계값·경로 비접촉 시나리오도 제공해 `알림 없음`을 정상 결과로 확인한다.

이 테스트는 문자열만 보여주는 미리보기와 구분한다. 서버가 승인된 고정 시나리오를 **실제 종류별 판정기 → 공통 이벤트 생성 → 실제 앱/PC 팝업·푸시 발송기 → 클릭 딥링크**에 통과시킨다. TAF의 `새 발표`/`AMD` 시나리오는 시험용 최초 보고로 기준점을 만든 다음 다음 발표를 평가한다. 시험 입력·평가 상태는 `user_alert_test_runs`에 격리하고, 생성한 시험 이벤트에는 `testRunId`와 `test=true`를 붙인다. 운영 기상 캐시와 실제 watch 평가 상태는 바꾸지 않고, 다른 사용자의 감시나 기관 전체 발송도 실행하지 않는다. 시험 이벤트는 소유자 본인에게만 보낸다. 푸시는 요청한 현재 기기의 구독만 대상으로 하며, 다른 기기로 보내려면 그 기기에서 테스트를 실행한다. 계정 권한, 구독 소유권, 요청 빈도, 같은 시험의 중복 실행을 서버에서 검사한다. 외부에서 임의의 기상 값·수신자·푸시 주소를 API로 지정할 수 없고, 운영 알람과 관리자 발송 경로에도 닿지 않는다.

화면에는 발송 전부터 제목과 본문에 **`테스트 · 모의 자료`**를 붙이고, 팝업·푸시·도착 패널에도 유지한다. 딥링크는 시험 이벤트 ID로 해당 공항·경로 패널을 열고 **시험 당시의 모의 자료 스냅샷**을 표시한다. 옆에 실제 기상자료가 있다면 `현재 실황`과 명확히 구분한다. 시험 이벤트는 실사용 `진행 중`·`지난 알림` 목록, 안 읽은 배지, 실제 발송 통계에 섞지 않는다. 설정 화면에는 마지막 시험의 `판정 결과 / 앱 표시 / 푸시 발송 결과`와 `시험 알림 다시 보기`를 짧게 보여준다. 시험 기록과 딥링크는 제한된 기간(예: 24시간)만 유지하고 자동 정리한다. OS에 실제로 표시됐는지는 서버의 발송 성공만으로 단정하지 않고 사용자가 기기에서 수신·탭을 직접 확인한다.

구현 API는 `POST /api/me/alert-tests`로 별도 두고 `watchId`, 허용된 `scenarioId`, 현재 기기의 구독 식별자만 받는다. 응답에는 시험 ID, 예상/실제 판정, 이벤트 ID, 채널별 발송 결과를 돌려준다. 미저장 편집값은 `alert-preview`의 화면 미리보기로만 확인하고, 실제 수신 테스트는 저장된 감시 기준으로 실행한다. 기관 감시는 구성원에게 번지는 시험을 막기 위해 개인 시험 대상만 만들고, 기관 전체 발송 시험은 별도 권한과 절차가 정해질 때까지 제공하지 않는다.

## 전환 순서와 완료 기준

1. **영향 조사와 운영 알람 분리.** 실제 활성 개인·기관 감시 건수와 소비자를 파악하고 옛 이력을 백업한다. 운영 알람의 `sendTelegram` 의존성을 옮겨 운영 알람 테스트를 통과시킨다. 새 엔진으로 옮길 수 없는 설정은 재등록 대상으로 식별한다. 완료 기준: 운영 알람의 판정·발송 결과가 전환 전과 같다.
2. **새 공통 코어.** 새 DB·watch/event/recipient/delivery 서비스와 소유권 검사, 재시작 가능한 상태·중복 방지를 만든다. 실제 발송은 끈 상태로 기존 자료와 테스트 fixture를 평가한다. 완료 기준: 동일 자료 재수집·재시작에서 중복 없이 같은 이벤트를 만들고, 소스 누락을 해소로 오인하지 않는다.
3. **패널과 첫 공항 세로 흐름.** 종 아이콘 3곳, 전체 패널·공통 편집기, METAR 수치 한 종류를 새 코어에 연결한다. PC 팝업·앱 목록·푸시가 하나의 이벤트 ID를 쓰는지 확인한다. 완료 기준: 공항에서 설정하고 전역 종에서 같은 감시를 보며, 모바일에서 페이지 이동 없이 돌아온다.
4. **공항 종류 완성.** METAR 동시 항목·FZRA, TAF 새 발표/AMD·전문 스냅샷, 공항경보, 낙뢰를 새 코어에 올린다. 종류별로 옛 발송을 끄고 새 발송을 켜는 전환점을 둔다. 완료 기준: 여러 공항의 다른 설정, 해소·재발, 지연 자료, TAF 중복/이력, 경보·낙뢰 유효성을 통과한다.
5. **경로 SIGMET.** 경로 생성 패널과 새 감시 API를 연결하고, 각 활성 경로의 영역·시간·고도를 평가한다. 옛 예정 비행 엔진의 다른 알림 종류는 새 시스템에 옮기지 않는다. 완료 기준: 여러 경로가 각각 평가되고, 경로 수정·재시작 뒤에도 중복이나 누락이 없으며 주변 범위를 `겹침`으로 오표기하지 않는다.
6. **기관·상황판과 부가 소비자.** 기관별 권한·확인/숨김, 상황판 읽기 전용 보기, Copilot·관리자 화면·브리핑 변경 띠를 새 API로 옮긴다. 완료 기준: 개인 이벤트가 다른 사용자/기관에 보이지 않고, 기관 상태는 구성원별로 유지된다.
7. **실기기 검증 후 옛 시스템 제거.** 새 엔진을 발송 없이 기존 판정과 비교한 기록을 검토하고 종류별 발송 소유권을 전환한다. PC·Android·iPhone 홈 화면 웹앱에서 수신·탭 이동·권한 거부·오프라인 복귀·만료 구독을 확인한다. `/alerts` 등 옛 링크는 패널을 여는 호환 경로로 처리한다. 옛 사용자 알림 스케줄러, 프런트 판정기, 저장/표시 중복 코드를 삭제한다. 완료 기준: 코드 검색상 사용자 알림 발행 경로가 새 코어 하나이고, 운영 알람은 그대로 동작한다.

전환은 한 종류당 **기존 발송 또는 새 발송 중 하나만 활성**인 상태로 한다. 전환 전에는 새 엔진을 발송 없이 병행 평가하고, 전환 후에는 이벤트 생성·발송·클릭 이동과 알림 공백을 관측한다. 활성 옛 설정은 의미가 같은 경우에만 새 watch로 가져오고, 그렇지 않으면 재설정 대상으로 표시한다. 옛 이력은 읽기 전용 보관하며 사용자에게서 조용히 사라지게 하지 않는다. 실제 DB 삭제와 보관 기간 결정은 별도 작업이다.

## 작동 확인과 검증 계획

**재현 가능한 입력부터 만든다.** 새 판정기는 수집 시각과 평가 시각을 주입받고, 실제 수집 자료에서 고정한 METAR·TAF·공항경보·낙뢰·SIGMET 스냅샷을 순서대로 재생할 수 있게 한다. 각 fixture에는 자료 식별자, 원문 또는 정규화 값, UTC 시각, 예상 이벤트 ID 수·상태·종료 이유를 명시한다. 경계값, 관측 누락, 늦게 도착한 자료, 중복 수집, 서버 재시작을 같은 순서로 다시 실행해도 결과가 같아야 한다. 개발 시나리오 도구가 새 엔진을 지원하도록 연결하되 시험은 격리된 DB에서 실행하고, 외부 기상 API나 실제 사용자 발송에 의존하지 않는다. 미리보기·시험 푸시는 저장 이벤트와 분리해 실제 알림 이력을 오염시키지 않는다.

| 검증 묶음 | 재현할 사례 | 합격 기준 |
| --- | --- | --- |
| METAR·FZRA | 각 수치의 기준 바로 안팎과 정확히 같은 값, 여러 항목 동시 초과, FZRA 진입·해소·재진입, 관측 누락·지연 | 비교 방향대로 발동하고 동시 항목은 한 이벤트에 모두 남는다. 새 관측 없이는 정상 해소하지 않으며 재진입만 새 이벤트가 된다. |
| TAF | 첫 관측, 새 정시 발표, AMD, 같은 전문 재수집, 원문/재구성 TAC, 날짜 경계, 새 발표로 대체 | 첫 관측은 기준점이고 이후 보고당 한 번만 발동한다. 대체된 알림에서도 당시 전문 전체·출처·유효기간을 읽는다. |
| 공항경보·낙뢰 | 동일 경보 재수집·취소·만료, 반경/시간창/최소 건수 경계, 관측 범위 불완전, 해소 후 재발 | 원자료 식별자로 중복을 막고 확인된 종료만 이력으로 옮긴다. 범위 불완전은 `확인 불가`로 남는다. |
| 경로 SIGMET | 실제 교차와 30NM 주변만 해당하는 경우, 유효시각·고도 일치/불일치/미상, 여러 경로, 경로 수정·재시작 | 해당 경로와 실제로 겹칠 때만 발동한다. 주변 자료를 교차로 표시하지 않고, 경로별 중복·누락이 없다. |
| 공통 상태·권한 | 일시정지·재개·삭제, 자료 장애, 읽음과 현상 종료, 개인·기관 구성원, 반복 평가·재시작 | 설정 중단을 기상 해소로 기록하지 않는다. 이력은 남고, 다른 소유자의 이벤트는 조회·딥링크·푸시에서 보이지 않는다. 동일 원자료의 이벤트·발송은 재시도에도 중복되지 않는다. |

**사용자 흐름은 새 브라우저 계약으로 검증한다.** 공항 패널 종 → 설정 저장 → 전역 종의 `진행 중` → 알림 클릭 → 해당 공항의 정확한 METAR/TAF/경보/낙뢰 섹션 → 원래 맥락 복귀를 한 흐름으로 검사한다. 경로 생성 패널에서도 같은 흐름으로 SIGMET 위치와 발생 당시 유효기간을 확인한다. 여러 공항·경로, 로그인 왕복, 미저장 변경 이탈, 일시정지·삭제, `지난 알림`, 직접 `/?alert=<event-id>` 접속과 새로고침을 포함한다. PC 팝업 닫기가 이벤트를 종료하지 않는지, 탭·읽음이 기상 상태를 바꾸지 않는지도 확인한다. 데스크톱·태블릿 가로·모바일 화면에서 패널 중첩, 작은 화면 스크롤, 키보드 포커스와 접근 가능한 이름을 검사하고 캡처를 남긴다. 기존 `alert-lab` 계약은 모형 확인용이므로 실제 API·DB·서비스 워커를 쓰는 `user-alerts` 브라우저 계약을 새로 만든다.

**전달은 이벤트 ID 단위로 끝까지 추적한다.** 격리된 시험 계정과 구독 기기에서 같은 사건이 앱 목록·PC 팝업·웹 푸시에 한 번씩 나타나는지 대조한다. Android와 iPhone 홈 화면 웹앱에서는 권한 허용·거부, 앱이 열림/닫힘, 푸시 탭, 오프라인 뒤 재접속을 실기기로 확인한다. 잠금화면 본문이 잘려도 탭한 앱에서 TAF 전문과 SIGMET 당시 정보가 전부 보이는 것이 합격 기준이다. 실패 응답과 만료된 푸시 구독을 주입해 전달 결과·재시도·구독 정리를 확인한다. 시험 푸시는 현재 시험 기기에만 보내며 발동 이벤트로 집계하지 않는다.

운영 배포 후에는 위 `실제 수신 테스트`를 공항의 각 종류와 경로 SIGMET에 대해 직접 실행한다. 설정값을 기준으로 만든 모의 자료가 판정기를 통과했는지, 화면과 기기에서 `테스트` 표시가 유지되는지, 알림을 눌렀을 때 그 모의 자료가 열리는지, 실제 알림 이력·읽지 않은 수·운영 통계가 변하지 않았는지를 시험 결과와 대조한다. 이는 운영 환경의 연결과 사용 경험을 확인하는 수단이다. 실제 기상 소스의 수집·시간 지연·자료 정확성은 고정 fixture 재생과 실황 관측으로 별도 검증한다.

**전환 전후를 분리해 확인한다.** 발송을 끈 새 엔진으로 고정 fixture와 실제 수집 스냅샷을 재생해 예상 이벤트 목록과 비교한다. 옛 판정과의 차이는 의도적으로 제거한 기능인지, 새 규칙의 오류인지 종류별로 기록한다. 운영 알람은 별도 회귀 시험으로 판정·중복 방지·관리자 수신 경로를 확인하되 시험 중 실제 관리자에게 메시지를 보내지 않는다. 각 종류의 발송 소유자를 한 번에 하나만 켠 뒤 새 이벤트 생성 수, 발송 성공/실패, 클릭 이동, 소스 지연과 누락, 같은 원자료의 중복 건수를 관측한다. 이상이 있으면 해당 종류의 발송 스위치를 되돌릴 수 있게 하고, 옛 발송 코드는 검증 완료 후 제거한다. 최종 코드 검색에서도 옛 사용자용 판정기·발송 호출자가 남지 않아야 한다.

구현 단계마다 관련 백엔드 단위·통합 시험을 실행하고, 최종에는 `npm run check`, `npm run dev:verify`, `npm run dev:contract -- --grep user-alerts`를 통과시킨다. `user-alerts` 계약은 구현하면서 추가할 새 테스트 이름이다. 검증 기록은 무시되는 `artifacts/alert-verification/<실행시각>/` 아래에 fixture 버전, 예상/실제 이벤트 ID와 상태, 전달 결과, 브라우저 캡처, 실패·수정 내역으로 남긴다. **완료 판정은** 각 종류의 위 사례 통과, 주요 사용자 흐름과 실기기 클릭 이동 통과, 개인·기관 권한 누출 없음, 운영 알람 회귀 통과, 사용자 알림 발송 경로 단일화가 모두 확인된 때로 한다.

## 현재 코드에서 확인한 제약

- 운영 알람은 `backend/src/alerts/ops-alerts.js`에서 별도 실행되지만 텔레그램 전송 함수는 옛 경로 알림의 `sender.js`에 의존한다.
- 사용자용 판정·저장은 개인 공항, 예정 비행, 기관, 상황판 브라우저에 분산돼 있다. 개인 알림 피드는 두 DB 테이블을 합쳐 보여주지만 통합 엔진은 아니다.
- 공항 딥링크는 공항 선택만 전달한다. TAF 보고·경보·낙뢰의 정확한 섹션을 열지 못한다.
- 경로 저장은 로그인 시 서버 저장이다. 옛 예정 비행 엔진은 사용자당 가장 임박한 1건만 평가하고 기준 스냅샷을 프로세스 메모리에 둔다.
- 국내 TAF 표시 문자열은 원본 TAC이 아닌 재구성 결과다. OS 푸시 잠금화면에는 전문 전체 표시를 보장할 수 없다.
