# 제안서 — 경로 생성 입력 체계 재정비

> 상태: 제안 · 작성 2026-10-23
> 근거: 2026-10-23 경로 생성 단계에서 버그 수정이 연달아 새 버그를 낳음(bad188a2 → d899bd6a → 1bd7d0fb).
> 범위: 비행 전 브리핑 ① 경로 생성 단계(공항·SID/STAR·경로 알약·교체공항)와 그 결과가 지도에 그려지기까지.
> 경로 비교·고도 비교·브리핑 생성 단계는 이 입력의 결과를 받아 쓰기만 하므로 2단계 이후에 다룬다.

## 1. 지금 구조

같은 정보를 **두 곳**이 따로 들고 있고, 둘을 맞추는 일을 효과(useEffect) 여러 개가 나눠 맡는다.

| 저장소 | 들고 있는 것 |
|---|---|
| 경로 알약 `routeTokenTexts` | 공항·SID·STAR·항로·FIX를 글자 목록으로 |
| 편집기 `routeEditor` | `routeForm`(출발·도착 공항, 진입·이탈 FIX, 비행 규칙), `procedures`(SID·STAR·RWY), `rawText`(항로 문자열) |
| 경로 결과 `routeResult`·`routeDesigns` | 서버/계산기가 만든 실제 경로, 비교안 |

둘을 맞추는 연결(파일: `frontend/src/features/route-briefing/useRouteBriefing.js`, 2,988줄 · useState 58 · useEffect 28 · useRef 37):

| 방향 | 담당 | 비고 |
|---|---|---|
| 알약 → 출발·도착 칸 | 효과(공항 동기화) | 값이 같으면 멈춤 |
| 알약 → SID·STAR 칸 | 효과(절차 동기화) | **넣기만 하고 지우지 않음** |
| 알약 → 경로 계산 | 효과(항로 문자열이 바뀌면 계산) | 같은 글자 두 번 계산 방지 기록 |
| 편집기 문자열 → 알약 | 효과(지도 편집 반영) | 알약을 통째로 다시 씀 |
| 처음 공항 선택 → 알약 | 효과(한 번만 채움) | `seededRef` |
| 출발·도착 칸 → 알약 | 처리 함수 `setEndpointAirportToken` | 양 끝만 바꿈 |
| SID·STAR 칸 → 알약 | 처리 함수 `setProcedureToken` | |
| 공항 변경 확인창 | `requestContextChange`·`confirmContextChange` | 비교안이 있을 때만 확인 |

한쪽을 고치면 다른 쪽 효과가 돌아 되돌리거나 덧쓴다. 어느 순서로 도는지는 코드만 봐서는 알기 어렵다.

## 2. 왜 고칠 때마다 새 버그가 나는가

1. **원본이 둘이다.** 알약이 원본이라고 주석에 적혀 있지만, 편집기도 공항·절차를 따로 들고 있고 경로 계산은 편집기 쪽을 쓴다. 한 곳만 고치면 다른 곳이 되돌린다(예: 확인창 '계속'이 편집기만 바꿔 알약이 공항을 되돌림 — bad188a2).
2. **규칙이 흩어져 있다.** "공항이 바뀌면 그 공항의 절차는 지운다"는 규칙이 처리 함수 셋·확인창·효과에 나뉘어 있어, 경로마다 다르게 동작했다(확인창 경로만 고침 → 확인창 없는 경로에서 STAR가 남음 — d899bd6a).
3. **알약을 통째로 다시 쓰는 곳이 있다.** 지도 편집을 반영하는 효과가 알약을 `[출발, 항로…, 도착]`으로 다시 만들면서 SID·STAR를 잃었다(1bd7d0fb).
4. **동작을 검사하는 시험이 없다.** `useRouteBriefing.*.test.js`는 소스 글자에 특정 문구가 있는지 보는 시험이라, 실제로 눌렀을 때의 결과는 아무도 확인하지 않는다. 그래서 고친 뒤에도 회귀가 그대로 통과한다.

## 3. 아직 남은 증상 (2026-10-23 점검)

- STAR 알약을 지워도 위쪽 STAR 칸과 경로 계산에는 그 STAR가 남을 수 있음(확인 필요).
- 입력 커서가 도착 공항 알약 앞에 있어, 공항을 치면 경로 중간에 들어가고 조용히 무시됨.
- IFR→VFR 전환 시 만든 경로가 확인 없이 지워짐.
- FIR 진입·이탈 흐름은 점검하지 못함.

## 4. 제안 — 원본 하나, 규칙 한 곳, 동작 시험 먼저

### 4.1 동작 시험부터 만든다 (고치기 전에)

- **순수 시험:** 아래 4.2의 입력 규칙 함수에 대해 "이 상태에서 이 조작을 하면 이 상태가 된다"를 표로 검사한다. 브라우저 없이 수백 개를 1초 안에 돌린다.
- **브라우저 계약 하나:** `route-editing` 계약에 2026-10-23 점검에서 쓴 시나리오(아래 5절)를 옮긴다. 데스크톱 한 화면만, 운영 자료 없이 고정 시각으로.
- 지금 코드에 먼저 붙여서 현재 동작을 기록한 뒤 구조를 바꾼다. 바꾼 뒤 같은 시험이 통과해야 한다.

### 4.2 입력 원본을 알약 목록 하나로

- 상태: `{ flightRule, tokens, alternate }` 하나. 출발·도착·SID·STAR·항로 문자열은 **모두 알약에서 계산**해서 읽는다(저장하지 않음).
- 모든 조작은 한 함수(`routeInputReducer`)를 거친다: 출발·도착 선택, 맞바꾸기, SID·STAR 선택, 알약 입력·삭제, 지도에서 지점 추가, 교체 선택, 규칙 전환, 초기화.
- 규칙은 이 함수 안에만 둔다: 공항이 바뀌면 그 공항 절차를 지운다 · 교체가 출발·도착과 같아지면 비운다 · 중간에 친 공항은 오류로 알린다 · FIR 진입·이탈은 알약에 넣지 않는다 등.
- 그러면 1절의 동기화 효과 다섯 개와 처리 함수 둘이 사라진다.

### 4.3 경로 계산과 지도는 결과만 받는다

- 경로 계산은 "알약에서 만든 입력 열쇠"가 바뀔 때만 돈다. 응답이 늦게 와도 열쇠가 다르면 버린다.
- 이미 만든 경로·비교안을 지우게 되는 조작(공항 변경·규칙 전환)은 reducer가 "확인 필요"를 돌려주고, 확인창은 그것만 보고 뜬다 — 지금처럼 조작마다 따로 확인하지 않는다.
- 지도는 계산 결과(또는 계산 전 알약 미리보기)만 그린다. 지도에서 고친 지점은 reducer 조작으로 들어온다.

### 4.4 파일 나누기

`useRouteBriefing.js`를 입력(`useRouteInput`) · 계산(`useRouteComputation`) · 단계 진행(비교·고도·브리핑)으로 나눈다. 이번 범위는 입력과 계산까지.

## 6. 순서와 크기

1. 동작 시험(4.1)을 지금 코드에 붙이고, 현재 실패하는 칸을 기록 — 하루 이내.
2. `routeInputReducer`와 순수 시험(4.2) — 1~2일.
3. 훅을 reducer로 갈아끼우고 동기화 효과 제거, 계약 통과 확인 — 1~2일.
4. 계산·확인창 정리(4.3) — 1일.
