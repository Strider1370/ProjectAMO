# KIM 구름·착빙·등온선 통합 보기 구현계획

작성: 2026-10-03. 상태: 1차 제품 구현 및 저장된 실제 KIM 자료 검증 완료.

> 후속 결정: 사용자가 **구름 배경 + 착빙 색 면·동일한 흰 점**의 A안을 선택했다. 현재 적용 정본은 [A안 프로젝트 적용 계획](2026-10-03-kim-cloud-icing-a-production-plan.md)이다. 아래 등급별 점 밀도·옅은 밑색 설명은 1차 구현의 기록이며 A안의 구현 완료를 뜻하지 않는다.
> 최종 지도 UI 결정: 사용자가 범례 옆 구름·착빙 두 버튼과 빨간 0°C/−20°C 고정 등온선을 승인했다. 아래 지도 체크박스·등온선 독립 조작·−10°C 옵션은 과거 구현 기록이며 후속 제품 구현에서는 정본 계획을 따른다.

기본 지도에서 기온·습도·착빙 버튼을 `구름·착빙` 보기 하나로 묶는다. 포화층 기반 구름 추정은 옅은 중립색으로, 착빙은 등급별 파랑 점무늬와 윤곽선으로, 기온은 등온선으로 함께 표시한다. 연직단면과 비행 전 브리핑에도 같은 표현을 적용한다.

사용자 지정(2026-10-03): **착빙은 등급별 점무늬로 표현하고, 모든 등급을 합친 최외곽에만 윤곽선을 그린다. 등급 사이·내부 구멍에는 윤곽선을 그리지 않는다.** HTML의 색 면 전환은 비교 참고용이다.

시각적 기준은 [HTML 비교 예시](../mockups/cloud-icing-comparison.html)다. 예시의 합성 기상장·가상 고도·임의 착빙 등급은 운영 코드로 옮기지 않는다. 운영에서는 현재 KIM 필드와 기존 계산값을 사용한다.

## 1. 목표와 기본 동작

| 항목 | 구현 후 |
| --- | --- |
| 기본 진입 | 기존 `기온 / 습도 / 착빙` 3개 타일 대신 `구름·착빙` 타일 1개 |
| 첫 사용 기본값 | 구름층 추정·착빙·등온선 모두 켬, 착빙은 점무늬 + 윤곽선, 등온선은 0°C·−20°C |
| 내부 조작 | 구름층 / 착빙 / 등온선 독립 켬·끔, −10°C 추가 |
| 다시 켜기 | 마지막 내부 설정 복원. 부모 보기 끄기는 모든 자식 표시를 함께 끔 |
| 구름 표시 | 기존 T−Td 기반 포화층 판정을 유지하고 옅은 회색으로 표현 |
| 착빙 표시 | 기존 등급·점수 사용, 파랑 계열 점의 색·밀도로 등급 구분, 착빙 전 등급 합집합의 최외곽에만 윤곽선 |
| 기온 표시 | 통합 보기에서 면 채색 대신 등온선. 실제 기온은 지점 조회에 함께 제공 |
| 고도·시간 | 기존 KIM 기압층 레일과 공통 타임라인 사용 |
| 단면 | 구름 추정 배경 + 착빙 강조 + 등온선을 동시에 표시 |

초기 구현은 HTML 예시의 핵심 조작부터 제공한다. 농도 슬라이더는 기본 화면에 늘어놓지 않고 상세 표시 설정에 둔다. 기본 농도는 실제 기본·위성·어두운 베이스맵에서 판독성을 확인한 뒤 고정한다.

수평 지도와 단면은 같은 표시 정의를 사용한다. 두 화면의 고도·시간 선택을 항상 강제로 묶는 새 기능은 만들지 않는다. 지도는 기존 지도 선택, 단면은 기존 항로·예보시간·고도 축을 사용하며, 현재 선택과 출처를 각각 정확히 표시한다.

## 3. 데이터 의미와 일치 계약

### 구름과 착빙

- 기본 구름 배경은 사용자가 설명한 **포화층에 의한 구름 모의**다. UI 명칭은 `구름층 추정`, 조회 상세는 `이슬점 편차 T−Td`로 한다.
- 기존 구름 추정 기준인 일반층 4°C, 500 hPa 6°C를 이번 표시 통합에서 바꾸지 않는다. 회색 농도는 기존 편차 밴드에 대응하며 구름량이나 검증된 발생 확률로 표시하지 않는다.
- 단면의 별도 CLD 윤곽은 `모델 구름량 윤곽`으로 구분한다. T−Td 추정과 CLD를 같은 변수처럼 합치지 않는다.
- 착빙 계산식·등급 임계값·원자료는 그대로 읽는다. 표시 농도가 등급을 바꾸지 않게 한다.
- 착빙은 구름 추정 표시의 하위 마스크로 잘라내지 않는다. 두 판정의 입력과 기준이 달라, 구름 추정 영역 밖의 착빙 계산값도 표시할 수 있어야 한다.
- `착빙 0`, `구름 추정 기준 밖`, `결측`, `지원층 밖`을 구분한다. 무채색 구름을 착빙 없음 등급으로 설명하지 않는다.

### 고도·시간·격자

- 통합 선택 키는 기존 `model + tmfc + hf + level`을 사용한다. 고정 자료에서는 bundle과 자료별 revision을 함께 검사한다.
- 발표·유효시각은 UTC/epoch로 비교하고 사용자가 선택한 KST/UTC로 표시한다.
- 세 변수는 같은 선택과 격자에서 조회한다. 변수가 누락되었다고 해당 변수만 다른 회차·시간·층으로 자동 이동하지 않는다.
- KIM은 현재 21개 기압층, 착빙 필드는 1000–300 hPa만 지원한다. 높은 층에서도 구름·등온선은 유지하고 착빙은 `지원층 밖`으로 표시한다. 착빙 지원층 때문에 레일 전체를 300 hPa에서 잘라내지 않는다.
- 원래 기압면을 예시 HTML의 9,000 ft 수평면으로 바꾸지 않는다. hPa 선택을 기준으로 하고, 예측 고도 표시가 필요하면 기존 hgt/MSL 계약을 사용한다.
- 고도·시간 변경 중에는 이전 요청 결과가 늦게 도착해 새 선택을 덮지 않도록 취소·요청 세대 검사를 적용한다.
- 같은 선택에서 일부 자료가 실패하면 정상 자식은 유지하고 실패 항목을 명시한다. 새 선택 화면에 옛 선택의 착빙을 섞지 않는다. 마지막 사용 가능한 전체 보기를 유지하는 경우에는 그 보기의 선택·시각도 함께 유지한다.

### 수집과 API

- 기존 `/api/kim/temp/*`, `/api/kim/cloud/*`, `/api/kim/icing/*`와 저장된 KIM 자료를 재사용한다.
- 이번 통합을 위해 기상청 변수 추가 수집, 새 collector, 새 난류/착빙 계산기를 만들지 않는다.
- 동시 표시는 브라우저가 프로젝트 서버에서 여러 필드를 읽는다는 뜻이다. 기존 단일 보기보다 조회량은 늘 수 있으므로 선택별 캐시·동시 요청 중복 제거를 적용한다. 이것을 기상청 키 추가 사용량과 혼동하지 않는다.
- 기본 구현은 기존 API 재사용이다. 묶음 API나 의존성 추가는 필수 조건으로 삼지 않는다.

## 4. 표현과 코드 소유권

### 공통 표현

`frontend/src/shared/weather/`에 지도·단면이 함께 읽는 표현 정의를 둔다. 기존 theme 토큰의 착빙 색 `#ACC7FF / #6B88CD / #383D6F`를 참조한다. 기존 feature 함수는 필요하면 이를 다시 내보내 호출부 호환성을 유지한다.

공통 정의에는 구름 편차 밴드별 회색, 착빙 등급 라벨·색·농도·점 밀도·윤곽선, 0/−10/−20°C 선 스타일과 범례 정의를 포함한다. backend 계산 코드가 frontend 모듈을 가져오지 않는다.

### 수평 지도

- 소스·레이어와 표현 변경은 `weather-overlays/lib/` 어댑터가 소유한다. `MapView.jsx`는 기존 조합·styleRevision 연결만 맡는다.
- 그리기 순서는 **구름 배경 → 착빙 점무늬·윤곽선 → 등온선·라벨 → 기존 필요한 항공 표식**이다. 공항·항로의 판독성을 베이스맵별로 확인한다.
- 등온선은 디코딩한 T의 °C 값을 이용한다. 단면의 marching-squares 기능을 좌표계에 독립적인 frontend 공통 함수로 추출해 재사용한다. 기압→고도·바람깃 등 다른 단면 로직까지 옮기지 않는다.
- 결측 셀을 가로질러 선을 잇지 않는다. 전 영역 영하/영상, 정확한 0°C 값, 복수의 분리된 선에서도 올바르게 처리한다.
- 점무늬는 같은 등급 셀의 영역을 연결한 도형과 Mapbox pattern으로 구현하며, 등급 경계를 임의로 부드럽게 바꾸지 않는다. 새 외부 라이브러리 없이 기존 격자/벡터 기능을 우선 사용한다.
- 모든 착빙 등급을 합친 영역의 최외곽에만 파랑 계열의 조금 더 짙은 실선을 그린다. 내부 등급 경계와 구멍에는 윤곽선을 그리지 않는다. 셀마다 테두리를 그리는 격자 무늬는 만들지 않는다. 분리 영역·내부 구멍·결측 경계를 보존하며, 윤곽선으로 결측을 정상 등급처럼 둘러 표시하지 않는다. 등온선은 중립색으로 두어 착빙 윤곽과 구분한다.
- 점 크기·밀도는 화면에서 읽히도록 정하고 pan/zoom 시 전체 격자를 다시 계산하지 않는다. pattern image는 스타일 교체 때 다시 설치한다.
- 벡터/등온선 생성은 필드 revision·선 구성별로 캐시한다. 보기 전환 때문에 동일 KIM 필드를 다시 다운로드하지 않는다.

### 연직단면

- `VerticalProfileChart.jsx`에서 구름과 착빙을 독립 레이어로 그린다. 두 값이 모두 존재하는 셀에는 두 표현이 함께 나타난다.
- SVG pattern과 전 등급 합집합 최외곽 윤곽선을 사용하되 여러 단면이 같은 페이지에 있어도 ID가 충돌하지 않게 한다.
- 기존 0°C 선을 활용하고 기본 `0 / −20°C`, 상세 `−10°C 추가` 모드를 공통 설정에 연결한다.
- CLD 윤곽은 별도 의미·범례를 갖는 상세 표시로 남긴다.
- 지도와 단면의 점무늬는 색·등급·밀도 단계가 같아야 한다. 화면 좌표에서 적절한 크기로 표현한다.

## 5. 메뉴·기존 동작·저장 상태 호환

- `temp/cloud/icing`의 자료 ID와 기존 API는 유지한다. 부모 `구름·착빙`은 UI 보기이며 새로운 기상 자료 종류가 아니다.
- 부모 켬·끔, 자식 켬·끔, 선택 상태를 하나의 순수 전이 모델로 정한다. 자식 셋을 모두 끄면 부모도 꺼진 상태로 계산하고, 부모를 다시 켜면 마지막 유효 설정 또는 기본값을 복원한다.
- 기존 바람·난류·운정과의 고도 레일 전환 규칙에서 구름·착빙 묶음을 하나의 보기로 취급한다. 세 자식이 서로를 끄지 않도록 한다.
- 새 상태에는 표시 설정 버전을 포함한다. 기존 상태의 `cloud`는 구름 추정 단독, `icing`는 착빙 단독, `temp`는 등온선 단독으로 해석하여 사용자가 저장한 활성 항목을 임의로 늘리지 않는다.
- 검색과 AI의 기존 `기온/습도/구름/착빙` 명령은 새 보기의 해당 자식을 켜도록 연결한다. `구름·착빙` 명령은 기본 묶음을 켠다.
- timestamp 카드는 동일 출처·선택이면 한 줄로 묶고, 부분 실패는 별도 상태로 표시한다. 지점 조회는 같은 좌표·선택의 기온·구름 추정·착빙을 함께 제공한다.
- 부모 상태와 자식 상태의 표현을 패널·검색·브리핑 칩·전체 끄기에 동일하게 적용한다.

| 비행 전 브리핑 | 인라인·확대 단면 모두 동일 표현, 기상 레이어 칩도 부모 보기와 연결 |
| 항로·고도 비교 | 수치 계산은 기존 값을 유지하고 이름·범례·상세 표시가 새 표현과 일치하는지 검사 |
| 기관 지도·기관 브리핑 | live/pinned 모두 동일 보기 제공, 고정 revision에 없는 자식은 지원 상태 표시 |
| 저장·공유·스냅샷 | 기상 표시 상태를 보존하는 기존 저장 경로를 조사하고 자식 켬/끔·점무늬와 윤곽선 표현 버전·등온선 모드·농도를 추가. 일반 KML 도형 저장과 기상 스냅샷을 혼동하지 않음 |
| 과거 고정 자료 | 과거 revision 그대로 읽고 자료가 사라지면 만료/누락 표시. live 자료로 자동 대체하지 않음 |
| 검색·AI | 레이어 레지스트리·사용자 별칭·화면 컨텍스트를 새 부모/자식 의미에 맞게 연결 |
| ADMIN | 기존 KIM 수집 상태·자료 가용성·API/저장량 유지. 표시용 새 collector를 등록하지 않음. 사용자 노출 명칭과 실제 자료 상태의 대응 확인 |
| 상황판·태블릿·모바일 | 공통 MapView/단면을 쓰는 표면에 적용. 좁은 화면은 설정을 접고 단면 판독성을 유지 |

저장 설정과 고정 자료 manifest의 실제 소유 모듈은 구현 첫 단계에서 확인하고 작업 기록에 남긴다. 모든 `my-map` 파일을 기상 설정 저장 대상으로 가정해 수정하지 않는다.

## 7. 단계별 구현 순서

| 단계 | 작업 | 단계 완료 기준 |
| --- | --- | --- |
| 1. 상태·데이터 계약 | 부모/자식 전이, 기존 상태 변환, 통합 선택·가용성 모델, 저장 소비자 조사 | 기존 상태를 해석할 수 있고 서로 다른 선택의 자료를 섞지 않는 검사 통과 |
| 2. 공통 표현·등온선 | 색/무늬/범례 정의, 공통 contour 함수와 캐시 | 지도·단면이 동일 표현을 참조, 결측·경계값 등온선 검사 통과 |
| 3. 연직단면 적용 | 독립 구름/착빙 채색, 점무늬, 등온선 옵션, CLD 상세 명칭 | 같은 셀의 구름·착빙 동시 표시, 단면 창·브리핑에서 확인 |
| 4. 수평 지도 적용 | 회색 구름, 착빙 점무늬·윤곽선, 등온선 어댑터, 공통 선택 조회 | 실제 보유 KIM 필드에서 고도/시간/격자 일치와 style reload 확인 |
| 5. 메뉴·조회 통합 | 3타일→1타일, 내부 설정, 범례·timestamp·지점 조회 | 전체 끄기·재진입·검색·기존 자식 명령 동작, 접근성 확인 |
| 6. 저장·기관·운영 연계 | 표시 설정 보존, 과거 상태 변환, pinned/브리핑/AI/ADMIN 점검 | 저장 후 재열기와 고정 revision 재현, 가용성 상태 일치 |
| 7. 최종 검증·보고 | 영향 범위 검사, 실자료 수치 불변 확인, 화면별 캡처·결과 기록 | 아래 완료 기준 충족, 미실행 검사는 이유와 범위 기록 |

1→2→3→4→5→6→7 순서로 진행한다. 중간에 일부 화면만 새 명칭으로 바뀐 상태를 운영에 배포하지 않는다. 구현 결과·변경 파일·검증 결과는 같은 proposals 디렉터리의 결과 보고서에 기록한다.

## 8. 검증 계획과 완료 기준

### 의미 있는 기능 검사

- 부모·자식 토글, 전체 끄기, 이전 단일 레이어 상태 변환, 보기 재진입 시 복원.
- 선택 변경 중 늦게 도착한 응답, 일부 필드 실패, 다른 tmfc/hf/level/격자 거부, 착빙 지원층 밖 상태.
- 원래 T−Td 판정·착빙 점수·등급·결측 위치가 표시 변경 전후 같음. 새 색·패턴이 수치값을 바꾸지 않음.
- 온도 디코딩과 K→°C 변환, 0/−10/−20°C 교차 위치, 결측 구멍, 전 영역 단일 온도, saddle 셀과 정확한 경계값.
- 분리된 착빙 영역·내부 구멍·맞닿은 등급의 최외곽만 그리는 윤곽선, 착빙 끄기 시 점과 윤곽선 동시 제거.
- 같은 셀의 구름/착빙 동시 렌더링, 지도·단면의 등급/색/무늬/윤곽선/범례 일치.
- 저장 설정 왕복, 기존 설정 변환, pinned revision 누락·만료 시 live 대체 금지.

기존 field·overlay·visibility·crossSectionGrid·layerActions·pinnedMapDataSelection 검사에 해당 사례를 추가한다. 단순히 구현 상수를 다시 비교하는 검사보다 실제 출력·전이·조회 동작을 확인한다.

### 화면 검사

- 실제 보유 KIM 자료로 수평 지도·단면 창·브리핑을 확인한다. 실자료로 부족한 결측/실패/경합 사례만 고정 fixture로 보완한다.
- 기본·위성·어두운 지도, 확대/축소, 베이스맵 두 번 변경에서 표시 순서·등온선·pattern 복원 확인.
- 지도 클릭, 내부 토글, 고도/시간 이동, 정상 → 실패 → 정상 복구를 확인한다.
- 데스크톱과 iPad 가로 1180×820 또는 1024×768, 모바일 390px에서 판독성·터치·키보드·범례를 확인한다.
- 점무늬·윤곽선을 함께 캡처한다. 구름 배경·등온선·항공 표식이 읽히고 착빙 경계가 구분되는지 확인한다.
- 화면 검사 동안 기상청 추가 수집을 유발하지 않고 저장 자료/fixture를 사용한다. 생성물은 ignored `artifacts/`에 둔다.

현재 사용자 지시에 따라 로컬 3001/5173 서버는 꺼져 있다. 계획 작성 중 서버·API·배포를 실행하지 않는다. 구현 검증에서도 서버를 자동으로 켜는 `dev:contract`를 무심코 실행하지 않는다. 파일 기반 headless/fixture 검사와 서버가 필요 없는 검사를 먼저 수행하고, 실제 앱의 서버가 필요한 브라우저 검사는 실행 가능한 환경·범위를 별도로 기록한다. HTML 예시의 통과를 제품 통합 검사 통과로 보고하지 않는다.

### 최종 완료

- 기본 타일 통합, 지도와 단면의 동시 표시, 모든 관련 소비자 연결이 완료됨.
- 기존 계산 결과와 고정 자료 선택의 의미가 유지되고, 추가 기상청 수집이 없음.
- 영향 범위 테스트와 frontend build 통과. 전체 변경이 모이면 `npm run check`를 한 번 수행하고 새로운 실패가 없으면 반복하지 않음.
- 실행한 검사·미실행 검사·실자료/fixture 범위를 결과 보고서에 구분함.
- 배포는 계획 작성 완료 기준에 포함하지 않는다. 구현 후 배포를 수행하는 경우 기존 AWS 지침과 의존성 변경 여부에 따른 배포 스크립트를 따른다.
