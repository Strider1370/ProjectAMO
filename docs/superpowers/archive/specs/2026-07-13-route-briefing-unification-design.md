# 경로·브리핑 생성 통일 설계 (Route & Briefing Unification)

- 날짜: 2026-07-13
- 상태: **초안 — 설계 승인 대기** (승인 후 별도 plan 문서로 구현 단계 분해)
- 관련: #13 경로 예보변화 알림, 딥링크 '전체 브리핑 보기'
- 성격: 기존 임시 구현을 갈아엎어 **경로 선(geometry) 생성과 브리핑 표시 경로를 하나로 통일**한다. 판정 로직(composeBriefing)은 건드리지 않는다.

---

## 1. 배경 — 왜 갈아엎나

브리핑에 필요한 것은 사실 **경로 선(coordinates) + 공항 + 시각** 셋뿐이다. 그런데 이 "경로 선"을 얻는 입구가 5개인데 방식이 제각각이다.

| 입구 | 경로 선 확보 방식 | 상태 |
|---|---|---|
| ① 수동 검색 후 브리핑 | 방금 검색한 결과 | 정상 |
| ② 저장 경로 '로드' 버튼 | **저장분 버리고 재검색** | 해외 IFR 실패 |
| ③ 딥링크 '전체 브리핑 보기' | **저장분 버리고 재검색** | 해외 IFR 실패 |
| ④ 파일 임포트 | 파일 좌표로 생성 | 정상 |
| ⑤ 백엔드 알림 감시 | **저장분 그대로 사용** | 정상 |

근본 원인 두 가지:

1. **저장이 lossy.** 저장 payload는 `routeGeometry`(최종 경로 선 모양)만 담고, "어떤 SID/STAR를 골랐는지"라는 **절차 선택은 저장하지 않는다**(routeForm엔 진입/이탈점만 있고 SID/STAR 이름 없음). 그래서 로드 시 잃어버린 선택을 **재검색+절차 자동추천으로 복원**한다.
2. **재검색이 해외에서 깨진다.** 재검색은 항로 그래프 탐색(`findShortestPath`)을 도는데, 해외 IFR 경로에서 `No RNAV route path`로 실패한다(`routePlanner.js:422`). 저장된 경로 선은 멀쩡히 있는데도 그걸 안 쓰고 다시 찾다가 실패하는 것.

여기에 상태 머신이 useEffect 사슬로 엉켜 타이밍 의존·footgun 가드(`lastVfrKeyRef` 등)로 간신히 지탱하고 있어, 뭘 덧붙일 때마다 취약해진다.

---

## 2. 목표 / 비목표

**목표**
- 경로 선의 **중간(항로) 부분은 저장분을 단일 소스**로 삼는다. 어떤 입구든 이 부분은 재검색하지 않는다.
- **SID/STAR(양 끝 절차)는 출발/도착 시각의 예보(TAF) 바람으로 재도출**한다. 예보 유효기간 밖이면 현재(METAR) 바람으로.
- 5개 입구를 **하나의 조립 규칙**으로 통일한다.
- 해외 경로 브리핑이 깨지지 않는다. 브리핑이 알림 시스템이 감시하는 경로와 일치한다.

**비목표**
- 브리핑 판정 로직(`composeBriefing`) 변경 아님.
- 모바일/태블릿 구조 재설계 아님.
- 새 항법 데이터 도입 아님.
- 상태 머신 전면 재작성은 아님 — 이 통일에 **필요한 만큼만** 정리.

## 3. 핵심 개념 — 경로를 두 조각으로 나눈다

```
[출발공항]──SID──[진입점]──── 항로(enroute) ────[이탈점]──STAR/IAP──[도착공항]
   \_____ 양 끝: 절차 _____/   \___ 중간: 스켈레톤 ___/   \____ 양 끝: 절차 ____/
        바람 따라 재도출            저장분 그대로 사용          바람 따라 재도출
```

- **중간(enroute skeleton)**: `출발→(진입점)→항로들→(이탈점)→도착`. **저장분을 그대로** 쓴다. 재검색 없음. (해외에서 깨지던 그 탐색을 아예 안 함.)
- **양 끝(절차, 국내 IFR만)**: SID(출발)·STAR/IAP(도착). 볼 때 **예보 바람으로 재도출**해 스켈레톤 양 끝에 이어붙인다.
- **VFR**: 절차 없음. 경유점 선이 곧 전체 경로. 저장분 그대로.
- **해외 IFR**: 활주로 기반 절차(SID/STAR)가 없다. 대신 **출발/도착 공항 근처 fix 후보 중 "총 경로거리 최소"인 fix**(방향 고려 최근접 — 순수 직선거리 최근접이 아님)를 진입/이탈점으로 쓴다. 이 fix는 **저장 시점에 고정(freeze)**되어 `routeForm.entryFix/exitFix` + 스켈레톤에 저장되고, **볼 때 재도출하지 않고 저장분을 그대로** 쓴다. (국내 SID/STAR는 바람으로 재도출하지만 해외 fix는 재도출 대상이 아님 — 재검색을 안 하므로 해외에서 안 깨지는 근거이기도 하다.)

## 4. 저장 구조 변경

- **지금**: `routeGeometry` = 절차가 이미 구워져 붙은 최종 선 (→ 절차를 되뽑을 수 없음, lossy).
- **바꿈**: 저장 = `{ routeForm(dep/arr/entryFix/exitFix/routeType), enrouteGeometry(절차 제외 스켈레톤), vfrWaypoints, cruiseAltitudeFt, cruiseSpeedKt, alternateAirport, etd }`.
  - `enrouteGeometry` = `routeResult.previewGeojson`의 `route-preview-line`(절차 증강 **이전**의 스켈레톤). 이미 존재하는 값이라 저장 시점만 바꾸면 된다.
- **⚠️ 기존 `routeGeometry`도 계속 저장한다(둘 다).** 이유는 §4.1. 즉 저장 = 기존 필드 유지 + `enrouteGeometry` 추가.
- **하위호환**: 구버전 저장분엔 `enrouteGeometry`가 없다 → 폴백: 저장된 최종 선(`routeGeometry`)을 그대로 브리핑에 사용하되 절차 색/라벨은 생략(§9).

## 4.1 백엔드 알림 시스템과의 호환 (⚠️ 리뷰에서 발견 — 반드시 처리)

저장 `routes` 테이블은 **프론트 경로 저장과 백엔드 알림 감시가 공유**한다. 알림 스케줄러(`backend/src/alerts/scheduler.js` `buildBriefingRequest`, L33)는 `payload.routeGeometry`를 읽어 감시할 경로를 만든다. 저장 포맷을 잘못 바꾸면 **이 키가 사라져 스케줄러가 경로를 못 찾고 알림이 조용히 안 울린다.**

결정·조치:
- **저장은 `routeGeometry`(최종선, 기존)를 그대로 유지하고 `enrouteGeometry`(스켈레톤)를 추가**한다. → 스케줄러는 **무변경으로 계속 동작**(항상 `routeGeometry` 존재).
- 그럼에도 스케줄러 읽기를 `p.enrouteGeometry ?? p.routeGeometry` **폴백으로 방어**해, 향후 저장이 스켈레톤만 남기더라도 깨지지 않게 한다.
- **감시 대상**: 스케줄러는 **절차와 무관하게** 저장된 경로(routeGeometry, 절차 포함 최종선)를 그대로 감시한다. 절차 재도출은 프론트 화면 표시 전용이며 백엔드 알림 판정에 관여하지 않는다(근거 §7 — 절차 구간은 공항 인근이라 이미 공항 감시로 커버, 날씨 판정 불변). → **알림 감시 경로와 화면 표시 경로가 절차 끝단에서 미세하게 다를 수 있으나, 날씨 판정은 동일**하다.

## 5. TAF 바람 규칙 (SID/STAR 재도출의 입력)

- **출발 절차(SID)**: 출발시각(ETD)이 출발공항 TAF **유효기간 안**이면 → 그 시각의 **예보 바람**. **밖**이면 → **현재(METAR) 바람**.
- **도착 절차(STAR/IAP)**: 도착시각(ETA) 기준으로 도착공항 TAF에 같은 규칙.
  - **ETA 순환 아님**(리뷰 지적): ETA는 저장하지 않아도 **조립 시점에 저장된 경로 거리 + 순항속도로 즉석 계산**된다(기존 `computeEtaIso`). 즉 "경로 로드 → 거리 → ETA → 도착 TAF 바람 → STAR" 순서로 성립. STAR 선택은 대략적 ETA면 충분(절차는 날씨 판정 불변, §7).
- 바람 → `pickBestRunwayGroup(활주로들, 풍향)`(이미 바람을 인자로 받음) → 활주로 → `filterProceduresByRunway` → 저장된 진입/이탈점에 연결되는 SID/STAR 선택.
- **이미 있는 조각**: TAF 파서는 유효기간을 1시간 단위로 쪼개 각 시각 풍향/풍속을 계산해 둠(`taf-parser.js` timeline). 활주로 선택 함수는 바람을 외부 인자로 받음. **없는 것**: ①TAF timeline에서 특정 시각 바람만 뽑는 헬퍼(작음), ②그 바람을 절차-선택 단계로 잇는 배선(중간), ③"TAF 안/밖" 분기 규칙.

## 6. 조립 흐름 (통일된 단일 경로)

저장 route 하나를 브리핑으로 만드는 표준 절차:

```
1. 로드      : enrouteGeometry + routeForm + etd  (재검색 없음)
2. 절차 재도출: 국내 IFR이면 — ETD/ETA의 TAF(밖이면 METAR) 바람으로
               SID/STAR/IAP 선택  → augmentRouteWithProcedures(enroute, sid, star, iap)
               → 최종 geometry
               (VFR·해외는 스켈레톤이 곧 최종 geometry)
3. 브리핑    : 최종 geometry + 공항 + etd + eta(거리로 산출) → POST /api/route-briefing
4. 표시      : 지도 = 스켈레톤 + 절차 색/라벨(재도출된 selectedSid/star)
               패널 = BriefingView(브리핑 객체)
```

- 5개 입구가 모두 이 조립을 공유한다. 차이는 **입력 출처**뿐:
  - 저장 로드/딥링크/알림 → 저장 route
  - 파일 임포트 → 파일에서 만든 route (VFR이거나, IFR이면 사용자가 절차 수동 지정 — 파일 좌표만으론 절차 미정)
  - **수동 편집** → 사용자가 화면에서 직접 고른 절차/경유점(이때만 "재도출" 대신 사용자 선택을 존중)

- **⚠️ 2단계(절차 재도출)의 선행 데이터 의존(리뷰 지적).** 국내 IFR 절차 재도출은 그 공항의 SID/STAR/IAP 목록이 **먼저 로드돼 있어야** 가능한데, 현재 이 목록은 공항이 바뀔 때 async effect로 채워진다(`useRouteBriefing.js` L142~). 새 조립은 **"절차 데이터 로드 완료"를 명시적으로 기다린 뒤** 재도출·조립해야 한다(예전 effect-사슬 타이밍 footgun의 재발 방지). 구현 시 이 순서를 상태/약속(await)으로 보장하고, Playwright로 검증(부록). 데이터가 안 오면 절차 없이 스켈레톤 폴백(§9).

## 7. SID/STAR가 "틀려도" 안전한 이유 (위험 경계)

- **브리핑 날씨 내용**(공항 천장·시정·비행범주, 경로 위험, 엔루트 착빙/난류)은 **경로 선이 지나는 지점 + 공항 + 시각**에만 의존한다. 어떤 SID/STAR를 골랐는지는 날씨 판정을 바꾸지 않는다.
- 절차 선택이 영향 주는 곳은 **(a) 지도 표시 색·라벨, (b) 양 끝 경로 모양(미세), (c) 총거리→eta(소폭)** 뿐.
- 따라서 절차 재도출/폴백이 다소 관대해도 **안전 판정을 오염시키지 않는다**. "표시 정확도" 문제이지 "브리핑 신뢰성" 문제가 아니다.

## 8. 사용자가 보게 될 것 (시나리오)

**A. 국내 IFR 저장 비행을 알림에서 '전체 브리핑 보기'**
- 경로 패널이 열리고, 지도에 **저장된 항로 선이 즉시** 그려진다(재검색 대기·실패 없음).
- 출발시각 예보 바람으로 활주로가 정해져 그 **SID가 색·라벨과 함께** 출발공항 쪽에, STAR/IAP가 도착공항 쪽에 그려진다.
- 오른쪽 브리핑 패널에 그 경로의 브리핑이 뜬다 — **알림이 근거로 삼은 바로 그 경로와 일치**.

**B. 해외 IFR 저장 비행(예: RKSI→RJOA)**
- 지금은 `No RNAV route path`로 브리핑이 안 떴다. 바뀐 뒤엔 **저장된 항로 선을 그대로 써서 정상적으로** 브리핑이 뜬다. 절차 색은 없거나 boundary fix 표시(해외는 활주로 절차 없음).

**C. VFR 저장 비행**
- 저장된 경유점 선이 그대로 그려지고 브리핑이 뜬다. 절차 개념 없음 — 지금도 되던 흐름을 단일 규칙 안으로 흡수.

**D. 같은 비행을 며칠 뒤, 바람이 바뀐 날 다시 봄**
- 항로(중간)는 그대로. **SID/STAR만 그날 예보 바람 기준으로 달라져** 그려진다(반대 활주로면 반대쪽 절차). 브리핑 날씨 내용은 경로·시각 기준이라 정상 반영.

**E. 사용자가 패널에서 직접 경로를 만들/편집(수동)**
- 지금처럼 공항·절차를 직접 고른다. 이때는 재도출이 아니라 **사용자가 고른 절차를 그대로** 써서 브리핑. (편집 흐름은 유지하되, 저장 시 §4 구조로 저장.)

## 9. 엣지 케이스 / 폴백

- **구버전 저장분(스켈레톤 없음)**: 저장된 최종 선을 그대로 브리핑. 절차 색·라벨 생략. 오류·경고 없음.
- **ETD가 TAF 유효기간 밖**: 현재(METAR) 바람으로 절차 도출. (근거 표기는 후속 §10.)
- **선택 활주로에 진입/이탈점으로 잇는 SID/STAR 없음**: 다른 활주로 후보 → 그래도 없으면 절차 없이 스켈레톤 끝점 사용(§7 근거로 안전).
- **해외 공항**: 절차 재도출 스킵, 저장 boundary/nearby fix 사용.
- **VFR**: `entryFix/exitFix`는 비어 있음(절차 개념 없음). 조립 2단계(절차 재도출)를 건너뛰고 저장 경유점 선을 곧 최종 geometry로 사용. (구현 시 VFR 저장분에 entryFix/exitFix가 빈 값인지 확인 — 리뷰 지적.)
- **TAF 자체가 없는 공항/시각**: 현재 바람 → 그것도 없으면 기본 활주로(기존 기본값 규칙 유지).

## 10. 범위 밖 / 후속 (이번에 안 함)

- 절차 근거(예보 바람 vs 현재 바람)를 화면에 배지/툴팁으로 표기.
- 수동 "현재 바람으로 절차 갱신" 버튼.
- 상태 머신(effect 사슬·가드 플래그·request-id 패턴) 전면 정리 — 이번엔 조립 통일에 필요한 최소만 손대고, 전면 정리는 별도 작업.
- eta를 경로 저장분에도 저장할지 — 브리핑엔 조립 시 즉석 산출로 충분(§5)하나, **알림 등록(alerts.js)은 eta를 컬럼에 저장**하므로, 같은 경로를 재등록할 때 거리 산출 로직이 바뀌면 값이 미세하게 달라질 수 있다. 정합성 필요하면 저장 schema에 eta 추가(후속 결정).

## 11. 2차 다각도 리뷰 발견 (구현 전 처리) — 3인 병렬 리뷰

**11-1. 🔴 저장 payload 20KB 상한(`routes.js` MAX_PAYLOAD).**
- 두 geometry(`routeGeometry` + `enrouteGeometry`)를 다 저장하면 경유점 많은 경로에서 payload가 20KB를 넘겨 저장 실패(400 `payload_too_large`)할 수 있다.
- 조치: 구현 착수 전 **실제 복잡 경로(조밀 IFR·경유점 많은 VFR) payload 크기 실측**.
  - 여유 있으면 §4.1대로 둘 다 저장.
  - 상한 근접이면 → **(a) `enrouteGeometry`만 저장 + 백엔드 스케줄러가 `enrouteGeometry ?? routeGeometry` 폴백으로 스켈레톤 감시**(§4.1 폴백이 이미 대비), (b) MAX_PAYLOAD 상향(서버 용량 검토), (c) 좌표 단순화 중 택1.
- 즉 §4.1의 "둘 다 저장"은 **실측 후 확정**한다. 초과 시 "스켈레톤만 저장"으로 전환해도 백엔드 폴백 덕에 알림은 안전.

**11-2. 🟠 알림 스냅샷 캐시 무효화(경로 변경 시).**
- 스케줄러는 인메모리 prev 스냅샷으로 prev→curr diff한다(`scheduler.js` snapshotCache). 저장 geometry가 (마이그레이션/재저장으로) 바뀌면 prev가 옛 geometry 기준이라 **한 번 오탐(전 구간 신규 발화)** 날 수 있다.
- 완화: 배포(재시작) 시 캐시가 비므로 배포 직후 첫 tick은 baseline(무발화)라 안전. 위험은 "백엔드 살아있는 채 특정 route 재저장" 경우뿐.
- 조치: 재저장 시 해당 route 캐시 무효화 또는 캐시 키에 geometry 해시 포함. 시뮬레이션으로 검증.

**11-3. 🟠 ETA — 화면(즉석 계산) vs 알림(등록 시 저장값) 불일치.**
- §5는 브리핑 화면 eta를 조립 때 즉석 계산한다. 그러나 백엔드 알림은 등록 시 저장된 `route.eta`를 쓴다(기존 동작, `scheduler.js` L43). 둘이 다를 수 있고 저장 eta는 지연 비행에서 낡는다.
- 판단: 알림은 "등록한 계획"을 감시하므로 저장 eta 사용이 의도에 부합. 화면은 최신 즉석 eta. **의도된 차이**로 두되, "알림이 평가한 시각(등록 eta) ≠ 화면 브리핑 시각(즉석 eta)"일 수 있음을 명시. 정합성 원하면 §10대로 eta를 경로 저장에 포함(후속).

**11-4. 🟡 저장 버튼 활성 조건(`disabled={!routeResult}`).**
- 새 로드가 routeResult를 안 만들면 로드 후 저장/편집이 막힌다.
- 조치: 새 조립 로드도 **(최소한의) routeResult를 항상 생성**해 저장/편집 흐름 유지(해외·절차 없는 경우 포함).

**11-5. 확인된 비이슈(안심).**
- 개발자 콘솔(`dev/scenario.js`)은 최종 routeGeometry에 주입 → 알림·브리핑과 일관. 영향 없음.
- 딥링크 열고 닫는 왕복은 loadSavedRoute 시작의 `clearRouteDisplay`로 이미 정리됨.
- §7("절차 틀려도 안전")는 위 11-2·11-3만 처리하면 성립.
