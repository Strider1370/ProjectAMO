# 경로 토큰 입력 — 진행 상황

**갱신:** 2026-08-15
**스펙:** [경로 토큰 입력 설계](../specs/2026-08-15-route-token-input-design.md)
**계획:** [구현 계획](../plans/2026-08-15-route-token-input.md)

## 상태

계획의 **Task 1~7 완료.** 데스크톱과 iPad 화면(834×1194, 터치) 양쪽에서 확인했다. 남은 것은 **실기기 사파리에서 화면 키보드를 눈으로 보는 것 하나**뿐이다 — 아래 "확인 방법의 한계" 참조.

## 확인한 것 (데스크톱, Playwright)

`RKSI`를 출발공항으로 고른 뒤 `BINIL A582 ANDOL CG050 GONXA`를 쳐서 확인했다.

| 확인 항목 | 결과 |
| --- | --- |
| 알약 생성 (스페이스/엔터) | 6개 정상 |
| 종류별 색 구분 | 공항·지점·항공로가 서로 다르게 표시됨 |
| 오타 판정 | `GONXA`만 빨간 알약 + 테두리 |
| 「⚠ 1 error」와 이유 펼치기 | 정상 — 「GONXA — 그런 지점이 없습니다」 |
| 옛 textarea / 「경로 적용」 버튼 | 두 화면 모두에서 사라짐 |
| 선택기 → 토큰 목록 | 출발공항을 고르면 `RKSI` 알약이 목록 맨 앞에 들어감 |
| React 실행 오류 | 없음 |

시험 1,216개 통과, 프로덕션 빌드 정상.

## 브라우저 확인에서만 잡힌 것 세 가지

소스 검사 시험과 빌드를 모두 통과했는데도 실제로는 깨져 있던 것들이다. **이 세 가지가 Task 7을 건너뛰면 안 되는 이유다.**

1. **`Cannot access 'routeTokenField' before initialization`** — 데스크톱 화면이 입력칸을 정의하기 전에 참조해서 그 화면이 통째로 죽었다. 정의를 두 화면보다 위로 옮겨 해결.
2. **알약이 오른쪽 끝으로 밀림** — 타이핑 칸이 알약보다 앞에 있으면서 남은 공간을 다 차지했다. 맨 끝에 있을 때만 늘어나게 해서 해결(`.rtf-input.is-last`).
3. **터미널 구역 FIX가 전부 오류로 잡힘** — `BINIL`·`CG050`처럼 절차 자료 안에만 있는 FIX는 `enroute.json`에 없다. 절차를 불러올 때 그 안의 FIX 이름도 함께 판정 자료에 담아 해결(`procedureFixIds`).

## 덧붙여 고친 것

옛 입력칸의 예시 문구가 `예: OSPAT Y711 GONA …`였는데 **`OSPAT`·`Y711`·`GONA`가 이 앱의 항법자료에 없다.** 예시를 그대로 따라 치면 오류가 뜨고 이용자는 자기가 틀린 줄 안다. 실제로 있는 이름(`RKSI BINIL A582 ANDOL RKPC`)으로 바꿨다.

## 확인한 것 (iPad 화면 834×1194, 터치)

| 확인 항목 | 결과 |
| --- | --- |
| 알약을 눌렀을 때 입력칸이 초점을 유지하는가 | **유지함.** 키보드가 닫히는 원인은 입력칸이 초점을 잃는 것이므로, 초점이 남으면 키보드도 남는다 |
| 긴 경로(14개 토큰)가 가로 스크롤 없이 접히는가 | 3줄로 접힘, 가로 넘침 없음, 칸 높이 106px |
| 문서 자체가 가로로 밀리는가 | 밀리지 않음 |
| 네 색이 실제로 다른가 | 공항 `rgb(211,227,247)` · 항공로 `rgb(205,234,234)` · 지점 `rgb(220,220,243)` — 계산된 값이 서로 다름 |
| 절차 FIX를 공항보다 먼저 치면 | `CG050`이 오류로 표시됨 → 공항을 넣은 뒤 오류 0개. 문서에 적은 대로 동작 |
| 토큰 → 선택기 | 경로 첫 알약이 `RKSI`면 위쪽 「출발 공항」이 「인천 RKSI」로 따라옴 |
| 되먹임 고리 | 없음 — 값이 같으면 멈추므로 렌더가 계속 돌지 않음 |
| 콘솔 오류 | 없음 |

### iPad 확인에서 추가로 잡힌 것 두 가지

1. **선택기가 토큰을 따라오지 않았다** — 경로에 `RKSI` 알약이 있는데 위쪽 「출발 공항」은 '선택'으로 남아, 같은 것을 두 곳에서 다르게 말했다. 목록 → 선택기 방향을 붙여 해결. 값이 같을 때 멈추게 해서 고리를 끊었고, 효과 안에서 확인 창을 띄우지 않도록 `updateRouteField`를 썼다.
2. **초기값 채우기가 이용자 입력을 지웠다** — 위 연결을 붙이자, 공항이 정해지는 순간 초기화 효과가 돌아 이미 친 `CG050`이 날아갔다. 목록이 비어 있을 때만 채우도록 해서 해결. 시험으로 굳혔다.

## 계약으로 심어둔 것

확인을 사람이 기억해서 하는 것에서 명령 하나로 바꿨다. `route-token-input` 계약 7건이
`frontend/verification/contracts/route-token-input.spec.mjs`에 있고, 계약 등록부에 등재했다.

```
npm --prefix frontend run dev:contract -- --grep route-token-input
```

담은 것: 스페이스 확정과 종류별 판정 · 오타 표시와 이유 문구 · 오류 알약의 테두리(색을 못
알아보는 경우) · 백스페이스 삭제 · 선택기와 목록의 일치 · 알약을 눌러도 초점이 유지되는지
(키보드가 닫히지 않는 조건) · 긴 경로의 접힘 · 네 색이 실제로 다른지.

입력칸을 다루는 도우미는 `frontend/verification/route-token-input.mjs` 한 곳에 모았다.
계약 네 곳이 이것을 함께 쓰므로 입력 방식이 또 바뀌면 한 곳만 고친다.

### 계약이 잡은 것 — 이것이 계약을 심은 이유다

기존 계약 4개가 없어진 옛 입력칸을 찾고 있었다(내가 깨뜨린 것). 고치면서 **네 가지 결함이
더 드러났고, 그중 하나는 이 기능의 핵심이 빠진 것이었다.**

1. **경로가 아예 만들어지지 않았다.** 「경로 적용」 버튼을 없애면서 그 자리를 대신할
   방아쇠를 붙이지 않았다. 알약은 생기는데 지도는 비어 있었다 — 「경로비교로」가 계속 꺼져
   있는 것으로 드러났다.
2. **VFR과 IFR이 받는 문자열이 다르다.** IFR은 en-route만, VFR은 공항까지 포함한 전체다.
   구분하지 않아 VFR 경로가 만들어지지 않았다.
3. **도착 공항이 출발 공항을 지웠다.** 목록에 공항이 하나뿐일 때 도착이 같은 자리를 덮어써,
   출발·도착이 같아지고 그것이 선택기로 되돌아가 두 칸이 같은 공항을 보여줬다.
4. **커서가 목적지 뒤로 갔다.** 공항이 양 끝에 놓인 뒤 다음에 치는 것은 그 사이에 들어가야
   한다. 끝으로 가면 `RKSS RKPK DCT`가 되어 경로가 성립하지 않는다. 입력칸을 누른 이벤트가
   상자로 번져 커서를 끝으로 끌어가는 것도 함께 고쳤다.

## 사파리 엔진 확인 (2026-08-15)

WebKit 26.5를 설치해 **실제 사파리 엔진에서 토큰 계약 7건이 통과했다.** Chromium 흉내가 아니다.

```
npm --prefix frontend run dev:contract -- --project=ipad-safari
```

`playwright.config.js`에 `ipad-safari` 프로젝트를 더했다. 기존 `ipad-landscape`의 엔진은
바꾸지 않았다 — 계약 24개와 스냅샷 기준선이 전부 그것에 걸려 있어, 엔진을 갈면 이 기능과
무관한 것들이 함께 흔들린다. `grep`으로 토큰 계약만 사파리에서 돌게 해, 계약 전부를 두
엔진으로 돌리는 비용은 지지 않는다.

사파리에서 확인된 것 중 가장 중요한 것: **알약을 눌러도 입력칸이 초점을 유지한다.** 이것이
화면 키보드가 닫히지 않는 조건이다.

## 확인 방법의 한계

**화면 키보드 자체는 프로그램으로 볼 수 없다.** 초점 유지로 판정했다 — 키보드가 닫히는
원인이 초점 상실이므로 실질적인 기준이지만, 실기기에서 눈으로 보는 것을 대신하지는 않는다.
사파리 엔진까지 통과했으므로 남은 위험은 iPadOS의 키보드 동작 자체뿐이다.

## 2차 요청 반영 (2026-08-15)

이용자가 실제로 써 보고 네 가지를 요청했다. 모두 반영했다.

**① 부분 경로를 지도에 보인다** — 출발공항만 쳐도 그 지점이 점으로 뜬다.
**② 목적지가 없어도 선을 그린다** — `RKSI ANDOL`만 쳐도 그 사이가 이어진다. 실시간.

`lib/tokenPreviewLayers.js`가 맡는다. **이 선은 계산된 경로가 아니다** — 항공로는 실제로
꺾여 가는데 여기서는 점과 점을 직선으로 잇는다. 그래서 실선이 아니라 **점선**이고 색도
확정 경로와 다르다. 곧게 그은 선을 실제 항로로 읽으면 위험하기 때문이다. 확정 경로가
생기면 이 미리보기는 사라진다 — 같은 경로를 두 겹으로 그리면 어느 쪽이 실제인지 흐려진다.

항공로와 DCT에는 점을 찍지 않는다. 항공로는 장소가 아니라 이어가는 방법이므로, 점을 찍으면
있지도 않은 위치를 그리는 것이 된다.

**함께 고친 것**: 목적지를 안 정한 상태에서 「출발·도착 공항을 확인하세요」가 빨갛게 떴다.
경로 계산기는 양 끝 공항을 요구하는데(`routePlanner.js:528`), 목적지를 아직 안 정한 것은
오류가 아니라 정상적인 중간 상태다. 양 끝이 갖춰지기 전에는 계산기를 부르지 않고, 그 사이
화면은 토큰 미리보기가 맡는다.

**③ 커서를 세로선으로** — 알약 사이에 60px 빈칸이 벌어지던 것을, 글자 칸처럼 깜빡이는
세로선 하나로 바꿨다. 목록에 구멍이 나면 무엇이 어디 있는지가 오히려 흐려진다. 폭 1px이어도
실제 `input`이므로 초점·키보드·붙여넣기는 그대로다.

**④ 화살표로 커서 이동** — 빈 칸에서 ←/→로 알약 사이를 옮기고, Home/End로 양 끝으로 간다.
글자를 치던 중이면 화살표는 그 글자 안에서 움직인다(브라우저 기본 동작).

계약 4건을 더해 11건이 됐다 — 부분 경로 점·목적지 없는 선·항공로에 점 없음·화살표 이동.

## 아직 안 한 것

스펙의 "이번 판에 넣지 않는 것" 4가지(알약 끌어 순서 바꾸기, 알약 안 고도 표시, 연료·바람 요약, 알약을 눌러 글자로 풀기)는 의도적으로 제외했다.

## 알려진 순서 의존

절차 판정은 공항 판정 뒤에만 된다. 절차와 그 안의 FIX는 공항에 딸린 자료라 어느 공항인지 모르면 불러올 수 없다. 공항보다 절차를 먼저 치면 잠깐 오류로 보였다가 공항이 들어온 뒤 제 색을 찾는다. 경로는 공항부터 치는 것이 자연스러운 순서라 실제로 걸릴 일은 드물다.
