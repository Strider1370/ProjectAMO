# Echo Top(재산출) 상태

**Plan:** docs/superpowers/plans/2026-07-25-radar-derived-echo-top.md
**Spec:** docs/superpowers/specs/2026-07-24-radar-derived-echo-top.md

## Gate 1 — QCD 가용성 실측 (2026-07-25)

- 시도한 후보 사이트: 18개
- 응답 확인 사이트: `BRI,GDK,KWK,KSN,MYN,PSN,GSN,SSP,JNI,GNG` (10개)
- 사이트당 다운로드 시간: 최소 115ms / 중앙값 142ms / 최대 374ms
- 표본 파일 크기: ~1MB (범위 490KB~2.7MB)
- **확정 운영 목록** (최종): `BRI,GDK,KWK,KSN,MYN,PSN,GSN,SSP,JNI,GNG`

### 실패 분석 (완전히 조사됨)

프로브 실행 후 컨트롤러가 8개 실패 코드(IIA, PMK, SBS, YIT, CHY, MUJ, ODS)와 1개 의심 코드(SDG)에 대해 추가 검증을 수행:

- **39바이트 응답**: API의 정해진 무효 지점코드 오류메시지 (`# 지점코드를 확인해 주세요.`)
  - 시도된 코드: 원래 프로브의 8개 + 추가 검증 16개(IMJ, SDS, GRS, MHS, YBS, SCK, BSL, KMA, JMS, DNH, HAN, SJN, ULJ, DGU, WJU, CJU) + SDG = 총 25개 코드 테스트
  - 결과: 모두 같은 39바이트 무효-코드 응답
- **SDG의 429**: 우연의 일시적 속도 제한이 아니라, 재검증 시 동일하게 39바이트 무효-코드 응답 수신

**결론**: 확인된 10개 사이트는 KMA 운영 기상레이더 네트워크의 **전체 집합**이다(백령도, 관악산, 광덕산, 오성산, 면봉산, 구덕산, 진도, 고산, 성산, 강릉). 이는 임시 추정치가 아니라 확정된 상태.

**스펙 추정치의 변경**: 스펙 "12~13개 사이트" 추정치는 실측으로 정정됨.
- 예정 일일 호출량: ~3,456회 (12개 × 288프레임/일) → **실제: 2,880회** (10개 × 288프레임/일, 5분 간격 = 288프레임)

### 용량 신호 (다운스트림 작업용 입력)

18개 코드를 순차 프로브 중 한 번 HTTP 429 응답 수신(SDG). 다운스트림 수집기(5분 주기, 동시성 4)의 재시도/백오프 전략은 Task 8에서 결정할 사항.

## Gate 2 — 단위 테스트 고정 (2026-07-25)

빔 기하, scale/fill 처리, 18 dBZ 판정, 상부 bracket 보간, 결측 처리, ragged HDF5 해석, 바이너리 왕복, 색상 밴드, 격자 색인이 모두 단위 테스트로 고정됨. 백엔드 461개 전량 통과.

계획서의 검산값 하나가 틀렸던 것을 구현 중 발견: 100 km·0도 앙각에서 빔 상승을 736 m로 적어뒀으나 4/3 지구반경의 실제 값은 588.6 m(= r²/2Rₑ)다. 계획서·브리프를 정정하고 허용 오차를 ±15 m → ±1 m로 좁혀, 4/3 보정이 빠진 구현이 통과하지 못하게 했다.

## Gate 3 — 통합 (2026-07-25)

시각 일치·부분 실패·stale 거부를 프로세서 테스트로 고정. API는 실서버로 확인:

| 검사 | 결과 |
|---|---|
| `/api/radar/echo-top-meta` | 200 |
| 오버레이 `.webp` | 200 |
| **원시 `.bin`** | **404** (사이트별 파생 정보 비노출) |
| `tm=../../../etc/passwd` | 400 |
| 잘못된 tm / 위도 999 | 400 |
| 없는 프레임 | 404 |
| 에코 없는 지점 | 404 `point_unavailable` |
| 실제 지점 (33.2280, 126.4573) | 200 — FL63 / 6,250 ft MSL / beam_center_floor / GSN. 바이너리 직접 디코딩 값과 일치 |

## Gate 4 — 운영 검증 (2026-07-26)

실제 KMA 자료로 전 구간 동작 확인. 관측소 10곳 전량 수집, 프레임당 **3.3초**(예산 300초).

레이더 반사도와의 공간 일관성(tm 202607260030, 1 km 격자 기준):

- 레이더 18 dBZ 이상 셀 4,682개 중 **4,006개(85.6%)에 에코탑이 있음**
- 에코탑에만 있는 셀 — 상층에는 있으나 지면까지 닿지 않는 강수. 레이더까지 거리 중앙값 139 km로, 양쪽에 있는 셀(127 km)과 비슷 → 지상 클러터가 아님
- 레이더에만 있는 셀 14.4% — 원리적 한계다. 원거리에서는 최저 앙각 빔이 이미 상공에 있어(200 km에서 약 2.5 km) 그 아래 얕게 깔린 강수는 기둥 스캔에 걸리지 않는다

스펙대로 공식 KMA ETOP과의 수치 동등성은 판정 기준으로 삼지 않았다.

## Gate 5 — 브라우저 계약 — **미완료**

`frontend/verification/contracts/echo-top.spec.mjs`를 작성했으나 **아직 통과시키지 못했다.** 셀렉터 정합 작업 중 실제 앱 결함 조사로 전환했고 복귀하지 못했다. 이 상태에서는 전체 계약 실행을 깨뜨린다.

이 공백의 대가는 이미 드러났다 — 아래 세 결함 모두 화면을 실제로 띄워야만 잡히는 종류였고, 그중 둘은 이 계약이 있었다면 잡혔을 것이다.

## Gate 6 — 용량 (2026-07-26)

| 항목 | 실측 |
|---|---|
| 프레임당 처리시간 | 3.3초 (5분 예산의 1.1%) |
| 사이트당 다운로드 | 115~375 ms |
| 사이트당 파싱+계산 | 25~33 ms |
| 일일 호출량 | 2,880회 (10 사이트 × 288프레임) |
| 프레임 산출물 | `.bin` 6.6 MB + `.webp` 약 60 KB |
| 보존 36프레임(3시간) | 229 MB |
| 시작 백필 | 36프레임 × 10사이트 = 360회, 약 4분 |

격자를 2 km → 1 km로 올려도 처리시간은 변하지 않았다(3.4 → 3.3초). 비용이 격자 크기가 아니라 광선 수에 비례하기 때문이다. API 호출량도 불변.

전체 사이트 확대는 해당 없음 — 10곳이 이 API로 접근 가능한 전체 망이다.

## 운영에서 드러난 결함 (2026-07-26)

계약·리뷰가 잡지 못하고 **앱을 실제로 실행해서** 발견한 것들:

1. **App.jsx가 `echoTopMeta`를 MapView에 넘기지 않았다.** 데이터 계층(Task 10)과 지도 계층(Task 11)이 각자 절반을 정확히 만들었으나 이음매를 아무도 맡지 않았다. 각 리뷰가 본 diff에 App.jsx가 없었다. 레이어가 영영 뜨지 않는 원인.
2. **수집 지연 불일치** — 레이더 10분 / 에코탑 15분. 실시간 보기의 기준 시각이 항상 레이더 최신 시각이 되어 에코탑 프레임이 없었고, 레이어가 상시 숨겨졌다. 실측(5·8·10·12·15분 전량 수신) 후 10분으로 통일.
3. **백필 부재** — 레이더는 시작 시 3시간치를 소급 수집하는데 에코탑은 비어 있어, 시간축을 되감으면 한쪽만 사라졌다.

1·2번은 화면을 띄우기 전에는 어떤 단위 테스트로도 드러나지 않는다.
