# 서버 관측 2단계 — 응답 계측과 장애 이력

## 목표

관리자 콘솔이 지금 답하지 못하는 두 가지를 답하게 만든다.

1. **사용자가 실제로 겪는 것.** 지금 콘솔은 전부 "자료를 잘 받아왔나"만 본다. 조종사가 브리핑 화면을 열었을 때 8초가 걸려도, 특정 기능이 계속 오류를 뱉어도, CPU가 1%면 화면은 초록이다. 요청량·오류율·응답시간은 서버 대시보드의 기본 세 가지인데 재는 코드 자체가 없다.
2. **"원래 이런가, 이번만 이런가."** 자료 상태는 물어볼 때마다 계산하고 어디에도 남기지 않는다. 그래서 에코탑이 자주 끊기는 자료인지 이번이 처음인지 알 수 없고, 지금 장애가 며칠째인지도 세어봐야 안다.

두 가지 모두 **지금부터 새로 측정해 쌓는** 성격이다. 과거는 채울 수 없으므로 일찍 켤수록 빨리 쓸모가 생긴다.

## 선행 조건

[1단계 스펙](2026-08-10-admin-console-redesign-design.md)이 구현돼 있다(커밋 `32b651b`~`d06763f`). 이 스펙은 그 위에 얹는다.

- 자료 34종의 판정은 `backend/src/admin/freshness.js`의 `judge()`가 이미 한다. 여기서는 그 결과를 **주기적으로 불러 변화만 기록**한다. 판정 규칙을 새로 만들지 않는다.
- 화면 두 곳이 이미 자리를 비워두고 있다 — 서버 자원 탭의 "사용자 응답" 카드와 자료 수집 탭의 30일 가동률. [목업](assets/2026-08-10-admin-console-mockup.html)에 그려져 있고 1단계에서 의도적으로 만들지 않았다.

## 범위

이번에 만드는 것:
- API 요청의 요청량·오류율·응답시간 계측과 저장
- 자료 34종의 상태 변화 이력과 가동률

이번에 만들지 않는 것:
- **브라우저에서 체감하는 시간.** 네트워크와 기기 느림까지 포함하는 값이라 더 진실에 가깝지만, 프런트엔드 수집 코드와 수집 엔드포인트가 따로 필요하다.
- **자료 파일(`/data/*`) 전송.** 실서버에서는 nginx가 직접 내보내 백엔드를 거치지 않는다. 백엔드에서 재면 개발 중에만 값이 잡히고 운영에서는 빈 숫자가 된다.
- **알림.** 3단계.
- 외부 기관 API의 상태 확인. 3단계.

## ① API 응답 계측

### 무엇을 재는가

`/api/*`로 들어오는 요청만 잰다. 요청 하나마다 응답이 끝나는 시점에 걸린 시간, 상태 코드, 그리고 어느 기능이었는지를 기록한다.

### 기능 이름 붙이기

주소를 그대로 쓰면 `/api/metar?icao=RKSI&t=...`가 공항마다 다른 항목이 되어 목록이 터진다. **Express가 매칭에 쓴 경로 틀**을 이름으로 쓴다.

```
label = req.baseUrl + (req.route?.path ?? '')
```

`app.get('/api/metar')`는 `/api/metar`가 되고, `/api/admin` 아래 라우터의 `/users`는 `/api/admin/users`가 된다. 쿼리스트링과 경로 파라미터 값은 이름에 들어가지 않는다. 어느 라우트에도 걸리지 않은 요청(404)은 `(unmatched)` 하나로 모은다 — 존재하지 않는 주소를 이름으로 삼으면 그것 자체가 목록을 터뜨리는 통로가 된다.

### 어떻게 쌓는가

요청마다 한 줄씩 쓰지 않는다. 하루 만 건이 넘고 대부분은 똑같은 정상 요청이다. **1분 × 기능마다 한 줄로 집계**한다. 메모리에 모았다가 1분마다 SQLite에 flush하며, 이는 기존 리소스 샘플러(`metrics`, 60초)와 같은 방식이다.

```sql
CREATE TABLE IF NOT EXISTS api_minutes (   -- API 응답 집계(1분 단위, 7일 보관)
  ts       TEXT NOT NULL,                  -- 분 단위 ISO ('2026-08-10T13:24')
  route    TEXT NOT NULL,                  -- 위에서 만든 기능 이름
  requests INTEGER NOT NULL DEFAULT 0,
  err_4xx  INTEGER NOT NULL DEFAULT 0,     -- 요청 잘못(대개 우리 문제가 아니지만 401/403 급증은 신호)
  err_5xx  INTEGER NOT NULL DEFAULT 0,     -- 서버 잘못
  b50 INTEGER NOT NULL DEFAULT 0,          -- 응답시간 구간별 건수
  b100 INTEGER NOT NULL DEFAULT 0,
  b250 INTEGER NOT NULL DEFAULT 0,
  b500 INTEGER NOT NULL DEFAULT 0,
  b1000 INTEGER NOT NULL DEFAULT 0,
  b2000 INTEGER NOT NULL DEFAULT 0,
  b5000 INTEGER NOT NULL DEFAULT 0,
  bslow INTEGER NOT NULL DEFAULT 0,        -- 5초 초과
  PRIMARY KEY (ts, route)
);
CREATE INDEX IF NOT EXISTS idx_api_minutes_ts ON api_minutes(ts);
```

### 왜 평균이 아니라 구간인가

평균은 아주 느린 요청 하나에 통째로 끌려가서, 정작 사용자가 겪는 느림을 가린다. 반대로 정확한 중앙값을 내려면 모든 요청 시간을 보관해야 하는데 그건 위에서 버린 방식이다.

**구간별 개수**는 저장량이 기능당 8개 정수로 고정되면서도 분포를 잃지 않는다. "10건 중 9건은 100 ms 안에 끝났고 1건이 5초를 넘었다"가 그대로 남는다.

중앙값과 상위 5%는 이 구간에서 **선형 보간으로 근사**한다. 정확한 값이 아니므로 화면에 그렇게 밝힌다("근사"). 이 화면이 답하는 질문("이 기능이 느려졌나")에는 근사로 충분하다.

경계는 포함하지 않는 쪽으로 통일한다 — 50 ms 정확히 걸린 요청은 `b50`에 센다(`≤`).

### 계측 위치

`server.js`에서 `/api` 라우터들보다 **앞**에 미들웨어를 하나 세우고, `res.on('finish')`에서 기록한다. 라우팅이 끝난 뒤라 `req.route`가 채워져 있다.

관리자 콘솔이 자기 자신을 재느라 숫자를 부풀리지 않도록 `/api/admin/*`은 집계에서 제외한다 — 5초마다 폴링하므로 켜두면 이 화면이 늘 1위가 된다.

## ② 장애 이력

### 무엇을 남기는가

**상태가 바뀐 순간만** 한 줄 남긴다. 5분마다 34종을 판정하되, 직전과 같으면 아무것도 쓰지 않는다.

```sql
CREATE TABLE IF NOT EXISTS product_status_log (  -- 자료 상태 변화(변할 때만, 1년 보관)
  ts       TEXT NOT NULL,              -- 바뀐 시각
  product  TEXT NOT NULL,              -- 카탈로그의 key
  prev     TEXT,                       -- 이전 상태(최초 기록이면 NULL)
  status   TEXT NOT NULL               -- ok | late | stopped | never | quiet
);
CREATE INDEX IF NOT EXISTS idx_product_status_log ON product_status_log(product, ts);
```

매 순간을 저장하면 5분 × 34종 = 하루 9,792줄, 한 달 30만 줄이 된다. 변화만 남기면 아무 일 없는 날에는 한 줄도 쌓이지 않는다.

### 판정 주기

5분마다 판정한다. 가장 짧은 지연 기준이 20분(5분 주기 자료)이라 5분 간격이면 놓치지 않는다.

돌리는 자리는 리소스 샘플러(`metrics.js`의 `startSampler`)와 같다 — `server.js`가 시작할 때 함께 건다. 수집기(`src/index.js`)에 붙이지 않는다: 수집을 끈 테스트 인스턴스(`DISABLE_COLLECTION`)에서도 상태 판정은 계속 돌아야 화면이 비지 않는다.

### 재시작 처리

시작할 때 자료마다 **마지막 기록을 읽어 직전 상태로 삼는다.** 이걸 안 하면 서버를 재시작할 때마다 "NULL → ok" 같은 가짜 변화가 기록되고, 재시작이 잦은 지금 상태에서는 이력이 금세 쓰레기가 된다.

### 가동률 정의

기간 안에서 각 상태로 머문 시간을 변화 기록 사이의 간격으로 계산한다.

- **정상으로 치는 것: `ok`와 `quiet`.** 야간에 위성 가시를 안 받는 것은 장애가 아니다. 이걸 장애로 세면 그 자료의 가동률이 매일 밤 깎인다.
- **장애로 치는 것: `stopped`와 `never`.**
- **`late`는 따로 센다.** 정상도 장애도 아닌 중간이라 합치면 둘 다 흐려진다. 화면에는 "정상 94.1% · 지연 3.2% · 멈춤 2.7%"처럼 나눠 적는다.

기간 끝은 "지금"이고, 마지막 변화 이후 지금까지는 그 상태로 머문 것으로 계산한다.

## 화면 변경

**서버 자원 탭 — "사용자 응답" 카드(목업에 이미 있음)**
- 24시간 요청 수, 응답시간 중앙값(근사), 상위 5%(근사), 5xx 오류율
- 느린 기능 순위표: 기능 이름 · 호출 수 · 중앙값 · 상위 5% · 오류 수
- 자료가 부족하면(켠 지 얼마 안 됨) 숫자 대신 "쌓이는 중 · N시간치"

**자료 수집 탭 — 자료별 가동률**
- 선택한 자료의 30일 가동률 막대(목업의 `.ac-upt`)와 정상/지연/멈춤 비율
- 끊긴 구간 목록: 시작 시각, 지속 시간, 진행 중이면 "진행 중"

**상단 신호등**
- "수집" 신호가 지금은 실패 여부만 본다. 5xx 오류율이 임계를 넘으면 여기서도 뜨게 한다. 임계는 **24시간 5xx 오류율 1% 이상**으로 시작하고, 실제 값을 보고 조정한다.

## 보관과 정리

| 표 | 보관 | 근거 |
|---|---|---|
| `api_minutes` | **7일** | 기존 `metrics`와 같다. "요즘 느려졌나"를 보는 값이라 한 주면 충분하다 |
| `product_status_log` | **1년** | 변화만 쌓여 양이 적고, 계절별 비교("작년 장마철엔 어땠나")가 가능해진다 |

## 검증

- 기능 이름 붙이기 단위 테스트 — 쿼리스트링과 경로 파라미터가 이름에 섞이지 않는지, 404가 `(unmatched)` 하나로 모이는지, `/api/admin/*`이 제외되는지
- 구간 집계 단위 테스트 — 경계값(50 ms 정확히)이 어느 칸에 들어가는지, 1분이 넘어가면 새 줄이 되는지
- 백분위 근사 단위 테스트 — 알려진 분포를 넣고 중앙값·상위 5%가 해당 구간 안에 떨어지는지. 정확값이 아니므로 구간 범위로 단언한다
- 상태 변화 기록 단위 테스트 — 같은 상태가 이어지면 줄이 늘지 않는지, 재시작 후 마지막 상태를 읽어 가짜 변화를 만들지 않는지
- 가동률 계산 단위 테스트 — `quiet`이 정상으로 계산되는지, 진행 중인 장애가 지금까지로 계산되는지, 기록이 하나도 없을 때 0으로 나누지 않는지
- 부하 확인 — 계측 미들웨어가 요청당 더하는 시간이 1 ms 미만인지 실측
- Playwright 계약에 두 화면 추가 — 자료가 부족할 때 "쌓이는 중"이 뜨는 경로까지 포함

## 안 하는 것

- 브라우저 체감 시간 수집
- `/data/*` 정적 파일 계측
- 알림, 외부 기관 API 상태 확인 — 3단계
- 요청 단위 원본 로그 보관 — 집계만 남긴다
- 정확한 백분위 — 구간 근사로 충분하고, 정확값은 원본 보관을 요구한다
