# 이용자 KML/KMZ 표출 가능성 확인 스파이크 설계

## 목표

이용자가 가져온 KML/KMZ를 우리 지도에 **구글 어스에서 보던 것과 같게** 띄울 수 있는지, 그리고 **어디서 무너지는지**를 실측한다. 기능을 만드는 것이 아니라 측정하는 것이 목적이다.

## 배경

### 왜 이 방향인가

우리는 기상기관이다. 공역·NOTAM 같은 항공정보를 직접 관리하면 개정 때마다 따라가야 하고 틀리면 책임이 우리에게 온다. 대신 **이용자가 준비한 자료를 그대로 보여주는 역할**을 맡으면 그 부담이 사라지고, 우리는 기상이라는 본업에 집중할 수 있다. 조종사 입장에서도 우리가 고른 자료보다 자기가 늘 보던 지도가 익숙하다.

조종사가 구글 어스로 자기 비행지도를 만들어 쓰는 것은 개인의 예외적 습관이 아니라 통용되는 방식이다. 국내에도 `KASP.kmz`(초경량·경량항공기용 한국비행공역도), 한국모형항공협회 배포 자료가 있고, 항공정보포털은 NOTAM을 구글 지도용으로 서비스한다. 해외도 마찬가지다.

### 지금까지 실측한 것 (맥케이 비행지도 ver.230729, 1.8MB KMZ)

| 항목 | 값 |
| --- | --- |
| 압축 해제 후 | `doc.kml` 하나, 16.5MB |
| 해석 + 변환 (Node) | XML 762ms + GeoJSON 988ms |
| GeoJSON 크기 | 11.5MB |
| 도형 | 폴리곤 16,170 / 선 39,319 / 점 1,491 |
| 좌표점 총합 | 222,632 |
| 고도값 보유 좌표 | 105,256 (47.3%) |
| Feature | 2,135 — **스타일이 없는 것 0개** |
| 라벨(name) | 1,954 |
| 아이콘 | 38종 중 37종이 `http://maps.google.com/mapfiles/kml/paddle/...` |
| 폴더 | 175개, `kmlWithFolders`로 트리 추출 가능 |

### 확인하지 못한 것 — 이 스파이크가 답할 것

위 수치는 전부 Node에서 파일만 분석한 결과다. **우리 지도에 단 하나도 그려보지 않았다.** 브라우저에서의 압축 해제, 해석 속도, 렌더 성능, 메모리, 라벨 부담, 아이콘 로딩은 모두 미확인이다.

## 범위

- `/kml` 경로에 독립 페이지를 만든다. **개발 빌드에서만 열린다**(`import.meta.env.DEV`). 운영 빌드에서는 코드가 제거된다 — `/test`, `/dev`와 같은 방식.
- 작업은 `frontend/src/features/kml-viewer/` 안에서만 한다. `frontend/src/app/App.jsx`에 라우트 한 줄만 추가한다. **기존 화면은 건드리지 않는다.**
- 지도는 Mapbox 기본 지도만 띄운다. 기상 레이어를 얹지 않는다.
- 파일에 적힌 스타일을 그대로 사용한다. 우리가 색을 고르지 않는다.
- 고도값은 무시하고 평면으로 그린다. 3D 변환은 범위 밖이다. **고도를 가진 도형도 숨기지 않고 전부 그린다** — 이 스파이크의 질문이 "그대로 보이는가"이므로 우리가 미리 골라 숨기면 답을 얻을 수 없다. 평면에서 겹쳐 지저분해지는 것 자체가 측정 결과이며, 치우는 것은 이용자가 폴더를 끄는 것으로 해결한다.
- 저장하지 않는다. 새로고침하면 사라지고 매번 파일을 올린다.
- 편집·생성 기능은 만들지 않는다.

## 화면

```
┌──────────────┬──────────────────────────────┐
│ 파일 올리기   │                              │
│              │                              │
│ 폴더 트리     │      Mapbox 기본 지도         │
│  ☑ RKTA      │      (기상 레이어 없음)        │
│   ☑ 출항절차  │                              │
│   ☐ 1NM 장주 │                              │
│              │                              │
│ 측정값        │                              │
└──────────────┴──────────────────────────────┘
```

- **파일 올리기** — KMZ·KML 선택 또는 끌어놓기
- **폴더 트리** — 작성자가 지은 폴더 이름을 그대로, 계층 그대로. 폴더 단위로 켜고 끈다.
- **라벨 스위치** — 폴더 토글과 별개로 이름표 전체를 켜고 끈다.
- **측정값** — 아래 항목을 화면에 표시한다.

## 측정 항목

| 항목 | 목적 |
| --- | --- |
| 원본 크기 / 압축 해제 후 크기 | 받을 파일 한도의 근거 |
| 압축 해제 시간 | 단계별 병목 파악 |
| XML 해석 시간 | 〃 |
| GeoJSON 변환 시간 | 〃 |
| 지도 소스 등록 시간 | 〃 |
| 폴리곤 / 선 / 점 / 좌표점 총합 | 렌더 부담 |

수치로 잡히지 않는 것은 눈으로 확인한다: 전부 켠 상태에서 확대·이동이 버벅이는가, 라벨이 겹쳐 읽을 수 없는가.

## 처리 규칙

### 압축 해제

브라우저 내장 압축 해제 기능(`DecompressionStream`)으로 zip에서 `doc.kml`을 꺼낸다. 새 라이브러리를 추가하지 않는다. **이 방법이 동작하지 않으면 그 사실 자체가 측정 결과**이며, 그때 라이브러리 도입을 판단한다.

`.kml` 파일이 직접 올라오면 압축 해제를 건너뛴다.

### 폴더

`@tmcw/togeojson`의 `kmlWithFolders`를 쓴다(설치된 7.1.2에 포함). 지금 경로 불러오기가 쓰는 `kml()`은 폴더를 평면으로 뭉개므로 이 페이지에서는 쓰지 않는다.

폴더 하나가 지도 레이어 한 묶음이 된다. 폴더를 끄면 그 안의 도형이 지도에서 사라진다.

**상위 폴더를 끄면 하위 폴더도 함께 꺼진다.** 하위를 개별로 켜고 끈 상태는 상위를 다시 켤 때 그대로 복원한다.

**폴더가 없는 KML**(모든 도형이 최상위에 있는 파일)은 `(폴더 없음)` 묶음 하나로 묶어 같은 방식으로 다룬다. 이름 없는 폴더는 `(이름 없는 폴더 N)`으로 표시한다.

### 스타일

`togeojson`이 각 feature에 실어주는 속성을 그대로 Mapbox 페인트 속성에 대응시킨다.

| KML에서 온 속성 | Mapbox |
| --- | --- |
| `stroke` | `line-color` |
| `stroke-width` | `line-width` |
| `stroke-opacity` | `line-opacity` |
| `fill` | `fill-color` |
| `fill-opacity` | `fill-opacity` |
| `icon-scale` | `icon-size` |
| `icon-color` | `icon-color` |
| `name` | 심볼 라벨 |

속성이 없는 feature에만 기본값을 쓴다.

### 아이콘

파일이 가리키는 주소는 `http://`다. 우리 페이지는 https이므로 그대로는 차단된다. `https://`로 바꿔 시도하고, 실패하면 단순한 원형 표시로 대체한다. **어느 쪽이 적용됐는지 측정값에 기록한다.**

### 크기 제한

두지 않는다. 한도를 정하려고 만드는 도구이므로 한도를 미리 정하면 목적에 어긋난다. 다만 매우 큰 파일에는 "시간이 걸릴 수 있다"는 안내만 표시한다.

### 실패 처리

측정 도구가 빈 화면으로 죽으면 아무것도 배울 수 없다. 실패한 **단계와 원인을 화면에 남긴다** — 압축 해제 실패, XML 해석 실패, 지도 등록 실패를 각각 구분한다.

## 검증

### 단위 시험

순수 함수에만 붙인다.

- zip 바이트에서 `doc.kml` 꺼내기 — 정상 파일, `.kml` 직접 입력, 손상된 zip
- `kmlWithFolders` 트리 → 레이어 목록 변환 — 계층 보존, 이름 보존, 빈 폴더 처리
- KML 스타일 속성 → Mapbox 페인트 속성 변환 — 있는 경우와 없는 경우

### 브라우저 확인

이 스파이크의 결과물은 코드가 아니라 **화면에 표시된 수치와 그림**이다. 개발 서버를 띄워 맥케이 파일을 올리고, 측정값과 지도 화면을 확보해 사용자에게 제시한다. Playwright 계약 시험은 이 페이지에 붙이지 않는다 — 운영 빌드에 존재하지 않는 페이지이며, 목적이 회귀 방지가 아니라 일회성 측정이다.

## 판단 기준

측정 후 다음 기준으로 본 기능 진행 여부를 정한다.

- **16MB 파일이 10초 이내에 표시되고, 전부 켠 상태에서 지도 조작이 매끄러우면** → 본 기능 설계로 넘어간다.
- **30초를 넘거나 지도가 멈추면** → 파일 크기를 제한하거나 폴더를 골라 읽는 방식으로 설계를 바꾼다.
- **압축 해제 또는 스타일 적용이 동작하지 않으면** → 접근 방식을 다시 검토한다.

## 이 스파이크가 끝나면 정할 수 있는 것

- 받을 파일 크기 한도
- 기본으로 꺼둘 폴더 종류(고도 벽처럼 평면에서 의미를 잃는 것)
- 라벨 기본 상태
- 아이콘을 외부에서 가져올지 우리가 보유할지
- 본 기능으로 진행할지 여부

## 하지 않는 것

- 저장(IndexedDB) — 되는 것을 확인한 뒤의 문제다.
- 기상 레이어와 겹쳐 보기 — 표시 자체가 확인된 뒤의 문제다.
- 3D 표출 — 파일의 벽 구조가 `fill-extrusion`으로 변환 가능함은 확인했으나(수직 4각판 + 바닥 테두리, 고도 1000/5000/10000ft), 평면 표시가 확인된 뒤에 다룬다.
- 편집·생성 — `@mapbox/mapbox-gl-draw`가 설치되어 있고 `frontend/src/features/custom-area/usePolygonDraw.js`에서 이미 사용 중임을 확인했다. 도구가 있다는 사실만 기록하고 이번에는 붙이지 않는다.
- 운영 빌드 노출 — 개발 빌드 전용이다. 실기기 확인이 필요해지면 그때 별도로 판단한다.
