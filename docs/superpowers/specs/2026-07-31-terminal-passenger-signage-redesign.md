# 터미널 승객용 도착지 날씨 사이니지 정식 편입·재설계 스펙

- 작성일: 2026-07-31
- 상태: 구현 전 검토본
- 대상 경로: `/terminal`
- 대상 화면: 비교안 1안(3열 보드), 3안(3행 예보 레일)

## 1. 목적

현재 `/terminal`은 디자인 비교용 프로토타입을 메인 프런트엔드에 임시 이식한 상태다. 이를 ProjectAMO의 정식 기능으로 편입하고, 공항 터미널의 50~65인치 Full HD TV를 3~5m 거리에서 보는 승객에게 맞는 디지털 사이니지 화면으로 재설계한다.

이번 작업의 핵심은 단순한 글자 확대가 아니다. 승객이 화면을 몇 초만 보더라도 다음 내용을 순서대로 파악할 수 있도록 정보 구조, 문구, 타이포그래피와 여백을 함께 다시 구성한다.

1. 어느 목적지로 가는 항공편인가
2. 편명과 운항 상태는 무엇인가
3. 언제 출발하고 탑승구는 어디인가
4. 언제 도착하며 도착 무렵 날씨는 어떤가
5. 도착 이후 날씨는 어떻게 변하는가

## 2. 사용자와 사용 환경

### 2.1 주 사용자

- 공항 터미널의 출발 승객과 동행인
- 화면 앞에 멈춰 읽는 사람뿐 아니라 통로를 걸으며 짧게 보는 사람
- 기상 전문 용어보다 목적지, 항공편, 출발 정보와 도착 날씨가 필요한 비전문 사용자

### 2.2 표시 환경

- 화면 크기: 50~65인치
- 출력 해상도: 1920×1080 Full HD
- 화면 비율: 16:9
- 예상 시청거리: 3~5m
- 브라우저 배율: 100%
- 화면 회전이나 세로형 레이아웃은 지원하지 않는다.
- 공통 레이아웃은 가장 불리한 50인치 환경을 기준으로 설계한다. 65인치에서는 동일한 1080p 레이아웃을 확대된 물리 크기로 표시한다.

### 2.3 판독 목표

- 3초 이내에 목적지, 편명, 출발 시각, 운항 상태를 찾을 수 있어야 한다.
- 이어서 도착 시각과 도착 무렵 날씨를 한 묶음으로 찾을 수 있어야 한다.
- 승객이 읽어야 하는 정보는 50인치 화면을 5m에서 보더라도 식별 가능해야 한다.
- 공간이 부족하면 글자를 최소 크기 아래로 줄이지 않고, 낮은 우선순위 정보를 축약하거나 제거한다.

## 3. 정식 편입 경계

### 3.1 소스 소유권

- `/terminal`은 메인 Vite 애플리케이션의 독립 전체화면 라우트로 유지한다.
- 정식 소스의 유일한 위치는 `frontend/src/features/terminal/`이다.
- `prototypes/destination-weather-comparison/`은 정식 화면과 동등성 검증 후 삭제한다.
- 운영 코드가 `prototypes/` 아래 파일, 패키지 또는 자산을 import해서는 안 된다.
- 터미널 화면의 이미지와 아이콘 자산은 `frontend`가 소유하고 production build에 포함한다.
- 외부 Google Fonts 요청을 제거하고 프로젝트에 자체 호스팅된 Pretendard 계열 글꼴을 사용한다.

### 3.2 구현 구조

현재 단일 화면 파일은 정식 구현에서 다음 책임으로 분리한다.

- `TerminalPage`: `/terminal` 진입점과 화면 모드 선택
- 1안 보드 뷰
- 3안 예보 레일 뷰
- 공통 헤더, 페이지 표시와 시험용 전환 컨트롤
- 항공편·시간·날씨 표시 모델
- 전환 애니메이션
- 임시 fixture 또는 향후 API adapter

화면 컴포넌트는 API 원본 구조를 직접 해석하지 않는다. 실제 데이터 연동 시 adapter가 정규화한 동일한 표시 모델을 1안과 3안이 공유한다.

## 4. 공통 정보 위계

모든 화면은 다음 우선순위를 따른다.

| 우선순위 | 정보 | 표시 원칙 |
|---:|---|---|
| 1 | 목적지·공항 코드 | 화면에서 가장 먼저 보이는 항공편 식별자 |
| 2 | 편명·운항 상태 | 서로 가까이 배치하고 상태는 텍스트를 병기 |
| 3 | 출발 시각·탑승구 | 같은 수준의 큰 숫자로 표시 |
| 4 | 도착 시각·도착 무렵 날씨 | 하나의 강조 면으로 묶어 핵심 기상정보로 표시 |
| 5 | 도착 이후 예보 | 시간 흐름이 왼쪽에서 오른쪽으로 이어짐 |
| 6 | 목적지 현재 날씨 | 참고정보로 축소해 배치 |
| 7 | 체감·습도·바람·항공사 영문명·면책 | 공간 경합 시 가장 먼저 축약 또는 제거 |

다음 정보는 더 중요한 정보를 밀어내면 안 된다.

- 항공사 영문 전체 이름
- 반복되는 `KST`
- 긴 설명형 라벨
- 목적지 현재 날씨의 체감온도·습도·풍향 상세
- 하단 면책과 업데이트 시각
- 테스트용 화면·애니메이션 버튼

## 5. 공통 문구 체계

### 5.1 고정 문구

| 기존 문구 | 정식 문구 |
|---|---|
| 곧 출발하는 항공편 · 목적지 날씨 | 출발 항공편 · 도착지 날씨 |
| 곧 출발 · 도착지 예보 | 출발 항공편 · 도착지 날씨 |
| 출발 예정 | 출발 |
| 예상 비행시간 | 비행시간 |
| 운항 상태 · 정상 운항 | ● 정상 운항 |
| 현재 도쿄 날씨 | 도쿄 현재 날씨 |
| 도착 예정 | 도착 |
| 예상 도착 | 도착 |
| 현재 시각 | 현지 시각 |
| 도착 현지 시간 기준 예보 | 도착지 현지시간 기준 |
| 다음 업데이트 09:30 KST | 한국 09:30 업데이트 예정 |

목적지명은 큰 글씨의 도시명과 작은 글씨의 공항명으로 분리할 수 있다. 긴 공항명을 한 줄의 핵심 목적지명에 모두 넣어 글자 크기를 줄이지 않는다.

예:

```text
파리 CDG
샤를 드골 국제공항
```

### 5.2 시간 문구

- 화면 전체의 기준 시각에는 `한국 시각`과 `KST`를 한 번 표시한다.
- 개별 항공편에서는 `현지`와 `한국`을 고정 라벨로 사용하고 `KST`를 반복하지 않는다.
- 날짜가 바뀌면 숫자 앞에 `다음 날`을 붙인다.
- 현지 시각과 한국 환산 시각은 같은 시각적 수준으로 나란히 배치한다.

예:

```text
도착
현지 18:50  |  한국 다음 날 01:50
```

### 5.3 날씨 문구

화면 간 표현을 다음 어휘로 통일한다.

- 맑음
- 구름 조금
- 구름 많음
- 흐림
- 비
- 소나기
- 눈
- 뇌우

외부 API의 더 세분된 상태는 adapter에서 이 표시 어휘로 변환한다. 아이콘만으로 날씨를 전달하지 않고 날씨 상태 문구를 항상 병기한다.

## 6. 사이니지 타이포그래피

### 6.1 기준 크기

아래 값은 1920×1080, 50~65인치 공통 화면의 구현 시작값이다.

| 토큰 | 크기 | 용도 |
|---|---:|---|
| 화면 제목 | 40px | 상단 제목 |
| 목적지 | 64px | 도시명 |
| 공항 코드 | 34px | HND, SIN, CDG |
| 편명 | 48px | JL090, SQ607 |
| 출발·탑승구 | 56px | 핵심 운항 숫자 |
| 현재 기온 | 60px | 목적지 현재 온도 |
| 도착 시각 | 40px | 현지·한국 도착 시각 |
| 현지 시각 | 36px | 목적지 현지 시각 |
| 운항 상태 | 30px | 정상·지연·탑승 준비 |
| 일반 정보 | 28px | 비행시간·현재 날씨 상세 |
| 항목 라벨 | 26px | 출발·탑승구·현지·한국 |
| 예보 시각·상태·기온 | 26px | 시간별 예보 |
| 날짜·환산 시각 | 24px | 날짜와 보조 시간 |
| 하단 안내 | 22px | 유지가 필요한 면책·업데이트 |

### 6.2 최소 크기 규칙

- 승객이 반드시 읽어야 하는 텍스트는 24px 미만을 사용하지 않는다.
- 일반 라벨과 예보는 원칙적으로 26px 이상을 사용한다.
- 22px은 날짜·면책처럼 중요도가 낮지만 실제로 읽을 필요가 있는 정보에만 허용한다.
- 20px 미만 텍스트는 사용하지 않는다.
- 페이지 점, 구분선과 아이콘처럼 글자가 아닌 요소는 이 제한의 대상이 아니다.
- 긴 문구 때문에 최소 크기를 위반하지 않는다. 짧은 문구, 줄바꿈 또는 정보 축약을 사용한다.

### 6.3 글꼴과 숫자

- 기본 글꼴은 자체 호스팅 Pretendard 계열을 사용한다.
- 지나치게 가는 굵기와 이탤릭은 사용하지 않는다.
- 목적지·편명·핵심 시각은 700 이상 굵기를 사용한다.
- 시간 숫자는 동일한 폭과 정렬을 유지할 수 있는 숫자 스타일을 사용한다.
- 외부 폰트 로딩 실패에 따라 글자 폭이 달라지는 구성을 허용하지 않는다.

## 7. 1안 — 3열 보드 재구성

### 7.1 기본 구조

- 한 화면에 항공편 3편을 세로 열로 표시한다.
- 세 열의 너비, 상하 시작점과 정보 행 높이는 동일하게 유지한다.
- 항공편 사이에는 세로 구분선을 유지하고, 각 열 안에서는 정보 묶음 사이의 여백과 얇은 구분선을 사용한다.

### 7.2 열 내부 순서

각 열의 정보는 위에서 아래로 다음 순서로 표시한다.

1. 목적지 도시명·공항 코드·공항명·현지 시각
2. 항공사 로고·편명·운항 상태
3. 출발 시각·탑승구
4. 도착 시각과 도착 무렵 날씨 강조 면
5. 도착 이후 시간별 예보
6. 목적지 현재 날씨와 필요한 경우 상세 기상

현재 구현처럼 목적지 현재 날씨가 도착 예보보다 먼저 큰 면적을 차지하지 않는다.

### 7.3 도착 날씨 강조

- `도착`, 현지·한국 도착 시각, 날씨 아이콘·상태·기온을 하나의 면으로 묶는다.
- 강조 면은 옅은 단색 배경과 얇은 테두리를 사용한다.
- 그림자, 강한 그라데이션, 큰 radius와 장식성 배지는 사용하지 않는다.
- 강조는 색만으로 전달하지 않고 크기, 굵기와 위치를 함께 사용한다.

### 7.4 시간별 예보

- 도착 시점부터 이후 시간만 왼쪽에서 오른쪽으로 표시한다.
- 각 칸은 `시각 → 아이콘 → 상태 → 기온` 순서를 동일하게 유지한다.
- 도착 시점 칸은 도착 강조 면과 시각적으로 연결한다.
- 다섯 칸을 유지하면 최소 글자 크기와 여백을 침해하는 경우, 미래 예보 칸 수를 줄이는 것을 글자 축소보다 우선한다.

### 7.5 현재 날씨

- `도쿄 현재 날씨`처럼 목적지를 먼저 표시한다.
- 현재 기온과 상태를 먼저 보여준다.
- 체감·습도·바람은 한 줄 또는 두 줄의 보조정보로 축약한다.
- 공간 경합 시 체감·습도·바람을 제거해도 목적지·운항·도착 정보는 유지한다.

## 8. 3안 — 3행 예보 레일 재구성

### 8.1 기본 구조

- 한 화면에 항공편 3편을 가로 행으로 표시한다.
- 각 행은 왼쪽 운항정보 32%, 오른쪽 도착·예보 68%를 기준으로 한다.
- 세 행의 높이와 내부 기준선은 동일하게 유지한다.

### 8.2 왼쪽 운항정보 순서

1. 목적지 도시명·공항 코드
2. 공항명 또는 현지 시각
3. 항공사 로고·편명·운항 상태
4. 출발 시각·비행시간·탑승구

출발 시각·비행시간·탑승구 사이의 세로 구분선은 유지한다. 편명 위아래의 불필요한 가로선은 사용하지 않는다.

### 8.3 오른쪽 도착·예보 순서

1. 도착 현지·한국 시각
2. 도착 무렵 날씨 강조 면
3. 도착 이후 예보
4. 보조정보인 도착 1시간 전 예보

- 과거 시간대의 일반 예보는 표시하지 않는다.
- `도착 1시간 전`은 비행기 아이콘 자리를 사용하는 보조 예보이며 도착 예보보다 작게 표시한다.
- 실제 도착시간대 예보가 행의 첫 번째 핵심 기준점이 된다.
- 이후 예보는 오른쪽으로 시간 순서대로 이어진다.
- 긴 `다음 날` 문구가 생겨도 `현지`와 `한국` 라벨의 기준 위치가 움직이지 않도록 고정 열을 사용한다.

## 9. 공통 헤더와 페이지 표시

### 9.1 헤더

- 공통 제목은 `출발 항공편 · 도착지 날씨`로 통일한다.
- 한국 시각은 화면 오른쪽에 표시한다.
- 날짜와 `KST`는 한국 시각에 종속된 보조정보로 표시한다.
- 제목, 시험용 컨트롤과 시각이 서로 밀거나 겹치지 않는 고정 영역을 사용한다.

### 9.2 페이지 표시

- 전체 페이지 수만큼 원형 표시를 상단 중앙에 배치한다.
- 현재 페이지는 채운 원, 나머지는 빈 원으로 표시한다.
- 원 지름은 12~14px, 원 사이 간격은 최소 10px로 한다.
- 원형 표시만으로 충분하지 않은 운영 환경을 위해 접근성 이름에 `현재 페이지 / 전체 페이지`를 제공한다.

### 9.3 시험용 컨트롤

- 1안·3안, FLAP·ROLL·WIPE·FADE·CASCADE와 `다음 3편` 버튼은 비교가 끝날 때까지 유지한다.
- 시험용 컨트롤은 승객 핵심정보보다 시각적으로 강하면 안 된다.
- 최종 운영에서 컨트롤을 기본 노출할지는 1안·3안 최종 선택과 함께 별도로 결정한다. 이번 스펙은 이를 자동으로 숨기지 않는다.

## 10. 전환 애니메이션

### 10.1 공통 원칙

- `출발`, `탑승구`, `도착`, `현지`, `한국`, `현재 날씨` 같은 고정 라벨은 움직이지 않는다.
- 목적지명, 공항 코드, 편명, 시각, 상태, 날씨 아이콘·문구·기온처럼 실제로 바뀌는 값만 전환한다.
- 전환 중 이전 값과 새 값이 같은 공간에 동시에 완전한 불투명도로 나타나지 않는다.
- 값의 길이가 달라도 고정 라벨과 열 기준선은 이동하지 않는다.
- 전체 화면이나 전체 패널을 불필요하게 움직이지 않는다.

### 10.2 지원 모드

- FLAP: 값 요소가 개별적으로 세로 축을 기준으로 뒤집힌다.
- ROLL: 단어 또는 값 요소가 짧은 시차로 위에서 아래로 교체된다.
- WIPE: 값 영역 안의 마스크로 새 내용을 공개한다.
- FADE: 위치 이동 없이 이전 값과 새 값을 교차 전환한다.
- CASCADE: 3안의 행 또는 값 묶음을 짧은 시차로 순차 전환한다.

### 10.3 동작 안전성

- `prefers-reduced-motion: reduce`에서는 실질적인 이동·회전을 제거한다.
- 자동 순환과 수동 `다음 3편` 전환은 동일한 상태 전이 함수를 사용한다.
- 전환 중 반복 입력이 들어와도 중간 상태가 화면에 남지 않는다.

## 11. 색상·면·여백

- 기본 배경은 흰색 또는 매우 옅은 중립색을 사용한다.
- 텍스트는 높은 명암의 짙은 중립색을 사용한다.
- 운항 정상 상태는 초록색 텍스트와 상태 문구를 함께 사용한다.
- 지연은 주황색 또는 경고색과 `지연` 문구를 함께 사용한다.
- 색만으로 상태를 전달하지 않는다.
- 카드 그림자 대신 여백, 정렬, 얇은 구분선과 제한된 면 강조를 사용한다.
- 관련 정보 내부 간격은 좁게, 서로 다른 정보 묶음 사이 간격은 크게 둔다.
- 화면 가장자리와 핵심정보 사이에는 안전 여백을 둬 TV overscan과 설치 오차에 대비한다.

## 12. 데이터와 상태

### 12.1 이번 단계

- 현재 fixture 데이터를 사용해 디자인과 전환 동작을 검증한다.
- 1안과 3안은 동일한 정규화 표시 모델을 사용해야 한다.
- 실제 운항·날씨 API 주소나 데이터 공급자 결정은 이번 재설계 범위에 포함하지 않는다.

### 12.2 향후 실제 연동

정규화 표시 모델은 최소한 다음 값을 지원해야 한다.

- 항공편: 편명, 항공사, 로고, 목적지, 공항 코드, 출발 예정·변경 시각, 탑승구, 운항 상태
- 시간: 한국 현재 시각, 목적지 현지 시각·시간대, 현지·한국 도착 시각, 날짜 변경 여부
- 날씨: 목적지 현재 날씨, 도착 1시간 전 예보, 도착시간대 예보, 도착 이후 예보
- 상태: 데이터 로딩, 일부 누락, 갱신 시각, 다음 페이지 존재 여부

누락된 값을 `--`, `undefined` 또는 빈 공간으로 방치하지 않는다. 해당 묶음을 축약하거나 승객이 이해할 수 있는 짧은 대체 문구를 표시한다.

## 13. 범위 제외

- 실제 한국공항공사 운항 API 연결
- 실제 국내·해외 목적지 기상 API 연결
- 다른 공항의 운영자용 모니터링 페이지
- 조건부 폭염·한파 안전수칙 슬라이드
- 터미널 장비 원격 관리와 콘텐츠 관리 서버

- 최종 1안·3안 선택

## 14. 검증 기준

### 14.1 자동·브라우저 검증

- 1920×1080 Chromium, 브라우저 배율 100%에서 1안과 3안을 각각 캡처한다.
- 페이지 가로·세로 스크롤이 없어야 한다.
- 목적지, 편명, 시각, 날씨 문구가 잘리거나 겹치지 않아야 한다.
- `다음 날`이 포함된 가장 긴 도착 시각과 가장 긴 목적지명을 포함해 검증한다.
- 승객이 읽어야 하는 텍스트의 computed font-size가 24px 미만이면 실패한다.
- 보조 면책을 제외한 일반 라벨과 예보가 26px 미만이면 실패한다.
- 외부 Google Fonts 요청이 없어야 한다.
- 1안·3안 전환, 다음 3편, 모든 애니메이션 모드가 동작해야 한다.
- FLAP·ROLL 중 고정 라벨이 움직이거나 이전·새 값이 겹치면 실패한다.
- 현재 페이지 원형 표시가 전체 페이지 수와 일치해야 한다.

### 14.2 현장 검증

- 50인치와 65인치 Full HD TV에서 각각 확인한다.
- 3m와 5m 거리에서 목적지·편명·출발·상태·도착 날씨를 읽는다.
- 통로를 걷는 속도로 3초 동안 본 뒤 핵심정보를 재진술할 수 있는지 확인한다.
- 밝은 터미널 조명에서 회색 보조문구와 옅은 도착 강조 면이 구분되는지 확인한다.
- TV overscan 또는 장비 자체 확대가 켜져 있지 않은지 확인한다.

## 15. 인수 조건

- `/terminal`이 메인 프런트엔드의 정식 독립 전체화면 라우트로 동작한다.
- `prototypes/destination-weather-comparison/`이 삭제되고 운영 코드에 프로토타입 경로 참조가 없다.
- 1안과 3안 모두 이 문서의 공통 문구와 정보 위계를 사용한다.
- 1안은 도착 날씨를 현재 날씨보다 먼저, 더 강하게 표시한다.
- 3안은 도착시간대 예보를 기준점으로 삼고 이후 예보만 오른쪽으로 이어간다.
- 50~65인치 Full HD 공통 타입 크기와 최소 크기 규칙을 만족한다.
- 고정 라벨은 애니메이션되지 않고 바뀌는 값만 전환된다.
- production build, 관련 테스트와 1920×1080 브라우저 검증이 통과한다.
- 현장 검증 전까지 실제 5m 판독성을 완료로 단정하지 않는다.

## 16. 미결정 사항

- 최종 운영안으로 1안과 3안 중 어느 하나를 선택할지
- 최종 운영 화면에서도 시험용 전환 컨트롤을 노출할지
- 한 항공편당 도착 이후 예보를 4개 또는 5개 표시할지
- 목적지 현재 날씨의 체감·습도·바람 중 최종적으로 남길 항목
- 실제 운항·날씨 API 공급자와 갱신 주기
