# 경로 토큰 입력 (ForeFlight식 알약) — 설계 스펙

**작성일:** 2026-08-15
**근거 조사:** 이 스펙 작성 시점의 `frontend/src/features/route-briefing` 직접 열람 — `useRouteBriefing.js`, `lib/routeEditor.js`, `lib/routePlanner.js`, `lib/manualRouteInput.js`, `lib/routeBriefingModel.js`, `RouteBriefingPanel.jsx`
**참고:** ForeFlight FPL 입력줄 (이용자 제공 스크린샷)

## 무엇을 만드나

비행경로 문자열 입력칸을 **토큰(알약) 입력**으로 바꾼다. 친 글자가 스페이스나 엔터에서 알약으로 확정되고, 종류에 따라 색이 붙고, 그 순간 지도와 요약이 같이 갱신된다. 「경로 적용」 버튼은 없어진다.

## 왜 만드나

지금 경로 문자열은 검은 글자 덩어리다. 어디까지가 절차이고 어디부터가 항공로인지 눈으로 구분되지 않고, 오타는 「경로 적용」을 누르기 전까지 드러나지 않는다. 그리고 경로가 문자열·공항 선택기·절차 선택기 세 군데에 나뉘어 있어, 전체 경로를 한눈에 보는 자리가 없다.

## 결정 사항

이 스펙은 아래 결정 위에 서 있다. 각 항목은 설계 대화에서 이용자가 직접 정한 것이다.

| # | 결정 |
| --- | --- |
| 1 | 토큰 확정 신호는 **스페이스 또는 엔터** |
| 2 | 색칠과 지도 반영은 **토큰이 확정되는 같은 순간**에 일어난다. 글자 한 자마다가 아니다 |
| 3 | 입력칸과 결과 표시를 **합친다**. 입력칸 자체가 색깔 알약 줄이다 |
| 4 | 오류는 **빨간 알약** + 입력칸 아래 「⚠ N error」. 누르면 이유가 펼쳐진다 |
| 5 | 오류가 있는 동안 **지도는 바뀌지 않는다**. 마지막으로 성립했던 경로가 남는다 |
| 6 | 알약 편집은 **백스페이스**로 한다. 알약을 눌러 글자로 푸는 방식은 만들지 않는다 |
| 7 | 위쪽 선택기는 **그대로 둔다**. 선택기에서 고르면 토큰 목록이 바뀐다 |
| 8 | 출발·목적지 공항은 **지울 수 있다**. 공항 없는 경로도 정상이다 |
| 9 | **VFR도 IFR과 같은 방식**. 좌표도 알약이 된다 |
| 10 | 색은 **네 종류** + 오류 + DCT |

## 원본은 하나

**경로는 토큰 목록 하나다.** 그 외에 경로를 담는 곳은 없다.

토큰 종류: 공항 · 절차(SID/STAR/접근) · 항공로 · 지점(FIX/좌표) · DCT.

토큰 목록을 고치는 방법은 둘이며, 둘 다 **같은 한 곳**을 고친다:

1. 입력칸에 친다 — 스페이스/엔터로 확정
2. 위쪽 선택기에서 고른다 — 공항·SID·STAR·활주로

선택기는 토큰 목록을 읽어 자기 상태를 보여주고, 이용자가 고르면 목록을 고친다. **두 상태를 서로 맞추는 구조가 아니다** — 양방향 동기화는 서로를 갱신하다 입력이 튀는 사고를 만든다.

선택기로 목록이 바뀌면 그 알약을 잠깐 강조한다. 긴 경로에서 어디가 바뀌었는지 눈으로 찾을 수 없기 때문이다.

### 지금과 달라지는 것

- 문자열 칸이 en-route 구간만 담던 것에서 **공항부터 절차까지 전부** 담는 것으로 바뀐다
- 「경로 적용」 버튼이 없어진다
- 입력칸 아래 안내문 「SID/STAR는 절차 선택에 따로 표시됩니다」는 사실이 아니게 되므로 지운다
- `RouteBriefingPanel.jsx:274`의 `canSearch`(출발·도착 공항이 둘 다 있어야 검색 가능)는 결정 8과 어긋나므로 완화한다
- 적용된 경로를 색깔 글자 줄로 보여주던 `route-check-sequence`(`RouteBriefingPanel.jsx:459`)는 **없앤다**. 결정 3이 입력칸과 결과 표시를 합치는 것이므로, 남겨두면 같은 것을 두 번 보여주게 된다
- 데스크톱과 모바일 **양쪽 모두** 바뀐다. 지금 문자열 칸은 두 곳에 각각 있다(데스크톱 `:587` 부근, 모바일 `:715` 부근). 새 입력칸 부품 하나를 양쪽이 함께 쓴다

### 지도 조작 확인은 그대로 둔다

`pendingRouteEdit` 확인("이렇게 바꿀까요?")은 **지도에서 선을 그리거나 점을 찍었을 때만** 뜬다(`useRouteBriefing.js:1136`, `:1193`). 앱이 손짓을 보고 가장 가까운 FIX를 추측한 것이라 확인이 필요하다. 타이핑 경로에는 원래 걸리지 않는다(`:575`에서 확인 상태를 지운다). 따라서 「경로 적용」을 없애도 이 확인은 손대지 않는다.

## 토큰과 색

색은 연한 배경 + 진한 글자다. 기상 뱃지는 진한 색이므로, 알약을 연하게 두면 무게가 달라 서로 섞이지 않는다.

| 종류 | 배경 | 글자 | 예 |
| --- | --- | --- | --- |
| 공항 | `#d3e3f7` | `#1c3f66` | `RKSS` `RKPC` |
| 절차 | `#d7ecd0` | `#2f5d3a` | `32L.BULT2Q.BULTI` · `DOTOL.DOTO2P` · `ILS Y RWY 07` |
| 항공로 | `#cdeaea` | `#14595c` | `Y711` |
| 지점 | `#dcdcf3` | `#3b3a8c` | `DOTOL` · `N3721.4E12712.8` (점선 테두리) |
| 오류 | `#fee2e2` | `#c0291f` | 테두리 `1.5px #c0291f` |
| DCT | 알약 없음 | `#64748b` | 연결어이므로 종류가 아니다 |

ForeFlight의 배색을 따르되 주황을 쓰지 않는다. ForeFlight가 접근절차에 쓰던 청록 자리가 우리 쪽에서는 비므로(절차 셋을 한 묶음으로 합쳤다) 항공로가 그 자리를 쓴다.

### 색 규칙

1. **빨강은 오직 오류.** 경로 칸 안에서 빨강은 다른 뜻을 갖지 않는다. 이 앱에서 빨강은 IFR이자 위험 등급이므로, 이 칸 안에서만큼은 뜻을 하나로 고정한다
2. **오류는 색 말고 모양으로도 구분된다.** 다른 알약에는 테두리가 없다. 색을 못 알아보는 경우와 햇빛에 화면이 씻긴 경우를 위한 것이다
3. **글자 대비는 4.5:1 이상.** 밝은 조종석에서 태블릿을 보는 환경이 기준이다
4. 좌표는 지점과 같은 색에 점선 테두리. 이름 없는 점이라는 것만 다르므로 색을 하나 더 늘리지 않는다

### 절차 셋을 한 색으로 묶은 이유와 그 대가

SID·STAR·접근절차는 색으로 구분되지 않는다. 구분 근거는 **자리**(SID는 출발공항 뒤, STAR·접근은 목적지 앞)와 **이름 자체**다.

쓰다가 구분이 필요해지면 **색을 늘리지 말고 같은 색의 진하기만 다르게** 한다. 같은 부류라는 정보가 유지된다.

### 초록을 절차에 쓰는 것에 대한 유보

이 앱에서 초록은 VFR이자 "좋음"이다. 절차 알약이 연두인 것은 ForeFlight 배색을 따른 결과이며, 알약이 연하고 안에 든 것이 절차 이름이라 기상 표시로 읽힐 위험은 낮다고 판단했다. 실제로 혼동이 생기면 색조를 청회색 계열로 옮긴다.

## 확정과 반영

토큰이 확정되는 순간 **세 가지가 같이** 일어난다:

1. 종류가 판정되어 색이 붙는다
2. 지도가 갱신된다
3. 아래 요약(거리·시간)이 갱신된다

하나의 순간이므로 "색은 됐는데 지도는 아직" 같은 어긋난 상태가 생기지 않는다.

**판정은 브라우저 안에서 끝난다.** 공항 목록(`procedureData.js`의 `KNOWN_AIRPORTS`), 절차(`procedureData.js`), 지점(`useRouteBriefing.js:97`의 `navpointsById`), 좌표 해석(`manualRouteInput.js`의 `parseCoordinateToken`)이 모두 화면 쪽에 있다. 서버 호출은 경로를 실제로 계산할 때뿐이며, 토큰이 확정된 뒤에만 일어난다.

## 입력칸 동작

**알약은 편집 대상이 아니라 그림이다.** 타이핑은 진짜 입력칸 하나가 맡고, 그 칸이 알약들 사이를 옮겨다닌다. 글자를 치는 곳이 끝까지 브라우저의 진짜 입력칸이므로 커서·선택·붙여넣기·모바일 키보드를 직접 다루지 않는다.

| 조작 | 결과 |
| --- | --- |
| 스페이스 / 엔터 | 지금 칸의 글자가 알약이 되고 칸이 비워진다 |
| 빈 칸에서 백스페이스 | 바로 앞 알약이 지워진다 |
| 알약 사이를 누름 | 그 자리로 입력칸이 옮겨간다 (중간 삽입) |

이 칸은 영문·숫자만 받는다. 한글 입력은 발생하지 않는다.

## 입력칸 아래 한 줄

「경로 적용」이 있던 자리를 채운다. 왼쪽에 상태, 오른쪽에 요약.

```
⚠ 1 error                      328 NM · 0h54m · ETA 17:13Z
```

**왼쪽 (상태)**
- 오류가 있으면 「⚠ N error」. 누르면 이유가 펼쳐진다
- 공항이 비어 있으면 안내: 「출발공항 없음 — 절차·공항 기상은 표시되지 않습니다」. 오류가 아니라 안내다
- 정상이면 비운다

**오른쪽 (요약)** — 총거리 · 소요시간 · 도착예정시각. 거리는 경로 결과에, ETA는 `lib/etaCalc.js`에 이미 있다. 새 계산은 없다.

**요약 숫자는 즉시 교체한다.** 부드럽게 굴리지 않는다 — 중간에 지나가는 값은 어떤 경로에도 해당하지 않는다. [UI 모션 스펙](2026-08-15-ui-motion-design.md)의 X-3과 같은 규칙이다.

## 오류 문구

종류별로 다른 문구를 낸다. 오타인지 우리 자료에 없는 것인지 구분되어야 한다.

```
GONXA — 그런 지점이 없습니다
Y999  — 그런 항공로가 없습니다
RKZZ  — 그런 공항이 없습니다
```

## 공항이 없는 경로

공항은 지울 수 있다. 경로 계산은 진입·이탈 FIX만 있으면 돌아간다(`lib/routePlanner.js:698` `canBuildBriefingRoutePath`). 공항을 요구하는 것은 화면 쪽 조건 하나뿐이다(`RouteBriefingPanel.jsx:274`).

공항이 없으면 아래가 **조용히 비지 않고 안내와 함께** 빠진다:

| 빠지는 것 | 이유 |
| --- | --- |
| SID / STAR | 절차는 공항에 딸린 것이라 고를 대상이 없다 |
| 출발·도착 공항 기상 (METAR/TAF, 비행범주) | 볼 공항이 없다 |
| 공항 기준 ETD/ETA | 기준점이 없다 |

브리핑에서 목적지 기상이 그냥 없는 것과 "목적지를 정하지 않아 없는 것"은 다르다. 앞엣것은 자료가 없는 것인지 이용자가 정하지 않은 것인지 구분되지 않는다.

이로써 "항공로만 보고 싶다"가 정식 사용법이 된다.

## 손대는 곳

| 파일 | 무엇 |
| --- | --- |
| 새 파일 | 토큰 입력칸 부품 |
| 새 파일 | 토큰 판정기 (글자 → 종류) |
| `RouteBriefingPanel.jsx` | 문자열 칸 교체, 「경로 적용」 제거, 아래 한 줄 추가, `canSearch` 완화 |
| `useRouteBriefing.js` | 토큰 목록을 원본으로, 선택기 ↔ 목록 연결 |

토큰 판정기는 화면 부품과 분리한다. 판정은 글자를 받아 종류를 돌려주는 순수한 계산이므로 화면 없이 시험할 수 있어야 한다.

## 시험

**깨뜨리면 안 되는 기준선** — 지금 경로 해석과 적용을 검사하는 시험들이다. 이 시험들은 그대로 통과해야 한다.

`lib/manualRouteInput.test.js` · `lib/routeEditor.test.js` · `lib/routePreview.test.js` · `lib/routePreview.interaction.test.js` · `lib/routeDesigns.test.js` · `useRouteBriefing.selection.test.js` · `RouteBriefing.mobile-alternatives.test.js` · `RouteBriefing.mobile-summary.test.js`

**새로 붙일 시험**
- 토큰 판정기: 각 종류가 제대로 판정되는가, 모르는 글자가 오류로 나오는가, 좌표가 해석되는가
- 오류가 있을 때 지도용 경로가 갱신되지 않는가 (결정 5)
- 선택기에서 고른 것이 토큰 목록에 반영되는가 (결정 7)
- 공항이 없어도 경로가 성립하는가 (결정 8)

## 확인 방법

브라우저에서 실제로 돌려 확인한다. 미리보기는 증거가 아니다 — [브라우저 검증](../../policies/verification/browser-verification.md)

- **iPad 실기기**에서 알약 사이로 입력칸이 옮겨갈 때 키보드가 닫히지 않는지. 이 설계에서 가장 위험한 지점이며 데스크톱에서는 재현되지 않는다
- 긴 경로를 쳤을 때 알약 줄이 여러 줄로 접히는 모양
- 오류 상태에서 지도가 실제로 안 바뀌는지
- 밝은 곳에서 네 색이 구분되는지

## 이번 판에 넣지 않는 것

| 항목 | 이유 |
| --- | --- |
| 알약을 끌어서 순서 바꾸기 | 백스페이스로 지우고 다시 치는 것으로 충분하다 |
| 알약 안 고도 표시 (`BULTI (FL160)`) | 고도는 별도 단계에서 다루고 있다 |
| 연료·바람 요약 | 아직 뽑지 않는 값이다 |
| 알약을 눌러 글자로 풀기 | 결정 6 — 백스페이스로 충분하다 |
