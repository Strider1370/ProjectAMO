# 경로 파일 불러오기 재설계 설계

## 목표

조종사는 경로를 우리 앱에서 처음부터 짜기보다 다른 앱(EFB)에서 만든 경로를 불러오는 경우가 더 많다. 지금의 불러오기는 "경로를 앱 안에서 짠다"는 전제로 만든 제약 때문에 외부 파일 상당수를 거부한다. 불러오기를 주 사용 흐름으로 보고, 경로를 읽어들이는 데 성공하기만 하면 그 경로의 기상정보를 보여줄 수 있도록 입구의 제약을 없앤다.

## 배경 — 지금 막히는 지점

기상 계산(경로 위험기상·연직단면도·고도비교)은 이미 좌표를 이은 선 하나(`routeGeometry`)만 있으면 동작한다. FIX 이름도 항공로도 필수가 아니다(`shared/route-model.js:40`, `routeResult`가 없으면 구간 정보를 `not_applicable`로 두고 나머지를 계산한다).

막는 것은 불러오기 입구의 두 가지다.

1. **양끝 공항 강제** — 끝점이 공항 5NM 안이 아니면 불러오기 전체를 거부한다(`useRouteBriefing.js:1517`).
2. **FIX 이름 강제** — 지점 이름이 항법 데이터에 없으면 `"○○ FIX를 찾을 수 없습니다"`로 전체가 실패한다(`routePlanner.js:480`, `routePlanner.js:585`).

경로 모델은 중간 경유점에 대해서는 이미 세 가지(이름 있는 픽스 / 좌표 / 사용자 지점)를 모두 받는다. 출발·도착 두 칸만 등록된 공항 코드를 요구한다. 이 비대칭이 병목이다.

## 범위

- 지원 형식에 **FPL**(Garmin 계열 비행계획 XML)을 추가한다. 기존 GeoJSON·GPX·KML은 유지한다.
- 불러오기는 파일을 해석하지 못하는 경우를 제외하면 **실패하지 않는다**. 공항 미확정, 이름 미해결, 좌표 과다는 모두 성공 처리하고 알림으로 전달한다.
- 출발·도착 공항은 **반드시 확정되어야** 기상 계산이 시작된다. 자동 인식하거나, 못 하면 조종사가 고른다.
- 경로 모델(`shared/route-model.js`)과 경로 생성기(`routePlanner.js`)의 인터페이스는 **변경하지 않는다**. 출발·도착 칸이 공항 코드만 받는 현재 계약을 유지한다.
- 불러온 경로는 직접 짠 경로와 구분되지 않는다. 편집·대체경로 비교·저장이 그대로 동작한다.
- 시뮬레이터 형식(.fms/.pln)과 경로 문자열 붙여넣기는 범위 밖이다.

## 불러오기 흐름

### 1단계 — 읽고 즉시 그린다

파일에서 경로 후보를 뽑으면 공항·이름 해석 여부와 무관하게 지도에 선으로 그리고 그 범위로 확대한다. 조종사는 경로가 들어왔는지를 먼저 확인한다.

파일에 경로 후보가 둘 이상이면 기존 선택 목록(`RouteImportChooser`)을 띄운다. 이 동작은 변경하지 않는다.

### 2단계 — 양끝 공항을 자동 인식한다

각 끝점에서 가장 가까운 공항을 찾는다. 임계거리는 **10NM**으로 한다(현재 5NM).

- **10NM 안에 공항이 있으면** 그 공항으로 출발·도착을 채우고, 파일의 해당 끝점은 공항에 흡수한다(같은 장소를 두 점으로 두지 않는다).
- **없으면** 공항 칸을 비워두고, 파일의 끝점은 경유점으로 남긴다.

FPL은 지점마다 종류(`AIRPORT`/`INT`/`VOR`/`NDB`/`USER`)를 싣는다. 첫·끝 지점이 `AIRPORT`이고 그 식별자가 항법 데이터에 있으면 거리 탐색을 건너뛰고 그 공항으로 확정한다.

자동 인식 결과는 조용히 확정하지 않는다. 인식한 공항과 거리를 알림으로 표시하고, 조종사가 언제든 바꿀 수 있다.

5NM에서 10NM으로 넓히는 근거: 5NM은 대형 공항의 계류장 출발점이나 이륙 후 첫 기록점을 놓친다. 10NM은 인접 공항을 오인할 만큼 넓지 않다. 실물 파일 검증 후 조정할 수 있는 값으로 둔다.

### 3단계 — 공항이 비었으면 조종사가 고른다

`출발·도착 공항을 골라주세요` 알림을 띄운다. 입력 수단은 경로 화면에 이미 있는 출발·도착 공항 선택 칸을 그대로 쓴다. 새 화면을 만들지 않는다.

조종사가 고른 공항은 파일 끝점 **바깥에 덧붙는다**. 파일 끝점을 공항으로 치환하지 않는다 — 치환하면 공항과 파일 시작점 사이 구간이 경로에서 사라진다.

### 4단계 — 공항이 둘 다 차면 기상이 계산된다

경로 위험기상, 연직단면도, 고도비교, 출발·도착 METAR/TAF가 평소대로 동작한다. 이 시점부터 불러온 경로와 직접 짠 경로는 구분되지 않는다.

3단계에서 조종사가 공항을 고른 경우, 두 칸이 모두 채워지는 순간 경로가 자동으로 다시 구성되고 기상 계산이 시작된다. 별도의 실행 버튼을 두지 않는다.

불러온 경로의 비행 방식은 **불러올 당시 조종사가 보고 있던 탭을 따른다.** IFR 탭에서 불러오면 IFR 경로로, VFR 탭에서 불러오면 VFR 경로로 들어간다.

현재 코드는 불러오기에서만 `flightRule: 'VFR'`을 고정한다(`useRouteBriefing.js:1522`). 앱의 다른 모든 경로 경로는 이미 `routeForm.flightRule`로 갈라 처리하고 있으므로(`useRouteBriefing.js:922`, `1016`, `1028`), 이 고정을 제거하고 기존 분기를 그대로 쓴다. 경로 문자열 생성도 같은 기준으로 `formatVfrDraftText`/`formatManualRouteString` 중 하나를 고른다. 새 코드가 아니라 예외 처리를 지우는 변경이다.

IFR 경로 생성기와 VFR 경로 생성기는 지점 해석에 같은 함수(`routePlanner.js`의 `manualPoint`)를 쓰므로, 이름 미해결 지점을 좌표로 넣는 규칙은 양쪽에서 동일하게 동작한다.

어느 쪽으로 불러오든 지점 간 연결은 직선(DCT)이다. 파일에 항공로 식별자가 없기 때문이며, IFR 표기에서도 `RKSI DCT GONAX DCT RKPK`는 유효하다. 불러온 뒤에는 일반 경로와 동일하게 편집할 수 있으므로 조종사가 항공로를 채워 넣거나 비행 방식을 바꿀 수 있다.

## 파일 해석 규칙

### 형식별로 읽는 것

| 형식 | 읽는 것 |
| --- | --- |
| FPL | `waypoint-table`의 식별자·종류·위경도, `route`의 `route-point` 순서, 경로 이름 |
| GPX | `rte`/`rtept`(계획), `trk`/`trkpt`(궤적), `wpt`(지점), 각 지점의 `name` |
| KML | togeojson 변환 후 LineString·MultiGeometry·Point, Placemark 이름 |
| GeoJSON | LineString·MultiLineString·Point·GeometryCollection, `properties.name` |

### 점 솎기 — 이름 유무가 기준이다

현재의 "무조건 20점" 규칙을 대체한다.

- **이름이 붙은 지점은 솎지 않는다.** FPL waypoint, GPX `rtept`·`wpt`처럼 이름이 달린 지점은 조종사가 의도적으로 넣은 것이다. 개수와 무관하게 전부 유지한다.
- **이름 없는 좌표 나열만 솎는다.** GPX `trkpt`, 이름 없는 KML·GeoJSON 선은 기계가 기록한 궤적이다. **경로 모양의 편차가 1NM을 넘지 않는 선까지** 줄인다. 직선 구간은 크게 줄고 선회 구간은 촘촘히 남는다.
- 솎은 뒤에도 **200점을 넘으면 200점에서 끊는다.** 이 상한은 **이름 없는 좌표에만 적용한다.** 이름 있는 지점은 200개를 넘어도 유지한다(실제 계획 경로가 그 규모가 되는 일은 없고, 조종사가 넣은 지점을 개수 때문에 버리지 않는다).

현재 `simplifyRoute`는 목표 점 개수를 맞추려고 tolerance를 이분 탐색한다. 기본 경로를 "1NM 고정 tolerance 한 번"으로 바꾸면 이분 탐색은 200점 상한을 넘긴 경우에만 필요하다.

`simplify-js`의 tolerance는 도 단위이므로 1NM을 위도 기준으로 환산해 쓴다(1NM ≈ 0.0167°). 경도 방향은 위도가 높을수록 실제 거리가 짧아지지만, 한반도 위도대에서 이 차이는 솎기 판정에 영향을 줄 정도가 아니다.

1NM은 기상 격자 간격 대비 충분히 촘촘하다. 실물 파일 검증 후 조정할 수 있는 값으로 둔다.

### 지점 이름 대조

파일의 지점 이름을 항법 데이터에서 찾는다.

| 결과 | 처리 | 알림 |
| --- | --- | --- |
| 찾았고 파일 좌표와 5NM 이내 | 이름 있는 픽스(`kind:'fix'`)로 사용 | 없음 |
| 찾았으나 5NM 초과로 어긋남 | **파일 좌표**(`kind:'coordinate'`)를 사용 | 이름·거리 명시 |
| 못 찾음 | 파일 좌표를 사용, 이름은 표시용으로 보존 | 개수 요약 |

위치가 어긋날 때 파일을 신뢰하는 근거: 같은 식별자가 다른 FIR에 존재하거나 항법 데이터 주기가 오래되었을 수 있다. 조종사가 계획한 위치는 파일 쪽이다.

이 규칙으로 `"○○ FIX를 찾을 수 없습니다"`가 불러오기를 중단시키는 경로가 사라진다.

### 읽지 않는 것

- **고도·속도·시각** — GPX `ele`, FPL의 부가 필드를 포함해 사용하지 않는다. 순항고도와 출발시각은 조종사 입력값으로 유지한다. 기록값을 섞으면 어느 쪽이 기준인지 흐려진다.
- **항공로 식별자** — FPL·GPX 모두 담지 않는다. 불러온 경로는 지점 간 직선(DCT)으로 잇는다.

## 오류와 알림

### 불러오기가 실패하는 경우

아래 세 가지만 실패로 처리한다. 각각 다른 문구를 쓴다(현재는 세 경우가 한 문구로 뭉쳐 있다).

1. **파일을 해석할 수 없음** — 지원 형식이 아니거나 내용이 깨짐.
2. **경로로 쓸 점이 2개 미만** — 해석은 되었으나 선을 그릴 수 없음.
3. **좌표가 유효 범위 밖** — 위도 ±90, 경도 ±180을 벗어난 값.

파일 크기는 **10MB**로 제한한다. 외부에서 온 파일은 내용을 신뢰할 수 없고, 대용량 궤적 파일은 브라우저를 멈추게 한다. 좌표 범위 검증과 크기 제한은 신뢰 경계에서의 입력 검증이므로 생략하지 않는다.

### 성공 시 붙는 알림

경로는 이미 그려진 상태에서 아래 항목을 표시한다.

| 상황 | 문구 | 성격 |
| --- | --- | --- |
| 공항 자동 인식 | `출발 RKSI (3NM), 도착 RKPK (2NM)로 인식 — 다르면 바꾸세요` | 보고 |
| 공항 미확정 | `출발·도착 공항을 골라주세요` | 조치 필요 |
| 이름 미해결 | `지점 3개는 이름을 찾지 못해 좌표로 넣었습니다` | 보고 |
| 이름-위치 불일치 | `WOLDO — 우리 데이터와 위치가 12NM 다릅니다. 파일 좌표를 씁니다` | 보고 |
| 궤적 솎음 | `기록점 5,214개를 187개로 줄였습니다 (경로 오차 1NM 이내)` | 보고 |
| FIR 밖 | `경로 일부가 한국 정보구역 밖 — 기상이 비어 있을 수 있습니다` | 보고 |

조치가 필요한 항목과 단순 보고는 시각적으로 구분한다. 조치 필요 항목은 해소될 때까지 유지한다.

## 검증

### 단위 시험 (`frontend/src/features/route-briefing/lib/routeImport.test.js` 확장)

- FPL 해석 — 지점 이름·종류·좌표, `route-point` 순서 적용, `AIRPORT` 종류로 끝점 확정
- 이름 대조 세 갈래 — 일치 / 5NM 초과 불일치 / 미발견
- 점 솎기 — 이름 있는 지점 불변, 궤적은 1NM 편차 이내, 200점 상한 적용
- 끝점 처리 — 10NM 이내 흡수, 초과 시 경유점 유지
- 무효 입력 — 위도 91, 빈 파일, 점 1개, 크기 초과

### 브라우저 계약 시험 (`frontend/verification/contracts/route-import.spec.mjs` 확장)

- 공항이 인접하지 않은 경로 파일 → 선이 그려지고 공항 선택 안내가 표시됨 → 공항 선택 후 기상 계산 동작
- FPL 파일 → 출발·도착이 자동 확정되고 기상 계산까지 진행
- 이름 미해결 지점이 포함된 파일 → 경고가 표시되되 경로 형상은 온전함
- 같은 파일을 IFR 탭과 VFR 탭에서 각각 불러옴 → 각 탭의 비행 방식으로 들어가고, 양쪽 모두 경로 형상과 기상 계산이 동일함

기존 다중 경로 GPX 계약 시험은 솎기 규칙 변경으로 점 개수 표시가 달라질 수 있으므로 함께 갱신한다.

### 실물 파일 의존성

EFB마다 FPL 작성 방식이 미묘하게 다르다. **ForeFlight 또는 Garmin Pilot에서 내보낸 실제 FPL 파일이 최소 1개 필요하다.** 규격서만으로 구현하면 실물에서 깨진다. 실제로 사용하는 GPX 파일이 있으면 함께 확보해 시험 fixture로 쓴다.

## 하지 않는 것

- 항공로 복원 — 파일에 정보가 없다.
- 파일의 고도·시각 사용.
- 시뮬레이터 형식(.fms/.pln), 경로 문자열 붙여넣기.
- 경로 모델·경로 생성기의 출발·도착 계약 변경 — 공항을 반드시 확정하게 했으므로 불필요하다.
- 공항 없이 기상 계산 — 이번 범위 밖이다. 필요해지면 출발·도착 칸이 좌표를 받도록 넓히는 별도 작업이 된다.
