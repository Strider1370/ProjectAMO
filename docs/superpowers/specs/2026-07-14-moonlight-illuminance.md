## 1. 모델 — USNO Circular 171 (원본 그대로, 독립 검증 완료)

**출처:** Janiczek, P.M. & DeYoung, J.A. (1987), *Computer Programs for Sun and Moon Illuminance
with Contingent Tables and Diagrams*, **US Naval Observatory Circular No. 171.**
원문 PDF: [DTIC AD1112511](https://apps.dtic.mil/sti/trecms/pdf/AD1112511.pdf) (138p)
계수는 부록 BASIC 리스팅(행 1030, 1090–1130, 2160–2250)에서 **직접 전사**했다.

**이 모델을 쓰는 이유 — 다른 게 더 정확해서가 아니라, 이것만 검증 가능해서다:**
- 원문 PDF를 받아 계수를 눈으로 확인했다. **출처가 추적 가능한 유일한 후보.**
- 태양·달·배경광·구름을 **하나의 일관된 체계**로 준다. 태양과 달이 같은 대기 감쇠 함수를 공유한다.
- 태양 쪽은 문헌값 대조를 통과했다(§1-D).
- 미 해군천문대 = NVG 임무계획이 실제로 쓰는 기관.

> **"1987년이면 낡은 것 아닌가?"** — 나이는 판단 기준이 아니다. **추적 가능성과 실측 대조**가 기준이다.
> 참고로 폐기한 GitHub 저장소의 위상함수는 **로멜-젤리거/람베르트 구 법칙(19세기)** 으로 USNO보다
> **더 오래된 뼈대**이며, 검증 이력도 출처 표기도 없다.
> 다만 **USNO 달 위상함수의 정확도는 아직 열린 문제다(§1-E).**

### 1-A. 공통 — 굴절 보정과 대기 감쇠

```
apparentAlt(h_deg):                              // BASIC 2160–2190
  h < -5/6  →  h
  else      →  h + (1 / tan((h + 8.59/(h + 4.42)) · π/180)) / 60

attenuation(HA_deg):                             // BASIC 2200–2250
  U = sin(HA)
  X = 753.6616
  S = asin(X · cos(HA) / (X + 1))
  M = X · (cos S − U) + cos S
  M = exp(−0.21·M)·U + 0.0289·exp(−0.042·M)·(1 + (HA + 90)·U/57.29578)
```

### 1-B. 조도 (lux) — USNO 원본

```
태양:   E_sun = 133775 · attenuation(apparentAlt(태양고도)) / SK         // BASIC 1030
        (133775 lx = 대기권 밖 태양 조도)

달:     ψ = 이각(elongation, rad) = π − 위상각.   보름 ψ=π, 삭 ψ=0
        P = 0.892·exp(−3.343 / tan(ψ/2)^0.632) + 0.0344·(sin ψ − ψ·cos ψ)
        P = 0.418·P / (1 − 0.005·cos ψ − 0.03·sin(달고도))
        E_moon = P · attenuation(apparentAlt(달고도)) / SK               // BASIC 1090–1120
        (달 고도 ≤ 0 이면 0)

야간배경광: E_sky = 0.0005 / SK  lux  =  0.5 mlx                          // BASIC 1130

총 조도:  E_total = E_sun + E_moon + E_sky
```

- ⚠️ `ψ`는 **위상각이 아니라 이각**이다. 위상각을 넣으면 보름달에서 0이 나온다(실제로 밟음).
  `위상각 α = acos(2·fraction − 1)` → `ψ = π − α`.
- **태양과 달이 같은 `attenuation`을 쓴다.** 이게 두 곡선이 물리적으로 어긋나지 않는 이유다.
- ⚠️ **USNO의 `P`에는 지구–달 거리 항이 없다.** 따라서 **슈퍼문이 반영되지 않는다** (§1-E 미해결 항목).

### 1-C. 구름 (SK) — 내장되어 있으나 v1은 안 쓴다

| SK | 원문 정의 |
|---|---|
| 1 | 태양/달 보임, 하늘 70% 미만 흐림 (**맑음**) |
| 2 | 얇은 구름에 가림 |
| 3 | 보통 구름에 가림 |
| 10 | 짙은 층운에 가림 (드묾) |

조도를 **그냥 나누는 제수(divisor)**다. 보름달 천정 397 mlx → SK=3이면 132 mlx.
**v1은 SK=1(맑음) 고정.** 이유: 기상청 SKY 예보값 → SK 1/2/3/10 매핑이 별도 결정이고,
"맑은 하늘 기준 상한값"이라고 화면에 명시하면 v1으로 충분하다. **훅은 열어둔다.**

### 1-E. 달 모델 독립 검증 — Krisciunas & Schaefer (1991)

**검증 출처:** Krisciunas, K. & Schaefer, B.E. (1991), *A Model of the Brightness of Moonlight*,
**PASP 103, 1033.** 원문 스캔: [ADS 1991PASP..103.1033K](https://articles.adsabs.harvard.edu/pdf/1991PASP..103.1033K)
(마우나케아 2800m 실측 기반. USNO와 **완전히 독립적인** 출처)

논문에서 직접 전사:
```
식 (9):   m  = −12.73 + 0.026·|α| + 4×10⁻⁹·α⁴          (α = 위상각, deg; 출처 Allen 1976 p.144)
식 (8):   I* = 10^(−0.4·(m + 16.57))                    [단위: footcandle]
식 (20):  I* = 10^(−0.4·(3.84 + 0.026·|α| + 4×10⁻⁹·α⁴)) [(8)+(9) 결합. 16.57 − 12.73 = 3.84]
```

> ⚠️ **논문 p.1035의 단서 — 이걸 놓치면 36% 틀린다 (v4가 그랬다):**
> *"식 (9)는 … 충효과(opposition effect)를 무시한다. |α| < 7°에서 달의 밝기는 이 관계에서 벗어난다.
> **달이 정확히 보름일 때는 이 외삽값보다 약 35% 더 밝다.**"*

**정면 대조 (대기권 밖 달 조도, lux):**

| 위상각 | K&S91 식(20) | USNO | 차이 |
|---|---|---|---|
| **0° (보름, +35% 충효과 반영)** | **0.4230** | **0.4249** | **+0.5%** |
| 20° | 0.1940 | 0.1675 | −14% |
| 45° | 0.1051 | 0.0907 | −14% |
| 90° (반달) | 0.0285 | 0.0281 | −1% |
| 120° | 0.0082 | 0.0084 | +2% |
| **충효과 구간 밖(α ≥ 7°) 평균 절대차** | — | — | **9.6%** |

**판정: USNO는 정확하다.**
- 보름달에서 **0.5% 차이.** 1987년 해군천문대 모델과 1991년 마우나케아 실측 모델이 사실상 일치.
- 9.6% 평균 차이는 **K&S91이 스스로 밝힌 자기 모델의 rms 불확실도(~23%)보다 작다.**
  두 모델은 서로의 오차범위 안에 있다.

**v4가 왜 틀렸나 (기록):** `V(α)` 공식 자체는 실재했다(= K&S91 식 9). 틀린 것은 **쓰는 방법**이었다.
논문이 그 식 바로 아래 달아둔 "충효과 제외" 단서를 읽지 않고 식만 가져다 썼다.
v4가 "발견"했다는 *USNO의 36% 과대*는 **논문이 "약 35%"라고 적어둔 충효과 그 자체**였다.
v4를 그대로 출시했다면 **보름달이 26% 어둡게** 나왔을 것이다.

**교훈: 공식을 가져올 때는 공식 주변의 산문도 읽는다. 계수만 복사하면 단서를 놓친다.**

### 1-F. 알려진 한계 (수용, 고치지 않음)

**USNO의 `P`에는 지구–달 거리 항이 없다 → 슈퍼문이 반영되지 않는다.**
K&S91 식(20)도 마찬가지로 평균 거리 기준이다. 실제 편차는 **±10~15%** 수준.

거리 보정은 역제곱 법칙(`× (384400/d)²`)이라 물리적으로 명백하지만, **v1에서는 넣지 않는다.**
- 두 1차 출처 **모두** 평균 거리 기준이므로, 보정을 넣으면 **검증된 것과 다른 것을 쓰게 된다.**
- ±15%는 등급 경계(§5-B)를 거의 흔들지 않는다(경계가 5배 간격).
- **넣으려면 별도 결정 사항으로 올린다.** 조용히 추가하지 않는다.

### 2-C. 결정적 사유 — 정확도가 아니라 **범위**

정확도만 놓고 보면 "고쳐 쓸 수도 있다"가 정직한 답이다. 폐기 사유는 다음이다:

1. **태양을 계산하지 못한다.** 달빛 전용 코드다. 총 조도(§4-2)를 보여주려면 태양 박명 모델을
   다른 출처에서 가져와 붙여야 하고, 그러면 **출처가 다른 두 모델의 잡종**이 된다.
   USNO는 태양·달·배경광이 **같은 대기 감쇠 함수를 공유**해 물리적으로 어긋나지 않는다.
2. **구름(SK)이 없다.** USNO는 같은 체계 안에 있다.
3. **검증 이력이 없다.** USNO는 문헌값 대조를 통과했다(§1-D).
4. NVG 운용이 실제로 쓰는 기관의 정본이다.

> 한 줄 요약: **고쳐도 절반밖에 못 하고, 그 절반마저 우리가 가장 신경 쓰는 어두운 구간에서 부정확하다.**

⚠️ 원본 `api.py:5`, `API/CLOUDS.py:11`에 **기상청 apihub 키가 평문 커밋**되어 있다. 폐기·재발급 대상(이 스펙 범위 밖).

## 4. 모듈 설계

### 4-1. 계산 — `frontend/src/shared/astro/illuminance.js` (신규, ~60줄)

```
illuminanceAt(date, lat, lon, sk = 1) -> {
  sun, moon, sky, total,     // lux
  sunAlt, moonAlt,           // deg
  fraction,                  // 조명률 0~1
}

nightSummary(eveningDate, lat, lon) -> {
  peakMoonLux, peakAt,       // 그 밤 달빛 최대와 그 시각
  fraction, phase,           // 달 모양 (자정 기준)
  grade,                     // §5
  moonrise, moonset,
  sunset, sunrise,
  dusk, nauticalDusk, night, nightEnd, nauticalDawn, dawn,   // 박명 경계
  samples,                   // [{ t, moon, total }] — 차트가 그대로 쓴다
}
```

- **"하룻밤" = 그날 일몰 ~ 다음날 일출.** 자정~자정이 아니다. 달은 자정을 넘겨 뜨고 지므로
  자정에서 자르면 "어두운 밤"을 못 찾는다. 운용 감각과도 맞는다("오늘 밤" = 오늘 저녁부터).
- 표본 간격 **10분**. 1시간이면 충효과 급등과 박명 급락을 놓친다.
- 달력은 이 함수를 그 달 날짜 수만큼 호출. 31일 × ~60표본 ≈ 1,900회 — 순수 산술이라 즉시 끝난다.
  **캐시·백엔드 불필요.**

> ### ⚠️ suncalc 2.x 단위 함정 — 이 세션에서 **두 번** 밟았다
> `getPosition()`과 `getMoonPosition()`은 `altitude`·`azimuth`를 **도(°)로 반환한다.**
> suncalc **1.x는 라디안**이었고 웹 예제 대부분이 1.x 기준이라 `* 180/Math.PI`를 곱하게 되는데,
> 그러면 고도가 1096° 같은 값이 되어 조도가 음수·수백만으로 튄다.
> **곱하지 말 것.** `distance`는 km. **테스트에 `|altitude| ≤ 90` 단언을 반드시 넣는다.**

**검증 (필수, `illuminance.test.js`):**

| 입력 | 기대 |
|---|---|
| 태양 고도 +90° | `123,000 < sun < 125,000` lx |
| 태양 고도 −6° | `2 < sun < 4` lx (시민박명 끝 ≈ 3.4) |
| 보름달(ψ=π) 천정 | `0.1 < moon < 0.45` lx |
| 보름/반달 비 | `> 10` (선형 아님을 고정) |
| 아무 시각 | `|sunAlt| ≤ 90`, `|moonAlt| ≤ 90` (단위 함정 회귀 방지) |
| 달 고도 < 0 | `moon ≈ 0` |
| 한 달치 `nightSummary` | `peakMoonLux` 최댓값 날짜가 보름 ±1일 안 |
| 총 조도 | `total ≥ sun`, `total ≥ moon`, `total ≥ 0.0005` (항상 양수) |

### 4-2. 화면 — `frontend/src/features/airport-panel/tabs/MoonTab.jsx` (신규)

공항 패널 **7번째 탭 `달빛`**. 기존 구조(`tabs/` 아래 파일 하나 = 탭 하나)를 그대로 따른다.
`frontend/scripts/airport-panel-capture.mjs:17`의 `TABS` 배열에도 추가한다.

**목업: [`docs/design/moonlight-tab-mockup.html`](../../design/moonlight-tab-mockup.html)** — 2026년 7월 RKSI **실측 계산값**으로 렌더 (가짜 데이터 아님).

**① 요약 줄** — 달 모양(야간색 칩) · 등급 · 조명률 · 월출/월몰/최대시각 · 달빛 최대 mlx

**② 지면 조도 곡선** — 일몰 ~ 다음날 일출

- **곡선 2개:**
  - **총 조도** (태양+달+별빛) — 짙은 실선. *이게 "지금 지면이 얼마나 밝은가"의 답이다.*
  - **달빛 기여분** — `--moon-lit` 실선. 총 조도 중 달의 몫.
  - 두 선이 **겹치는 구간 = 달빛이 지면을 지배하는 시간.** 이게 이 차트의 핵심 정보다.
- **왜 총 조도가 필요한가:** 달빛만 그리면 일몰 직후 곡선이 수십 mlx를 지나가는데,
  그 시각 실제 지면은 **84만 mlx**(태양)다. 달빛 숫자만 보면 **1만 배 틀린 값을 읽게 된다.**
  박명 밴드는 "밝다"고 말만 할 뿐 **얼마나**를 답하지 못한다.
- **세로축 로그** (0.3 mlx ~ 100만 mlx, 6단). 태양-달 범위가 100만 배라 선형은 불가능.
- **박명 밴드** (§4-2-A) + **별빛 배경선 0.5 mlx** + 최대점 마커 + 월출·월몰 눈금
- 손으로 만든 SVG (`VerticalProfileChart.jsx` 패턴)

**③ 월간 달력** — 이번 달, 7열. 한 칸 = 하룻밤(그날 저녁 시작). 상세는 §5-B.
   - 칸을 누르면 그 밤이 ②에 로드된다 → **날짜 선택기 겸용** (별도 picker 불필요)

**④ 캡션** — 모델 출처 + `맑은 하늘 기준. 구름 미반영.`

### 4-2-A. 박명 밴드

| 구간 | 태양 고도 | suncalc `getTimes()` |
|---|---|---|
| 시민박명 | 0° ~ −6° | `sunset` → `dusk` |
| 항해박명 | −6° ~ −12° | `dusk` → `nauticalDusk` |
| 천문박명 | −12° ~ −18° | `nauticalDusk` → `night` |
| **완전한 어둠** | < −18° | `night` → `nightEnd` |
| (새벽 역순) | | `nightEnd` → `nauticalDawn` → `dawn` → `sunrise` |

- 가장 짙은 밴드에 `완전한 어둠 21:28–03:52` 라벨. 여름밤은 짧다(2026-07-29 인천 = 6시간 24분).
- ⚠️ 고위도/백야에서는 `night`·`nightEnd`가 **`Invalid Date`**로 온다. 한국에선 안 나지만
  해외 공항으로 확장하면 터진다 → **null 가드 필수** (밴드만 생략, 곡선은 그대로).

## 5. 색 설계

### 5-A. 등급에 유채색을 쓰지 않는다

**초안은 밝은 밤을 앰버로 칠했다 — 디자인 헌법 위반이라 폐기했다:**
- 앰버는 이 프로젝트에서 **IFR = 기상 위험**이다(`--cat-ifr: var(--level-amber)`).
  달빛에 쓰면 **"한 색에 두 의미"**(design-language §3 금지)가 되고, 조종사는 주황을 위험으로 읽는다.
- design-language §2-2: **"정상=무채색, 위험만 색."** 달빛은 물리량이지 위험도가 아니다.

**→ 등급은 이름·숫자·막대·명도로만 표현한다.**

### 5-B. 달력 칸

| 등급 | 달빛 최대 | 칸 |
|---|---|---|
| **밝음** | ≥ 100 mlx | 중립 흰 면 + 헤어라인. 막대 길이로 구분 |
| **보통** | 20 ~ 100 mlx | 〃 |
| **어두움** | 2 ~ 20 mlx | 〃 |
| **무월광** | < 2 mlx | **반전 — `--surface-night` 면 + 흰 글자** |

- **반전은 무월광 하나뿐.** 램프가 아니라 이진 강조. 사용자가 달력에서 찾는 것은
  "이번 달 어느 밤이 어두운가" 하나이므로 그것만 pre-attentive하게 튀어야 한다.
  (4단계 회색 램프를 깔아봤더니 전체가 회색 덩어리가 되어 보름과 반달이 구별되지 않았다 — 실측)
- 칸 하단 **가로 막대**: 길이 ∝ `log(mlx)`, 색 `--accent`. 차고 기우는 리듬이 막대로 스캔된다.
- 숫자(mlx) + 조명률(%) + 달 모양 + 막대 + 범례 = design-language §3의
  **"색만으로 등급 구분 금지"** 요구를 중복 인코딩으로 충족.
- 임계값 `2 mlx`는 야간배경광(0.5 mlx)의 4배. 그 아래면 달의 기여가 별빛에 묻힌다.

### 5-C. 예외 — 달 원반의 노랑

**달 아이콘의 빛나는 면 + 차트의 달빛 곡선에만** `--moon-lit: #E8B54B`.

정당화 — design-language §4 색 3버킷의 **"관습 차용"**: 노란 달은 만국 공통 관습이며,
**"달"이라는 사물의 정체성 색**이지 위험도 신호가 아니다 (착빙=파랑과 같은 논리).

**제약:**
- 이 탭에서 유채색은 **이것 하나뿐.** → "이 노랑 = 달" 단일 의미가 유지된다.
- 칸 배경·텍스트·배지·등급 표시에 **절대 금지.**
- IFR 앰버(`#92400e`/`#fdecc8`)와 명확히 구분되는 톤. 위험색으로 오독되면 실패다.
- 달 모양은 조명률의 **그림 표현**일 뿐 등급이 아니다.

### 5-D. 신규 토큰 — 확정 시 디자인 헌법에 등록

| 토큰 | 값 | 용도 | 제약 |
|---|---|---|---|
| `--surface-night` | `#1c2530` | 무월광 칸 배경, 달 아이콘 칩 배경 | 배경 전용 |
| `--moon-lit` | `#E8B54B` | 달 원반 + 달빛 곡선 **전용** | 이 탭의 유일한 유채색 |

## 7. 참고

- 항공에서의 위치: 민간 야간 VFR 규정은 달빛을 **다루지 않는다**(일몰/일출·시정·운고만).
  조도를 실제로 쓰는 곳은 **NVG 운용**이며 단위는 lux가 아니라 **조명률 %** 와 **밀리럭스**.
- 표출 관례: Clear Sky Chart(하늘 어둡기 등급), LightPlan(달력 + 조명률 %), USNO(월출월몰 + 조명률 %)
  — **어느 도구도 lux 원값을 전면에 노출하지 않는다.** 우리도 등급·조명률을 병기한다.
- ⚠️ **계절 효과 (버그 아님).** 여름 보름달은 남중고도가 낮아(2026-07-29 인천 = **31°**)
  최대 **135 mlx**에 그친다. 겨울 보름달은 고도 70°대까지 올라 훨씬 밝다.
  따라서 **여름에는 `밝음`(≥100) 칸이 드물다.** "여름밤이 겨울밤보다 어둡다"는 실제 물리를
  그대로 보여주는 것이므로 **임계값을 계절 상대값으로 바꾸지 않는다.**
