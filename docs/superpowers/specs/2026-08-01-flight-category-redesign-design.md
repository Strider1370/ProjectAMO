# flight_category 오버레이 재설계 — 설계 명세

**작성일**: 2026-08-01
**상태**: 설계안 (사용자 검토 대기)
**대체 대상**: `docs/superpowers/archive/specs/flight-category-overlay.md` (2026-06-08, v1.1)

---

## 1. 목적

VFR 비행계획을 세울 때 **"출발지와 목적지 사이 어디가 시계비행 기준에 못 미치는가"**를 지도 한 장으로 보여준다.

기존 스펙에는 목적이 적혀 있지 않았다. 무엇을 하는가만 있고 왜 하는가가 없어 "품질이 나쁘다"를 판정할 기준조차 없었다. 이 문서는 목적을 먼저 고정한다.

### 1.1 판정하지 않는다

화면은 기준선 대비 위치만 보여주고 **판단은 조종사가 한다.**

- 별표 24는 **비행시정**(조종석에서 전방으로 본 거리) 기준인데 시정 자료는 지상 관측 기반 **지상시정**이다. 연무·황사처럼 에어로졸 층이 두꺼울 때 둘은 크게 갈린다.
- 별표 24의 F·G 저고도 기준에는 "지표면 육안 식별", "구름을 피할 수 있는 거리"처럼 수치화 불가능한 조건이 있다.
- 운고 면은 **모델 산출**이지 관측이 아니다.

화면에는 각 자료의 출처와 성격을 항상 표기하고 "VMC 충족" 같은 단정 표현을 쓰지 않는다.

### 1.2 범위 밖

- 예보 시간축 선택(슬라이더) — 현재 시각 한 장 + 추세만
- 경로 자동 판정, 비행시정 추정
- VFR 항공지도 대체
- 관측으로 모델값을 덮어쓰는 수치 병합 (5.4 참조)

## 2. 배경 — 왜 껐고, 실제 문제가 무엇이었나

기능은 `backend/src/index.js:153`(시작 수집)과 `:203`(cron) 두 줄이 주석 처리되어 **꺼져 있다.**

> TEMP 중단: flight_category(sfc_vis 27MB+ctps 18MB/시간 = ~1GB/일)를 KIM 30h 용량 확보 위해 임시 OFF.

끈 커밋은 `f4fefdd`이며 메시지에 `콜 ~82%, 용량 ~83%로 일일 한도 내 유지`가 적혀 있다.

그러나 이번 조사에서 **용량과 별개로 정확도 결함 여러 건**을 발견했다. 품질이 나쁘게 보였던 주된 원인은 이쪽이다.

### 2.1 좌표 버그 — 투영 불일치

`sfc_grid_latlon.nc` 원본 확인 결과 격자는 **Lambert Conformal Conic**이다(`map_pro` 명시, 표준경위도 126°E/38°N, 격자 0.5 km, `map_sx`/`map_sy` = 880/1540). 현재 구현은 **위경도 등간격 평면**으로 가정한다.

**행 순서는 정상이다.** `.nc`의 row 0은 남쪽이지만 `parseSfcAscii`가 41–49행에서 이미 북쪽 우선으로 뒤집고 있고, `sfcPixelToLatLon`의 관례(row 0 = 북)와 일치한다.

행 뒤집기를 반영한 실제 위치 오차 (남한 33–39°N / 125–130°E):

| | 값 | 0.5 km 격자 환산 |
|---|---|---|
| 남한 평균 | **13.5 km** | 27 셀 |
| 남한 최대 | **44.1 km** | 88 셀 |
| 전체 평균 | 23.1 km | |

0.5 km 해상도 자료를 수십 셀씩 밀어놓는 오차이므로 고칠 값어치가 있다. 폴리곤 좌표를 만드는 `pixelToLonLat()`과 CTH 룩업을 만드는 `getCthLookup()`도 같은 가정을 쓰므로 함께 틀린다.

**투영 파라미터는 WGS84 타원체다.** 저장소의 기존 `lib/lcc-projection.js`는 구면 근사(R = 6371009)라 같은 표준경위도로도 최대 2.2 km 잔차가 남는다. WGS84 타원체 공식으로 계산하면 `.nc` 값을 **오차 0.000 km로 재현**한다(표본 8점 검증).

> **부수 발견**: `ctps-grid.js`도 같은 구면 `latLonToEN`을 쓴다. CTPS 격자가 동일한 WGS84 LCC라면 최대 약 2 km(픽셀 크기 2 km 기준 1픽셀) 어긋날 수 있다. 이번 범위에서는 **CTPS 동작을 바꾸지 않고** 검증 항목으로만 남긴다 — `구름 꼭대기` 레이어가 같은 모듈을 쓰고 있어 영향 범위가 넓다.

### 2.2 결측을 VFR로 분류

`flight-category-processor.js:28-29`

```js
const vc = vis_m < 0 ? 'VFR' : ...
const cc = ceil_ft < 0 ? 'VFR' : ...
```

운고 지점이 없으면 격자 전체를 −1로 채우므로(`:263`) **자료가 없을수록 화면이 안전해 보인다.**

### 2.3 운고 면의 근거가 7개 지점

`getAmosCeilingPoints()`는 AMOS 공항만 쓴다. `shared/airports.js`에서 `amos_stn`이 있는 곳은 **7곳**(RKSI·RKSS·RKPC·RKJB·RKJY·RKPU·RKNY)뿐이다.

2026-06-08 계획서 `:1140`이 "ASOS CH_MIN 96개 지점을 추가하라, 1차 배포 후 별도 태스크"라고 갭을 남겼으나 수행되지 않았다(`shared/asos-stations.js` 부재). 계획서는 "AMOS 15개"라 적었지만 실제 운고를 주는 곳은 절반인 7곳이다.

worst-case 규칙 때문에 **가장 근거가 약한 성분이 결과를 지배**했다.

### 2.4 CTPS 중복 수집

`convective-satellite-processor.js:9`가 `config.flight_category.ctps_url`을 사용해 **위성 수집(5분 주기)마다 CTPS를 이미 받고 있다.** 프론트 레이어 `구름 꼭대기`가 그것을 쓴다. 켜져 있던 시절에는 같은 자료를 두 번 받았다.

### 2.5 원 자료의 성격

기상청 「기상자료 3차원 객관분석 기술 개발」(2022.5)에 따르면 지상 격자는 **2단계 Barnes 객관분석**(영향반경 35km / 12km)으로 만든다. 기술노트 기준 분석 지점은 ASOS 96 + 기상청 AWS 509 + 경기도 AWS 84 = 689소이며, 기상청 관측소의 **64%가 해발 100m 이하**다. 산악 값은 저지대 관측이 끌려 올라간 결과라는 한계가 원 자료 단계에 있다.

단 이 노트는 기온·습도·눈비 판별을 다루며 **시정은 언급하지 않는다.**

### 2.6 관측 실측 (2026-08-01)

`kma_sfctm2.php?stn=0`은 **ASOS 97개 지점만** 반환한다. AWS는 포함되지 않으며 **AWS에서 운고를 받을 방법은 없다.**

7개 시각 표본:

| 시각(KST) | 지점 | 운고 보고 | 시정 보고 | 전운량>0 |
|---|---|---|---|---|
| 07-26 03시 | 97 | 67 | 95 | 89 |
| 07-28 03시 | 97 | 66 | 95 | 85 |
| 07-29 03시 | 97 | 70 | 96 | 87 |
| 07-30 03시 | 97 | 11 | 96 | 21 |
| 07-31 03시 | 97 | 7 | 96 | 10 |
| 07-31 15시 | 97 | 33 | 96 | 66 |
| 08-01 03시 | 97 | 10 | 97 | 25 |

- **시정은 항상 95~97개 전부 보고** — ASOS 전 지점에 시정계가 있다.
- **운고 보고 수는 구름 낀 지점 수를 따라간다.** 센서 부재가 아니라 구름이 없어 보고할 운고가 없는 것이다. 흐릴 때는 대부분이 보고한다.
- 그러나 최대 70점이라도 남한 100,000 km²에서 **평균 간격 약 38 km**다. 기술노트가 시정·기온 격자에 쓴 Barnes 2단계 영향반경 12km의 3배이며, 맑은 날 10점이면 약 100 km가 된다. **운고를 지점 보간으로 면화하기에는 부족하다.**

## 3. 좌표계 수정 (최우선)

나머지 계산이 이 위에 얹히므로 먼저 고친다.

**WGS84 타원체 LCC 함수를 새로 추가한다.** 기존 구면 함수(`latLonToEN` / `enToLatLon`)는 CTPS가 쓰고 있으므로 **건드리지 않는다.**

| 제원 | 값 |
|---|---|
| 투영 | Lambert Conformal Conic, **WGS84 타원체** |
| 표준위도 | 30°N / 60°N |
| 원점 | 38.0°N, 126.0°E |
| 격자 크기 | 500 m |
| 격자 수 | 2049 × 2049 |
| 원점 격자 위치 (`map_sx`/`map_sy`) | col 880 / row 1540 (남쪽 기준) |

격자 인덱스 → 좌표 변환:

```
easting  = (col - 880)  × 500
northing = (rowFromSouth - 1540) × 500
(lat, lon) = enToLatLon84(easting, northing)
```

`parseSfcAscii`가 행을 북쪽 우선으로 뒤집으므로 `rowFromSouth = SFC_H - 1 - row`다.

`.nc`(7 MB)를 정적 자산으로 넣는 대안은 채택하지 않는다 — 2049²×2 float32(약 33 MB)를 메모리에 올려야 한다. **`.nc`에서 뽑은 표본 좌표를 테스트 픽스처로** 커밋해 계산이 실제 격자와 일치하는지 확인한다.

**수정 대상**: `sfcPixelToLatLon()`, `pixelToLonLat()`, `getCthLookup()`.

## 4. 두 개의 독립 레이어

시정과 운고를 **하나의 색으로 합치지 않는다.** 출처와 갱신 주기가 근본적으로 다르기 때문이다.

| | 시정 면 | 운고 면 |
|---|---|---|
| 출처 | 기상청 지상 관측 객관분석 (`obs=vs`) | **KIM 수치모델 `cld`** |
| 성격 | 관측 기반 | 모델 산출 |
| 갱신 | 10분 | KIM 발표 주기 (하루 4회 추정, 계획 단계 확인) |
| 해상도 | 0.5 km 격자 | 7.4 × 9.3 km 격자 |

합치면 worst-case 규칙이 다시 약한 쪽(모델·저해상도·저빈도)에 결과를 넘겨준다. 이는 2.3에서 확인된 실패 방식과 같다. 사용자는 레이어를 각각 켜고 끈다.

## 5. 자료별 역할

각 자료를 **그것이 실제로 아는 것**에만 쓴다.

| 자료 | 아는 것 | 쓰는 방식 |
|---|---|---|
| 지상 시정 격자 | 지상시정 분포 | **시정 면** |
| KIM `cld` + `hgt` | 격자별 층 운량과 그 고도 | **운고 면** |
| 위성 CTPS | 구름 **꼭대기** 고도 | **"구름 없음" 한 방향 마스크** |
| ASOS·AMOS 운고 | 그 지점의 실제 운저 | **지점 표시** (덮어쓰지 않음) |

### 5.1 시정 면

`nph-sfc_obs_nc_api?obs=vs&disp=A`를 직접 수집한다. **ASOS 시정은 따로 받지 않는다** — 이 격자가 이미 ASOS/AWS 시정 관측을 객관분석한 결과물이므로 중복이다.

기준선은 **5,000 m**(별표 24, 해발 10,000ft 미만 구간). 별표 24의 8,000m는 해발 10,000ft 이상 기준이라 지상시정 면에 얹기에 층위가 맞지 않아 쓰지 않는다.

밴드:

| 시정 | 표시 |
|---|---|
| < 3,000 m | 진한 빨강 |
| 3,000 ~ 5,000 m | 주황 |
| 5,000 ~ 7,000 m | 옅은 노랑 (기준 충족이나 여유 적음) |
| ≥ 7,000 m | 색 없음 |

등치선을 세 겹 떠서 농도로 표현한다. 연속 격자 이미지는 전송량이 커지므로 쓰지 않는다.

### 5.2 운고 면 (KIM `cld` 기반)

미국 GFA가 운고·시정 면을 NBM 격자에서 만드는 것과 같은 방식이다. GFA는 모델을 면으로, METAR를 지점으로 쓰며 둘을 섞지 않는다.

`cld`는 KIM 원본 `frcc`, CF 표준명 `cloud_area_fraction_in_layer`, 단위 무차원 0~1이다(`2026-05-20-kim-icing-potential-layer.md:33`). 저장 형식은 `int16-scaled-json-v1`, 스케일 0.0001, 결측 −32768.

**운저 계산**: 저층부터 위로 훑어 `cld`가 임계값 이상인 첫 층의 `hgt`를 운저로 삼는다.

- **탐색 시작은 975 hPa**. 1000 hPa는 평균 고도 36 m로 지표에 너무 붙어 지형 아래 격자가 많고, 실측에서 `cld ≥ 0.6`이 0%였다.
- **임계값 초기값 0.6.** 항공에서 ceiling은 BKN(5/8) 이상이 관례다. 계획 단계에서 흐린 날 표본으로 조정한다.
- 고도는 표준대기 환산이 아니라 격자별 `hgt`를 쓴다.

실측 분포 (`hf000`, 2026-07-31 06Z, 34,645점 — 대체로 맑은 시각):

| 층 | 평균 고도 | 최대 | 중앙값 | cld ≥ 0.6 |
|---|---|---|---|---|
| 1000 hPa | 36 m | 0.800 | 0.000 | 0.0% |
| 975 hPa | 261 m | 0.920 | 0.000 | 0.8% |
| 950 hPa | 491 m | 1.000 | 0.000 | 2.0% |
| 925 hPa | 727 m | 1.000 | 0.000 | 3.3% |
| 900 hPa | 969 m | 1.000 | 0.000 | 3.5% |

**한계를 명시한다.** 저층 기압면 간격이 200~250 m라 §172①의 450 m(1,500 ft) 기준선이 975 hPa(261 m)와 950 hPa(491 m) 사이에 걸린다. 운저를 그 단위로만 짚을 수 있으므로 "1,500 ft 미만인가"를 단정하지 않고 층 구간으로 표시한다.

밴드는 1,500 ft(450 m)를 기준으로 **그 아래와 근처 두 구간만** 그린다. 900 m를 넘으면 색을 칠하지 않는다 — 시정 면이 7,000 m 이상을 비워두는 것과 같은 규칙이다. "색 없음 = 여유 있거나 구름 없음"으로 범례에 명시한다.

세 번째 밴드를 두지 않는 이유: 900 m 초과 구간은 국토 대부분을 덮어 전송량만 키우면서 "여기는 괜찮다"는 정보밖에 주지 않는다. 구름이 높다는 것과 구름이 없다는 것의 구분이 필요해지면 그때 추가한다.

### 5.3 위성 마스크

위성 CTPS는 구름 **꼭대기** 고도이므로 운저를 말할 수 없다. 다만 **"여기는 구름이 없다"는 한 방향으로는 유효**하다. CTPS가 무효(fill 또는 품질 불량)인 격자는 운저 없음으로 처리한다.

위성 프로세서가 발행한 `data/satellite/convective/ctps_{tm}.bin`을 읽는다. **별도 수집하지 않는다** — `fetchCtps()`·`parseCthBuffer()`를 제거한다.

재사용 가능성은 검증했다. `AMOCTPS1` 이진의 픽셀 인덱스가 `ctpsIndexForLatLon()`이 만드는 인덱스와 일치하고(900×900, 2000 m, ulEasting −899000, ulNorthing 899000), `decodeCtpsRecord()`가 무효 픽셀에 `null`을 반환한다. 현행보다 낫다 — 현행은 품질 플래그를 보지 않지만 저장본은 `flag !== 0`을 이미 걸러냈다.

### 5.4 관측 지점 표시 (덮어쓰기 없음)

ASOS·AMOS의 실제 운고를 **지점으로 표시**한다. 모델 면 위에 얹되 **값을 덮어쓰지 않는다.**

덮어쓰지 않는 이유:

- 모델 800 m, 관측 300 m인 지점에 관측을 꽂으면 불연속이 생긴다. 부드럽게 이으려면 결국 보간해야 하고, 그러면 2.6에서 확인한 38 km 간격 IDW로 되돌아간다.
- GFA도 섞지 않는다. 모델은 면, 관측은 점으로 두고 조종사가 조정한다.

대신 **모델과 관측이 벌어진 지점을 눈에 띄게** 한다. 지점 표식의 색이나 테두리로 차이를 보이되 면의 값은 고치지 않는다. "어디를 믿으면 안 되는지"를 알려주는 것이 목적이다.

ASOS 지점 좌표 테이블은 `shared/asos-stations.js`로 신설한다. `stn_inf.php?inf=SFC`가 97지점의 `STN / LON / LAT / STN_KO / HT`를 준다(실측 2026-08-01: 97행, 응답 22 KB, EUC-KR). 관측 97지점 전부가 이 표에 있다 — 좌표 누락 0을 확인했다.

`CH_MIN`(100 m 단위)을 피트로 변환한다. **−9는 결측이자 "구름 없음" 표시이므로 변환 전에 제외한다.** 거르지 않으면 −2,953 ft가 나온다.

```
CH_MIN === -9  →  운고 없음 (지점을 목록에서 뺀다)
ceiling_ft = CH_MIN × 100 × 3.281
```

**갱신 주기는 매시 1회다.** `kma_sfctm2.php`는 정시에만 자료가 있다(실측: `tm=202608012100` 97행, `tm=202608012110`·`202608012130` 0행). 더 조밀한 주기는 현재 인증키로 열리지 않으며(`kma_sfctm3`·`kma_sfctm5`·`nph-aws_min` 모두 403 "활용신청이 필요한 API"), 열려도 실익이 낮다 — 구름은 목측 요소라 자동관측 분자료에 운고가 없고, `nph-aws_min`은 ASOS가 아니라 AWS다(§2에서 AWS 운고 불가를 이미 확인). 그래도 수집 주기는 설정값으로 빼둔다.

보고 지점 수는 기상에 따라 크게 변한다. 스펙 초안은 7~70개로 적었으나 **맑은 날에는 그보다 적다** — 2026-08-01 21시 실측은 97곳 중 **4곳**이었다(서울 108: 전운량 0, `CH_MIN` −9). 점이 몇 개 없는 것이 정상 상태이므로 산출물에 보고 지점 수를 담아 화면이 이를 구분할 수 있게 한다. 흐릴 때 많아지므로 운고가 실제로 문제되는 날에 지점이 가장 촘촘하다.

### 5.5 결측

판정에서 제외하고 **별도 폴리곤**으로 만든다. `vis_m < 0 ? 'VFR'` 분기는 삭제한다.

시정 격자의 81.8%가 결측이고 대부분 해상·국외이므로 **기본은 표시하지 않고 토글로 켠다.** 범례에 **"색 없음 = 기준 충족 또는 자료 없음"**을 명시한다.

## 6. 추세

시정 면에만 적용한다. 운고는 모델 발표 주기가 길어 추세 의미가 약하다.

사이클마다 128×128 조회 격자를 남기고 3시간 전과의 차이를 낸다. 20분 주기이므로 3시간에 9점이 확보된다. **면 전체에 화살표를 그리지 않고 점 조회에 수치로만 넣는다.**

## 7. 점 조회

지도에서 한 지점을 누르면:

```
시정   4,200 m          (지상 관측 격자)
       3,800 m — 청주 12km  (가장 가까운 ASOS 실측)
운고   950~975 hPa 사이  (KIM 모델)
       1,200 ft — 청주      (관측 지점값)
추세   지난 3시간 시정 −2.1 km
```

여유 비율과 제한 요인은 표시하지 않는다. 두 값이 나란히 보이면 어느 쪽이 걸리는지 바로 읽힌다.

## 8. 산출물

`store.save('flight_category_overlay', …)` 한 건에 담는다. 원본 격자는 저장하지 않는다.

| 항목 | 내용 |
|---|---|
| `visibility.geojson` | 시정 3밴드 + 결측 1밴드 폴리곤 (turf simplify) |
| `ceiling.geojson` | 운고 2밴드 폴리곤 (§5.2) |
| `stations` | ASOS·AMOS 운고 지점값과 모델값 차이 |
| `query_grid` | 128×128 — 시정(m), 운고(ft). **음수가 결측이다** |
| `trend` | 3시간 전 `query_grid`와의 시정 차이 |
| `sources` | 운고 보고 지점 수, CTPS 프레임 시각, KIM run·hf, 결측 비율 |

**결측 플래그를 따로 두지 않는다.** 시정 값이 음수면 그 자체로 결측이다(파서가 −999를 −1로 매핑). 플래그를 병기하면 같은 사실을 두 곳에 적게 되고 둘이 어긋났을 때 어느 쪽이 참인지 정할 근거가 없다. 면에서 쓰는 `classifyVisibility`의 규칙과 동일하게 음수를 결측으로 읽는다.

**보존 정책을 함께 바꾼다.** `max_files_per_category`가 10이면 20분 주기에서 200분치만 남아 3시간 추세가 경계에 걸린다. `max_files_by_type`에 `flight_category_overlay: 12`를 추가한다(3시간 = 9사이클 + 여유). `lightning: 48`, `sigwx_low: 12` 선례가 있다.

## 9. 수집 주기와 용량

**주기: 20분.** 원 자료는 10분 격자이나(`formatKstTm`이 분을 10분 단위로 내림), 용량을 우선해 절반만 받는다.

| 항목 | 호출/일 | 용량/일 | 키 |
|---|---|---|---|
| sfc_vis (20분) | 72 | **1.92 GB** | 항공기상 |
| ASOS `kma_sfctm2` (매시) | 24 | 0.7 MB | 항공기상 |
| KIM `cld` | **0** | 0 | — |
| 위성 CTPS | **0** | 0 | — |
| AMOS 운고 | **0** | 0 | — |
| **합계** | **96회** | **약 1.92 GB** | |

키당 일일 한도 5 GB 대비 **38%**.

호출 수는 제약이 아니다 — 항공기상 키는 이미 하루 약 10,100회를 쓰고 있어 96회는 1% 증가다. 용량만이 문제다.

KIM·CTPS·AMOS는 **추가 수집이 없다.** 이미 다른 목적으로 받고 있는 것을 디스크에서 읽는다. 이전 구현이 CTPS를 중복 수집하던 것(하루 432 MB)은 제거되므로 실질 증가는 그만큼 상쇄된다.

### 9.1 용량 가드 (필수)

재시도 한 번이 26.7 MB이고 재시작 시 초기 수집이 한 번 더 부른다. 이 키는 METAR·TAF·AMOS도 함께 쓰므로 **한도를 넘기면 다른 수집까지 죽는다.** 저장소에 한도 소진 이력이 있다(`2026-07-13-metar-taf-raw-tac-reconstruction-plan.md:87`).

이 수집기의 일일 누적 바이트를 세고 **임계치 3 GB를 넘으면 그 사이클을 건너뛰고 로그를 남긴다.** 정상 사용량(1.92 GB) 대비 여유를 두되, 폭주하는 재시도가 키 전체를 먹지 못하게 막는 값이다. 자정(KST) 기준 초기화.

### 9.2 조달 방식 개선 (계획 단계)

결측 81.8%를 통째로 받는 것이 구조적 낭비다.

- `disp` 파라미터에 이진 형식이 있는가 → 있으면 4~13배 절감
- 영역 지정(bbox 등)이 되는가

`help=1`은 이 엔드포인트에서 무시되고 데이터를 반환한다. API 허브 웹 문서는 자동 접근이 차단된다. 파라미터 탐색은 회당 26.7 MB이므로 신중히 한다.

## 12. 명칭
