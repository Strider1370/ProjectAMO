# Spec: 레이더 에코 이동 화살표

**Status:** Ready for planning and implementation
**Created:** 2026-07-26
**Supersedes:** `2026-07-22-radar-lightning-motion.md`의 레이더 이동벡터 부분 (해당 구현은 폐기)

## Goal

조종사가 지도에서 **비구름이 어디로 얼마나 빠르게 이동 중인지** 한눈에 읽고, 자기 비행경로에 걸릴지를 스스로 판단할 수 있게, 레이더 에코의 **다가오는 앞면(leading edge)**을 따라 일정 간격으로 빨간 이동 화살표를 표시한다.

관측 기반 표시이며 예측 산출물이 아니다. 도달 시각, 경로 충돌 판정, 위험등급, Go/No-go 권고를 제공하지 않는다.

## Decisions Already Made

- **표시 단위는 에코 앞면**이다. 격자 균일 채움도, 대류 세포별 대표 화살표도 아니다.
  - 근거: 한국은 종관규모(전선대)와 중규모(소나기·뇌우)가 모두 발생한다. NEXRAD SCIT 같은 세포 추적기는 대류 세포에 특화되어 긴 전선 에코대를 제대로 다루지 못한다. 일정 간격 앞면 표시는 **규모를 가리지 않는다.**
- **경로 연동은 하지 않는다.** 경로 입력 여부와 무관하게 동일 동작한다. 강조·필터·도달시각 산출 없음.
- **속도는 화살표 길이로 표현**한다. 길이는 지도 축척에 실제 비례한다(5분 이동거리 기준).
- **색은 빨강 고정.**
- **1차에서는 품질 필터를 걸지 않는다.** 계산된 화살표를 모두 내보내고, 실제 화면을 본 뒤 거를지 결정한다. 품질 지표는 속성으로 함께 실어 보내므로, 나중에 거르기로 해도 백엔드 재작업이 없다.
  - 단, `max_speed_kmh`(탐색 반경)와 `min_reflectivity`(계산 대상)는 품질 필터가 아니라 **계산 자체의 정의역**이다. 논문 절차의 일부이며 1차에도 적용한다.
- **격자는 2 km를 유지한다.** 기상청(KMA)이 MAPLE/VET를 512×512, 2 km 해상도로 운영한다. 1 km 승격은 측정으로 이득이 확인되기 전에는 하지 않는다.
- **화살촉 아이콘은 점 위에 놓고 방위값으로만 회전**시킨다. 선 위 배치(`symbol-placement: line-center`)를 쓰지 않는다. 회전 기준이 하나뿐이므로 이중 회전이 구조적으로 불가능하다. (화살대는 별도 선 레이어로 그린다 — 표시 절 참조.)
- **표시 세부값** — 화살표 색 `#e11d2e`. 화살대 굵기와 화살촉 크기는 줌에 따라 보간한다(줌 5에서 각각 1.2 px·0.7배, 줌 10에서 2.4 px·1.1배). 두 레이어 모두 Mapbox `slot: 'top'`에 둔다.
- **최소 표시 속도 3 kt.** 이보다 느린 벡터는 앞면 판정에서 제외한다. 품질 필터가 아니라 **방향이 정의되지 않는 값을 거르는 것**이다(정지에 가까운 벡터는 방위가 무의미하고, 화살대 길이가 0에 수렴해 화살촉만 남는다).
- **이웃 일치도(`neighbourAgreement`)는 이웃 벡터와의 사잇각 45° 이내 비율**로 정의한다. 기록용 지표이며 1차에서 표시나 필터에 쓰지 않는다.
- **no-data 셀은 계산 전에 0으로 클램프한다.** KMA HSR 합성 격자는 `-25000`을 no-data로 쓰며, 실측 결과 작업 격자의 **89~91%**가 no-data다. 이 무늬는 프레임 간 98.8% 동일한 고정 무늬여서, 클램프하지 않으면 정합이 실제 에코 이동이 아니라 고정 무늬에 끌려간다.

## 폐기하는 기존 구현

`radarMotionLayers.js`와 관련 프론트엔드 코드는 폐기하고 새로 만든다. 폐기 사유는 각각 확인된 결함이다.

| 항목 | 기존 동작 | 문제 |
|---|---|---|
| 표시 개수 | 뷰포트를 15×12로 나눠 칸당 최고 신뢰도 1개 = 최대 180개 | 요구되는 밀도에 크게 미달 |
| 화살표 모양 | `symbol-placement: line-center`로 화살촉만 배치 | 길이로 속도를 못 읽음 |
| 회전 | 선 방향 정렬 + `icon-rotate` 중첩 | 이중 회전 의심 (미검증) |
| 활성 상태 | 죽은 플래그 **3개** — `radar-echo-processor.js`의 `MOTION_ENABLED`, `weatherOverlayModel.js`의 `RADAR_MOTION_ENABLED`, `WeatherLegends.jsx`의 `radarMotionEnabled` | 기능 자체가 꺼져 있음 |

**폐기하지 않고 그대로 쓰는 것:** 토글 UI(`WeatherLegends.jsx`의 `이동 화살표 표시` 버튼), 표시 상태 훅(`useRadarMotionOverlay.js`), `MapView.jsx`의 배선, `map-base.spec.mjs`의 토글 계약. 이미 온전하며 위 플래그 하나에만 막혀 있다. 표시 여부의 단일 소유자는 훅이다 — 모델에 별도 가시성 키를 만들지 않는다.

백엔드 `radar-motion.js`는 폐기하지 않고 **다중 스케일 구조로 확장**한다(아래 참조).

## 계산 방식 — MTREC 2단계

Wang et al. (2013), *Application of Multi-Scale Tracking Radar Echoes Scheme in Quantitative Precipitation Nowcasting*, Advances in Atmospheric Sciences 30(2):448–460 의 추적 부분을 따른다. 해당 논문의 이류(advection)·강수예측 부분은 **채택하지 않는다** — 우리 산출물은 벡터이지 예측 영상이 아니다.

논문이 보고한 검증: MTREC 벡터 대 도플러 실측 시선속도 상관계수 0.99, RMSE 4.93 m/s.

### 논문 수치와 우리 적용값

| 항목 | 논문 | 본 구현 | 비고 |
|---|---|---|---|
| 원본 격자 | 1 km | **2 km** | HSR 0.5 km를 stride 4로 솎음. KMA 운영값과 동일 |
| 프레임 간격 | 6 min | **5 min** | 논문이 인용한 Rinehart(1981) 권고는 5분 이하 |
| 큰 덩어리 (지향류) | 100/150/200 km 시험 → **150 km 채택** | **150 km** | 종관규모를 잡는 단계 |
| 작은 덩어리 (국지) | 20 km | **20 km** | 중규모를 잡는 단계 |
| 벡터 간격 | 10 km | **8 km (설정값)** | 핀란드 기상청(FMI) 운영값이 8 km |
| 유사도 척도 | 최대 상관계수 | **최대 상관계수** | 기존 코드의 절대차이 합(SAD)에서 변경 |
| 최대 속도 | 100 km/h | **100 km/h** | 탐색 반경 R = v_max × Δt. 기존 150 kt에서 강화 |
| 품질 기준 | 상관계수 < 0.25 폐기 | **속성으로 기록만, 1차는 폐기 안 함** | 위 결정 사항 참조 |
| 마무리 평활화 | 있음 | **있음** | |

### 단계

1. **지향류 산출** — 150 km 덩어리로 전체 이동을 구한다. 종관규모 흐름 1개.
2. **국지 움직임 산출** — 20 km 덩어리로 각 지점의 움직임을 구한다. **탐색은 1단계 지향류 위치에서 시작한다.**
3. **합성** — 지향류 + 국지 움직임.
4. **평활화** — 이웃 벡터 중앙값 필터.

> **의도적 단순화 (ponytail):** 논문 원본은 2단계 전에 준-라그랑주 이류로 영상 전체를 지향류만큼 밀어놓고, 잔차에 대해 작은 덩어리를 적용한다. 본 구현은 영상을 밀지 않고 **탐색 시작점만 지향류로 이동**한다. 수학적으로 근사이며 훨씬 싸다. 측정 결과 부족하면 정식 이류로 승격한다. 코드에 `ponytail:` 주석으로 명시한다.

### 앞면 판정

각 벡터에 대해, **자기 이동 방향으로 6 km 앞의 격자에 에코가 없으면** 그 벡터는 앞면이다. 에코 내부와 후면은 자동으로 탈락한다. 덩어리 분할이나 윤곽선 추출을 하지 않는다.

## 구현 전 필수 측정 (Task 1)

아래를 측정하기 전에는 계산 방식 관련 결정을 확정하지 않는다. 근거 없는 단정을 방지하기 위한 게이트다.

측정 방법은 **개별 화살표 단위 정답 대조**다. 프레임 T-5·T로 화살표를 구하고, 각 화살표 방향대로 국지 패치를 밀어 **실제 T+5 관측**과 비교한다. "안 움직인다고 가정"보다 나은지가 그 화살표의 정오답이다. 정답이 실제 관측이므로 조작 여지가 없다.

측정은 **두 지점**에서 한다. 2단계 알고리즘이 존재해야만 잴 수 있는 항목이 있으므로 하나로 합칠 수 없다.

**게이트 A — 알고리즘 작업 착수 전**

1. **기존 1단계 방식의 개별 화살표 정확도** — 몇 %가 실제로 옳은가. (현재 미측정)
2. **소수점 변위 보정의 효과** — 정수 칸 단위 변위는 방향을 8방향으로 양자화한다. 2 km 격자에서 1칸 = 약 13 kt이며, 변위가 1~2칸일 때 표현 가능한 방위가 극히 제한된다. 최적 정합 주변 점수에 포물선을 맞춰 소수점 변위를 얻는 보정의 효과를 잰다.
3. **no-data 클램프의 효과** — 클램프 전후의 정확도 차이.

게이트 A의 수치는 **클램프를 적용한 상태로** 산출한다. 클램프 없이 잰 값은 고정 무늬에 오염되어 두 방식을 구분하지 못한다.

**게이트 B — MTREC 2단계 구현 직후, 발행 배선 전**

4. **MTREC 2단계 정확도** — 게이트 A 대비 개선 폭.
5. **품질 지표별 판별력** — 정합도, 이웃 일치도가 정답표를 각각 얼마나 잘 예측하는가. 1차에서 필터를 안 걸더라도, 나중에 걸 때 쓸 근거를 확보한다.

**게이트 B가 개선을 보이지 않으면**, MTREC 채택을 재검토하고 사용자에게 보고한다. 게이트 A 방식으로 되돌리는 선택지를 열어둔다.

측정 표본은 실제 강수 사례 4건 이상을 쓴다. 확인된 사례: `202607180635`(에코 34,940칸), `202607180035`(34,500), `202607210335`(28,115), `202607200935`(26,918). 합성 데이터로 대체하지 않는다. 두 게이트는 같은 표본을 쓴다.

## 데이터 계약

### 백엔드 산출

레이더 프레임과 같은 주기(5분)로 생성하며, 기존 PNG·메타 발행 흐름에 얹는다.

파일: `{DATA_PATH}/radar/motion_korea_{tm}.geojson`

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": { "type": "Point", "coordinates": [127.05, 37.42] },
      "properties": {
        "bearingDeg": 68,
        "speedKt": 27,
        "correlation": 0.71,
        "neighbourAgreement": 0.88
      }
    }
  ]
}
```

- `bearingDeg` — 진북 기준 0–360, 이동해 가는 방향.
- `speedKt` — 노트.
- `correlation`, `neighbourAgreement` — 품질 지표. **1차에서는 표시에 쓰지 않고 기록만 한다.**

레이더 메타(`echo_meta.json`)의 해당 프레임에 참조를 추가한다:

```json
"motion": { "tm": "202607261200", "observedAtMs": 0, "comparedFromMs": 0, "path": "/data/radar/motion_korea_202607261200.geojson" }
```

보존은 레이더 프레임과 동일(`radar_echo.max_images`, 36프레임 = 3시간).

### 설정값

`config.js`의 `radar_echo_motion` 절에 둔다.

| 키 | 기본값 | 뜻 |
|---|---|---|
| `enabled` | `true` | 기능 활성 |
| `work_stride` | `4` | HSR 0.5 km 대비 솎음 배수. 4 = 2 km |
| `large_box_km` | `150` | 지향류 덩어리 |
| `small_box_km` | `20` | 국지 덩어리 |
| `spacing_km` | `8` | 화살표 간격 |
| `max_speed_kmh` | `100` | 탐색 반경 제한 |
| `edge_lookahead_km` | `6` | 앞면 판정 거리 |
| `min_reflectivity` | `2000` | 계산 대상 최소 반사도(스케일 dBZ) |

밀도 조정은 `spacing_km`으로 한다. 화면 확인 후 조정한다.

## 프론트엔드 표시

### 레이어 구성

두 레이어로 화살표 하나를 그린다.

1. **화살대** — `line` 레이어. 실제 좌표 LineString(시작점 → 시작점 + 5분 이동거리). 지도 축척에 비례하므로 확대 시 함께 커진다. 빨강.
2. **화살촉** — `symbol` 레이어. 끝점 Point + `icon-rotate: ['get','bearingDeg']`, `icon-rotation-alignment: 'map'`, `icon-allow-overlap: true`. **`symbol-placement`를 지정하지 않는다**(기본 `point`).

화살대 LineString은 프론트엔드가 `bearingDeg`·`speedKt`로 생성한다. 백엔드는 점만 보낸다.

### 표시 조건

- 레이더 레이어가 켜져 있고, 선택 시각과 `motion.tm`이 정확히 일치할 때만 표시한다. 이전 프레임을 재사용하지 않는다.
- 화살표 파일이 없으면 아무것도 그리지 않는다. **틀린 방향을 그리느니 그리지 않는다.**
- 토글은 이미 있는 `이동 화살표 표시` 버튼을 그대로 쓴다. 기본 OFF이며, 레이더를 끄면 자동으로 해제된다(`useRadarMotionOverlay`의 기존 동작).

### 범례

기존 토글 옆 설명줄이 이미 관측·비교 시각과 "예측 아님"을 표기한다. 여기에 **길이의 뜻만 추가**한다: "길이 = 5분 이동거리". 문구를 새로 만들지 않고 기존 줄을 늘린다.

### 밀도

1차는 서버가 보낸 화살표를 **전부** 그린다. 줌별 솎음은 넣지 않는다. 화면 확인 후 필요하면 `spacing_km` 조정으로 대응하고, 그래도 부족하면 줌 기반 솎음을 추가한다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 직전 프레임 없음 / 간격이 5분이 아님 | 화살표 파일 미생성. 화면 표시 없음 |
| 계산 시간 초과 | **계산을 중도 포기**하고 화살표 파일 미생성. 레이더 PNG·메타 발행은 정상 진행 |
| 에코 없음 / 앞면 벡터 0개 | 화살표 파일 미생성. 메타에 `motion` 키 없음 |
| 파일 수신 실패 | 화면 표시 없음, 레이더는 정상 표시 |

이동 계산 실패가 레이더 레이어 자체를 막지 않는다.

시간 초과는 **계산 루프 안에서** 확인해 즉시 빠져나와야 한다. 결과를 다 만든 뒤 버리는 방식은 5분 주기 수집을 밀리게 하므로 요건을 만족하지 않는다.

## 검증

- **백엔드 단위 테스트** — 앞면 판정, 지향류 산출, 합성, 좌표 변환. 기존 `radar-motion.test.js`의 "동쪽 화살표가 하나라도 있으면 통과" 식 약한 단언은 **다수가 옳은 방향인지**를 확인하는 단언으로 교체한다.
- **정확도 측정** — 위 Task 1의 개별 화살표 정답 대조. 결과를 status 문서에 수치로 남긴다.
- **브라우저 계약** — `frontend/verification/contracts/`에 추가. 레이어 등록, 토글, 시각 불일치 시 미표시, 베이스맵 전환 후 유지, 재동기화 시 중복 없음, 3개 뷰포트(1280/1024/375).
- **실화면 확인** — 실제 강수 사례 시각으로 Playwright 스크린샷을 남기고 사용자가 밀도를 확인한다.

## Out of Scope

- 예측 영상(다음 시각 레이더 그림) 생성
- 도달 시각 산출, 경로 충돌 판정
- 대류 세포 식별·추적(SCIT/TITAN 계열)
- 낙뢰 이동벡터
- 해외 레이더(RainViewer) 이동벡터
- 1 km 격자 승격 — Task 1 측정에서 필요성이 확인되면 별도 작업으로 분리
