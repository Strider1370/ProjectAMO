# 수집기 실행 상태와 미실행 감지 설계

**작성일:** 2026-08-31

**상태:** 사용자 검토 대기

## 배경

2026-08-31 지상예보 수집기는 11:30 KST에 마지막으로 성공한 뒤, 14:30·17:30 KST 예정 실행의 콜백이 시작되지 않았다. 다른 수집기는 계속 실행됐고 API 키도 활성 상태였다. 현재 시스템은 마지막 성공 시각만 남기므로, 이 사례를 오래된 자료로만 보며 `수집기가 실패했는지`, `의도적으로 건너뛰었는지`, `스케줄러가 실행하지 않았는지`를 구분할 수 없다.

운영 서버는 30GB 디스크 중 12GB만 여유가 있고, PM2 stdout/stderr 로그 회전이 설정되어 있지 않다. 5분·1분 주기 수집기가 다수이므로 모든 실행을 장기 SQLite 이력으로 저장하는 방식은 이 서버 규모에 비해 복잡하고 불필요하다.

## 목표

모든 백엔드 수집기에 대해 관리자 콘솔과 회전된 서버 로그만으로 다음 질문에 답한다.

1. 마지막으로 언제 시작·완료했는가?
2. 성공, 실패, 의도적 건너뜀, 미실행 중 어느 상태인가?
3. 마지막 오류 또는 미실행의 원인은 무엇인가?
4. 자료는 최신인가? (기존 자료 건강도)

외부 알림, 장기 실행 이력 분석, 자동 재시작은 이 범위에 넣지 않는다.

## 기존 구조와 판단

- `backend/src/stats.js`는 성공·실패·skip과 공용 최근 50건만 보존한다. 시작 이벤트와 수집기별 현재 실행 상태가 없다.
- `backend/src/admin/data-health.js`는 마지막 성공 시각으로 자료 신선도를 판정한다. 예정 실행의 미시작을 판정할 근거가 없다.
- `saved: false`는 내용이 같아 새 파일을 만들지 않았다는 뜻일 수 있으므로 실패가 아니다.
- `failedAirports`에는 실제 수집 실패뿐 아니라 일부 제품에서 허용된 설정 누락도 포함된다. 전 수집기의 공통 실행 결과로 쓰면 안 된다.
- PM2 로그는 82MB, 약 287만 줄이지만 회전 설정이 없다. 이는 현재 확인된 유일한 무한 증가 로그다.

기존 자료 건강도는 자료의 최신성·가용성을, 새 실행 상태는 스케줄러와 수집 실행을 각각 나타낸다. 두 상태를 하나의 신호등으로 합치지 않는다.

## 설계

### 1. 작고 영속적인 수집기 실행 상태

새 SQLite 테이블을 만들지 않는다. 기존 `stats/latest.json`의 수집기별 통계에 아래 `execution` 상태만 추가한다.

```js
{
  last_started_at,
  last_scheduled_started_at,
  last_finished_at,
  last_outcome, // succeeded | failed | skipped | missed
  last_issue: null, // 이상이 있으면 { outcome, at, code, message }
  last_missed_at
}
```

- `succeeded`: 수집기가 예외 없이 완료됐다. `saved: false`도 성공이다.
- `failed`: 수집기가 예외로 끝났거나 유효한 결과를 만들지 못했다.
- `skipped`: `already_running`, `api_hub_key_blocked`처럼 명시 사유로 실행하지 않았다.
- `missed`: 기대 주기와 유예시간을 넘길 때까지 새 시작 기록이 없다.
- 자료 품질의 부분 경고는 기존 `data-health`가 계속 담당한다. 새 전역 `degraded` 결과를 만들지 않는다.

`last_outcome`은 현재 상태이고, `last_issue`는 성공 뒤에도 남는 가장 최근 이상 사건이다. 콘솔의 높은 우선순위 문제는 현재 상태가 `failed`·`missed`일 때만 표시한다. `skipped`는 전체 상태표에 보이되 경고 수에 넣지 않고, 복구된 수집기의 과거 오류를 현재 오류처럼 표시하지 않는다.

정규 cron, 시작 초기 수집, 수동 수집은 각각 `scheduled`, `startup`, `manual` 출처로 기록한다. `last_started_at`은 마지막 모든 시도를, `last_scheduled_started_at`은 정규 cron 시도만 나타낸다. watchdog는 후자만 사용하므로 초기·수동 수집이 정규 실행 누락을 가리지 않는다.

새 `execution` 부분은 수집기당 한 항목만 덮어쓰므로 수집 횟수에 따라 커지지 않는다. 기존 `stats/latest.json`의 누적 오류·공항 통계는 별도 기존 동작이며, 이 작업이 그 보존 성질을 바꾸지 않는다. 시작 상태는 메모리에 즉시 반영하고 파일 저장은 최대 30초에 한 번으로 묶는다. 정상 완료·실패의 기존 통계 저장은 그대로 유지한다. 마지막 이상 사건의 안전한 코드와 짧은 메시지만 남기고, 인증키·원본 응답·스택 전문은 저장하지 않는다.

### 2. 시작 기록과 미실행 감지

기존 `runWithLock` 흐름에 시작 기록을 추가하고, 기존 성공·실패·skip 기록이 종료 상태를 갱신한다. 수집기 콜백이 실제 호출되는 순간 먼저 `last_started_at`을 기록하므로, 처리 실패와 스케줄러 미실행을 구분할 수 있다.

등록된 수집기마다 cron 식·시간대·`type`·최대 기대 간격·유예시간·의도적 비운영 시간·생성 자료 메타데이터를 하나의 등록부에 둔다. 이 등록부는 정규 cron 등록, watchdog, 실행 상태 목록, 자료 건강도 카탈로그가 함께 사용하며, 설정으로 꺼진 선택 수집기는 명시적으로 비활성 상태가 된다. 1분 watchdog는 활성 선언과 `last_scheduled_started_at`을 비교한다.

- 마지막 시작 이후 `최대 기대 간격 + 유예시간`을 넘으면 상태를 `missed`로 전환한다.
- 같은 중단 상태에서는 한 번만 `missed` 로그를 남기며, 다음 시작 기록이 생기면 해소한다.
- 서버가 재시작된 직후에는 유예시간이 지날 때까지 과거 실행을 소급해 `missed`로 만들지 않는다.
- watchdog는 같은 Node 프로세스 안에 있으므로 프로세스 전체 정지나 호스트 장애는 감지하지 못한다. 이 범위는 PM2/호스트 운영의 책임으로 남긴다.

정확한 cron 슬롯별 이력·다음 예정 시각 계산은 만들지 않는다. 현재 상태와 마지막 정규 시작 시각이면 이번과 같은 수집기 미실행을 판정하기에 충분하다.

### 3. 새 수집기·산출물의 단일 등록부

새 정기 수집기나 그 산출물을 추가할 때 `locks`, `stats` type 목록, cron 호출, 자료 건강도 카탈로그, 관리자 실행 목록을 각각 수동으로 고치지 않는다. `backend/src/collector-registry.js`의 등록부가 다음을 한 항목으로 소유한다.

- 수집기 type, processor binding key, cron 식과 시간대, API Hub category 같은 실행 옵션, 최대 기대 간격·유예·비운영 조건
- 활성화 조건과 관리자 표시명
- 수집기가 직접 생성하는 자료 제품의 key, 자료 건강도 source/character, 신선도 기준, 저장 메타 경로, 이벤트성 여부

스케줄러는 활성 등록부에서만 cron과 실행 옵션을 만들고, stats는 기록 대상 type을 동적으로 보장하며, 관리자 `collectorExecution`은 활성 등록부 전체를 그대로 표시한다. 자료 제품은 등록부 메타데이터에서 자료 건강도 카탈로그를 만든다. 하나의 수집기가 여러 제품을 생성하면 그 제품들을 같은 수집기 항목 아래에 선언한다.

수집기 구현 자체의 processor 함수는 index의 type→job binding에 남긴다. 제품 선언에는 `store` type 또는 meta 경로의 publication target도 들어간다. 모든 `store.save`와 제품 meta 쓰기는 공용 publication seam을 거쳐 그 target을 검증하며, 제품 파일을 직접 쓰는 기존 processor도 이 seam으로 이관한다. 시작 시 binding 없는 활성 등록부 항목, 등록부 없는 정기 binding, 불완전하거나 중복된 자료 제품 메타데이터, 미등록 publication target은 명시적으로 실패한다. 따라서 새 산출물을 등록부에 넣지 않거나 등록만 하고 processor를 연결하지 않은 변경은 테스트와 시작 검증을 통과하지 못한다.

### 4. 서버 로그와 보존 상한

각 실행 완료와 이상 상태는 PM2 stdout/stderr에 짧은 한 줄로 남긴다. 기존처럼 processor 결과 객체 전체를 출력하지 않는다.

```text
[collector] ground_forecast started
[collector] ground_forecast succeeded duration_ms=15324 saved=true
[collector] ground_forecast missed last_started=2026-08-31T02:30:00Z threshold_ms=12900000
```

성공은 수집기·결과·소요시간만, 실패·건너뜀·미실행은 분류 코드와 짧은 메시지도 기록한다. 요청 URL의 인증키·응답 본문·세션 정보는 로그에 남기지 않는다.

PM2 로그 회전을 설정한다. stdout와 stderr는 파일이 10MiB에 도달하거나 하루가 지나면 회전하고, 압축한 보관본은 최근 7개만 남긴다. 따라서 원본 운영 로그는 단기 원인 추적에 쓰되 무한히 디스크를 차지하지 않는다.

### 5. 관리자 콘솔

기존 관리자 자료 수집 화면과 `GET /api/admin/data-health` 응답을 확장한다. 응답에는 자료 행과 별도로 모든 활성 수집기의 `collectorExecution` 목록을 포함한다. 별도 실행 이력 API나 이력 펼침 화면은 만들지 않는다.

- 각 수집기 또는 연결된 자료 행에 실행 상태와 마지막 시작·완료 시각을 표시한다.
- 자료 행에 연결되지 않는 수집기도 `collectorExecution`에서 빠지지 않으며, 실패·미실행은 모두 컴팩트한 실행 문제 목록과 상단 수에 포함한다.
- 현재 문제의 코드와 짧은 메시지, 그리고 복구된 경우에는 가장 최근 이상 시각만 표시한다.
- 자료 신선도 `ok/late/stopped` 표시는 그대로 유지하며, 실행 상태와 혼합하지 않는다.
- PM2 로그 보존 기준(회전/압축/7개)을 화면에 복제하지 않는다. 로그 파일은 서버 운영 자료이고 콘솔은 현재 상태를 보여주는 곳이다.

## 오류 처리

- 상태 파일 기록 실패는 수집 자체를 실패시키지 않되, stderr에 `collector_observability_write_failed`로 남긴다.
- 활성 등록부 항목에 processor binding이 없거나, binding에 등록부 항목이 없거나, 제품 메타데이터가 불완전하면 개발·테스트와 서버 시작에서 명시적으로 실패시킨다. 조용히 관측에서 빠지면 안 된다.
- 수동 초기 수집은 시작·완료 상태를 기록하지만, 정규 스케줄 `missed` 상태를 해소하거나 정규 스케줄 미실행의 증거로 취급하지 않는다. 정규 수집의 다음 시작만 그 `missed` 상태를 해소한다.

## 검증

1. 상태 기록 단위 테스트: start→succeeded, failed, skipped, `saved:false` 성공 처리, 성공 뒤 과거 `last_issue`가 현재 실패로 표시되지 않는지, 새 execution 상태가 수집 횟수에 따라 늘지 않는지 확인한다.
2. watchdog 단위 테스트: 지상예보처럼 3시간 주기의 수집기가 유예시간을 넘기면 한 번만 `missed`가 되는지, 이후 시작하면 해소되는지, 비운영 시간이 제외되는지 확인한다.
3. 등록부·publication 테스트: 활성·비활성 설정 조합에서 모든 정규 스케줄 수집기와 processor binding이 정확히 한 등록부 항목에 대응하고, 모든 자료 건강도 제품이 등록부 메타데이터에서 만들어지는지 확인한다. `store` 저장과 meta publication이 미등록 target을 거부하고, type·제품 key·target이 중복되거나 필수 health 메타데이터가 빠지면 시작 검증이 실패하는지 확인한다.
4. 수집 wrapper 테스트: 시작 기록이 processor 호출보다 먼저 남고, startup/manual 시작이 `last_scheduled_started_at`을 바꾸지 않는지 확인한다.
5. 상태 저장 테스트: 시작 기록의 파일 쓰기가 30초 안에 반복 실행 수만큼 늘지 않고, 완료·실패의 기존 통계 저장이 유지되는지 확인한다.
6. 관리자 API·콘솔 테스트: `missed`와 `failed`가 자료 최신성 상태와 별도로 보이고, 자료 행 밖의 활성 수집기도 `collectorExecution`에 있으며, 관리자 인가 규칙이 유지되는지 확인한다.
7. Playwright: 관리자 자료 수집 화면에서 정상·실패·건너뜀·미실행·복구 상태와 선택된 시간대의 실행 시각을 브라우저로 확인한다.
8. 운영 검증: 배포 뒤 지상예보의 다음 정규 실행에서 PM2 로그와 관리자 콘솔 모두 같은 시작·완료·성공 상태를 보이는지, PM2 stdout/stderr가 한 줄 구조화 로그로 회전·압축되고 보관 파일 수가 상한을 넘지 않는지 확인한다.
